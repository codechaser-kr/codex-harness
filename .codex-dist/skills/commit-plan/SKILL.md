# Commit Plan

현재 브랜치/PR 단위의 상위 계획을 유지하면서 실행 가능한 커밋 단위 계획을 제안한다. 계획 확정과 실제 파일 수정, 커밋 메시지 확정, 커밋 생성은 Workflow Engine의 후속 작업에서 처리한다.

## 먼저 읽을 문서

- `../github-agentic-loop/references/artifact-output-contract.md`에서 ``커밋 계획(`commit-plan`) 출력 판정 규칙`` 섹션만 읽는다.

## 입력

- 기준 이슈 유형, 번호와 본문
- 사용자가 확정한 현재 브랜치/PR 단위의 ID, 작업 내용, 구현 순서, 선행 조건, 검증 기준
- 현재 작업 브랜치와 base branch
- 관련 설계 문서와 연관 이슈
- 현재 코드와 작업트리 상태
- 저장소의 구현, 테스트, 커밋 관례

## 책임

1. 현재 브랜치/PR 단위의 작업 내용, 선행 조건과 검증 기준을 상위 계획으로 사용한다.
2. 현재 코드와 관련 문서를 확인해 상위 계획 범위 안의 변경 대상을 식별한다.
3. 변경을 독립적으로 검증하고 커밋할 수 있는 의미적 커밋 단위로 나눈다.
4. 각 커밋 단위에 고유한 ID, 작업 범위, 수정 대상과 검증 기준을 제안한다.
5. 모든 커밋 단위를 한 번씩 포함하는 구현 순서를 제안한다.
6. 상위 계획의 범위, 선행 조건과 PR 단위 검증 기준을 충족하는지 확인한다.
7. 상위 계획을 변경해야 하거나 필수 입력이 부족하면 계획을 제시하지 않고 `보류 질문`에 기록한다.

## 출력

- 기존 `필수 출력 섹션`의 커밋 단위 후보, 구현 순서, `보류 질문`만 반환한다.
- 계획은 사용자 검토용 후보이며 현재 커밋 단위, 커밋 메시지, 커밋 생성 또는 작업 범위의 확정값이 아니다.

## 하지 않는 일

- 상위 브랜치/PR 단위나 커밋 단위 계획, 사용자 결정, 현재 Workflow 상태를 확정하지 않는다.
- 파일을 수정하거나 브랜치·커밋·이슈·PR·체크리스트 등 GitHub와 작업트리 상태를 변경하지 않는다.
- 확정된 상위 계획의 범위를 재해석하거나 넓히지 않는다.

## 사용자 결정

- 제안한 커밋 단위와 구현 순서를 사용자 결정으로 해석하지 않는다. 계획 채택, 구현 요청, 커밋 메시지 확정과 커밋 생성 여부는 `github-agentic-loop`가 처리한다.

## 중단 조건

- 확정된 브랜치/PR 단위, 선행 조건, PR 단위 검증 기준, 현재 브랜치 또는 코드 상태가 없거나 충돌하면 계획을 확정하지 않는다.
- 상위 계획 변경이나 범위 밖 변경이 필요하면 구체적인 사유와 재개에 필요한 입력을 `보류 질문`에 반환한다.

## 후속 전이

- 제어와 기존 출력 구조를 `github-agentic-loop`에 반환한다.
- Workflow Engine이 산출물 판정과 사용자 결정을 거쳐 현재 커밋 단위와 확정된 구현 요청을 결정한다.

## 필수 출력 섹션

커밋 계획은 다음 섹션과 항목을 순서대로 빠짐없이 채운다.

- `기준 이슈`
- `현재 브랜치/PR 단위`
  - `단위 ID`
  - `작업 내용`
  - `선행 조건`
  - `PR 단위 검증 기준`
- `현재 작업 브랜치`
- `계획 근거`: 확인한 코드 상태와 저장소 관례
- `커밋 단위`
  - `단위 ID`
  - `작업 범위`
  - `수정 대상`
  - `검증 기준`
- `구현 순서`
- `보류 질문`

`커밋 단위`의 `단위 ID`는 계획 안에서 고유해야 한다. `구현 순서`는 모든 커밋 단위 ID를 한 번씩 포함해야 한다.
