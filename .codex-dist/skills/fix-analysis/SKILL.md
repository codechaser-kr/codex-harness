# Fix Analysis

기능결함 이슈의 원인 조사 결과를 사용자 결정용 초안으로 작성한다. 원인 조사 결과 확정과 이슈 본문 반영은 Workflow Engine이 처리한다.

## 먼저 읽을 문서

- `../github-agentic-loop/references/artifact-output-contract.md`에서 ``결함 원인 분석(`fix-analysis`) 출력 판정 규칙`` 섹션만 읽는다.
- `../github-agentic-loop/references/artifact-handoff-contract.md`
- `../github-agentic-loop/artifact-manifests/fix-analysis.json`
- `../github-agentic-loop/references/github-templates.md`

## 입력

- 기능결함 이슈 번호와 본문
- `어떤 문제가 있나요?`
- `재현 과정 또는 확인 위치가 어떻게 되나요?`
- `올바른 동작은 어떻게 되나요?`
- 연관 이슈와 연결 PR
- 관련 설계 문서, 규칙 문서, 코드, 템플릿, 스킬, 설정
- 재현 또는 검증 결과

## 책임

1. 보고된 현상과 올바른 동작의 차이를 정리한다.
2. 재현 과정 또는 확인 위치를 따라 현재 상태를 확인한다.
3. 관련 문서와 구현에서 원인을 뒷받침하거나 반박하는 근거를 원인 후보별로 수집한다.
4. 관찰 사실과 추론을 구분해 원인 후보를 작성한다.
5. 각 원인 후보의 영향 범위, 확인 수준, 반증 조건을 제시한다.
6. 근거가 가장 충분한 추천 원인과 잠정 해결 방향을 제안한다.
7. 확정에 필요한 근거가 부족하면 `보류 질문`에 확인할 내용을 기록한다.

## 조사 기준

- `확인됨`: 현재 산출물이나 재현 결과에서 원인과 현상의 인과관계가 확인된다.
- `유력`: 직접 증거와 정황이 일치하지만 인과관계 확인이 하나 이상 남아 있다.
- `가설`: 현상을 설명할 수 있으나 직접 근거가 부족하다.

원인 후보가 둘 이상이면 차이와 반증 조건을 모두 제시한다. `가설`만 있으면 추천 원인을 확정하지 않는다.

## 출력

- 공통 handoff 계약의 닫힌 envelope만 반환한다.
- `artifact_type: fix-analysis`를 사용하고 `artifact`는 `fix-analysis.json` manifest에 맞춰 구성한다.
- 추천 원인과 해결 방향은 사용자 검토용 분석이며 기능결함 이슈에 반영할 확정 원인이나 수정 지시가 아니다. Markdown 표시는 runtime renderer가 담당한다.

## 하지 않는 일

- 원인, 해결 방향, 사용자 결정, 현재 Workflow 상태를 최종 확정하지 않는다.
- 파일 수정, 이슈 갱신, 체크리스트 변경, GitHub 상태 변경을 수행하지 않는다.
- 조사 근거가 가리키는 기능결함 이슈와 확인 위치를 넘어 해결 범위나 추가 결함을 확정하지 않는다.

## 사용자 결정

- 추천 원인을 사용자 결정으로 해석하지 않는다. 원인 조사 결과의 확정과 이슈 본문 반영, 해결 계획 진입은 `github-agentic-loop`가 사용자 결정과 전이 규칙으로 처리한다.

## 중단 조건

- 현상, 재현 또는 확인 위치, 올바른 동작, 조사 근거가 없거나 서로 충돌하면 추천 원인을 확정하지 않는다.
- 재현 불가, 근거 부족, 범위 밖 조사 필요 상황이면 구체적인 사유와 재개에 필요한 관찰·재현·입력을 `보류 질문`에 반환한다.

## 후속 전이

- 제어와 기존 출력 구조를 `github-agentic-loop`에 반환한다.
- Workflow Engine이 산출물 판정과 사용자 결정을 거쳐 원인 조사 결과 확정 또는 `fix-plan` 호출 여부를 결정한다.

## Structured artifact handoff

의미 내용은 위 조사 기준과 확인 수준에 따라 작성하고, 기계 구조는 `fix-analysis.json`만 따른다. envelope 밖의 설명이나 직접 조립한 Markdown을 반환하지 않는다.
