# GitHub Workflow Engine Rules

이 문서는 설치된 Workflow Engine 스킬이 실행 중 적용하는 판정 규칙이다. 이 파일은 기준 대상, 상태 근거, 현재 작업, 진행 판단, 실행 범위, 작업 전이, 사용자 입력 유효성, 명령 실행 경로를 산출하는 판정 기준만 정의한다. 실행 지침과 전용 스킬 호출 책임은 `SKILL.md`가 가진다.

## 적용 범위

- 이 파일은 런타임에서 독립적으로 참조하는 규칙 파일이다.
- 현재 작업 산출에 필요한 조건은 이 파일 안에서 판정 가능해야 한다.
- 작업 전이표의 조건은 이 파일의 상태 읽기 규칙, 필드 판정 규칙, 파생 상태 규칙으로 판정한다.
- 이슈와 PR 본문 형식은 타겟 레포의 `.github/ISSUE_TEMPLATE/*.md`와 `.github/pull_request_template.md`를 기준으로 판정한다.
- `github-templates.md`는 title prefix, label, 필수 섹션, 연결 규칙 판정에 사용한다.

## 상태 읽기 규칙

- 기준 대상은 열린 PR에서 먼저 찾고, 이어갈 PR 후보가 비어 있으면 열린 이슈에서 찾는다.
- 열린 PR 중 unresolved review thread, 미체크 marker 요약 피드백, merge 대기 상태가 있으면 새 이슈보다 먼저 처리한다.
- PR 연결 이슈는 PR 본문의 `연관 이슈 (optional)` 섹션에서 `Refs #번호` 형식으로 판단한다.
- Workflow Engine 관리 이슈는 PR 본문에 `Refs #번호`로 연결한다.
- Pull Request review threads는 diff가 있는 피드백과 resolved/unresolved 상태를 우선 상태 원천으로 읽는다.
- Pull Request issue comments는 diff 위치 밖 marker 요약 피드백의 체크 상태를 보조 상태 원천으로 읽는다.
- marker 요약 피드백은 다음 marker가 있는 PR comment로 식별한다.

```markdown
<!-- codex-harness:summary-feedback v1 -->
```

## 필드 판정 규칙

| 판정 | 산출 규칙 |
| ---- | --------- |
| 본문 섹션 값 있음 | 지정된 heading 아래에서 다음 heading 전까지의 본문에 공백, HTML comment, 템플릿 안내문을 제외한 텍스트, 체크항목, issue 번호, PR 번호 중 하나가 존재한다. |
| 본문 섹션 빈 상태 | 지정된 heading 아래에서 다음 heading 전까지의 본문이 공백, HTML comment, 템플릿 안내문만 가진다. |
| 체크항목 체크됨 | Markdown 체크항목이 `- [x]` 또는 `- [X]` 형식이다. |
| 체크항목 미체크 | Markdown 체크항목이 `- [ ]` 형식이다. |
| GitHub 이슈 open | GitHub issue state가 `OPEN` 또는 `open`이다. |
| GitHub PR open | GitHub pull request state가 `OPEN` 또는 `open`이다. |
| GitHub PR merged | GitHub pull request merged 값이 `true`이거나 state가 `MERGED` 또는 `merged`다. |
| 사용자 선택 확정 | 사용자 입력이 직전 응답에서 제시한 번호, 선택지 문구, 유효한 `기타 의견 입력` 형식 중 하나와 일치한다. |
| 로컬 수정 존재 | `git diff --name-only` 출력에 현재 작업 범위에 속한 파일이 하나 이상 포함된다. |
| 검증 성공 | 현재 작업의 검증 명령이 exit code `0`으로 종료된 결과가 실행 로그에 기록된다. |
| 커밋 생성 완료 | 현재 작업 범위의 마지막 commit hash가 실행 로그 또는 연결 이슈/PR 본문에 기록된다. |
| 원격 push 완료 | 원격 head branch가 존재하고 원격 head branch의 HEAD commit이 로컬 작업 브랜치 HEAD commit과 일치한다. |

## 파생 상태 규칙

| 파생 상태 | 산출 규칙 |
| --------- | --------- |
| 이슈 유형 | 이슈 label이 `기능제안`, `정책검토`, `기능변경`, `기능결함` 중 하나이면 해당 label을 이슈 유형으로 사용한다. |
| 이슈 유형 충돌 | 유형 label이 비어 있거나 둘 이상이면 진행 판단을 `사용자 결정`으로 둔다. |
| 정책검토 출발점 | 정책검토 이슈의 `연관 이슈`가 비어 있으면 `단독 시작`으로 둔다. `연관 이슈`의 유형 label이 `기능제안`이면 `기능제안`으로, `기능결함`이면 `기능결함`으로 둔다. |
| 설계 문서 반영 필요 | 정책검토 이슈 본문의 `검토 결과`에 `설계 문서 반영 필요` 문구와 반영 대상 파일 경로가 기록된 상태다. |
| 설계 문서 반영 불필요 | 정책검토 이슈 본문의 `검토 결과`에 `설계 문서 반영 불필요` 문구가 기록된 상태다. |
| 설계 문서 구현 완료 | 정책검토 이슈의 `후속 작업은 무엇인가요?`에서 `결정된 정책을 관련 설계 문서에 반영` 항목이 체크되고 PR 번호가 덧붙은 상태다. |
| 기능변경 계획 반영 완료 | 기능변경 이슈 본문의 `작업 범위는 어디까지인가요?`에 구현 단위, 브랜치/PR 분할, 구현 순서, 검증 기준이 기록되고, `완료 기준은 무엇인가요?`에 구현 단위별 체크항목이 기록된 상태다. |
| 기능결함 해결 계획 반영 완료 | 기능결함 이슈 본문의 `원인과 해결 방향은 무엇인가요?`에 원인, 해결 단위, 브랜치/PR 분할, 구현 순서, 검증 기준이 기록되고, `완료 기준은 무엇인가요?`에 해결 단위별 체크항목이 기록된 상태다. |
| 정책 또는 설계 변경 필요 | 원천 변경, 현재 원천과의 충돌, 신규 기준 추가, 정책 선택지 결정 필요 중 하나 이상이 원인 조사 결과에 기록된 상태다. |
| 정책 또는 설계 변경 필요 없음 | 기존 원천을 그대로 적용할 수 있음이 원인 조사 결과에 기록된 상태다. |
| 정책검토 결과 반영 완료 | 원본 기능결함 이슈의 `원인과 해결 방향은 무엇인가요?`에 정책검토 이슈 번호와 결정된 정책 방향이 기록되고, `완료 기준은 무엇인가요?`에 정책검토 결과로 수행할 해결 단위 체크항목이 기록된 상태다. |
| 새 기능제안 요청 | 사용자 요청에 `기능제안`, `기능 제안`, `feature proposal` 중 하나가 포함되고 기준 이슈 번호와 PR 번호가 모두 빈 상태다. |
| 새 기능결함 보고 | 사용자 요청에 `기능결함`, `기능 결함`, `버그`, `bug`, `오류`, `에러` 중 하나가 포함되고 기준 이슈 번호와 PR 번호가 모두 빈 상태다. |
| 새 정책검토 요청 | 사용자 요청에 `정책검토`, `정책 검토`, `설계 검토`, `policy review` 중 하나가 포함되고 기준 이슈 번호와 PR 번호가 모두 빈 상태다. |
| 초안 확정 | 사용자 선택 확정이며 선택지가 초안 확정이다. |
| 계획 확정 | 사용자 선택 확정이며 선택지가 계획 확정이다. |
| 정책 방향 확정 | 사용자 선택 확정이며 선택지가 정책 방향 확정이다. |
| 원인 조사 결과 확정 | 사용자 선택 확정이며 선택지가 원인 조사 결과 확정이다. |
| 결함 해결 계획 확정 | 사용자 선택 확정이며 선택지가 결함 해결 계획 확정이다. |
| 세부 구현 계획 확정 | 사용자 선택 확정이며 선택지가 세부 구현 계획 확정이다. |
| 브랜치 이름 확정 | 사용자 선택 확정이며 선택지가 브랜치 이름 확정이다. |
| 변경 내용과 커밋 메시지 확정 | 사용자 선택 확정이며 선택지가 변경 내용과 커밋 메시지 확정이다. |
| 피드백 수정 커밋 메시지 확정 | 사용자 선택 확정이며 선택지가 피드백 수정 커밋 메시지 확정이다. |
| 구현 단위 입력 확정 | 구현 흐름 입력에 구현 단위, 해결 단위, 반영 단위 중 하나와 브랜치/PR 분할, 순서, 검증 기준이 기록된 상태다. |
| 브랜치 이름 제안 필요 | 구현 단위 입력 확정 상태이고 브랜치 이름 후보와 브랜치 이름 확정 기록이 없는 상태다. |
| 기능변경 전환 입력 확정 | 기능제안 또는 정책검토 작업 결과에 기능변경 이슈 제목, 본문 초안 입력, 연관 이슈 번호가 기록된 상태다. |
| 정책검토 전환 입력 확정 | 기능제안 또는 기능결함 작업 결과에 정책검토 이슈 제목 작성 입력, 본문 초안 작성 입력, 연관 이슈 번호가 기록된 상태다. |
| 현재 작업 브랜치 전환 필요 | 브랜치 이름 확정 상태이고 현재 git branch 이름이 확정 브랜치 이름과 다른 상태다. |
| 현재 작업 브랜치 전환 완료 | 현재 git branch 이름이 사용자가 확정한 브랜치 이름과 일치하는 상태다. |
| 세부 구현 계획 수립 필요 | 현재 작업 브랜치 전환 완료 상태이고 세부 구현 계획 확정 기록이 없는 상태다. |
| 미완료 커밋 단위 존재 | 세부 구현 계획 또는 기준 이슈의 변경 계획/해결 계획에 적힌 구현 단위 중 commit hash 또는 완료 기록이 없는 항목이 하나 이상 있는 상태다. |
| 현재 커밋 단위 수정과 검증 완료 | 현재 커밋 단위에 대해 로컬 수정 존재와 검증 성공이 모두 참인 상태다. |
| 현재 커밋 단위 커밋 생성 완료 | 현재 커밋 단위에 commit hash가 기록된 상태다. |
| 모든 커밋 단위 커밋 생성 완료 | 세부 구현 계획과 기준 이슈의 변경 계획/해결 계획에 적힌 모든 구현 단위에 commit hash 또는 완료 기록이 있는 상태다. |
| 전역 commit 스킬 설치 확인 완료 | `$CODEX_HOME/skills/commit/SKILL.md` 또는 `$HOME/.codex/skills/commit/SKILL.md`가 존재하는 상태다. |
| 작업 브랜치 push 완료 | 원격 push 완료 상태다. |
| PR 제목과 본문 확정 | 사용자 선택 확정이며 선택지가 PR 제목과 본문 확정이다. |
| PR open | GitHub PR open 상태다. |
| PR merged | GitHub PR merged 상태다. |
| 리뷰 실행 모드 확정 | 사용자가 `claude/code-review`, `claude/awesome-code-review`, `codex/awesome-code-review` 중 하나를 번호 또는 선택지 문구로 선택한 상태다. |
| 리뷰 실행 모드 검사 완료 | 선택된 리뷰 실행 모드의 의존성 확인 결과가 성공으로 기록된 상태다. |
| 리뷰 실행 결과 생성 완료 | 선택된 리뷰 실행 모드의 리뷰 결과 파일 경로가 기록되고 해당 파일이 읽기 가능한 상태다. |
| 게시 가능한 PR Review Template 확정 | 리뷰 결과가 PR Review Template 판정 규칙을 충족한 상태다. |
| review thread 또는 marker 댓글 게시 초안 정리 완료 | 리뷰 코멘트 초안 산출물에 PR 번호, 게시 대상, 게시 본문, diff 위치 또는 marker 요약 피드백 항목이 기록된 상태다. |
| 리뷰 코멘트 게시 완료 | review thread 생성 결과 또는 marker 댓글 생성 결과의 GitHub id가 기록된 상태다. |
| 피드백 1건 대응 방향 확정 | 사용자가 `수용`, `거절`, `기타 의견 입력` 중 하나를 번호 또는 선택지 문구로 선택한 상태다. |
| 피드백 수정 완료 | 선택된 피드백 1건의 대응 방향이 `수용`이고, 해당 피드백에 연결된 파일 diff와 검증 성공 결과가 기록된 상태다. |
| 피드백 수정 커밋 완료 | 선택된 피드백 1건의 수정 커밋 hash가 기록된 상태다. |
| 수정 push 완료 | 원격 push 완료 상태다. |
| 선택된 피드백 1건의 처리 결과 확정 | 선택된 피드백 1건의 대응 방향이 `거절` 또는 `기타 의견 입력`이거나, 대응 방향이 `수용`이고 수정 push 완료 상태다. |
| 피드백 처리 결과 댓글 완료 | 선택된 review thread 또는 marker 요약 피드백 항목에 처리 결과 댓글 id가 기록된 상태다. |
| 해당 피드백 해결 여부 확정 | 사용자가 `해결` 또는 `미해결` 중 하나를 번호 또는 선택지 문구로 선택한 상태다. |
| 피드백 해결 또는 미해결 결정 반영 완료 | `해결` 선택 시 review thread resolved 또는 marker 항목 checked 상태가 확인되고, `미해결` 선택 시 상태 유지 결과가 기록된 상태다. |
| 미해결 review thread 또는 미체크 요약 피드백 존재 | GitHub PR에 unresolved review thread가 하나 이상 있거나 marker 요약 피드백 댓글에 미체크 항목이 하나 이상 있는 상태다. |
| 리뷰 대응 대상 없음 | GitHub PR의 review thread가 모두 resolved이고 marker 요약 피드백 댓글의 모든 항목이 체크된 상태다. |
| PR merge 가능 | GitHub PR state가 open이고 mergeable 값이 true이며 필수 checks 결론이 success 또는 skipped인 상태다. |

## 상태 근거 분류 규칙

| 묶음 | 포함할 수 있는 근거 |
| ---- | ------------------- |
| 완료 근거 | 체크된 완료 조건, merged PR, resolved review thread, diff 위치 밖 marker 요약 피드백의 체크 상태 |
| 미완료 근거 | 미체크 완료 조건, open 연결 PR, unresolved review thread, diff 위치 밖 marker 요약 피드백의 미체크 상태 |
| 보조 근거 | 현재 코드 상태, 보조 로그, 현재 대화에서 확인한 마지막 관련 작업, 마지막 사용자 결정, 마지막 실행 결과 |
| 무효 근거 | 이슈 본문의 일반 설명, 추천 문장, 미선택 후보, 구조화된 스킬 출력 필드 밖의 설명 문장 |

- 완료 근거와 미완료 근거는 GitHub 실행 상태에서 읽는다.
- 보조 근거는 GitHub 실행 상태 밖의 중간 실행 상태를 판단할 때 사용한다.
- 보조 근거가 완료 근거 또는 미완료 근거와 충돌하면 GitHub 실행 상태를 우선한다.
- 무효 근거는 배경 설명으로만 참고한다.
- 현재 작업은 완료 근거, 미완료 근거, 보조 근거만으로 하나의 작업을 산출할 수 있을 때 확정한다.

## 현재 작업 산출 규칙

1. 기준 이슈 또는 PR의 GitHub 실행 상태와 현재 코드 상태를 읽는다.
2. 읽은 상태를 완료 근거, 미완료 근거, 보조 근거, 무효 근거로 분류한다.
3. 기준 대상의 이슈 유형 또는 PR 연결 이슈 유형을 확인한다.
4. 현재 기준 대상에 해당하는 작업 전이표에서 조건을 만족하는 작업을 찾는다.
5. 조건을 만족하는 작업이 하나이면 현재 작업으로 확정한다.
6. 조건을 만족하는 작업 수가 0개이면 진행 판단을 `중단`으로 둔다.
7. 조건을 만족하는 작업이 둘 이상이면 진행 판단을 `중단`으로 둔다.
8. 현재 작업의 `사용자 결정` 필드가 값을 가지면 진행 판단을 `사용자 결정`으로 둔다.
9. 현재 작업의 `사용자 결정` 필드가 `없음`이고 실행 범위가 확정되면 진행 판단을 `자동 실행`으로 둔다.
10. 기준 대상의 완료 조건이 충족되면 진행 판단을 `완료`로 둔다.

## 사용자 입력 판정 규칙

유효 입력 형식은 다음 네 가지다.

- 제시된 번호
- 선택지 문구 그대로
- `기타 의견 입력 항목 번호: 의견`
- `기타 의견 입력: 의견`

유효 입력 판정:

- 제시된 번호 또는 선택지 문구를 그대로 입력하면 해당 선택지를 사용자 결정으로 처리한다.
- `기타 의견 입력` 허용 형식으로 구체 의견을 입력하면 그 의견을 사용자 결정으로 처리한다.
- 기타 의견이 현재 사용자 결정 대상에 속하고, 실행 범위 안에 있으며, 완료 판정 기준으로 확인할 수 있으면 해당 의견을 사용자 결정으로 처리한다.
- 기타 의견이 처리 범위 밖이면 진행 판단을 `중단`으로 둔다.
- `기타 의견 입력` 항목 번호만 입력했거나 `기타 의견 입력` 문구만 입력하면 진행 판단을 `사용자 결정`으로 유지한다.
- 사용자 입력이 유효 입력 형식 밖이면 진행 판단을 `사용자 결정`으로 유지한다.
- `이대로 진행`, `생성해주세요`, `좋습니다`, `네` 같은 일반 진행 표현은 제시된 선택지 문구와 정확히 일치할 때 유효 입력으로 처리한다.

## 실행 범위 규칙

- 실행 범위는 현재 작업 이름, 사용자 결정, 작업 전이표의 완료 판정 기준으로 산출한다.
- 실행 범위에는 변경할 수 있는 GitHub 상태, 파일 또는 디렉터리, 댓글 또는 review thread, 브랜치, 커밋, PR 생성 여부를 포함한다.
- 이슈 생성, 계획 확정, 브랜치 이름 확정, 커밋 메시지 확정, PR 제목/본문 확정, 리뷰 실행 모드 선택, 리뷰 피드백 대응, PR merge는 사용자 결정으로 처리한다.

## 중단과 재개 판정 규칙

자동 실행 루프는 진행 판단이 `사용자 결정`, `중단`, `완료` 중 하나로 산출될 때 멈춘다.

- 현재 작업의 `사용자 결정` 필드가 값이면 진행 판단을 `사용자 결정`으로 둔다.
- 정보 부족, 의존성 확인 실패, 의도 불명확, 실행 오류, 상태 충돌, 사용자 보류 요청, 처리 범위 밖 요청은 진행 판단을 `중단`으로 둔다.
- 기준 대상의 완료 조건이 충족되면 진행 판단을 `완료`로 둔다.

재개 규칙:

- 재개할 때는 GitHub 실행 상태와 현재 코드 상태를 먼저 다시 읽는다.
- 실행 로그는 GitHub 실행 상태 밖의 중간 실행 상태를 확인할 때 보조 근거로 사용한다.
- 실행 로그와 GitHub 실행 상태가 충돌하면 GitHub 실행 상태를 우선한다.
- 중단된 흐름을 재개할 때 사용자 요청이 직전 응답에서 제시한 번호, 선택지 문구, 허용된 `기타 의견 입력` 형식과 일치하면 해당 입력을 사용자 결정으로 처리한다.
- 입력 형식이 유효 입력 형식 밖이면 진행 판단을 `사용자 결정`으로 유지한다.

## PR Review Template 판정 규칙

게시 가능한 PR Review Template은 다음 필드를 모두 가진다.

필수 섹션:

- `Required Changes`
- `Important Suggestions`
- `Minor Suggestions`
- `Learning Notes`
- `Security Considerations`
- `Test Coverage`
- `리뷰 결론`

필수 값:

- `리뷰 결론` 값은 `승인`, `의견`, `변경 요청` 중 하나다.
- 각 피드백의 중요도 라벨은 `[차단]`, `[중요]`, `[사소]`, `[제안]`, `[학습]`, `[칭찬]` 중 하나다.

피드백 필수 필드:

- 파일 경로와 diff 위치 또는 요약 피드백 표시
- 문제
- 영향
- 권장 조치

테스트 판단 필수 필드:

- 테스트 커버리지 판단 또는 테스트 영향 없음 판단

판정 결과:

- 모든 필수 섹션과 필수 필드가 있으면 `게시 가능한 PR Review Template 확정`으로 판정한다.
- 필수 섹션 또는 필수 필드가 비어 있으면 중단 사유와 보완 질문을 산출한다.

## 명령 실행 경로 규칙

명령 실행 경로는 일반 경로와 권한 확인 경로 중 하나로 판정한다.

권한 확인 경로:

- `gh pr comment`, `gh pr review`, `gh pr merge`, `gh issue edit`, `gh api --method POST|PATCH|PUT|DELETE`처럼 GitHub PR, issue, review, checks, comment 상태를 바꾸는 GitHub API 계열 명령
- `git push`, `git fetch`, `git pull`, `git ls-remote`처럼 네트워크나 원격 저장소 접근이 필요한 Git 명령
- `git commit`, `git tag`, `git merge`, `git rebase`처럼 `.git` 쓰기가 필요한 명령
- `sed -i`, `find -delete`, 쓰기나 삭제를 수행하는 `find -exec`처럼 로컬 파일을 수정하거나 삭제하는 명령

일반 경로:

- `gh pr view`, `gh issue view`, `gh pr checks`, `gh api` GET 조회처럼 GitHub 실행 상태를 읽는 명령
- `git status`, `git diff`, `git log`, `git show`, `rg`, 출력 또는 파이프 변환용 `sed`, `ls`, 탐색 전용 `find`, `wc`처럼 로컬 파일이나 로컬 Git 상태를 읽는 명령
- `git diff --check`처럼 로컬 변경사항을 검증하는 명령

변경 손실 가능 명령:

- `rm`, `git reset --hard`, `git clean`, 강제 push처럼 되돌리기 어렵거나 사용자 변경을 잃게 할 수 있는 명령

추가 규칙:

- 명령 실행 경로는 현재 작업, 실행 범위, 사용자 결정의 판정 결과를 유지한다.
- 변경 손실 가능 명령은 현재 작업의 실행 범위 안에 있고 사용자 의도가 명확한 상태에서만 실행한다.

## 작업 전이 규칙

각 작업표의 `조건`은 이전 작업에서 해당 작업으로 넘어올 수 있는 객관적 완료 근거 또는 확인 결과만 사용한다. `사용자 결정`은 현재 작업에서 사용자가 확정해야 하는 결정 대상이다. `완료 판정 기준`은 작업 실행 뒤 다음 전이로 넘어가기 위해 확인할 상태다. `사용자 결정`이 `없음`이면 실행 범위 안에서 자동 실행한다.

### 다음 계획 요청

| 순서 | 기준 대상 조건 | 현재 작업 |
| ---- | -------------- | --------- |
| 1 | merge 대기 PR 존재 | PR merge 대기 |
| 2 | unresolved review thread 또는 미체크 marker 요약 피드백 존재 | 리뷰 대응 대상 확인 |
| 3 | open PR 존재 | 해당 PR의 현재 작업 산출 |
| 4 | 열린 기능변경 또는 기능결함 이슈 존재 | 해당 이슈의 현재 작업 산출 |
| 5 | 열린 정책검토 이슈 존재 | 정책검토 현재 작업 산출 |
| 6 | 열린 기능제안 이슈 존재 | 기능제안 현재 작업 산출 |
| 7 | 이어갈 PR 또는 이슈 후보가 비어 있음 | 기능제안 초안 작성 |
