# GitHub Workflow Engine Rules

이 문서는 설치된 Workflow Engine 스킬들이 공통으로 따르는 운영 규칙이다. 원천 설계 문서는 `codex-harness` 저장소의 `docs/github-workflow-engine.md`이며, 이 파일은 전역 스킬 배포본에서 바로 읽을 수 있는 실행 기준이다.

## 공통 원칙

- GitHub Issue와 PR 상태를 프로젝트 작업 상태의 기준 저장소로 사용한다.
- 별도 Run State Runtime은 만들지 않는다.
- 상태 전이는 LLM 자유 판단이 아니라 이 문서의 규칙과 스킬별 책임을 따른다.
- 이슈 생성, 계획 승인, 브랜치 이름 승인, 커밋 메시지 승인, PR 제목/본문 승인, 리뷰 피드백 대응, PR merge는 Human Checkpoint다.
- 계획/제안형 전용 스킬은 후보, 초안, 분석 결과를 만들고 상태 확정이나 사용자 승인은 Workflow Engine의 Human Checkpoint에서 처리한다.
- 외부 의존 스킬인 전역 `commit`과 Claude `code-review-skill`은 이 저장소에서 관리하지 않는다. 해당 액션 진입 전 설치 여부를 확인하고, 없으면 설치 안내 후 워크플로우를 중단한다.
- PR merge는 사람이 수행한다.
- Workflow Skill은 merge 알림 또는 다음 계획 요청 시 GitHub Run State를 다시 읽어 연결 이슈의 체크리스트와 종료 조건을 판단한다.
- 로컬 `.harness/logs/github-workflow-log.md`는 보조 체크포인트이며, GitHub 상태를 대체하지 않는다.

## 이슈 유형

- `기능제안`: 기능 추가, 기능 수정, 운영 흐름 개선 요청을 판단한다.
- `정책검토`: 설계, 정책, 운영 기준 결정을 추적한다.
- `기능변경`: 기능 추가 또는 기존 기능 수정을 실행한다.
- `기능결함`: 결함, 회귀, 문서와 구현 불일치, 반영 누락을 해결한다.

## PR 연결 기준

- PR 본문의 `연관 이슈` 섹션에서 `Refs #번호` 형식을 파싱한다.
- 정책검토 PR은 정책검토 이슈와 연결한다.
- 기능 구현 PR은 기능변경 이슈와 연결한다.
- 결함 해결 PR은 기능결함 이슈와 연결한다.
- Workflow Engine 관리 이슈에는 `Closes`, `Fixes`, `Resolves` 자동 close 키워드를 사용하지 않는다.
- 이슈 close는 PR merge 후 Workflow Skill이 완료 기준과 후속 작업을 확인한 뒤 수행한다.

## 기능제안 흐름

| 액션 | 조건 | Human Checkpoint | 기록 |
| --- | --- | --- | --- |
| 기능제안 초안 작성 | 사용자가 비정형 기능 요청을 함 | 기능제안 초안 승인 | `issue-creation`이 템플릿 초안을 작성한다. |
| 기능제안 이슈 생성 | 사용자가 초안을 승인함 | 없음 | Workflow Engine이 승인된 초안 그대로 GitHub 이슈를 생성한다. |
| 진행 방향 판단 | 기능제안 open, 판단 결과 미확정 | 진행하지 않음 / 정책검토 필요 / 기능변경 필요 승인 | 판단 근거를 이슈에 반영한다. |
| 정책검토 전환 | 사용자가 정책검토 필요를 승인함 | 정책검토 초안 승인 | 정책검토 이슈의 `연관 이슈`에 기능제안 번호를 기록한다. |
| 기능변경 전환 | 사용자가 기능변경 필요를 승인함 | 기능변경 초안 승인 | 기능변경 이슈의 `연관 이슈`에 기능제안 번호를 기록한다. |
| 기능제안 종료 | 판단 결과와 후속 이슈 반영 완료 | 없음 | 완료 기준 체크 후 close한다. |

## 정책검토 흐름

| 액션 | 조건 | Human Checkpoint | 기록 |
| --- | --- | --- | --- |
| 정책 결정 | 정책검토 open, 검토 결과 미확정 | 정책 방향 승인 | `검토 결과`에 결정과 근거를 기록한다. |
| 설계 문서 반영 계획 | 정책 결정 승인됨 | 설계 반영 계획 승인 | 설계 문서 반영 단위를 구현 단위로 나눈다. |
| 기능 구현 흐름 진입 | 설계 반영 단위가 확정됨 | 브랜치 이름 승인부터 진행 | 정책검토 이슈를 연결 이슈로 사용한다. |
| 기능변경 이슈 초안 작성 | 정책검토 결과가 기능변경으로 이어짐 | 기능변경 초안 승인 | 새 기능변경 이슈의 `연관 이슈`에 정책검토 번호를 기록한다. |
| 정책검토 종료 | 설계 반영과 필요한 후속 이슈 반영 완료 | 없음 | 후속 작업 체크리스트와 `검토 결과`를 확인한 뒤 close한다. |

정책검토가 기능결함에서 이어진 경우 기능변경 이슈 반영 항목을 임의로 추가하지 않는다.

## 기능변경 흐름

| 액션 | 조건 | Human Checkpoint | 기록 |
| --- | --- | --- | --- |
| 기능 개발 계획 수립 | 기능변경 open | 기능 개발 계획 승인 | `feature-plan`으로 구현 단위, 브랜치 수, 순서, 검증 기준을 제안한다. |
| 기능 구현 착수 | 사용자가 기능 개발 계획을 승인함 | 없음 | 각 기능 구현 단위를 기능 구현 흐름으로 넘긴다. |
| 완료 기준 갱신 | 연결 PR merged | 없음 | 충족된 체크항목을 체크하고 PR 번호를 덧붙인다. |
| 기능변경 종료 | 완료 기준이 모두 충족됨 | 없음 | 연결 PR과 현재 코드 상태를 확인한 뒤 close한다. |

## 기능결함 흐름

| 액션 | 조건 | Human Checkpoint | 기록 |
| --- | --- | --- | --- |
| 기능결함 초안 작성 | 사용자가 비정형 결함 보고를 함 | 기능결함 초안 승인 | `issue-creation`이 템플릿 초안을 작성한다. |
| 원인 조사 | 기능결함 open, 원인 미확정 | 원인 조사 결과와 대응 방향 승인 | 원인은 기록하되 해결 방향은 승인 후 확정한다. |
| 정책검토 전환 | 정책 판단이 필요함 | 정책검토 초안 승인 | 정책검토 이슈의 `연관 이슈`에 기능결함 번호를 기록한다. |
| 기능 결함 해결 계획 수립 | 정책 수정 없는 결함이거나 정책검토 결과가 반영됨 | 기능 결함 해결 계획 승인 | `fix-plan`으로 해결 단위, 브랜치 수, 순서, 검증 기준을 제안한다. |
| 기능 구현 착수 | 사용자가 해결 계획을 승인함 | 없음 | 각 결함 해결 단위를 기능 구현 흐름으로 넘긴다. |
| 완료 기준 갱신 | 연결 PR merged | 없음 | 충족된 체크항목을 체크하고 PR 번호를 덧붙인다. |
| 기능결함 종료 | 완료 기준이 모두 충족됨 | 없음 | 원인, 해결 방향, 현재 코드 상태를 확인한 뒤 close한다. |

## 기능 구현 흐름

| 액션 | 조건 | Human Checkpoint | 기록 |
| --- | --- | --- | --- |
| 브랜치 이름 제안 | 구현 단위 확정 | 브랜치 이름 승인 | `branch-plan`으로 후보와 근거를 제시한다. |
| 세부 구현 계획 수립 | 작업 브랜치 전환 완료 | 세부 구현 계획 승인 | 커밋 단위와 검증 기준을 제시한다. |
| 구현 작업 | 승인된 커밋 단위가 남음 | 없음 | 승인된 범위만 수정한다. |
| 커밋 스킬 검사 | 커밋 단위 변경 완료 | 없음 | 전역 `commit` 스킬 설치를 확인한다. 없으면 설치 안내 후 중단한다. |
| 커밋 메시지 제안 | 커밋 스킬 설치 확인 완료 | 변경 내용과 커밋 메시지 승인 | `commit`으로 메시지 후보를 제안하고 Workflow Engine이 변경 범위와 함께 승인받는다. |
| 커밋 생성 | 변경 내용과 메시지 승인 | 없음 | 승인된 변경만 커밋한다. |
| PR 초안 작성 | 모든 커밋 단위 완료 | PR 제목과 설명 승인 | `pr-proposal`로 제안한다. |
| 작업 브랜치 push | PR 제목과 설명 승인 | 없음 | 원격 head branch를 확인한다. |
| PR 생성 입력 검증 | 원격 head branch 확인 | 없음 | `pr-creation`으로 PR 생성 입력을 검증하고 생성 요청 초안을 만든다. |
| PR 생성 | PR 생성 입력 검증 완료 | 없음 | Workflow Engine이 검증된 입력으로 GitHub PR을 생성한다. |
| 리뷰 스킬 검사 | PR open | 없음 | Claude `code-review-skill` 설치를 확인한다. 없으면 설치 안내 후 중단한다. |
| Claude 리뷰 실행 | 리뷰 스킬 설치 확인 완료 | 없음 | Workflow Engine이 diff, 이슈 맥락, 출력 템플릿 요구사항을 준비해 Claude `code-review-skill`로 리뷰 결과를 만든다. |
| 리뷰 코멘트 초안 정리 | `code-review-skill` 템플릿 출력 결과 존재 | 없음 | `review-comment`가 template section과 severity label을 읽어 thread 또는 요약 댓글 게시 초안을 정리한다. |
| 리뷰 코멘트 게시 | 리뷰 코멘트 게시 초안 확인 완료 | 없음 | Workflow Engine이 review thread 또는 요약 피드백 댓글을 게시한다. |
| 피드백 대응 제안 | unresolved thread 또는 미체크 요약 피드백 존재 | 피드백 대응 승인 | 적용, 보류, 거절, 사람 승인 필요로 분류한다. |
| PR merge 대기 | 모든 피드백 처리, checks 통과, merge 가능 | PR merge | 사람이 merge한다. |
| PR merge 반영 | PR merged | 없음 | base branch를 갱신하고 연결 이슈의 PR merged 전이로 이동한다. |

## Review Feedback Triage

- `적용`: 실제 결함 또는 명확한 개선이다. 해당 PR 범위 안에서 수정한다.
- `보류`: 더 많은 맥락이 필요하다. 이슈 또는 PR에 보류 사유를 기록한다.
- `거절`: 오탐 또는 범위 밖 제안이다. 거절 근거를 기록한다.
- `사람 승인 필요`: 고위험 변경 또는 애매한 판단이다. Human Checkpoint로 전달한다.

라인 피드백은 review thread의 `isResolved`로 추적한다. 라인에 붙일 수 없는 피드백은 `<!-- codex-harness:summary-feedback v1 -->` marker가 있는 요약 피드백 댓글 체크리스트로 추적한다.
