# GitHub Workflow Engine Rules

이 문서는 설치된 Workflow Engine 스킬들이 공통으로 따르는 운영 규칙이다. 원천 설계 문서는 `codex-harness` 저장소의 `docs/github-workflow-engine.md`이며, 이 파일은 전역 스킬 배포본에서 바로 읽을 수 있는 실행 기준이다.

## 공통 원칙

- GitHub Issue와 PR 상태를 프로젝트 작업 상태의 기준 저장소로 사용한다.
- 별도 Run State Runtime은 만들지 않는다.
- 상태 전이는 LLM 자유 판단이 아니라 이 문서의 규칙과 스킬별 책임을 따른다.
- 이슈 생성, 계획 확정, 브랜치 이름 확정, 커밋 메시지 확정, PR 제목/본문 확정, 리뷰 실행 모드 선택, 리뷰 피드백 대응, PR merge는 Human Checkpoint다.
- 계획/제안형 전용 스킬은 후보, 초안, 분석 결과를 만들고 상태 확정이나 사용자 의도 확인은 Workflow Engine의 Human Checkpoint에서 처리한다.
- 이슈, PR, 체크리스트, 댓글 같은 GitHub 상태 변경은 사용자의 생성/수정/닫기 의도가 자연어 맥락에서 명확할 때만 수행한다.
- 사용자의 의도가 모호하면 GitHub 상태를 변경하지 않고 초안, 수정 후보, 필요한 확인 질문만 제시한다.
- 이슈와 PR 본문 형식의 단일 원천은 타겟 레포의 `.github/ISSUE_TEMPLATE/*.md`와 `.github/pull_request_template.md`다.
- `github-templates.md`는 실제 템플릿 본문 복제본이 아니라 title prefix, label, 필수 섹션, 연결 규칙을 검증하는 계약 문서다.
- 설치 기본 리뷰 실행 모드는 타겟 레포의 `.harness/workflow-engine.json`에 `review.defaultMode`로 저장한다. 값은 `claude/code-review`, `claude/awesome-code-review`, `codex/awesome-code-review` 중 하나여야 한다. 이 값은 기본 후보이며, 사용자의 명시 선택 없이 리뷰 실행 모드 검사로 전이하지 않는다.
- 외부 의존성인 전역 `commit`, `awesome-code-review`, `sendbird/cc-plugin-codex`는 이 저장소에서 관리하지 않는다. 해당 액션 진입 전 설치 여부를 확인하고, 없으면 설치 가능한 소스, 설치 대상 경로, 설치 후 확인할 파일 또는 명령, 재개 조건을 안내한 뒤 워크플로우를 중단한다.
- `awesome-code-review`는 `https://github.com/codechaser-kr/repo-bootstrap`의 install 절차로 설치한다. 원천 스킬은 `https://github.com/awesome-skills/code-review-skill`이지만, Codex 전역 설치명과 frontmatter `name`은 기본 내장 리뷰 스킬과의 이름 충돌을 피하기 위해 `awesome-code-review`로 맞춘다.
- `sendbird/cc-plugin-codex` 설치 관리는 `https://github.com/codechaser-kr/repo-bootstrap`의 install 절차에서 담당한다. `claude/*` 리뷰 실행 모드에서 이 의존성이 없으면 다른 리뷰 실행 모드로 자동 fallback하지 않는다.
- `sendbird/cc-plugin-codex` 설치 여부는 `$CODEX_HOME/plugins/cache/sendbird/cc/*/.codex-plugin/plugin.json` 또는 `$HOME/.codex/plugins/cache/sendbird/cc/*/.codex-plugin/plugin.json`, 같은 플러그인 루트의 `skills/setup/SKILL.md`, `scripts/claude-companion.mjs`, `$cc:setup` 실행 결과로 확인한다.
- `claude/*` 리뷰 실행 모드의 Claude CLI 인증은 `$cc:setup`의 `auth.available: true`, `auth.loggedIn: true` 또는 authenticated 사용자 표시 출력으로만 완료 판정한다. 인증이 없거나 판단할 수 없으면 리뷰 실행을 중단하고 `$cc:setup`의 login 안내와 재실행 조건을 전달한다.
- `claude/code-review`는 `$cc:review` companion review가 아니라 base/head 브랜치를 target으로 전달해 Claude Code의 `/code-review` command를 단독 호출한다. PR 맥락과 출력 조건은 command arguments에 붙이지 않고 별도 정규화 프롬프트로 넘긴다. `/code-review --comment`와 `/code-review --fix`는 사용하지 않고, GitHub 게시와 파일 수정은 Workflow Engine 후속 단계에서만 수행한다.
- `claude/code-review` stdout findings는 PR 전체 `Verdict`, 각 피드백의 severity label, 파일 경로와 diff 위치 또는 요약 피드백 여부, 문제와 영향, 권장 조치, 테스트 커버리지 판단을 갖춘 PR Review Template으로 정규화한다. 위치, severity, verdict, 문제 영향, 권장 조치, 테스트 커버리지 판단 중 하나라도 판단할 수 없으면 게시하지 않고 보류 질문으로 중단한다.
- PR merge는 사람이 수행한다.
- Workflow Skill은 merge 알림 또는 다음 계획 요청 시 GitHub Run State를 다시 읽어 연결 이슈의 체크리스트와 종료 조건을 판단한다.
- 로컬 `.harness/logs/github-workflow-log.md`는 보조 체크포인트이며, GitHub 상태를 대체하지 않는다.
- 기능변경/기능결함 계획과 완료 기준 갱신처럼 후속 전이 판단에 쓰이는 상태는 댓글이 아니라 이슈 본문에 반영한다.
- PR 리뷰 결과, 보조 로그, merge 반영 알림처럼 댓글이나 로그가 맞는 항목은 이슈 본문 반영 대상과 구분한다.

## 명령 실행 경로 선택

이 섹션은 `docs/github-workflow-engine.md`의 명령 실행 경로 규칙을 전역 스킬 공통 실행 기준에 복제한 사본이다. 규칙을 바꿀 때는 원천 설계 문서와 배포본 `SKILL.md`의 같은 섹션을 함께 정렬한다.

Workflow Engine은 명령을 실행하기 전에 일반 경로와 승인 경로 중 어느 쪽이 맞는지 판단한다. 일반 경로는 현재 권한 안에서 바로 실행할 수 있는 읽기, 조회, 로컬 검증 명령을 뜻한다. 승인 경로는 권한 상승, 원격 접근, GitHub 상태 변경, `.git` 쓰기, 파일 수정 또는 삭제 가능성이 있어 실행 전 사용자 의도 확인이 필요한 명령을 뜻한다. 실행 경로 선택은 권한과 실패 가능성을 줄이기 위한 판단이며, Human Checkpoint를 대체하지 않는다. 사용자 결정이 필요한 상태 변경, 커밋 메시지 확정, PR merge 같은 항목은 승인 경로를 쓰더라도 별도로 사용자 의도가 명확해야 한다.

처음부터 승인 경로를 사용하는 명령:

- `gh pr comment`, `gh pr review`, `gh pr merge`, `gh issue edit`, `gh api --method POST|PATCH|PUT|DELETE`처럼 GitHub PR, issue, review, checks, comment 상태를 바꾸는 GitHub API 계열 명령
- `git push`, `git fetch`, `git pull`, `git ls-remote`처럼 네트워크나 원격 저장소 접근이 필요한 Git 명령
- `git commit`, `git tag`, `git merge`, `git rebase`처럼 `.git` 쓰기가 필요한 명령
- `sed -i`, `find -delete`, 쓰기나 삭제를 수행하는 `find -exec`처럼 로컬 파일을 수정하거나 삭제하는 명령

일반 경로를 우선 사용하는 명령:

- `gh pr view`, `gh issue view`, `gh pr checks`, `gh api` GET 조회처럼 GitHub Run State를 읽기만 하는 명령
- `git status`, `git diff`, `git log`, `git show`, `rg`, 출력 또는 파이프 변환용 `sed`, `ls`, 탐색 전용 `find`, `wc`처럼 로컬 파일이나 로컬 Git 상태를 읽는 명령
- `git diff --check`처럼 로컬 변경사항만 검증하는 명령

파괴적 명령은 실행 경로와 별개로 사용자 의도가 명확해야 한다. `rm`, `git reset --hard`, `git clean`, 강제 push처럼 되돌리기 어렵거나 사용자 변경을 잃게 할 수 있는 명령은 승인 경로 사용 여부만으로 실행하지 않는다.

## 이슈 유형

- `기능제안`: 기능 추가, 기능 수정, 운영 흐름 개선 요청을 판단한다.
- `정책검토`: 설계, 정책, 운영 기준 결정을 추적한다.
- `기능변경`: 기능 추가 또는 기존 기능 수정을 실행한다.
- `기능결함`: 결함, 회귀, 문서와 구현 불일치, 반영 누락을 해결한다.

## PR 연결 기준

- PR 본문의 `연관 이슈` 섹션에서 `Refs #번호` 형식을 파싱한다.
- 정책검토 PR은 정책검토 이슈와 연결한다.
- 기능 구현 PR은 기능변경 이슈와 연결한다.
- 결함 해결 PR은 기능결함 이슈와 연결한다.
- Workflow Engine 관리 이슈에는 `Closes`, `Fixes`, `Resolves` 자동 close 키워드를 사용하지 않는다.
- 이슈 close는 PR merge 후 Workflow Skill이 완료 기준과 후속 작업을 확인한 뒤 수행한다.

## 기능제안 흐름

| 액션               | 조건                                 | Human Checkpoint                                   | 상태 반영                                                        |
| ------------------ | ------------------------------------ | -------------------------------------------------- | ---------------------------------------------------------------- |
| 기능제안 초안 작성 | 사용자가 비정형 기능 요청을 함       | 기능제안 초안 확인                                 | Issue Creation Skill이 타겟 템플릿 형식으로 초안을 작성한다.     |
| 기능제안 이슈 생성 | 사용자의 생성 의도가 명확함          | 없음                                               | 확정된 초안 그대로 GitHub 이슈를 생성한다.                       |
| 진행 방향 판단     | 기능제안 open, 판단 결과 미확정      | 진행하지 않음 / 정책검토 필요 / 기능변경 필요 확정 | 판단 근거를 기능제안 이슈 본문에 반영한다.                       |
| 정책검토 전환      | 사용자의 정책검토 전환 의도가 명확함 | 정책검토 초안 확인                                 | 새 정책검토 이슈 본문의 `연관 이슈`에 기능제안 번호를 반영한다.  |
| 기능변경 전환      | 사용자의 기능변경 전환 의도가 명확함 | 기능변경 초안 확인                                 | 새 기능변경 이슈 본문의 `연관 이슈`에 기능제안 번호를 반영한다.  |
| 기능제안 종료      | 판단 결과와 후속 이슈 반영 완료      | 없음                                               | 완료 기준을 체크하고 close한다.                                  |

## 정책검토 흐름

| 액션                    | 조건                                   | Human Checkpoint          | 상태 반영                                                                      |
| ----------------------- | -------------------------------------- | ------------------------- | ------------------------------------------------------------------------------ |
| 정책검토 초안 작성      | 정책 또는 설계 판단이 필요함           | 정책검토 초안 확인        | Issue Creation Skill이 정책검토 템플릿 초안을 작성한다.                        |
| 정책검토 이슈 생성      | 사용자의 생성 의도가 명확함            | 없음                      | 확정된 초안 그대로 생성하고 `검토 결과`는 비워 둔다.                           |
| 정책 방향 결정 요청     | 정책검토 open, 검토 결과 미확정        | 정책 결정                 | 결정 질문, 배경, 선택지를 제시한다.                                            |
| 정책 결정 반영          | 사용자가 정책 방향을 결정함            | 없음                      | 정책검토 이슈 본문의 `검토 결과`에 결정과 근거를 반영한다.                     |
| 설계 문서 반영 계획     | 정책 결정 완료                         | 설계 반영 계획 확정       | 설계 원천 반영 단위, 대상 문서, 검증 기준을 정리한다.                          |
| 설계 문서 반영 착수     | 설계 반영 계획 확정                    | 브랜치 이름 확정부터 진행 | 설계 원천만 기능 구현 흐름으로 반영한다.                                       |
| 설계 문서 PR 반영       | 정책검토 PR merged                     | 없음                      | 설계 문서 반영 PR을 이슈 체크리스트에 반영한다.                                |
| 후속 기능변경 초안 작성 | 실행 산출물 변경이 필요함              | 기능변경 초안 확인        | 새 기능변경 이슈 본문의 `연관 이슈`에 정책검토 번호를 반영한다.                |
| 기능결함 이슈 반영      | 원본이 기능결함 이슈임                 | 기능결함 반영 확인        | 원본 기능결함의 원인, 해결 방향, 완료 기준에 정책 결과를 반영한다.             |
| 정책검토 종료           | 설계 반영과 필요한 후속 이슈 반영 완료 | 없음                      | 후속 작업 체크리스트와 `검토 결과`를 확인한 뒤 close한다.                      |

정책검토가 기능결함에서 이어진 경우 기능변경 이슈 반영 항목을 임의로 추가하지 않는다.

| ------------------- | ----------------------------------- | ------------------- | -------------------------------------------------------------------------------------------- |

| 기능 구현 착수      | 기능 개발 계획이 이슈 본문에 반영됨 | 없음                | 각 기능 구현 단위를 기능 구현 흐름으로 넘긴다.                                               |

## Review Feedback Triage

리뷰 결과를 처리할 때 `Verdict`, `Severity`, `Workflow response`, `Resolution decision`을 서로 다른 판단 축으로 다룬다.

- `Verdict`: `awesome-code-review`가 제시하는 PR 전체 결론이다. 값은 `Approve`, `Comment`, `Request Changes`다.
- `Severity`: `awesome-code-review`가 제시하는 개별 피드백 중요도다. 값은 `[blocking]`, `[important]`, `[nit]`, `[suggestion]`, `[learning]`, `[praise]`다.
- `Workflow response`: 사용자가 Human Checkpoint에서 확정하는 대응 방향이다. 값은 `수용`, `거절`, `기타`다.
- `Resolution decision`: 수정 push와 필요한 댓글 처리 뒤 사용자가 별도로 확정하는 resolve, 체크, 미해결 유지 결정이다.

`Severity`는 피드백 처리 우선순위와 위험을 설명하는 입력일 뿐이며, `Workflow response`로 직접 매핑하지 않는다.

- `수용`: 피드백을 현재 PR 범위에서 반영한다. 승인된 범위만 수정하고 커밋 메시지를 다시 확정한다.
- `거절`: 오탐, 범위 밖, 또는 반영하지 않을 피드백이다. 거절 근거를 남기고 파일은 수정하지 않는다.
- `기타`: 추가 질문, 범위 재조정, 별도 이슈화 등 즉시 수용/거절로 닫기 어려운 피드백이다. 사용자가 지정한 후속 액션만 수행한다.

라인 피드백은 review thread의 `isResolved`로 추적한다. 라인에 붙일 수 없는 피드백은 `<!-- codex-harness:summary-feedback v1 -->` marker가 있는 요약 피드백 댓글 체크리스트로 추적한다.

피드백은 한 번에 하나만 처리한다. Workflow Engine은 여러 unresolved thread나 미체크 요약 피드백을 한 번에 수정하지 않고, 피드백 1건마다 맥락 설명, 대응 방향 Human Checkpoint, 수정, 커밋 메시지 Human Checkpoint, push, 수정 댓글 게시 또는 생략 판단, resolve 여부 확인, resolve 결정 반영, 남은 피드백 확인을 반복한다.

`수용`은 선택된 피드백 1건을 반영하라는 승인만 의미한다. 파일 수정과 검증이 끝난 뒤에는 `commit` 스킬로 커밋 메시지 후보를 제안하고, 사용자가 특정 커밋 메시지를 확정하기 전까지 `git commit`을 실행하지 않는다. 작업 진행 안내나 추천 메시지 표시만으로 커밋 메시지 확정 Human Checkpoint를 충족한 것으로 보지 않는다.

여러 피드백을 조회하거나 맥락으로 확보했더라도 현재 처리 대상은 Workflow Engine이 이번 단계에서 선택해 사용자에게 제시한 피드백 1건뿐이다. 선택되지 않은 피드백은 읽기 전용 맥락이며, 같은 수정 작업이나 같은 커밋에 함께 포함하지 않는다.

피드백 대응 방향은 사용자가 `수용`, `거절`, `기타` 중 하나를 명시해야 확정된다. `수정`, `계속 진행`, `다음으로`, `네`, `좋습니다`, `진행해주세요` 같은 일반 진행 표현은 권장 대응 승인으로 해석하지 않는다. 권장 대응은 기본값이 아니라 제안이며, 방향이 명시되지 않으면 선택된 피드백 1건도 파일 수정이나 댓글 처리로 넘어가지 않고 대응 방향을 다시 질문한다.

리뷰 피드백 대응 방향은 상태 전이를 확정하는 선택지이므로 `수용`, `거절`, `기타`만 유효하다. `수정` 같은 액션 지시는 어떤 대응 방향을 선택했는지 명확히 표현하지 않으므로 대응 방향 확정으로 보지 않는다.

다음 피드백으로 이동하려면 현재 선택된 피드백 1건의 대응 방향 확정, 필요한 수정, 커밋, push, 수정 댓글 게시 또는 생략 판단, resolve 또는 체크 여부 결정, GitHub Run State 재조회가 끝나야 한다. 재조회 전에는 남은 피드백을 이어서 수정하지 않는다.

수정 댓글 형식은 피드백 출처에 따라 다르다. `commit-hash 수정했습니다.` 형식은 현재 Workflow Engine 실행이 `review-comment`로 게시한 review thread 또는 marker 요약 피드백에만 사용한다. 판단 기준은 작성자 계정, bot 이름, 리뷰 문체가 아니라 현재 `리뷰 코멘트 게시` 액션의 게시 결과 또는 같은 실행 로그에 남은 thread/comment id 또는 marker 요약 피드백 항목 추적 근거다. `피드백 수정 댓글` 액션에 진입하기 전에 이 추적 근거를 확인해야 하며, 추적 근거가 없거나 현재 실행이 게시한 피드백인지 확정할 수 없으면 이 액션을 생략하고 `외부 피드백 수정 댓글 생략`을 거쳐 `피드백 해결 여부 확인`으로 이동한다. 외부 리뷰 도구, 사람이 남긴 피드백, 이전 실행에서 생성된 피드백에는 `commit-hash 수정했습니다.` 형식의 자동 댓글을 남기지 않는다. 사용자가 외부 피드백 답글 작성을 별도로 요청한 경우에만 외부 피드백 형식이나 사용자가 지정한 문구에 맞춰 답글을 작성한다.

resolve 또는 체크는 피드백 출처와 무관하게 별도 Human Checkpoint다. Workflow Engine 생성 피드백과 외부 피드백 모두 수정 push와 수정 댓글 게시 또는 생략 판단이 끝난 뒤 사용자에게 resolve 여부를 확인한다.
