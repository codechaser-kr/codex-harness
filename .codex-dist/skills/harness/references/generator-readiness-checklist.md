# Generator Readiness Checklist

이 문서는 `harness` 생성기가 Codex에서 실행 가능한 메타하네스 시스템을 만들 준비가 됐는지 점검하는 기준이다.

여기서 말하는 준비도는 타겟 프로젝트에 생성된 하네스가 충분하다는 판정과 다르다. 실제 판정은 타겟 프로젝트에 하네스를 생성한 뒤, 생성된 `.harness/docs/*`, `.codex/agents/*`, `.codex/skills/*`, 세션 로그, 재진입 요약을 읽어야 가능하다.

이 문서의 목적은 제한적이다. 이 저장소 안에서는 **생성기가 타겟 프로젝트에서 충분성 평가를 수행할 기준과 절차를 갖췄는가**만 본다.

---

## 1. 준비도 점검 원칙

- 이 저장소에서는 타겟 하네스의 충분성을 직접 판정하지 않는다.
- 이 저장소에서는 생성기가 충분성 평가에 필요한 입력, 역할, 문서, 검증 기준을 만들 수 있는지만 점검한다.
- 운영 기준의 진실원천은 `SKILL.md`, reference 계약 문서, `team-spec`, 생성된 로컬 하네스 자산이다.
- 다른 런타임의 팀 호출 방식, 명령어, 환경 변수, 파일 구조를 전제로 삼지 않는다.
- 준비도 평가는 `SKILL.md` 본문 하나만 보지 않는다. `references/`, templates, 검증 기준이 같은 운영 모델을 말하는지 함께 본다.

---

## 2. 확인 가능한 범위

이 저장소에서 확인할 수 있는 범위는 아래로 제한된다.

- `SKILL.md`가 메타하네스 생성 생명주기를 설명하는가
- reference 문서가 각 판단 축의 기준을 제공하는가
- `team-spec`이 생성 결과의 단일 기준으로 설명되는가
- 생성 결과가 Codex 로컬 실행 자산으로 설명되는가
- 주 에이전트가 같은 운영 기준을 읽고 실행할 수 있는가
- 로그와 재진입 규칙이 다음 세션의 입력으로 이어지는가
- 타겟 프로젝트에서 충분성 평가를 수행할 운영 감사 기준이 준비돼 있는가

아래 항목은 이 저장소만으로 판정할 수 없다.

- 특정 타겟 프로젝트에서 생성된 역할 팀이 충분한가
- 생성된 역할 스킬이 실제 프로젝트 작업 품질을 개선했는가
- `with-skill` 결과가 `without-skill`보다 나은가
- 생성된 하네스가 운영 가능, 재작성 필요, 재구성 필요 중 어디에 해당하는가

이 항목은 타겟 프로젝트에 하네스를 생성한 뒤 `Phase 6` 운영 감사와 `Phase 7` 품질 비교에서 판단한다.

---

## 3. 생성기가 갖춰야 할 최소 축

아래 축이 있어야 타겟 프로젝트에서 충분성 평가까지 이어질 수 있다.

### 1) 도메인 입력 해석

- 저장소 재독해를 전제로 둔다.
- 자동 탐색 결과를 최종 판단으로 쓰지 않고, 역할 스킬이 다시 읽을 입력으로 남긴다.
- 사용자 입력이 부족할 때는 질문과 `project-setup.md` 작성을 앞에 둔다.
- 도메인 언어, 실패 비용, 실행 경계, 검증 비용을 역할 설계의 근거로 연결한다.

### 2) 팀 아키텍처 선택

- 프로젝트마다 역할 팀이 달라질 수 있음을 명시한다.
- `파이프라인`, `생성-검증`, `팬아웃/팬인`, `오케스트레이션 중심`, `전문가 풀` 같은 실행 패턴을 선택할 기준이 있다.
- 역할 수를 늘리는 것이 목적이 아니라, 현재 프로젝트에서 운영 가능한 팀 크기를 고르는 기준이 있다.
- 중심 조율 역할, 시작 진입 역할, QA 역할, 운영 감사 역할의 경계가 섞이지 않는다.

### 3) 역할 스펙 진실원천

- `team-spec`이 역할 인벤토리와 생성 결과의 단일 기준으로 작동한다.
- `AGENTS.md`, `.codex/config.toml`, `.codex/agents/*.toml`, `.codex/skills/*`가 `team-spec`을 구현한 결과로 설명된다.
- 각 역할에는 이름, 책임, 입력, 출력, 다음 역할, 시작 조건, 종료 조건, 재진입 트리거, 금지 판단이 포함된다.
- 추상 직무명만 복사하지 않고, 저장소 고유 용어와 실패 경계를 역할명에 반영한다.

### 4) 로컬 실행 자산 생성

- Codex가 읽을 수 있는 로컬 에이전트 정의와 로컬 역할 스킬을 생성 대상으로 둔다.
- 에이전트 정의는 “누가 하는가”를 맡고, 역할 스킬은 “어떻게 하는가”를 맡도록 분리한다.
- 생성기는 고정 역할 목록을 완성본처럼 복사하지 않고, `team-spec`의 최종 역할 인벤토리를 읽어 만든다.
- 생성 결과는 저장소 루트 기준 상대 경로로 설명되며, 사용자 홈 디렉터리나 절대경로에 의존하지 않는다.

### 5) 오케스트레이션과 handoff

- 시작 진입 역할(`run-harness`)이 현재 상태를 읽고 첫 역할과 다음 역할을 안내할 수 있다.
- 역할 간 입력/출력, handoff 형식, 실패 시 되돌아갈 Phase가 문서로 고정된다.
- 병렬 위임은 독립 입력과 독립 산출이 있을 때만 사용하고, 최종 통합 책임은 주 에이전트 또는 중심 조율 역할에 남긴다.
- 재진입 기준이 `latest-session-summary.md`와 연결된다.

### 6) QA와 운영 감사

- QA 역할은 품질 전략과 검증 질문을 제공한다.
- 운영 감사 역할은 파일 존재만 보지 않고, 역할 경계, 문서 목적, 재진입 가능성, 로그 완결성을 본다.
- 구조 검증과 운영 감사의 책임을 구분한다.
- 검증 결과가 다음 재진입 Phase나 다시 쓸 문서로 이어진다.

### 7) 로그와 재진입

- 세션 시작, 역할 완료, 실패, 보류, 종료 요약이 Markdown 로그에 남는다.
- `session-log.md`와 `latest-session-summary.md`가 다음 실행의 입력이 된다.
- 비동기 subagent 결과는 `completed`, `failed`, `timed_out`, `skipped`, `blocked` 중 하나로 정리된다.
- 다음 시작 역할, 다음 재진입 Phase, 다시 읽을 입력, 최근 출력이 세션 종료 시점에 남는다.

### 8) 피드백 반영과 진화

- 하네스는 한 번 생성하고 끝나는 구조가 아니라, 실행 결과를 다음 생성과 정렬에 반영하는 구조여야 한다.
- 타겟 프로젝트에서 `with-skill` / `without-skill` 비교를 수행할 기준이 준비돼 있어야 한다.
- 부족한 축이 입력 문서 문제인지, 역할 설계 문제인지, 스킬 작성 문제인지, 운영 기준 문제인지 분리할 기준이 있어야 한다.
- 개선 결과가 `team-spec`, 역할 스킬, 운영 문서, reference 기준 중 어디에 반영될지 지정할 수 있어야 한다.

---

## 4. `SKILL.md` 준비도 점검

`SKILL.md`는 아래 질문에 답할 수 있어야 한다.

- 이 스킬이 메타하네스 생성기라는 정체성이 첫 문단과 핵심 원칙에서 드러나는가
- 새 프로젝트 구축, 기존 확장, 운영 유지보수의 진입 방식이 분리돼 있는가
- Phase 0~7이 도메인 분석에서 피드백 반영까지 이어지는 생성 생명주기로 읽히는가
- `team-spec`이 에이전트 정의와 역할 스킬 생성의 기준으로 반복해서 명시되는가
- Codex에서 가능한 병렬 subagent 위임과 장기 역할 팀의 차이를 혼동하지 않는가
- 시작 진입 역할, 중심 조율 역할, QA 역할, 운영 감사 역할의 책임이 구분되는가
- 문서 산출물이 보조 설명이 아니라 운영 상태를 고정하는 입력으로 설명되는가
- 완료 기준이 파일 존재가 아니라 운영 가능성, 로그 완결성, 재진입 가능성을 포함하는가

---

## 5. Reference 준비도 점검

reference 문서 묶음은 아래 축을 빠짐없이 다뤄야 한다.

- 런타임 계약: `codex-runtime-contract.md`
- 역할 스펙 계약: `team-spec-contract.md`, `team-spec-schema.md`
- 패턴 선택: `agent-design-patterns.md`, `orchestrator-template.md`
- 스킬 작성: `skill-writing-guide.md`
- QA와 검증: `qa-agent-guide.md`, `verification-checklist.md`, `skill-testing-guide.md`
- 로그와 재진입: `logging-contract.md`, `reentry-rules.md`
- 품질 비교와 성숙도: `quality-evaluation-guide.md`, `meta-system-maturity-guide.md`, `target-evaluation-playbook.md`
- 문서 체계: `reference-map.md`, `reference-writing-guide.md`

새 reference를 추가할 때는 단순 부록으로 두지 말고, `reference-map.md`에서 어떤 판단 축에 쓰이는지 함께 연결한다.

## 6. 준비도 부족 신호

아래 신호가 보이면 생성기 준비도가 부족하다.

- `SKILL.md`가 역할 팀 생성보다 문서 작성 절차처럼 읽힌다.
- 생성 대상이 고정 에이전트 몇 개로 보이고, 프로젝트마다 달라지는 `team-spec` 기준이 약하다.
- 오케스트레이션이 역할 호출 순서만 설명하고, 실패/보류/재진입 기준을 다루지 않는다.
- QA와 운영 감사가 마지막 체크리스트로만 남고, 다음 구조 개선으로 이어지지 않는다.
- 로그가 결과 보고에 머물고 다음 세션의 시작 입력으로 쓰이지 않는다.
- 생성 판단의 본체가 문서 계약과 역할 스킬이 아닌 다른 실행 파일처럼 설명된다.
- 다른 런타임의 파일 구조나 호출 모델을 전제로 한 문구가 남아 있다.
- 생성된 문서가 저장소 사실보다 범용 조언과 단계 설명을 더 많이 말한다.

---

## 7. 준비도 완료 판정

생성기 준비도가 갖춰졌다고 말하려면 아래 조건을 모두 만족해야 한다.

1. `SKILL.md`가 도메인 분석, 팀 설계, 에이전트 정의, 스킬 생성, 오케스트레이션, QA/운영 감사, 피드백 반영을 하나의 생명주기로 설명한다.
2. reference 문서가 각 생명주기 단계의 판단 기준을 제공한다.
3. 생성 결과가 Codex의 로컬 실행 자산으로 설명된다.
4. 주 에이전트가 문서를 읽고 같은 운영 기준으로 하네스를 구성할 수 있다.
5. 타겟 프로젝트의 다음 세션에서 `latest-session-summary.md`를 읽고 재진입 Phase를 정할 수 있게 한다.
6. 운영 감사 역할이 타겟 프로젝트에서 부족 축과 다음 수정 위치를 실행 가능한 수준으로 지정할 수 있게 한다.

이 기준을 통과하지 못하면 생성기 문서나 reference 기준을 먼저 보강한다. 타겟 프로젝트의 충분성 평가는 실제 생성 결과가 생긴 뒤에만 수행한다.
