# Initial Generation Contract

이 문서는 타겟 프로젝트에 하네스를 처음 만들 때 생성물이 갖춰야 할 자기진화 계약을 정의한다.

초기 생성은 빈 골격을 만드는 일이 아니다. 첫 실행 직후의 하네스도 저장소를 다시 읽고, 역할을 고르고, 학습 후보를 남기고, 다음 재진입 Phase를 설명할 수 있어야 한다.

## 핵심 전제

- 기존 하네스 평가 루프가 아니라 신규 구축 시점의 생성 품질을 다룬다.
- 초기 생성물은 나중에 좋아질 여지를 남기는 수준이 아니라, 첫 세션부터 자기진화 루프를 실행할 수 있어야 한다.
- 자기진화 루프는 별도 스크립트, 외부 실행기, 자동 프로젝트 재작성 도구에 의존하지 않는다.
- 생성기는 타겟 프로젝트 파일을 임의로 일반화하지 않고, 저장소 재독해와 `team-spec`을 기준으로 역할 자산을 만든다.
- 초기 문서가 부족한 상태라면 완료가 아니라 `자동 판단 보류`와 다음 입력을 남긴 상태로 본다.
- 저장소 근거가 적은 경우도 신규 구축 대상이다. 이때는 사용자 도메인 설명을 정상 입력으로 삼고, 코드 근거 부족은 실패가 아니라 보류 판단으로 기록한다.

## 초기 생성물 필수 계약

초기 하네스 생성이 끝났다고 보려면 아래 계약이 생성물 안에 있어야 한다.

### 1. `team-spec.md`

`team-spec.md`는 초기 생성의 단일 진실원천이다.

필수 내용:

- 상태 모드가 `신규 구축`인지, 제한적 입력인지 설명한다.
- 저장소 근거가 적다면 어떤 사용자 입력을 근거로 제한적 역할 팀을 설계했는지 적는다.
- 저장소 도메인 근거와 아직 보류한 판단을 분리한다.
- 최종 역할 인벤토리를 비워 두지 않는다. 단, 입력이 부족하면 어떤 질문 뒤에 채울지 남긴다.
- 최종 역할 인벤토리는 fenced `text` 블록으로 남긴다. 헤더와 모든 역할 행은 같은 블록 안에 있어야 한다.
- 각 역할에 학습 후보 기록 규칙과 승격 대상 기준을 둔다.
- 각 역할에 생성기 환류 후보 기준을 둔다. 단일 타겟 로컬 보강과 여러 타겟에서 반복될 생성기 보강 후보를 구분해야 한다.
- 시작 진입 역할, 중심 조율 역할, QA 역할, 운영 감사 역할의 책임 경계를 둔다.
- 역할별 출력 형식이 다음 역할, 재진입 Phase, 남은 위험을 전달할 수 있게 한다.

### 2. `.codex/agents/*`

에이전트 정의는 `team-spec.md`의 역할 인벤토리를 구현해야 한다.

필수 내용:

- 시작 진입 역할이 현재 상태를 읽고 다음 역할을 고를 수 있다.
- 중심 조율 역할이 정상, 보류, 실패, 재진입 흐름을 설명할 수 있다.
- QA 역할과 운영 감사 역할이 생성 직후부터 구분된다.
- 각 description이 실제 요청에서 트리거될 만큼 구체적이다.

고정 역할명을 강제하지 않는다. 타겟 프로젝트의 도메인과 실패 경계를 반영한 이름이 우선이다.

### 3. `.codex/skills/*/SKILL.md`

역할 스킬은 처음부터 실행 가능한 판단 단위를 가져야 한다.

필수 내용:

- 대표 시작 경로와 우선 입력 문서
- 작업 시작 체크리스트
- 주요 판단 기준과 금지 판단
- 출력 형식
- 다음 역할 또는 handoff 기준
- 재진입 트리거와 종료 판정 기준
- 학습 후보 기록 위치

생성된 역할 스킬은 아래 공통 학습 출력 블록을 그대로 출력 형식에 포함해야 한다. 일부 항목을 생략하거나 다른 문서에만 맡기면 초기 생성 계약을 통과한 것으로 보지 않는다.

```markdown
- 새로 확인한 저장소 사실: `<facts or 없음>`
- 반복될 수 있는 판단: `<pattern or 없음>`
- 하네스 갱신 후보: `<local docs/skills or 없음>`
- 승격 대상: `<Phase and target or 없음>`
- 생성기 환류 후보: `<yes/no and reason>`
```

관찰이 없으면 길게 설명하지 않고 `없음`으로 남긴다.

### 4. `.harness/docs/*`

보조 운영 문서는 역할 자산을 대신하지 않는다. 초기 생성에서는 다음 실행에 필요한 기준을 고정하는 데 집중한다.

필수 내용:

- `exploration-notes.md`: 자동 판단 보류, 사용자 입력 부족, 다음 확인 질문
- `project-setup.md`: 사용자 입력과 초기 방향
- `team-spec.md`: 역할 팀 기준과 최종 역할 인벤토리
- `logging-policy.md`: 세션 로그와 최신 요약 기준. 별도 스크립트나 TSV 이벤트 파일을 필수 전제로 두지 않는 Markdown 로그 정책이어야 한다.

저장소 재독해 뒤에는 필요한 범위에서 아래 문서를 채운다.

- `domain-analysis.md`
- `qa-strategy.md`
- `harness-architecture.md`
- `orchestration-plan.md`
- `team-structure.md`
- `team-playbook.md`

초기 생성 시점에 모든 문서를 억지로 완성하지 않는다. 대신 어떤 역할이 어떤 입력을 읽고 채울지 남긴다.

저장소 근거가 적은 신규 구축의 `project-setup.md`에는 최소한 아래 항목을 둔다.

- 도메인 또는 만들 제품
- 목표 사용자나 운영 주체
- 첫 성공 시나리오
- 품질 실패 비용이 큰 지점
- 아직 코드가 없어 보류한 구현 경계
- 코드나 설정이 생긴 뒤 재진입할 Phase

입력 상태를 어떻게 판정하고 질문을 몇 개로 제한할지는 `exploration-model.md`의 `저장소 근거가 적을 때` 절차를 따른다. 이 문서는 그 절차가 끝난 뒤 초기 생성물 안에 남아야 할 필수 항목과 완료 기준만 정의한다.

### 5. `.harness/logs/*`

초기 생성 세션도 로그를 남긴다.

필수 내용:

- `session-log.md`: 세션 ID, 시작 요청, 진입점, 생성한 역할 자산, 보류한 판단, 남은 위험
- `latest-session-summary.md`: 다음 시작 역할, 다음 재진입 Phase, 다시 읽을 입력, 최근 출력, 학습 후보, 반복 신호, 승격 대상, 생성기 환류 후보

로그가 없으면 다음 세션이 자기진화 루프를 이어 갈 수 없다.
`logging-policy.md`가 없으면 로그를 사람이 어떻게 남기고 읽어야 하는지 알 수 없으므로 초기 생성 계약을 통과한 것으로 보지 않는다.

## Phase별 초기 생성 게이트

### Phase 0

- 신규 구축인지 기존 확장인지 먼저 판단한다.
- 기존 자산이 없으면 바로 역할명을 확정하지 않고, 입력 상태와 보류 판단을 남긴다.
- 시작 진입 역할(`run-harness`)이 `logging-policy.md` 초안을 만들고, 필수 로그 문서와 기록 목적을 고정한다.

### Phase 1

- 저장소 근거, 사용자 입력, 보류 질문을 분리한다.
- 자동 탐색 결과를 최종 도메인 분석처럼 쓰지 않는다.
- 저장소 근거가 적어도 여기서 멈추지 않는다. 사용자 설명을 기준으로 `project-setup.md`를 필수 항목과 함께 작성하고, 가능한 범위에서 제한적 `domain-analysis.md`도 작성한다. 코드가 생긴 뒤 다시 확인할 경계도 분명히 남긴다.

### Phase 2

- `team-spec.md`에 최종 역할 인벤토리와 역할별 실행 기준을 채운다.
- 최종 역할 인벤토리는 fenced `text` 블록으로 작성하고, inline code 행 나열로 대신하지 않는다.
- 각 역할에 학습 후보 기록 규칙, 승격 대상 기준, 생성기 환류 후보 기준, 재진입 트리거를 넣는다.

### Phase 3

- `.codex/agents/*.toml`은 `team-spec.md`의 역할만 구현한다.
- 시작 진입 역할, 중심 조율 역할, QA 역할, 운영 감사 역할의 경계가 드러나야 한다.

### Phase 4

- 역할 스킬은 이름만 특화된 껍데기로 남으면 안 된다.
- 출력 형식에는 다음 역할, 남은 위험, 공통 학습 출력 블록이 있어야 한다.

### Phase 5

- handoff가 입력, 출력, 다음 역할, 재진입 Phase를 전달해야 한다.
- 보류와 실패도 다음 세션에서 이어 읽을 수 있어야 한다.
- 흐름 조율 역할이 `logging-policy.md`, `session-log.md`, `latest-session-summary.md`를 같은 handoff와 세션 종료 기준으로 정렬한다.

### Phase 6

- 운영 감사는 파일 존재가 아니라 초기 생성물의 자기진화성을 판정한다.
- 운영 감사 역할은 `logging-policy.md`, `session-log.md`, `latest-session-summary.md`가 같은 로그 계약을 말하는지 확인한다.
- 판정은 `운영 가능 / 재작성 필요 / 재구성 필요` 중 하나로 남긴다.

## 완료 기준

- 초기 생성물만 읽어도 다음 시작 역할과 다음 재진입 Phase를 알 수 있다.
- 모든 역할 스킬 출력 형식에 공통 학습 출력 블록이 있다.
- `team-spec.md`와 실제 agent/skill 자산이 같은 역할 집합을 말한다.
- QA와 운영 감사 역할이 생성 직후부터 구분된다.
- 보류한 판단과 남은 질문이 로그와 문서에 남아 있다.
- 초기 자기진화 루프가 스크립트나 외부 실행기에 의존하지 않는다.

## 다른 레퍼런스와의 연결

- `team-spec-contract.md`: 초기 생성의 단일 진실원천과 역할 필드를 정의한다.
- `skill-writing-guide.md`: 생성된 역할 스킬의 출력 형식과 공통 학습 블록을 정의한다.
- `logging-contract.md`: 초기 생성 세션의 로그와 최신 요약 기준을 정의한다.
- `verification-checklist.md`: 운영 감사가 초기 생성물의 자기진화성을 확인할 때 쓴다.
- `evolution-contract.md`: 학습 후보와 승격 대상의 의미를 정의한다.
