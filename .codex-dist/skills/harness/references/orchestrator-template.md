# Flow Coordination Reference (Codex용 오케스트레이터 기준)

이 문서는 실행 하네스 팀에서 오케스트레이터 역할이 맡을 책임을 정의한다.

오케스트레이터는 단순한 흐름 설명자가 아니다. 실행 하네스 팀의 중심 역할로서, 여러 역할이 하나의 팀처럼 움직이도록 연결 구조를 만들고 유지한다.

원본 하네스의 오케스트레이터는 팀원 간 직접 통신과 공유 작업 목록으로 팀을 조율한다. Codex용 오케스트레이터는 같은 책임을 주 에이전트 중심 실행, 파일 기반 handoff, 세션 로그, 필요한 경우 좁은 subagent 위임으로 구현한다.

---

## 핵심 전제

- 오케스트레이터는 반드시 탐색 결과와 앞선 역할 산출물을 입력으로 삼아 판단한다.
- 오케스트레이터는 리포트를 읽는 역할이 아니라, 리포트를 포함한 팀 구조를 다시 조율하는 역할이다.
- 오케스트레이터의 핵심 가치는 시작점 선정, 역할 연결, 재진입 판단, 운영 감사 피드백 루프 유지에 있다.

---

## 1. 흐름 조율 역할의 핵심 책임

오케스트레이터는 다음을 맡는다.

- 어떤 역할이 먼저 시작해야 하는지 결정한다
- 각 역할의 입력과 출력을 연결한다
- 역할 간 중복이나 끊김을 줄인다
- QA / 운영 감사의 피드백이 다시 구조 보완으로 이어지게 만든다
- 실행 하네스 팀이 프로젝트에 맞게 운용되도록 흐름을 정리한다

오케스트레이터는 모든 일을 대신하지 않는다. **팀 전체를 작동시키는 역할**이다.

## 중심 조율 역할과 진입 역할

실행 하네스 팀에서는 아래 둘을 분리해 설계한다.

- 중심 조율 역할 또는 오케스트레이터 역할: 팀 구조와 흐름의 중심을 잡는 역할
- 시작 진입 역할(`run-harness`): 팀을 실제로 시작시키는 엔트리포인트 역할

중심 조율 역할 또는 오케스트레이터 역할은 "흐름을 설계하고 유지"하는 책임을 맡고, 시작 진입 역할은 "현재 상태를 읽고 첫 시작 역할과 다음 역할을 제시"하는 책임을 맡는다.

이 둘이 섞이면 다음 역할 판단, 재진입 판단, 운영 감사 피드백 루프가 흐려진다.

---

## 2. 흐름 조율 역할이 항상 확인해야 하는 것

흐름 조율 역할은 최소한 아래 항목을 항상 확인한다.

### 1) 시작점이 있는가
- domain-analysis가 충분한가
- 지금 구조 설계를 시작해도 되는가
- 입력 정보가 부족하다면 사용자에게 먼저 확인할 질문이 정리되었는가

### 2) 역할 구성이 적절한가
- 현재 프로젝트에 어떤 특화 역할 세트가 맞는가
- 줄이거나 늘리거나 이름을 다시 설계할 필요가 있는가

### 3) 흐름이 단순한가
- 너무 많은 분기가 생기지 않았는가
- 누가 무엇을 보고 다음 단계로 가는지 분명한가

### 4) 피드백 루프가 있는가
- 운영 감사의 지적이 구조 설계 역할 / 스킬 규칙 정렬 역할 / 품질 전략 역할로 다시 연결되는가
- QA 질문이 구조 수정으로 이어질 수 있는가

---

## 3. 시작 컨텍스트 확인

흐름 조율 역할은 새 흐름을 바로 시작하지 않는다. 먼저 현재 하네스 상태와 사용자의 요청이 어떤 실행 모드에 가까운지 확인한다.

확인할 항목:

- `.harness/logs/latest-session-summary.md`가 있는가
- 직전 세션의 다음 시작 역할과 재진입 Phase가 남아 있는가
- 사용자가 신규 구축, 부분 보강, 운영 점검, 재구성 중 무엇을 요청했는가
- 이전 산출물을 이어서 읽어야 하는가, 새 기준으로 다시 작성해야 하는가
- 지금 필요한 것이 전체 흐름 재시작인가, 특정 Phase 재진입인가

이 확인 결과는 `orchestration-plan.md`나 `latest-session-summary.md`에 다음처럼 남긴다.

- 현재 상태 모드
- 이번 실행 모드
- 시작 역할
- 다음 재진입 Phase
- 우선 읽을 입력 문서
- 보류한 판단과 확인 질문

---

## 4. 기본 실행 흐름

범용 실행 하네스 팀의 기본 흐름은 다음 성격을 따라 설계한다.

1. 저장소 입력 문서를 고정하는 역할
2. 팀 구조와 경계를 설계하는 역할
3. 품질 기준을 설계하는 역할
4. 전체 흐름을 조율하는 역할
5. 운영 기준을 감사하는 역할

이 순서는 절대 규칙이 아니라 기본 골격이다.
프로젝트에 따라 일부는 생략되거나 반복될 수 있고, 더 세분화된 특화 역할로 나뉠 수도 있다.

스킬 규칙 정렬 전용 역할은 이 기본 골격에 항상 들어가는 역할이 아니다.
로컬 스킬 설명 불일치, 구조 문구 불일치, 스킬 규칙 재정렬이 필요한 정렬 상황에서만 보조적으로 끼운다.

기본적으로 흐름 조율 역할은 이 흐름 전체를 한 번에 보는 역할이어야 한다.

---

## 5. 운영 모드별 조율 기준

흐름 조율 역할은 항상 같은 방식으로 움직이지 않는다.  
현재 저장소의 하네스 상태에 따라 조율 우선순위가 달라진다.

### 신규 구축

- 저장소 입력 문서 고정 → 팀 구조 설계 → QA 기준 설계 → 전체 흐름 조율 → 운영 기준 감사 순서의 기본 파이프라인을 먼저 안정화한다.
- 이 단계에서는 분기 수를 늘리기보다, 입력/출력 연결을 선명하게 두는 것이 우선이다.

### 기존 확장

- 어떤 문서나 역할이 먼저 재진입해야 하는지 정하는 것이 핵심이다.
- 모든 산출물을 다시 만드는 대신, 현재 요청과 불일치 지점을 기준으로 최소 재진입 루프를 만든다.

### 운영 유지보수

- 새 초안 생성보다 불일치 감지, 피드백 루프, 운영 로그 상태를 먼저 본다.
- 운영 감사 역할과 logging-policy, latest-session-summary, orchestration-plan의 연결이 끊기지 않게 유지한다.

---

## 6. 역할별 연결 기준

### 저장소 입력 문서 담당 역할 → 구조 설계 담당 역할
- 분석 결과는 구조 설계의 출발점이 된다
- 단순 요약이 아니라 역할 팀 설계에 영향을 줘야 한다

### 구조 설계 담당 역할 → 스킬 규칙 정렬 역할
- 구조 설계와 로컬 스킬 설명이 서로 어긋나는 정렬 상황에서만 연결한다
- 기본 흐름의 필수 역할 연결이 아니라 불일치 보정용 예외 연결이다

### 저장소 입력 문서 담당 역할 / 구조 설계 담당 역할 → 품질 전략 담당 역할
- QA는 반드시 실제 구조와 흐름을 근거로 질문을 만들어야 한다
- 분석이나 설계와 분리된 QA는 힘이 약하다

### 전체 구조 → 흐름 조율 역할
- 흐름 조율 역할은 앞선 결과를 읽고 팀 흐름으로 재구성한다
- 흐름이 산만하면 여기서 정리해야 한다

### 전체 구조 → 운영 감사 역할
- 운영 감사 역할은 결과를 다시 최소 품질 기준으로 점검한다
- 운영 감사 역할의 피드백은 다시 팀 보강에 사용될 수 있어야 한다

## 7. 데이터 전달과 handoff 기준

흐름 조율 역할은 역할 호출 순서만 적지 않는다. 각 역할이 무엇을 읽고 무엇을 남기는지 handoff 기준까지 고정해야 한다.

좋은 handoff에는 아래가 포함된다.

- 입력 문서: 다음 역할이 반드시 읽어야 할 파일
- 최근 출력: 직전 역할이 남긴 파일이나 요약
- 판단 상태: 확정, 보류, 추정 중 무엇인지
- 다음 역할: 바로 이어질 역할과 그 이유
- 실패 시 되돌아갈 Phase
- 로그 반영 여부
- 학습 후보와 승격 대상

파일 기반 산출물은 가능한 한 저장소 기준 상대 경로로 적는다. 절대경로나 사용자 홈 경로를 남기지 않는다.

### 보존 문서 호환성 메모

기존 `.harness/docs/*` 문서를 보존하면서 새 역할 팀을 만들면, 예전 역할명이나 진입점이 새 `team-spec`과 다를 수 있다. 이때 흐름 조율 역할은 보존 문서 원문을 즉시 고치지 않는다. 먼저 `orchestration-plan.md`나 `team-playbook.md`에 호환성 메모를 남겨 다음 실행이 같은 충돌을 다시 해석하지 않게 한다.

호환성 메모에는 아래 항목이 필요하다.

- 보존 문서 경로
- 문서 안의 이전 역할명 또는 진입점
- 현재 `team-spec`의 역할명 또는 진입점
- 이번 실행에서 우선할 기준
- 원문 처리 방침: 보존 / 사용자 승인 후 정렬 / 다음 재진입에서 재작성

예:

```text
preserved-doc-compatibility:
- source: .harness/docs/team-playbook.md
- previous: qa-specialist, orchestration-lead
- current: release-regression-qa, delivery-orchestrator
- priority: 현재 team-spec과 .codex/agents/* 기준을 우선한다.
- action: 원문은 보존하고, Phase 5 재진입 때 사용자 승인 후 정렬한다.
```

예:

```text
handoff:
- from: workspace-map-analyst
- to: boundary-architect
- inputs: .harness/docs/domain-analysis.md, .harness/docs/project-setup.md
- output: .harness/docs/harness-architecture.md
- status: 확정 근거 3개, 보류 질문 1개
- reentry: Phase 1 입력 근거가 약하면 domain-analysis 재작성
- learning: 새 저장소 사실 없음, 승격 대상 없음
```

## 8. 보류와 오류 처리 기준

오케스트레이션은 모든 역할이 성공한다고 가정하지 않는다.

흐름 조율 역할은 최소한 아래 상황을 다룬다.

- 입력 부족: 사용자 질문 또는 `project-setup.md` 보강으로 되돌린다.
- 역할 출력 부족: 해당 역할의 입력과 완료 기준을 다시 확인하고 필요한 Phase로 재진입한다.
- 역할 간 판단 충돌: 한쪽을 삭제하지 않고 출처와 충돌 지점을 함께 남긴다.
- 보조 위임 실패 또는 지연: 주 에이전트가 현재까지의 산출물을 통합하고 남은 위험으로 기록한다.
- 운영 감사 실패: 단순 수정으로 끝내지 않고 재진입 Phase와 책임 역할을 지정한다.
- 반복될 수 있는 역할 오판이나 검증 공백: 학습 후보와 승격 대상을 함께 남긴다.

보류나 실패는 `session-log.md`와 `latest-session-summary.md`에 남겨야 한다. 다음 세션에서 같은 문제를 다시 추측하지 않게 하기 위해서다.

## 9. 패턴 선택 기준

흐름 조율 역할은 현재 저장소에 맞는 운영 패턴을 선택할 수 있어야 한다.

### 파이프라인

- 입력/출력 의존성이 선명하고 새 구조를 안정적으로 세워야 할 때

### 생성-검증

- 스킬/문서 생성 직후 운영 감사 피드백을 빠르게 반영해야 할 때

### 팬아웃 / 팬인

- 하위 영역이 독립적으로 분석 가능하고, 최종적으로 다시 하나의 구조 문서로 모아야 할 때

### 감독자

- 역할 수가 늘고 다음 역할 결정과 재진입 판단이 중요해졌을 때

### 계층적 위임

- 상위 경계와 하위 경계가 분명하고, 한 단계 보조 위임 뒤 다시 통합해야 할 때

핵심은 패턴 이름이 아니다. 현재 요청에서 “어디서 시작하고 어디로 되돌릴지”를 가장 명확하게 만드는 선택인지가 중요하다.

- 위임 단위를 정할 때도 같은 수준의 판단을 해야 한다. 문서, 로그, 역할 연결을 계속 유지해야 하는 핵심 책임은 장기 역할 팀에 두고, 입력과 출력이 좁은 일회성 보조 분석만 서브에이전트로 위임한다.
- fan-out 분석이 필요한 모노레포라도 최종 통합 책임은 항상 팀 역할로 다시 모으고, 저장소 입력 문서 담당 / 구조 설계 담당 / 품질 전략 담당 / 운영 감사 담당 역할을 서브에이전트만으로 대체하지 않는다.
- 요청을 받을 때는 사용자가 저장소 고유 용어와 파일 경로를 정확히 말하는지, 요청 범위가 단일 보강인지 구조 재설계인지 운영 점검인지 분명한지도 함께 본다.
- 사용자 맥락이 약하면 질문 루프를 먼저 두고, 맥락이 강하면 갱신 범위를 좁혀 바로 시작한다.

## 10. 흐름 조율 역할이 피해야 하는 실수

### 1) 모든 역할을 동등하게 다루는 것
실제 프로젝트에는 중심 역할이 필요하다.
대부분의 경우 흐름 조율 역할 자신이 중심 흐름을 잡아야 한다.

### 2) 문서를 본체처럼 다루는 것
리포트는 보조다. 본체는 역할 팀과 역할 스킬이다.

### 3) 과도한 병렬화
범용 단계에서는 복잡한 병렬화보다 단순하고 추적 가능한 순차 흐름이 더 낫다.

### 4) 운영 감사 피드백을 끝 단계에서만 소비하는 것
운영 감사 역할은 단순 마지막 검사자가 아니다. 팀 구조를 더 낫게 만드는 피드백 공급자다.

---

## 11. 좋은 흐름 조율 역할의 조건

좋은 흐름 조율 역할은 다음 조건을 가진다.

- 중심 역할임이 분명하다
- 각 역할의 입력/출력을 명확히 연결한다
- 리포트를 보조 문서로 다루고, 본체는 역할 팀으로 본다
- QA / 운영 감사의 피드백을 실제 수정 루프에 연결한다
- 프로젝트에 따라 역할 수를 조정할 수 있다
- 팀이 복잡해질수록 더 단순한 흐름을 만들려 한다

---

## 12. 흐름 조율 역할이 남겨야 하는 산출물

흐름 조율 역할은 최소한 다음 문서를 남긴다.

- `.harness/docs/orchestration-plan.md`

이 문서에는 적어도 다음 항목이 포함돼야 한다.

- 현재 프로젝트의 역할 팀 흐름
- 역할별 입력/출력 연결
- 중심 역할과 보조 역할 구분
- 운영 감사 / QA 피드백 반영 지점
- 이후 프로젝트 특화 실행 하네스로 확장 가능한 포인트
- 시작 컨텍스트 확인 결과
- 역할 간 handoff 규칙
- 보류와 오류 처리 기준
- 정상 흐름과 보류 흐름 시나리오

## 보조 운영 문서와 handoff

보조 운영 문서는 오케스트레이션을 대신하지 않는다. 역할 handoff와 재진입 판단을 뒷받침하는 공유 입력으로 다룬다.

대표 보조 운영 문서는 다음과 같다.

- 저장소 근거와 검증 기준: `domain-analysis.md`, `qa-strategy.md`
- 역할 연결과 운영 흐름: `harness-architecture.md`, `orchestration-plan.md`, `team-structure.md`, `team-playbook.md`

흐름 조율 역할은 이 문서들이 역할 팀과 같은 운영 기준을 말하도록 관리한다.

- 저장소 근거 문서는 역할 팀이 왜 그런 구조로 설계됐는지 설명한다.
- 운영 흐름 문서는 역할 연결, 재진입 기준, 운영 루프를 보조한다.

보조 운영 문서가 역할 자산을 대신하기 시작하면 "리포트는 많은데 팀 구조는 약한 상태"가 된다. 이 경우 운영 감사 피드백에서 책임 역할과 재진입 Phase를 먼저 지정한다.

---

## 13. 흐름 시나리오 기준

`orchestration-plan.md`에는 최소한 정상 흐름과 보류 흐름이 들어가야 한다.

정상 흐름은 다음을 설명한다.

- 어떤 입력으로 시작하는가
- 어떤 역할이 먼저 실행되는가
- 어떤 문서가 다음 역할의 입력이 되는가
- 운영 감사가 무엇을 기준으로 완료를 판단하는가

보류 흐름은 다음을 설명한다.

- 입력 부족, 역할 출력 부족, 판단 충돌, 보조 위임 실패 중 무엇이 발생했는가
- 어느 Phase로 되돌아가는가
- 어떤 파일을 먼저 다시 읽는가
- 다음 세션 요약에 무엇을 남기는가

이 시나리오는 자동 실행 절차가 아니라, 사람이 흐름을 검토하고 다음 재진입을 이해하기 위한 운영 기준이다.

---

## 14. 운영 감사 / QA와의 관계

### 흐름 조율 역할과 QA
- QA는 흐름의 건강성을 질문한다
- 흐름 조율 역할은 그 질문이 실제 흐름에 반영되게 한다

### 흐름 조율 역할과 운영 감사 역할
- 운영 감사 역할은 최소 요건과 약한 연결을 지적한다
- 흐름 조율 역할은 그 지적이 구조 보완으로 이어지게 한다

흐름 조율 역할은 QA와 운영 감사의 결과를 흡수해 팀 구조를 조정하는 중심 역할이다.

---

## 15. 사람 개입과 흐름 조율 역할

흐름 조율 역할은 사람의 개입을 가장 잘 흡수해야 하는 역할 중 하나다.

사람은 보통 다음 지점에서 개입한다.

- 어떤 흐름이 더 중요한가
- 어떤 역할이 과한가
- 지금 단계에서 무엇까지 엄격해야 하는가

흐름 조율 역할은 이런 판단을 팀 구조와 흐름에 반영해야 한다.

흐름 조율 역할은 **사람의 우선순위가 실행 하네스 팀 구조로 번역되는 접점**이다.

---

## 16. 핵심 요약

- orchestrator는 단순 설명자가 아니다
- orchestrator는 실행 하네스 팀의 중심 조율자다
- 흐름, 연결, 피드백 루프를 책임진다
- 시작 컨텍스트, handoff, 보류 흐름을 함께 고정한다
- QA와 운영 감사의 결과를 구조 보완으로 연결한다
- 본체는 역할 팀이고, 리포트는 보조다
- 좋은 orchestrator는 팀을 더 단순하고 더 강하게 만든다
