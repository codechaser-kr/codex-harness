# Phase Selection Matrix

이 문서는 기존 하네스를 확장하거나 유지보수할 때 어떤 단계만 다시 수행해야 하는지 정의한다.

목표는 두 가지다.

- 기존 확장이 무조건 전체 보강으로 흐르지 않게 한다.
- 변경 유형에 따라 `하네스 Phase 0 ~ 7` 중 어디부터 다시 들어갈지 명확히 만든다.

---

## 핵심 전제

- 기존 확장은 전부 다시 만드는 작업이 아니다.
- 먼저 불일치와 변경 범위를 읽고, 필요한 단계만 다시 수행한다.
- 부분 구조 불일치나 상위 운영 기준 충돌이 크면 부분 갱신보다 재구성을 우선한다.
- 제품/로드맵 Phase 완료나 다음 제품/로드맵 Phase 진입은 문서 존재만으로 선언하지 않고, 로드맵 항목별 완료 근거를 기준으로 보수적으로 판단한다.
- "초안 작성", "화면/디자인 산출물 제작", "환경 구성", "테스트 확인"처럼 결과물이 필요한 항목은 실제 파일, 설정, 캡처, 링크, 로그, 테스트 결과 중 하나 이상의 근거가 필요하다.

---

## 1. 기본 분기

### 신규 구축

- `하네스 Phase 0 감사` -> `하네스 Phase 1 도메인/작업 분석` -> `하네스 Phase 2 팀 설계` -> `하네스 Phase 3 에이전트 정의` -> `하네스 Phase 4 로컬 역할 스킬 생성` -> `하네스 Phase 5 통합 및 오케스트레이터 구성` -> `하네스 Phase 6 검증 및 운영 감사` -> `하네스 Phase 7 하네스 피드백 반영`

### 기존 확장

- `하네스 Phase 0 감사` 후 변경 범위에 따라 필요한 단계만 다시 수행한다.

### 운영 유지보수

- `하네스 Phase 0 감사` -> 필요한 `하네스 Phase` 재진입 -> `하네스 Phase 6 검증 및 운영 감사` -> 필요 시 `하네스 Phase 7 하네스 피드백 반영`

### 재구성

- `하네스 Phase 0 감사`에서 부분 구조 불일치 또는 상위 규칙 충돌이 크면 기존 구조 정리 후 `신규 구축` 흐름으로 다시 간다.

---

## 2. 변경 유형별 권장 재진입

### domain 근거가 약하거나 오래된 경우

- 시작: `하네스 Phase 1 도메인/작업 분석`
- 이후: `하네스 Phase 2`, `하네스 Phase 4`, `하네스 Phase 5`, `하네스 Phase 6`, 필요 시 `하네스 Phase 7`

### 역할 경계나 구조 설명이 흐린 경우

- 시작: `하네스 Phase 2 실행 하네스 팀 설계`
- 이후: `하네스 Phase 3`, `하네스 Phase 4`, `하네스 Phase 5`, `하네스 Phase 6`, 필요 시 `하네스 Phase 7`

### 에이전트 정의가 team-spec과 어긋난 경우

- 시작: `하네스 Phase 3 에이전트 정의 생성`
- 이후: `하네스 Phase 4`, `하네스 Phase 6`, 필요 시 `하네스 Phase 7`

### 로컬 역할 스킬 설명이나 트리거가 약한 경우

- 시작: `하네스 Phase 4 로컬 역할 스킬 생성`
- 이후: `하네스 Phase 5`, `하네스 Phase 6`, 필요 시 `하네스 Phase 7`

### 오케스트레이션 흐름과 다음 역할 기준이 약한 경우

- 시작: `하네스 Phase 5 통합 및 오케스트레이터 구성`
- 이후: `하네스 Phase 6`, 필요 시 `하네스 Phase 7`

### 구조 검증은 통과하지만 운영 피드백 반영이 약한 경우

- 시작: `하네스 Phase 7 하네스 피드백 반영`
- 이후: 부족 축에 따라 `하네스 Phase 1`~`하네스 Phase 5` 중 하나로 재진입

### AGENTS.md와 하네스 운영 기준이 충돌하는 경우

- 시작: `하네스 Phase 0 감사`
- 이후: `정렬 가능하면 하네스 Phase 2 또는 하네스 Phase 5`, 충돌이 크면 `재구성`

### 로그 정책과 실제 운영 루프가 어긋난 경우

- 시작: `하네스 Phase 0 감사`
- 확인 포인트: 다음 시작 역할, 다음 하네스 재진입 Phase, 다음 시작 전 우선 확인 입력 파일, 최근 출력 파일이 실제 로그와 요약에 남는지 본다.
- 이후: `하네스 Phase 5` 또는 `하네스 Phase 6`, 필요 시 `하네스 Phase 7`

### 제품/로드맵 Phase 완료 근거가 불명확한 경우

- 시작: `하네스 Phase 0 감사`
- 확인 포인트: 현재 제품/로드맵 Phase의 로드맵 항목을 절차/설계 문서로 충족되는 항목과 실제 코드, 설정, 산출물, 시안, 테스트 결과가 필요한 항목으로 나눠 본다.
- 확인 포인트: 실제 산출물이 필요한 항목에 파일, 캡처, 링크, 로그, 테스트 결과 같은 근거가 없으면 완료로 보지 않는다.
- 이후: 산출물 확인 또는 작성이 필요하면 해당 구현/기획 역할로 재진입하고, 로그/요약 문구 정렬이 필요하면 `하네스 Phase 5` 또는 `하네스 Phase 6`으로 재진입한다.

---

## 3. 재진입 범위와의 연결

- `--domain`: `하네스 Phase 1` 결과가 약한 경우 우선 사용한다.
- `--architecture`: `하네스 Phase 2` 결과가 약한 경우 우선 사용한다.
- `--qa`: `하네스 Phase 4` 결과가 약한 경우 우선 사용한다.
- `--orchestration`: `하네스 Phase 5` 중 흐름 보강이 필요한 경우 우선 사용한다.
- `--team-structure`, `--team-playbook`: 구조 설명 또는 운영 플레이북만 약한 경우 우선 사용한다.

옵션은 파일 단위 선택일 뿐이고, 실제 판단은 항상 Phase 기준으로 내려야 한다.

---

## 4. 재구성을 선택해야 하는 경우

- 역할 스킬과 보고서가 부분적으로만 남아 있다.
- `AGENTS.md`와 현재 하네스가 서로 다른 운영 모델을 강하게 말한다.
- run-harness, orchestrator, validator 설명이 함께 어긋난다.
- 부분 갱신을 반복해도 불일치가 계속 되돌아온다.

이 경우에는 필요한 문서만 덧칠하지 말고, 기존 구조 정리 후 다시 구성하는 것이 맞다.

## 5. 다른 레퍼런스와의 연결

- `agents-sync-guide.md`: `AGENTS.md` 충돌이 있을 때 갱신보다 감사와 정렬을 먼저 두는 기준을 제공한다.
- `agent-design-patterns.md`: 어떤 변경이 구조 설계까지 다시 흔드는지 상위 기준을 제공한다.
- `orchestrator-template.md`: 재진입 후 어떤 역할 연결과 피드백 루프를 복구해야 하는지 연결한다.
