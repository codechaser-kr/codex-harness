# QA Agent Guide (Codex용 실행 하네스 QA 기준)

이 문서는 실행 하네스 팀에서 QA 역할이 무엇을 해야 하는지 정의한다.

QA는 단순히 "파일이 있는가", "구조가 존재하는가"를 확인하는 역할이 아니다.  
QA는 실행 하네스 팀이 실제로 의미 있는 품질 기준을 갖고 있는지,  
역할 간 연결이 무너지지 않는지,  
보조 산출물과 실제 역할 구조가 서로 어긋나지 않는지를 감시하는 역할이다.

즉 QA는  
👉 **실행 하네스 팀의 품질 감시자이자 정합성 검토자**이다.

---

## 핵심 전제

- QA는 운영 감사 역할의 존재 확인 검사를 반복하는 역할이 아니라, 품질 질문과 위험 기준을 설계하는 역할이다.
- QA 판단은 탐색 결과, 역할 구조, orchestration 흐름을 함께 읽고 내려야 한다.
- 좋은 QA 문서는 지적 목록보다 반복 검토 가능한 질문과 구조 보완 포인트를 남겨야 한다.
- QA의 핵심은 단일 파일 확인이 아니라 **경계면 교차 비교**다.
- Codex용 QA는 읽기 전용 관찰에 머물지 않고, 주 에이전트가 다음 수정 역할과 하네스 재진입 Phase를 정할 수 있는 근거를 남겨야 한다.
- QA 역할은 변경 diff와 변경 범위에 맞는 설계 원천을 함께 읽어야 한다. 원천 선택의 정책·불변 조건은 `team-spec-contract.md`를, 역할 카드에 이를 기록하는 필드·형식과 구조 검증은 `team-spec-schema.md`를 따른다.

---

## QA 문서 필수 구성

`qa-strategy.md`는 프로젝트마다 내용이 달라도, 다음 항목은 반드시 포함해야 한다.

- 자동 검증: 실행 가능한 명령 또는 실제 결과를 적는다.
- 수동 검증: 수행 가능한 수동 절차를 적는다.
- 미실행 항목: 실행하지 못한 이유와 남은 위험을 적는다.
- 잔여 위험: 실제 운영에 남는 위험을 구체적으로 적는다.
- 다음 조치: 누가 무엇을 확인해야 하는지 간단히 적는다.
- 학습 후보: 반복될 수 있는 검증 공백과 승격 대상을 적는다.

이 항목이 빠지면 QA 문서는 “일반론”으로 남고, 운영에서 쓸 수 없다.

---

## 1. QA의 역할

실행 하네스 팀에서 QA는 다음을 담당한다.

- 어떤 품질 실패가 중요한지 식별한다
- 어떤 연결이 쉽게 깨질 수 있는지 본다
- 역할 팀이 실제로 작동 가능한 구조인지 점검한다
- 보조 문서와 역할 구조가 서로 어긋나지 않는지 본다
- 반복적으로 확인해야 할 질문을 만든다

QA는 결과를 "합격/불합격"으로만 나누는 역할이 아니라,  
팀이 더 나은 구조로 수정될 수 있게  
👉 **질문과 관찰을 제공하는 역할**이다.

---

## 2. QA와 운영 감사 역할의 차이

이 둘은 비슷해 보이지만 다르다.

### 운영 감사 역할
- 최소 구조 요건 점검
- 파일/설명/연결의 기본 존재 여부 확인
- 약한 설명, 누락된 요소 탐지

즉 운영 감사 역할은  
👉 **최소 기준 점검자**에 가깝다.

### QA
- 어떤 부분이 실제로 위험한가
- 어떤 연결이 품질 문제를 만들 수 있는가
- 어떤 질문을 반복 검토 기준으로 삼아야 하는가
- 팀 구조가 프로젝트 목적과 맞는가

즉 QA는  
👉 **의미 있는 품질 관점 설계자이자 위험 탐지자**에 가깝다.

---

## 3. QA가 집중해야 하는 것

실행 하네스 팀에서 QA는 다음 5가지에 집중한다.

### 1) 역할 간 정합성

예:
- domain-analysis와 구조 설계 문서가 서로 맞는가
- architecture와 실제 생성된 역할 스킬의 `team-spec.md` 포인터가 맞는가
- orchestration-plan과 역할 팀 구조가 맞는가

### 2) 품질 질문의 실용성

예:
- 이 질문이 실제 프로젝트에 의미가 있는가
- 너무 추상적이거나 공허하지 않은가
- 팀이 반복적으로 사용할 수 있는가

### 3) 흐름의 끊김 여부

예:
- 앞 단계 출력이 다음 단계 입력으로 충분한가
- 역할 간 연결이 설명만 있고 실제 기준으로는 약하지 않은가

### 4) 위험 지점

예:
- 특정 역할이 과도하게 많은 책임을 가진다
- 흐름 조율 역할이 중심이어야 하는데 흐름이 분산되어 있다
- 리포트는 많은데 역할 팀 본체가 약하다

### 5) 경계면 교차 비교

QA 가이드는 생산자와 소비자, 설정과 참조 경로, 상태 정의와 실제 상태 변경처럼 서로 다른 경계의 정합성을 함께 읽는 방식을 강조한다.

Codex용 하네스에서도 같은 원칙을 적용한다. 다만 검증 대상은 프로젝트마다 다르므로, QA 역할은 아래 질문을 먼저 만든다.

- 이 프로젝트에서 서로 맞물려야 하는 생산자와 소비자는 무엇인가
- 한쪽만 보면 정상처럼 보이지만 함께 읽으면 깨질 수 있는 계약은 무엇인가
- 역할 출력과 `.codex/agents/*.toml`의 `role_id`가 같은 `team-spec.md` 역할 섹션으로 연결되는가
- `team-spec.md`의 역할 인벤토리와 `.agents/skills/*/SKILL.md`의 역할 포인터가 맞는가
- 역할 세부 기준이 `team-spec.md` 밖에 중복되어 drift 위험을 만들지 않는가
- `orchestration-plan.md`의 handoff와 `latest-session-summary.md`의 다음 재진입 정보가 맞물리는가

### 6) 변경 범위별 설계 원천 확인

QA 역할은 변경 diff, 대상 영역의 `AGENTS.md`, `team-spec.md`의 설계 원천 우선순위 또는 설계 원천 인벤토리, 최신 세션 요약 또는 재진입 상태를 기본 입력으로 읽는다. 그다음 변경 범위에 맞는 원천을 선택했는지, 필요한 원천이 없을 때 보류 판단과 다음 재진입 역할을 남겼는지 확인한다.

원천 선택의 세부 조건은 이 문서에 반복하지 않는다. `team-spec-contract.md`의 정책·불변 조건과 `team-spec-schema.md`의 필드·형식·구조 검증을 함께 기준으로 감사(audit)를 수행한다.

즉 QA는 “있다/없다”보다 “서로 맞는가”를 우선 본다.

---

## 4. QA는 언제 개입해야 하는가

QA는 마지막 한 번만 개입하면 늦다.

실행 하네스 팀에서는 QA가 최소한 다음 시점에 개입하는 것이 좋다.

### 1) 구조 설계 직후
- 역할 분리가 적절한가
- 너무 많거나 적지 않은가

### 2) 로컬 스킬 생성 직후
- 설명과 책임 범위가 충분한가
- 역할이 실제로 구분되는가

### 3) 오케스트레이션 정리 직후
- 흐름이 자연스러운가
- 입력/출력이 연결되는가

### 4) 운영 감사 피드백 이후
- 단순 수정이 아니라 더 근본적인 품질 질문이 필요한가

즉 QA는  
👉 **한 번의 최종 점검 역할이 아니라, 여러 단계에 걸쳐 개입하는 역할**이다.

---

## 5. 좋은 QA 질문의 조건

좋은 QA 질문은 다음 조건을 가진다.

- 프로젝트와 직접 연결된다
- 역할 팀 구조를 흔들 수 있는 질문이다
- 한 번 보고 끝나는 질문이 아니라 반복 검토 가능하다
- 구체적이지만 특정 사례 하나에만 묶이지 않는다

예:

좋지 않은 질문:
- "구조가 괜찮은가?"

좋은 질문:
- "domain-analysis에서 식별한 핵심 흐름이 실제 role 배치에 반영되었는가?"
- "흐름 조율 역할이 중심 역할인데, 설명과 산출물 모두 그 위치를 드러내는가?"
- "리포트가 본체처럼 커지고 역할 팀이 약해지는 징후가 있는가?"
- "`team-spec.md`의 역할별 입력/출력 계약을 실제 로컬 역할 스킬이 올바른 `role_id`로 참조하는가?"
- "역할별 우선 입력의 설계/정책/사양 문서가 `team-spec.md` 상단 원천 우선순위에 빠짐없이 포함되었는가?"
- "역할의 목적, 책임, 주요 출력과 우선 입력 문서가 서로 맞물리는가?"
- "추가 원천 선택이 필요한 역할이 `team-spec.md` 상세 기준을 직접 참조하고, 자체 기준을 중복 작성하지 않는가?"
- "역할별 우선 입력, 절차, 다음 역할이 agent/skill 파일에 중복 복제되어 drift 위험을 만들지 않는가?"
- "오케스트레이션 문서의 다음 역할과 latest-session-summary의 하네스 재진입 Phase가 같은 방향을 가리키는가?"

## 6. 통합 정합성 검증 패턴

QA는 프로젝트 유형에 맞는 교차 비교 축을 만든다.

### 1) 하네스 자체 경계

모든 프로젝트에서 공통으로 본다.

| 왼쪽 | 오른쪽 | 확인 질문 |
|------|--------|-----------|
| `team-spec.md` | `.codex/agents/*.toml` | 역할 인벤토리와 agent 파일 수가 맞고, `role_id`와 description이 올바른 역할 섹션을 가리키는가 |
| `team-spec.md` | `.agents/skills/*/SKILL.md` | 스킬 파일 수가 맞고, 해당 `role_id` 섹션과 공통 출력 블록을 명확히 참조하는가 |
| `team-spec.md` | `.codex/agents/*.toml`, `.agents/skills/*/SKILL.md` | 역할별 우선 입력, 절차, 다음 역할, 종료 기준이 밖에 중복 복제되어 있지 않은가 |
| `team-spec.md` 역할별 우선 입력 | `team-spec.md` 설계 원천 우선순위 | 역할이 정책 판단에 쓰는 설계/정책/사양 문서가 상단 원천 목록에 포함되고, 로그/세션 요약은 제외됐는가 |
| `team-spec.md` 상세 기준 | `team-spec.md` 역할별 우선 입력 | 역할별 원천 선택 기준이 상세 기준을 참조하고, 다른 문서에 중복 기준을 만들지 않았는가 |
| 변경 diff | QA 역할 우선 입력 | QA가 변경 범위별 원천 선택을 `team-spec.md` 상세 기준으로 판단하도록 정의됐는가 |
| `orchestration-plan.md` | `latest-session-summary.md` | 다음 역할과 하네스 재진입 Phase가 어긋나지 않는가 |
| `qa-strategy.md` | 운영 감사 결과 | QA 질문이 실제 감사 지적과 연결되는가 |
| 역할 출력 | `latest-session-summary.md` | 새 학습 후보와 승격 대상이 다음 실행 입력으로 이어지는가 |

### 2) 웹 애플리케이션 경계

웹 앱에서는 API, 상태, UI 경로가 자주 어긋난다.

- API 응답 shape과 프론트 소비 타입이 맞는가
- 라우트 파일 구조와 링크/라우터 경로가 맞는가
- 상태 전이 정의와 실제 업데이트 코드가 맞는가
- 서버 응답의 동기/비동기 성격을 프론트가 구분하는가

### 3) CLI / 라이브러리 경계

- 명령어 옵션과 도움말, 실제 파서가 맞는가
- 공개 API 타입과 문서 예시가 맞는가
- 출력 형식과 소비자가 기대하는 형식이 맞는가
- 오류 메시지와 종료 코드가 운영 문서의 기준과 맞는가

## 7. QA가 피해야 하는 것

### 1) 단순 존재 확인
이건 운영 감사 역할에 가깝다.

### 2) 추상적인 미사여구
"더 좋아져야 한다" 같은 문장은 의미가 약하다.

### 3) 실제 수정으로 이어지지 않는 지적
QA는 팀 구조를 더 낫게 만드는 데 기여해야 한다.

### 4) 프로젝트 목적과 무관한 품질 기준
중요하지 않은 기준을 과도하게 강제하면 하네스가 무거워진다.

---

## 8. QA와 흐름 조율 역할의 관계

흐름 조율 역할은 흐름과 연결 구조를 만든다.  
QA는 그 흐름이 실제로 건강한지 본다.

즉:

- 흐름 조율 역할 = 흐름 설계자
- QA = 흐름 감시자

좋은 실행 하네스 팀은  
흐름 조율 역할이 중심에 서고,  
QA가 그 중심 구조가 제대로 유지되는지 계속 질문하는 구조다.

---

## 9. QA와 사람 개입

실행 하네스 팀에서 QA는  
사람 개입이 가장 자연스럽게 들어오는 지점 중 하나다.

왜냐하면 다음은 AI가 완전히 확정하기 어렵기 때문이다.

- 어떤 실패가 치명적인가
- 어느 정도 품질을 현재 시점에 요구할 것인가
- 무엇을 반드시 반복 검토할 것인가

따라서 QA는  
AI가 초안을 만들고,  
사람이 그중 중요한 것을 선택하고 수정하는  
👉 **사람-AI 협업 접점**으로 보는 것이 맞다.

---

## 10. 핵심 요약

- QA는 단순 체크리스트 작성자가 아니다
- QA는 실행 하네스 팀의 품질 감시자다
- 운영 감사 역할과는 역할이 다르다
- QA는 여러 단계에서 반복적으로 개입해야 한다
- 좋은 QA 질문은 팀 구조를 실제로 더 낫게 만든다
- QA는 경계면 교차 비교를 우선한다
- QA는 사람 개입이 가장 자연스럽게 들어오는 지점이다
