# Reentry Rules

이 문서는 하네스 작업이 한 번에 끝나지 않을 때 어느 Phase로 되돌아가야 하는지와, 다음 시작을 위해 무엇을 남겨야 하는지 정의한다.

재진입은 예외 처리가 아니라 운영 루프의 일부다.

## 핵심 전제

- 재진입 판단은 저장소 입력, 역할 경계, 에이전트 정의, 역할 스킬, 오케스트레이션, 운영 감사, 피드백 반영 중 약한 축에 따라 달라진다.
- 모든 재진입은 `latest-session-summary.md`에 다음 시작 정보로 남아야 한다.
- 재진입은 전체 재생성보다 좁은 Phase 수정부터 본다.

## 기본 재진입 축

- 입력이 약하면 `Phase 1`
- 역할 경계가 약하면 `Phase 2`
- 에이전트 정의가 약하면 `Phase 3`
- 역할 스킬의 `team-spec` 포인터나 트리거가 약하면 `Phase 4`
- 오케스트레이션과 handoff 기준이 약하면 `Phase 5`
- 운영 감사에서 구조 불일치가 남으면 `Phase 6`
- 피드백 반영과 다음 개선 판단이 약하면 `Phase 7`

## Phase별 재진입 조건

### Phase 1로 재진입

- `project-setup.md`가 비어 있거나 방향을 좁히지 못한다
- `domain-analysis.md`가 저장소 근거보다 일반론에 가깝다
- 핵심 사용자 문제나 첫 성공 시나리오가 분명하지 않다

### Phase 2로 재진입

- 역할 이름이 범용적이거나 현재 저장소 용어를 반영하지 못한다
- 다음 역할 흐름이 약하다
- 시작 진입 역할과 중심 조율 역할이 섞여 있다

### Phase 3으로 재진입

- `team-spec.md`와 `.codex/agents/*.toml`이 일치하지 않는다
- description만으로 트리거 조건을 파악하기 어렵다
- 시작 진입 역할과 중심 조율 역할의 agent 정의가 섞여 있다

### Phase 4로 재진입

- `.codex/skills/*/SKILL.md`가 해당 `role_id`의 team-spec 섹션을 명확히 참조하지 못한다
- 역할 스킬이 `team-spec`의 공통 출력 블록을 따르도록 지시하지 않는다
- 역할별 우선 입력, 절차, 다음 역할, 종료 기준이 역할 스킬 본문에 중복 복제되어 drift 위험을 만든다

### Phase 5로 재진입

- `orchestration-plan.md`, `team-playbook.md`, `team-structure.md`가 다음 역할 흐름을 분명히 보여주지 못한다
- 시작 진입 역할이 다음 역할, 보류 흐름, 실패 흐름을 안정적으로 안내하지 못한다
- 최신 세션 요약에 다음 시작 정보가 부족하다

### Phase 6으로 재진입

- 운영 감사가 누락/불일치/골격 잔존을 남긴다
- 역할 구조가 확장 가능한 팀으로 읽히지 않는다
- 에이전트 정의, 역할 스킬, 보조 운영 문서, 로그가 같은 운영 기준을 말하지 않는다

### Phase 7로 재진입

- 구조는 맞지만 운영 가능성을 설명하지 못한다
- `with-skill`과 `without-skill` 비교 관찰이 약하다
- 다음 재진입 판단이 로그와 운영 감사 피드백에 연결되지 않는다

## latest-session-summary.md에 남겨야 할 재진입 정보

최신 요약에는 최소한 아래 항목을 남긴다.

- 다음 시작 역할
- 다음 재진입 phase
- 다음 시작 전 우선 확인 입력 파일
- 최근 출력 파일
- 최근 변경 파일
- 남은 위험 또는 미해결 항목

## 판단 원칙

- 전체를 다시 만들기보다 가장 이른 실패 지점으로 되돌아간다.
- 역할 계약 충족 여부와 오케스트레이션 실행 가능성을 우선한다.
- 재진입 이유는 한 문장으로 설명 가능해야 한다.

## 다른 레퍼런스와의 연결

- `phase-selection-matrix.md`: Phase 선택 기준을 더 자세히 볼 때 쓴다.
- `logging-contract.md`: 최신 세션 요약에 무엇을 남겨야 하는지 정의한다.
- `verification-checklist.md`: 재진입이 필요한 불일치 유형을 검토할 때 쓴다.
