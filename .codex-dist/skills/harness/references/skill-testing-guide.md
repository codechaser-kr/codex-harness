# Skill Testing Guide (Codex용 스킬 검증 기준)

이 문서는 생성된 스킬이 실제로 올바르게 작동하는지 검증하는 방법을 정의한다.

스킬은 작성하는 것으로 끝나지 않는다.  
반드시 테스트를 통해 유효성을 확인해야 한다.

범용 하네스 생성기에서는 특히 다음을 검증해야 한다.

- 스킬이 실제로 트리거되는가
- 스킬 사용 여부에 따른 원본 결과와 관찰 가능한 차이를 준비할 수 있는가
- 역할 분리가 적절한가
- 입력과 출력이 자연스럽게 연결되는가
- 위임 가능한 판단 단위로 잘 설계되었는가
- 후속 실행, 부분 재진입, 보류/실패 흐름을 처리할 수 있는가

---

## 핵심 전제

- 테스트는 파일 존재 확인보다 역할 판단, 입력/출력 연결, 구조적 회귀를 우선 검증해야 한다.
- With-skill vs Without-skill 실행은 사용자가 결과를 비교할 자료를 준비하는 도구다. 하네스와 역할 에이전트가 우열을 판정하지 않는다.
- 테스트는 특정 예시 최적화가 아니라, 반복 가능한 회귀 방지 규칙으로 남아야 한다.
- Codex용 하네스에서는 테스트 기준도 별도 실행 파일에 의존하지 않는다. 검증 질문, 비교 산출물, 로그와 운영 감사 관찰로 반복 점검 가능해야 한다.

---

## 1. 테스트의 목적

- 스킬이 실제로 트리거되는가
- 스킬 사용 여부에 따른 결과 차이를 사용자가 검토할 수 있는가
- 다양한 입력에서도 안정적으로 동작하는가
- 역할 위임 구조가 과하거나 부족하지 않은가
- 생성된 하네스가 사람이 검토 가능한 구조로 남는가

---

## 2. 테스트 방식

### 1) 현실적인 테스트 프롬프트 작성

테스트 프롬프트는 실제 사용자가 입력할 법한 문장이어야 한다.

좋은 프롬프트는 아래 조건을 가진다.

- 구체적인 저장소 맥락이나 산출물 요구가 있다.
- 공식적 표현과 캐주얼한 표현을 섞는다.
- 명시적 요청과 암시적 요청을 모두 포함한다.
- 정상 흐름뿐 아니라 부분 갱신, 보완, 운영 점검 요청도 포함한다.

나쁜 예:

- "하네스 테스트"
- "스킬 확인"
- "문서 만들어줘"

좋은 예:

- "이 저장소에 하네스를 구성하되, 기존 AGENTS.md와 충돌하지 않게 시작 역할과 QA 역할을 나눠줘."
- "이전에 만든 하네스에서 QA 흐름만 보완하고, 다음 하네스 재진입 Phase를 로그에 남겨줘."
- "로컬 역할 스킬 설명이 서로 비슷해졌는지 점검하고, 필요한 스킬만 다시 정렬해줘."

### 2) With-skill vs Without-skill 비교

같은 요청을 두 가지 방식으로 비교한다.

- With-skill: 스킬을 사용하는 경우
- Without-skill: 스킬 없이 수행하는 경우

### 관찰 항목

- 실제로 인용한 저장소 근거와 사용자 입력
- 역할, 파일, 질문과 handoff 수
- 구조·계약 검증의 통과·실패
- 다음 역할과 후보 하네스 Phase의 유무
- 보류/실패 상황의 기록과 재개 조건
- 확인할 수 없는 항목과 실행 조건 차이

### 목표

같은 요청과 가능한 한 같은 기준선에서 두 원본 결과와 비교 조건을 보존해 사용자가 품질과 적합성을 직접 판단할 수 있게 한다.

---

## 3. 트리거 테스트

스킬은 description 기반으로 트리거된다.

따라서 다음을 반드시 테스트한다.

### 1) Should-trigger

스킬이 반드시 실행되어야 하는 요청

예:
- "하네스 역할 설계해줘"
- "로컬 스킬 구조 만들어줘"
- "이 저장소에 맞는 실행 하네스 팀을 구성해줘"
- "기존 하네스의 역할과 스킬이 서로 맞는지 감사해줘"
- "하네스 오케스트레이션 흐름을 다시 정렬해줘"
- "QA와 운영 감사 역할까지 포함해서 프로젝트별 팀을 설계해줘"

### 2) Should-NOT-trigger

스킬이 실행되면 안 되는 요청

예:
- "피보나치 함수 만들어줘"
- "간단한 코드 한 줄 수정"
- "단일 파일 버그만 고쳐줘"
- "README 문장 하나만 다듬어줘"
- "현재 브랜치 이름 추천해줘"

### 핵심

경계가 애매한 요청을 포함해야 한다.  
명백히 무관한 요청만 넣으면 테스트 가치가 낮다.

should-trigger와 should-NOT-trigger는 각각 8~10개 정도 준비하는 것이 좋다. 단, 이 프로젝트에서는 별도 실행 파일이 아니라 문서화된 쿼리 묶음과 운영 감사 판단으로 관리한다.

---

## 4. 드라이런 테스트

전체 하네스 흐름을 실제 실행 전 단계에서 검토한다.

### 확인 항목

- 단계 순서가 논리적인가
- 입력/출력 연결이 맞는가
- 중간에 끊기는 흐름이 없는가
- 역할 간 책임이 겹치지 않는가
- 결과가 파일 기반 산출물로 남는가
- 시작 컨텍스트 확인 결과가 남는가
- 역할 간 handoff 기준이 입력, 출력, 다음 역할, 하네스 재진입 Phase까지 설명하는가
- 역할 출력과 handoff에 학습 후보, 승격 대상, 생성기 환류 후보를 남길 위치가 있는가
- 보류나 실패 상황에서 어느 문서와 Phase로 되돌아갈지 설명하는가
- 정상 흐름과 보류 흐름 시나리오가 함께 있는가
- 오케스트레이터 역할이 팀 조율 책임을 Codex 방식으로 수행하는가
- 주 에이전트 통합 책임과 subagent 보조 위임 책임이 섞이지 않는가

---

## 5. 역할 위임 구조 테스트

서브에이전트 활용을 염두에 둘 경우,  
역할 분리 자체도 테스트해야 한다.

### 확인 질문

- 이 역할은 한 문장으로 목적을 설명할 수 있는가
- 입력이 명확한가
- 출력이 명확한가
- 다른 역할과 지나치게 겹치지 않는가
- 굳이 분리할 필요가 없는 역할을 과하게 나누지 않았는가

### 역할 구분 근거가 드러나는 예

- workspace-map-analyst: 저장소 분석
- boundary-architect: 구조 설계
- interaction-qa: 품질 질문 설계
- release-auditor: 최소 구조 점검

### 역할 구분 근거가 약한 예

- 저장소 분석 A
- 저장소 분석 B
- 저장소 분석 C

이처럼 구분 이유가 약하면 역할별 입력·출력과 책임 차이를 관찰 사실로 남기고, 역할 통합 여부는 사용자가 판단한다.

---

## 6. 입력/출력 연결 테스트

좋은 하네스는 역할 간 연결이 자연스럽다.

### 확인할 것

- domain-analysis.md가 구조 설계 문서의 실제 입력으로 기능하는가
- 구조 설계 문서가 역할 생성과 운영 기준의 실제 기준이 되는가
- qa-strategy.md가 흐름과 검증 관점에 연결되는가
- orchestration-plan.md가 실제 협업 순서를 설명하는가

즉 단순히 파일이 존재하는지가 아니라  
👉 **실제로 다음 단계의 기준으로 기능하는지**를 봐야 한다.

---

## 7. 반복 개선 루프

테스트 후 반드시 개선을 반복한다.

### 과정

1. 테스트 실행
2. 문제 발견
3. 문제를 일반화
4. 관찰과 수정 후보를 사용자에게 제시
5. 사용자가 확정한 경우에만 스킬 수정
6. 재테스트
7. 확정된 하네스 재진입 Phase와 수정 대상을 기록

### 주의

- 특정 한 예시에만 맞춘 수정 ❌
- 여러 프로젝트에서도 통할 일반화된 개선 ✔
- 별도 실행 파일 추가로 문제를 숨기는 수정 ❌
- 역할 스킬, reference, team-spec, orchestration 기준 중 어디를 고쳤는지 남기는 수정 ✔

---

## 8. 테스트와 사용자 판단 자료 형식

테스트와 관찰 결과는 길게 쓰기보다 다음 순서로 남긴다.

1. 요청
2. with-skill 결과 요약
3. without-skill 결과 요약
4. 관찰 가능한 차이
5. 직접 비교할 수 없는 조건과 남은 위험
6. 구조·계약 검증 결과
7. 수정 후보: `description / SKILL.md / reference / team-spec / orchestration / QA`
8. 후보 하네스 재진입 Phase
9. `현재 유지 / 부분 수정 / 구조 재설계` 선택지별 영향
10. 사용자 결정 상태와 확정 범위
11. 학습 후보와 승격 대상

예:

```markdown
- 요청: 기존 하네스 역할과 스킬 정렬 점검
- with-skill: 시작 역할과 운영 감사 역할이 분리되고, 하네스 재진입 Phase가 하네스 Phase 4로 지정됨
- without-skill: 파일 목록 점검에 머물고 다음 역할이 불명확함
- 관찰된 차이: with-skill 결과에는 역할 경계와 다음 조치가 있고 without-skill 결과에는 없음
- 남은 위험: QA 질문이 저장소 고유 흐름까지 연결되지는 않음
- 수정 후보: qa-strategy, interaction-qa SKILL.md
- 후보 하네스 재진입 Phase: 하네스 Phase 5
- 사용자 결정 상태: 대기
- 학습 후보와 승격 대상: QA 질문 구체화 필요, qa-strategy와 QA 역할 스킬
```

## 9. 자주 발생하는 문제

### 문제 1: 스킬이 트리거되지 않음
원인:
- description이 약함

해결:
- 더 구체적으로 작성
- 언제 써야 하는지 분명히 적기

### 문제 2: 사용자가 결과 품질 문제를 확인함
원인:
- 본문이 모호함
- 입력/출력 정의 부족

해결:
- 관찰 근거와 수정 범위를 사용자 결정에 연결
- 사용자가 확정한 입력/출력 섹션만 명확화

### 문제 3: 특정 상황에서만 동작
원인:
- 과도한 특화

해결:
- 일반화

### 문제 4: 역할이 너무 많아 흐름이 복잡해짐
원인:
- 분리 기준이 약함

해결:
- 역할 통합 고려
- 파이프라인 단순화

### 문제 5: 파일은 있는데 실제 연결이 약함
원인:
- 산출물이 존재만 하고 흐름 기준이 되지 못함

해결:
- 역할 간 연결 설명 강화
- orchestration 문서 보강

### 문제 6: 후속 실행에서 스킬이 죽음
원인:
- description에 `다시 실행`, `보완`, `부분 갱신`, `이전 결과 기반` 같은 후속 표현이 없음

해결:
- description에 후속 작업 키워드를 추가
- 시작 컨텍스트 확인과 이전 산출물 읽기 규칙 추가

### 문제 7: 테스트가 파일 존재 확인에 머묾
원인:
- 산출물 경로만 보고 역할 판단 품질을 보지 않음

해결:
- with/without 비교 문장을 남김
- 다음 역할, 후보 하네스 Phase, 보류/실패 처리 차이를 관찰 자료로 남김

---

## 10. 좋은 테스트의 조건

- 현실적인 요청 사용
- 다양한 표현 포함
- 경계 케이스 포함
- 역할 분리와 흐름도 함께 점검
- 파일 존재가 아니라 구조적 유효성을 본다
- 후속 실행과 보류 흐름을 포함한다
- 사용자 결정이 확정된 수정 대상과 하네스 재진입 Phase로 연결된다

---

## 11. 범용 하네스에서 특히 중요한 점

범용 하네스 생성기에서는  
스킬 하나의 성능만 볼 것이 아니라,  
👉 **여러 역할이 함께 만든 구조를 사용자가 판단할 자료**를 함께 봐야 한다.

즉 테스트는 다음을 함께 본다.

- 개별 스킬 품질
- 트리거 적절성
- 역할 분리 적절성
- 입력/출력 연결성
- 전체 구조의 검토 가능성
- Codex 런타임에 맞는 오케스트레이션 책임 분리

---

## 12. 핵심 요약

- 스킬은 반드시 테스트해야 한다
- with/without 원본 결과와 비교 조건 보존이 중요하다
- 트리거 테스트가 중요하다
- 역할 위임 구조도 테스트 대상이다
- 입력/출력 연결성을 함께 봐야 한다
- 반복 개선이 필수다
- 후속 실행과 부분 재진입까지 봐야 한다
- 문서 계약만으로 반복 점검 가능해야 한다
