# Skill Writing Guide (Codex용 스킬 작성 기준)

이 문서는 하네스에서 사용하는 스킬을 어떻게 작성해야 하는지 정의한다.

스킬은 단순 설명 문서가 아니라,  
Codex가 실제로 어떤 역할을 언제 어떻게 사용할지 판단하는 기준이 된다.

범용 하네스 생성기에서는 특히 다음이 중요하다.

- 어떤 역할이 어떤 판단을 맡는가
- 언제 이 스킬을 써야 하는가
- 입력과 출력이 무엇인가
- 다른 역할과 어떻게 연결되는가
- 필요하면 어떤 단위로 위임 가능한가
- 본문은 가볍게 유지하고, 긴 판단 기준은 필요할 때만 읽을 reference로 분리했는가

---

## 핵심 전제

- 좋은 스킬 문서는 트리거 조건, 판단 단위, 입력/출력 연결을 한 번에 드러내야 한다.
- 스킬 본문은 자연스러운 설명보다 역할 선택과 협업 판단에 실제로 쓰일 문장을 우선해야 한다.
- references 분리는 본문을 가볍게 만들기 위한 것이 아니라, 판단 기준과 예시를 안정적으로 재사용하기 위한 구조다.
- Codex용 하네스에서는 별도 실행 파일을 전제로 스킬을 만들지 않는다. 반복 절차는 스킬 본문, reference, 로그, handoff 규칙으로 남긴다.

---

## 1. 스킬의 역할

스킬은 다음을 담당한다.

- 무엇을 할 수 있는가
- 어떤 상황에서 사용해야 하는가
- 어떤 입력을 받아 어떤 출력을 만드는가
- 어떤 판단 기준을 사용하는가

중요:

스킬은 단순히 "누가 하는가"를 적는 문서가 아니다.  
👉 **"어떤 판단 단위를 어떤 방식으로 수행하는가"**를 정의해야 한다.

---

## 2. description 작성 (가장 중요)

description은 스킬의 **트리거 조건**이다.

Codex는 description을 보고  
이 스킬을 써야 하는지 판단한다.

범용 하네스에서는 description이 특히 중요하다.  
왜냐하면 역할이 많아질수록 description이 약하면 적절한 역할 선택이 어려워지기 때문이다.

---

### 나쁜 예

"파일을 분석하는 스킬"

문제:
- 너무 추상적이다
- 언제 써야 하는지 모른다
- 다른 역할과 구분되지 않는다

---

### 좋은 예

"저장소의 목적, 핵심 런타임 경계, 실행·검증 흐름, 하네스 관점의 주요 관심사를 분석합니다. 프로젝트 구조 분석, 사용자 입력 해석, 핵심 흐름 정리가 필요할 때 적극적으로 사용합니다."

장점:
- 무엇을 하는지 분명하다
- 언제 써야 하는지 드러난다
- 다른 역할과 구분된다

---

## 3. description 작성 원칙

- 무엇을 하는지 구체적으로 쓴다
- 언제 사용해야 하는지 명시한다
- 유사 역할과 구분되게 작성한다
- 가능하면 "이런 요청이 오면 사용" 의미가 드러나게 쓴다
- 입력과 출력의 성격이 어느 정도 드러나게 한다
- 후속 작업 표현을 포함한다. 예: `다시 실행`, `보완`, `부분 갱신`, `이전 결과 기반`, `운영 점검`
- 트리거하면 안 되는 near-miss 경계도 본문에 짧게 둔다

좋은 description은 단순 홍보 문구가 아니라  
👉 **역할 선택 기준**이다.

---

## 4. 본문 작성 원칙

---

### 1) Why 중심으로 작성

나쁜 예:

"항상 이 순서를 따른다"

좋은 예:

"이 순서를 따르는 이유는 앞 단계 결과가 뒤 단계의 핵심 입력이기 때문이다"

이유:
- LLM은 이유를 이해할 때 더 안정적으로 일반화한다
- 엣지 케이스에서 더 나은 판단을 할 수 있다

---

### 2) 책임 단위를 분명히 쓴다

스킬은 무엇을 맡고, 무엇은 맡지 않는지 드러나야 한다.

예:
- 저장소 입력 문서 담당 역할은 구조 분석을 담당한다
- 구조 설계 담당 역할은 구조 설계를 담당한다
- 운영 감사 역할은 생성 이후 점검을 담당한다

이렇게 구분해야 역할 간 충돌이 줄어든다.

---

### 3) 입력/출력을 명시한다

스킬은 가능하면 다음을 문서에 포함해야 한다.

- 입력
- 출력
- 주요 작업

이유:
- 역할 위임이 쉬워진다
- 다른 역할과 연결하기 쉬워진다
- 결과를 파일 기반으로 추적할 수 있다

---

### 4) 일반화

- 특정 프로젝트 한 개에만 맞는 규칙 ❌
- 다양한 프로젝트에 적용 가능한 판단 원칙 ✔

범용 하네스 생성기에서는  
특정 기술에 과도하게 고정된 문장을 피한다.

---

### 5) 짧지만 판단 가능하게 유지한다

- 제목만 있는 얇은 문서 ❌
- 쓸데없이 길어서 흐름이 안 보이는 문서 ❌
- 짧지만 실제로 행동 판단이 가능한 문서 ✔

---

## 5. Progressive Disclosure 원칙

원본 하네스처럼 스킬은 단계적으로 정보를 공개해야 한다.

### 1) Metadata

- `name`과 `description`은 항상 노출되는 트리거 정보다.
- 여기에는 스킬 정체성, 사용 조건, near-miss 경계가 들어가야 한다.

### 2) SKILL.md 본문

- 역할의 핵심 워크플로우, 입력/출력, 판단 기준, 완료 조건만 둔다.
- 본문은 스킬이 트리거됐을 때 바로 실행 가능한 수준이어야 한다.
- 너무 긴 배경 설명, 도메인별 세부 변형, 예시는 본문에 쌓지 않는다.

### 3) references/

- 긴 판단 기준, 도메인별 분기, 예시 팀, 테스트 기준은 reference로 분리한다.
- SKILL.md 본문에는 언제 어떤 reference를 읽을지 포인터를 남긴다.
- 모든 reference를 한 번에 읽게 하지 말고, 현재 판단 축에 맞는 문서만 읽게 한다.

이 구조는 원본 하네스의 핵심 동작과 같다. Codex용 하네스에서도 SKILL.md 하나가 모든 내용을 품는 방식이 아니라, 본문과 reference가 함께 역할을 수행해야 한다.

---

## 6. 출력 형식 정의

산출물이 중요한 역할 스킬은 출력 형식을 명확히 둔다.

좋은 출력 형식은 다음을 포함한다.

- 출력 파일 경로
- 필수 섹션
- 각 섹션에 들어갈 판단 근거
- 보류 질문과 남은 위험을 적는 위치
- 다음 역할이 읽어야 할 요약
- 새로 확인한 저장소 사실과 하네스 갱신 후보를 적는 위치

예:

```markdown
## 출력

- 파일: `.harness/docs/qa-strategy.md`
- 필수 섹션: 검증 범위, 자동 검증, 수동 검증, 미실행 항목, 잔여 위험, 다음 조치, 학습 후보
- 다음 역할 입력: `.harness/docs/orchestration-plan.md` 작성 시 검증 범위와 잔여 위험을 반드시 반영한다.
```

출력 형식은 고정 파일을 복사하라는 뜻이 아니다. 다음 역할이 같은 의미로 읽을 수 있도록 산출물의 계약을 고정하는 것이다.
학습 후보가 없으면 `없음`으로 짧게 남긴다. 학습 후보가 있으면 `evolution-contract.md` 기준으로 재진입 Phase와 승격 대상을 함께 적는다.

### 공통 학습 출력 블록

생성된 역할 스킬은 역할 유형과 상관없이 아래 블록을 출력 형식에 포함할 수 있어야 한다. 신규 구축에서 만든 역할 스킬은 이 블록을 포함하거나 같은 의미의 항목을 반드시 가져야 한다. 관찰이 없으면 각 항목을 길게 설명하지 말고 `없음`으로 남긴다.

```markdown
- 새로 확인한 저장소 사실: `<facts or 없음>`
- 반복될 수 있는 판단: `<pattern or 없음>`
- 하네스 갱신 후보: `<local docs/skills or 없음>`
- 승격 대상: `<Phase and target or 없음>`
- 생성기 환류 후보: `<yes/no and reason>`
```

이 블록은 모든 역할이 메타 보고서를 쓰라는 뜻이 아니다. 구현, QA, 조율, 감사 중 어느 역할에서든 다음 실행에 영향을 줄 사실이 드러났을 때 같은 형식으로 전달하기 위한 최소 계약이다.

---

## 7. 위임 친화적인 스킬의 조건

Codex의 서브에이전트 활용을 염두에 둘 때,  
좋은 스킬은 다음 조건을 가진다.

### 1) 목적이 한 문장으로 요약 가능하다
예:
- "저장소를 분석한다"
- "하네스 구조를 설계한다"
- "QA 질문을 정리한다"

### 2) 입력이 분명하다
예:
- 저장소 루트
- domain-analysis.md
- harness-architecture.md

### 3) 출력이 분명하다
예:
- qa-strategy.md
- orchestration-plan.md
- 구조 보완 제안

### 4) 책임이 너무 넓지 않다
"분석 + 설계 + 생성 + 검증"을 모두 한 스킬이 맡으면  
위임 가치가 떨어진다.

즉 좋은 스킬은  
👉 **하나의 명확한 판단 덩어리**여야 한다.

---

## 8. 구조 분리 원칙

역할 정의는 4단계 구조로 나눈다.

### 1) agent 정의 파일
- 누가 이 역할을 맡는가
- 어떤 책임과 경계를 가지는가
- 어떤 입력을 받고 다음에 누구에게 넘기는가

### 2) description
- 항상 존재
- 트리거 역할

### 3) SKILL.md 본문
- 실행 흐름
- 판단 기준
- 입력/출력
- 책임 범위

### 4) references/
- 상세 가이드
- 예시
- 선택적으로 읽어야 하는 긴 내용

agent 정의 파일은 "누가 하는가"를, SKILL.md는 "어떻게 하는가"를 담당한다.
둘을 한 파일에 모두 몰아넣지 않는다.

---

## 9. 언제 references로 분리하는가

다음 경우에는 references로 분리한다.

- 설명이 길어질 때
- 특정 도메인/기술 분기 설명이 필요할 때
- 예시가 많을 때
- 모든 상황에서 항상 읽을 필요는 없을 때

이유:
- 본문은 흐름과 핵심 판단에 집중해야 한다
- 세부 문서까지 항상 읽으면 컨텍스트가 무거워진다

---

## 10. 스킬 설계 실수

### 실수 1: description이 약함
→ 스킬이 트리거되지 않거나 잘못 선택됨

### 실수 2: 책임 범위가 너무 넓음
→ 위임도 어렵고 품질도 약해짐

### 실수 3: 입력/출력이 없음
→ 다른 역할과 연결되지 않음

### 실수 4: 특정 프로젝트에 과도하게 고정됨
→ 범용 생성기로서 가치가 떨어짐

### 실수 5: 이유 없는 규칙만 나열
→ 상황이 바뀌면 잘 대응하지 못함

### 실수 6: 생성 과정의 메타 정보를 스킬에 넣음
→ 스킬은 사용자 설명서나 변경 이력 문서가 아니라, 에이전트가 실행할 지시서다.

### 실수 7: 반복 절차를 별도 실행 파일에 맡김
→ 이 프로젝트의 목표는 외부 실행 파일에 기대지 않는 메타 하네스다. 반복 판단은 문서 계약과 역할 스킬로 남긴다.

---

## 11. 좋은 스킬의 조건

- 언제 써야 하는지 명확하다
- 무엇을 맡는지 분명하다
- 입력과 출력이 보인다
- 다른 역할과 연결 가능하다
- 위임 가능한 판단 단위다
- 사람이 읽어도 이해 가능하다
- reference를 필요할 때만 읽게 한다
- 후속 실행과 부분 재진입을 처리할 수 있다

---

## 12. 다른 레퍼런스와의 연결

- `agent-design-patterns.md`: 어떤 역할을 분리하고 어떤 실행 단위를 택할지 상위 기준을 제공한다.
- `orchestrator-template.md`: 스킬이 실제 흐름과 역할 연결 안에서 어떻게 소비되는지 연결한다.
- `skill-testing-guide.md`: 여기서 정의한 description, 입력/출력, 책임 범위가 어떻게 테스트되는지 연결한다.
- `evolution-contract.md`: 역할 출력에 학습 후보와 하네스 갱신 후보를 어떻게 남길지 연결한다.

---

## 13. 범용 하네스에서 특히 중요한 점

범용 하네스 생성기에서는  
각 스킬이 실제 작업 수행기이면서 동시에  
👉 **하위 역할로 위임 가능한 단위**가 되어야 한다.

즉 스킬은 단순 설명서가 아니라:

- 역할 선택 기준
- 작업 연결 기준
- 파일 기반 산출물 생성 기준

을 함께 담아야 한다.

---

## 14. 핵심 요약

- description이 곧 트리거다
- 스킬은 판단 단위를 정의해야 한다
- 입력과 출력이 명확해야 한다
- 책임 범위가 적절해야 한다
- 본문은 흐름과 판단 기준에 집중한다
- 상세 내용은 references로 분리한다
