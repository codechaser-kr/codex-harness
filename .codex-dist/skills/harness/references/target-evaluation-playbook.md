# Target Decision Support Playbook

이 문서는 실제 타겟 프로젝트에서 하네스를 생성하거나 갱신한 뒤, 사용자가 결과를 판단할 수 있도록 구조·계약 검증 결과, 관찰 사실, 불확실성과 변경 선택지를 준비하는 절차를 정의한다.

하네스와 역할 에이전트는 생성 결과의 품질이나 운영 적합성을 최종 판정하지 않는다. `현재 유지 / 부분 수정 / 구조 재설계` 선택과 실제 변경 범위는 사용자만 확정한다.

---

## 1. 언제 사용하는가

- 전역 하네스 생성기를 크게 변경한 뒤 타겟 프로젝트의 생성 결과를 확인할 때
- 하네스 Phase 0~7 규칙이 실제 생성 결과에 반영되는지 검증할 때
- 문서, 역할 자산, 오케스트레이션과 로그의 차이를 사용자에게 설명할 때
- 사용자가 부분 수정과 구조 재설계 중 변경 범위를 결정해야 할 때

---

## 2. 기본 절차

### 1) 타겟 프로젝트 준비

- 기존 하네스 산출물이 있으면 현재 기준선과 보존 방법을 기록한다.
- 이번 실행이 신규 생성인지, 사용자 확정 범위의 부분 재진입인지 구분한다.
- 상위 `AGENTS.md` 충돌 가능성과 확인하지 못한 입력을 먼저 기록한다.

### 2) 하네스 생성 또는 갱신

- 신규 생성이면 시작 진입 역할이 `하네스 Phase 0` 감사부터 시작한다.
- 기존 구조 변경은 사용자가 확정한 하네스 Phase와 파일 범위만 수행한다.
- 생성 직후 초기 산출물을 품질이 검증된 완성본으로 선언하지 않는다.

### 3) 구조·계약 검증

- 운영 감사 역할이 `verification-checklist.md`를 기준으로 결정론적인 조건을 확인한다.
- 파일·필드·참조·테스트·계약 조건은 실제 결과에 따라 통과 또는 실패로 기록한다.
- 구조 검증 결과를 하네스 전체의 품질이나 운영 적합성 판정으로 확대하지 않는다.

### 4) 사용자 판단 자료 준비

- 관찰된 차이와 영향을 경로·역할·하네스 Phase 근거와 함께 기록한다.
- 확인할 수 없는 항목과 추론을 사실과 분리한다.
- `with-skill`과 `without-skill` 자료가 있으면 `quality-evaluation-guide.md`에 따라 원본 결과와 비교 조건을 보존한다.
- 아래 세 선택지를 모두 같은 수준으로 제시하고 어느 하나를 최선으로 표시하지 않는다.
  - `현재 유지`
  - `부분 수정`
  - `구조 재설계`

### 5) 사용자 결정과 실행 게이트

- 사용자 결정 전 상태는 `사용자 결정 대기`다.
- `현재 유지`가 선택되면 하네스 자산을 변경하지 않고 관찰과 잔여 위험만 기록한다.
- `부분 수정` 또는 `구조 재설계`가 선택되면 사용자가 확정한 대상과 하네스 Phase를 하네스 Phase 7 입력으로 사용한다.
- 사용자 결정을 추정하거나 더 넓은 범위로 해석하지 않는다.

---

## 3. 타겟 프로젝트 관찰 체크리스트

### A. 입력 문서

- `exploration-notes.md`가 자동 판단 보류와 다음 확인 질문을 남기는가
- `domain-analysis.md`가 인용한 저장소 근거와 사용자 입력은 무엇인가
- `qa-strategy.md`가 실행 가능한 검증, 미실행 항목과 잔여 위험을 기록하는가

### B. 보조 운영 문서

- `harness-architecture.md`가 패턴 선택 근거를 설명하는가
- `orchestration-plan.md`가 요청 유형별 시작점과 재진입 조건을 설명하는가
- `team-structure.md`, `team-playbook.md`가 역할 자산과 오케스트레이션을 대신하지 않는가
- 보존 문서의 이전 역할명과 현재 역할명 사이에 호환성 매핑이 있는가

### C. 에이전트 팀 계약

- `AGENTS.md`, `.codex/config.toml`, `.codex/agents/*.toml`, `.agents/skills/*`가 같은 역할 집합을 말하는가
- `team-spec.md`의 최종 역할 인벤토리가 fenced `text` 블록으로 존재하는가
- 각 역할 스킬이 해당 `role_id` 섹션과 공통 출력 블록을 참조하는가
- 시작 진입, 중심 조율, QA와 운영 감사 역할의 책임이 구분되는가

### D. 로그와 재진입

- `session-log.md`와 `latest-session-summary.md`가 같은 세션 ID를 설명하는가
- 다음 시작 역할, 후보 또는 확정 하네스 Phase, 다시 읽을 입력과 최근 출력이 남아 있는가
- 사용자 결정 전 후보와 결정 후 확정 범위가 구분되는가

## 4. 사용자 선택지의 범위

다음 조건은 선택지를 설명하기 위한 관찰 축이며 자동 판정 규칙이 아니다.

### 현재 유지

- 하네스 자산을 변경하지 않는다.
- 구조·계약 실패, 관찰된 차이와 잔여 위험을 사용자가 수용한다.
- 후속 확인이 필요하면 변경 명령이 아니라 재검토 조건만 기록한다.

### 부분 수정

- 기존 역할 팀 아키텍처와 기준 원천을 유지한다.
- 수정 대상을 특정 문서, 역할, 포인터, handoff, 로그 또는 하네스 Phase로 좁힐 수 있다.
- 사용자에게 대상 파일, 후보 하네스 Phase, 예상 영향과 보존할 자산을 제시한다.

### 구조 재설계

- 역할 팀 아키텍처, 기준 원천 또는 운영 흐름을 다시 선택할 수 있다.
- 여러 문서와 역할 자산이 서로 다른 구조를 말하거나 부분 수정이 반복되는 관찰을 근거로 제시할 수 있다.
- `하네스 Phase 0` 감사부터 다시 시작할 범위, 보존 후보와 교체 후보를 사용자에게 제시한다.

부분 수정이 가능한지 또는 구조 재설계가 더 적절한지는 비용, 프로젝트 의도와 허용 범위를 포함한 사용자 판단이다. 에이전트는 관찰 신호만 제공하고 선택하지 않는다.

---

## 5. 사용자 판단 자료 형식

결과는 다음 순서로 남긴다.

1. 타겟 프로젝트와 기준선
2. 실행한 구조·계약 검증과 실제 결과
3. 관찰된 차이와 영향
4. 확인할 수 없는 항목과 불확실성
5. `with-skill` / `without-skill` 원본 결과와 비교 조건(있는 경우)
6. `현재 유지` 선택 시 영향과 잔여 위험
7. `부분 수정` 후보 대상과 하네스 Phase
8. `구조 재설계` 후보 범위와 보존 대상
9. 사용자 결정 상태: `대기 / 현재 유지 / 부분 수정 / 구조 재설계`
10. 사용자 확정 범위(결정된 경우)

예:

- 계약 검증: 역할 스킬 2개가 `team-spec.md`의 해당 `role_id` 섹션을 참조하지 않음
- 관찰: 나머지 역할 집합과 오케스트레이션은 같은 역할명을 사용함
- 불확실성: 현재 역할 구성이 프로젝트 의도에 적합한지는 확인할 수 없음
- 현재 유지: 포인터 누락 위험을 수용하고 파일을 변경하지 않음
- 부분 수정: 해당 역할 스킬 2개, 후보 `하네스 Phase 4`
- 구조 재설계: 역할 팀과 기준 원천 전체 재검토, 후보 `하네스 Phase 0`부터 시작
- 사용자 결정 상태: `대기`

---

## 6. 관찰 분류와 후속 후보

관찰을 아래 축으로 분류하되 자동으로 변경하지 않는다.

### 입력 문서 관찰

- 예: 저장소 경로만 나열하고 사용자 흐름이나 실패 비용 근거가 없음
- 후보: `하네스 Phase 1`, `domain-analysis.md`, `qa-strategy.md`

### 역할 설계 관찰

- 예: 역할명이 추상적이거나 시작·조율·QA·감사 책임이 겹침
- 후보: `하네스 Phase 2`, `team-spec.md`, `harness-architecture.md`

### 역할 포인터와 생성 자산 관찰

- 예: agent/skill이 `team-spec` 역할 집합 또는 공통 출력 블록과 불일치
- 후보: `하네스 Phase 3` 또는 `하네스 Phase 4`

### 오케스트레이션과 로그 관찰

- 예: 다음 역할, 실패 흐름, 재개 조건 또는 최신 세션 정보가 서로 다름
- 후보: `하네스 Phase 5` 또는 `하네스 Phase 6`

### 보존 문서 호환성 관찰

- 예: 이전 역할명과 현재 역할명 사이의 매핑이나 우선 기준이 없음
- 후보: `하네스 Phase 5`, 관련 보존 문서와 호환성 메모

### 구조 전반 관찰

- 예: 입력 문서, `team-spec`, 생성 자산과 운영 문서가 서로 다른 역할 팀 구조를 설명함
- 후보: `하네스 Phase 0` 감사와 `하네스 Phase 2` 역할 팀 재설계

단일 타겟 관찰은 먼저 로컬 후보로 남긴다. 같은 계약 결함이 여러 타겟에서 반복되거나 생성기 계약 자체가 관찰을 수집하지 못할 때만 생성기 reference 보강 후보로 기록한다. 실제 반영은 사용자 확정 뒤 수행한다.

## 7. 다른 레퍼런스와의 연결

- `quality-evaluation-guide.md`: 사용자 판단을 위한 `with-skill` / `without-skill` 비교 자료를 준비할 때 사용한다.
- `evolution-contract.md`: 관찰을 로컬 보강과 생성기 환류 후보로 나눌 때 사용한다.
- `phase-selection-matrix.md`: 선택지와 연결된 후보 하네스 Phase를 설명할 때 사용한다.
- `verification-checklist.md`: 결정론적인 구조·계약 검증과 사용자 판단 자료 형식을 확인할 때 사용한다.
