# Verification Checklist

이 문서는 의존성 없는 하네스에서 운영 감사 역할이 확인할 최소 검증 기준과 사용자 판단 자료 형식을 정의한다.

예전 셸 검증기의 동작을 그대로 복제하려는 문서가 아니다. 목적은 역할 계약, 오케스트레이션, 보조 운영 문서, 로그가 실제로 맞물리는지 점검하는 데 있다.

## 핵심 전제

- 검증은 파일 존재 확인보다 역할 계약과 실행 흐름의 일관성 확인을 우선한다.
- 결정론적인 파일·필드·참조·테스트·계약 조건은 통과/실패로 기록하고, 그 밖의 항목은 관찰과 불확실성으로 분리한다.
- 운영 감사는 단순 문서 검사자가 아니라 메타시스템 감사자이지만 하네스 품질이나 운영 적합성의 최종 판정자는 아니다.
- `현재 유지 / 부분 수정 / 구조 재설계` 선택과 실제 변경 범위는 사용자가 확정한다.

## 1. 구조 검증

최소한 다음 구조가 필요하다.

- `AGENTS.md`
- `.codex/config.toml`
- `.codex/agents/`
- `.agents/skills/`
- `.harness/docs/`
- `.harness/logs/`
- `team-spec.md`
- `project-setup.md`
- `exploration-notes.md`
- `logging-policy.md`

필요한 하네스 Phase까지 진행됐다면 아래 문서도 검토한다.

- `domain-analysis.md`
- `qa-strategy.md`
- `harness-architecture.md`
- `orchestration-plan.md`
- `team-structure.md`
- `team-playbook.md`

## 2. 역할 계약 검증

- `team-spec.md`에 최종 역할 인벤토리가 있다.
- 최종 역할 인벤토리는 fenced `text` 블록이며, 헤더와 모든 역할 행이 같은 블록 안에 있다.
- 역할 행이 inline code로 흩어져 있으면 구조 계약 위반과 `하네스 Phase 2` 부분 수정 후보로 기록한다.
- 각 역할의 `agent_file`에 대응하는 `.codex/agents/*.toml`, `.agents/skills/*`가 존재한다.
- `.codex/config.toml`, `.codex/agents/*.toml`, `.agents/skills/*`가 `team-spec.md`의 역할 수, `agent_file`, description 기준과 어긋나지 않는다.
- `.codex/config.toml`에 `[agents] directory` 또는 `skills_directory`가 없고, 역할 연결은 `[agents.<role_id>] config_file` 형식을 따른다.
- `.codex/agents/*.toml`은 `model_reasoning_effort`, `sandbox_mode`를 사용하며 `reasoning`, `sandbox` 키를 사용하지 않는다.
- QA, 운영 감사, cross-check, 문서/구현/로그/정책 교차 검증, 하네스 정합성 검토 역할은 team-spec에서 `reasoning = high`이고 agent TOML에서 `model_reasoning_effort = "high"`로 매핑돼 있다.
- 일반 구현/문서/콘텐츠 역할과 시작 진입 역할은 특별한 복잡도 근거가 없으면 `reasoning = medium`으로 남아 있다.
- 모든 역할 스킬이 `team-spec.md`의 해당 `role_id` 섹션을 참조한다.
- 모든 역할 스킬이 `team-spec.md`의 공통 출력 블록을 따르도록 지시한다.
- `.codex/agents/*.toml`과 `.agents/skills/*/SKILL.md`에 역할별 우선 입력, 절차, 다음 역할, 종료 기준이 중복되어 있지 않다.
- description이 실제 요청에서 트리거될 만큼 구체적이다.
- 시작 진입 역할과 중심 조율 역할이 구분된다.
- 코드 수정 요청을 별도 역할에 위임하면, `run-harness`와 실제 코드 수정 역할이 구분되고 `run-harness`가 직접 수정하거나 모델을 임의 선택하지 않는다.
- 코드 수정 후보 역할마다 team-spec 역할 카드의 허용 변경 범위, 책임과 `role_id`/`agent_file`이 선언돼 있으며 `.codex/agents/<agent_file>.toml`, `.agents/skills/<agent_file>/SKILL.md`와 정확히 일치한다.
- agent TOML에서 확인한 `model`, `model_reasoning_effort`, `sandbox_mode`가 team-spec의 `model`, `reasoning`, `sandbox`와 대응하고, 라우팅 결과에 확인 가능한 값으로 남는다.
- `orchestration-plan.md`가 작업 설명, 대상 파일, 기준선, 변경 제약과 검증 기준을 handoff하고 재판단이나 확대를 금지한다.
- 라우팅 규칙이 정확히 하나의 후보만 선택하며 후보 0개/복수, role/agent/skill 불일치 또는 누락에서는 파일을 수정하지 않고 중단하도록 정의한다.
- QA 역할과 운영 감사 역할이 구분된다.
- 역할별 `우선 입력`에 등장하는 설계/정책/사양 문서가 모두 `설계 원천 우선순위` 또는 `설계 원천 인벤토리`에 포함돼 있다.
- `설계 원천 우선순위`에 없는 문서를 역할이 정책 판단 기준으로 사용하지 않는다.
- 역할의 목적, 책임, 주요 출력과 우선 입력 문서는 `team-spec-contract.md`의 정책·불변 조건에 맞고, 필수 구조·필드·형식은 `team-spec-schema.md`의 구조 검증을 통과한다.
- QA, 표현 계층, 정책성 책임처럼 추가 원천 선택이 필요한 역할이 있으면 해당 상세 기준의 보류/재진입 조건까지 충족한다.
- 우선 입력에 포함된 문서는 해당 역할의 판단이나 출력 근거로 설명 가능하다.
- 운영 로그, 세션 요약, 임시 산출물이 설계 원천 우선순위에 잘못 포함돼 있지 않다.
- 문서 간 충돌 시 어떤 문서를 우선해야 하는지 `team-spec.md`만 보고 판단할 수 있다.
- team-spec의 역할별 출력 규칙이 하네스 Phase, 제품/로드맵 Phase, 오해 가능한 한국어 기술 용어의 표기 기준을 포함한다.
- 생성된 문서와 로그에서 audit 뜻의 `감사`는 `감사(audit)` 또는 `감사(audit)를 수행한다`로 쓰고, 감사 인사로 오해될 수 있는 종결 표현은 피한다.

## 3. 보조 운영 문서 검증

- 보조 운영 문서가 역할 자산과 오케스트레이션을 대신하지 않는다.
- `exploration-notes.md`는 자동 판단 보류와 다음 확인 질문을 남기고, 최종 도메인 분석이나 역할 설계를 대신하지 않는다.
- `project-setup.md`는 사용자 입력, 초기 방향, 아직 확인되지 않은 전제를 정리하고, 저장소 재독해 결과나 팀 구조를 확정하지 않는다.
- `team-spec.md`는 역할 인벤토리, 책임 경계, 우선 입력, 출력, 다음 역할, 완료 기준의 단일 원천을 유지하고, 분석 보고서나 실행 로그가 되지 않는다.
- `logging-policy.md`는 세션 로그와 최신 요약을 남기는 방식을 설명하고, 개별 세션의 실제 진행 기록을 대신하지 않는다.
- `domain-analysis.md`는 저장소 근거, 도메인 경계, 핵심 흐름, 실패 비용을 설명하고 역할 목록이나 실행 순서를 반복하지 않는다.
- `qa-strategy.md`는 검증 범위, 위험 우선순위, 자동/수동 검증, 미실행 위험을 설명하고 역할 handoff 절차를 대신하지 않는다.
- `harness-architecture.md`는 팀 구조와 실행 패턴을 선택한 이유를 설명하고 역할별 상세 책임이나 운영 매뉴얼을 반복하지 않는다.
- `team-structure.md`는 역할 목록과 책임 경계를 설명하고 패턴 선택 이유나 실행 흐름을 길게 반복하지 않는다.
- `orchestration-plan.md`는 역할 순서, handoff, 정상/보류/실패/재진입 흐름을 설명하고 역할 설명서나 운영 매뉴얼을 대신하지 않는다.
- `orchestration-plan.md`가 코드 수정 선택 handoff의 역할 식별자, agent config path, local skill path, 실행 설정과 라우팅 근거를 전달한다.
- `team-playbook.md`는 실제 요청에서 팀을 어떻게 운용할지 설명하고 아키텍처 근거나 전체 역할 스펙을 다시 쓰지 않는다.
- 같은 내용이 여러 보조 운영 문서에 반복되어 있으면 해당 질문에 가장 직접 답하는 문서에만 남기고 나머지는 짧은 참조로 줄인다.
- 보존 문서에 이전 역할명이나 진입점이 남아 있으면 `orchestration-plan.md` 또는 `team-playbook.md`가 이전 역할명 -> 현재 역할명 매핑과 우선 기준을 설명한다.

## 4. 로그 검증

- `session-log.md`에 현재 세션의 진행과 종료가 남아 있다.
- `latest-session-summary.md`가 마지막 종료 세션 기준으로 갱신돼 있다.
- `logging-policy.md`가 세션 로그와 최신 요약을 어떻게 남길지 설명한다.
- 로그 정책이 별도 스크립트, TSV 이벤트 파일, 자동 append 도구를 필수 조건으로 삼지 않는다.
- 두 로그 문서가 같은 세션 ID를 기준으로 현재 작업을 설명한다.
- 최신 요약에 다음 시작 역할과 다음 하네스 재진입 Phase가 있다.
- 최신 요약에 다음 시작 전 우선 확인 입력 파일과 최근 출력 파일이 있다.
- `latest-session-summary.md`의 `남은 위험`이 다음 실행 판단에 직접 필요한 내용이다.
- `latest-session-summary.md`의 현재 하네스 Phase 또는 현재 제품/로드맵 Phase 문구가 로드맵 완료 상태를 과장하지 않는다.
- 하네스 생명주기 단계와 제품/로드맵 단계가 모두 `Phase N`으로만 적혀 있으면 문서 충돌 사실과 수정 후보를 기록한다.
- 한국어만으로 뜻이 모호한 기술 용어가 영어 병기 없이 반복되면 문서 충돌 후보와 영향을 기록한다.
- 현재 제품/로드맵 Phase의 로드맵 항목 중 실제 산출물 확인이 필요한 항목이 완료 근거 없이 남아 있지 않다.
- 절차 문서만 있는 항목을 실제 산출물 완료로 잘못 판정하지 않는다.
- 다음 제품/로드맵 Phase 진입 문구가 Phase 잔여 작업을 건너뛰게 만들지 않는다.
- 세션 환경 메모, 승인 이력, 일회성 권한 문제가 `latest-session-summary.md`에 섞여 있지 않다.
- 환경성 권한/승인 이슈가 있었다면 `session-log.md`에 기록돼 있다.
- `completed`, `timed_out`, `failed`가 subagent 작업 결과 상태일 뿐 실행 리소스 정리 완료가 아님을 로그 정책이 구분한다.
- 현재 오케스트레이션에서 발급된 subagent ID마다 결과·오류·timeout 보존과 소비 후, 다음 전이 또는 최종 응답 전에 `close_agent`를 호출하도록 오케스트레이션과 로그 정책이 정렬돼 있다.
- `close_agent` 성공 또는 `not_found`만 실행 리소스 정리 완료로 기록하고, `not_found`를 이유로 내부 상태 DB를 직접 수정하지 않는다.

세부 기준은 `logging-contract.md`를 따른다.

## 5. 재진입 검증

- 현재 관찰된 부분이 `하네스 Phase 1`~`하네스 Phase 7` 중 어느 후보와 연결되는지 설명할 수 있다.
- 재진입 사유가 저장소 입력, 역할 경계, 에이전트 정의, 역할 스킬, 오케스트레이션, 운영 감사, 피드백 반영 중 무엇인지 구분돼 있다.
- 최신 세션 요약에는 사용자 결정 전 후보와 결정 후 확정 재진입 정보를 구분해 반영한다.

세부 기준은 `reentry-rules.md`를 따른다.

## 6. 비교 관찰과 사용자 결정 준비

- 가능하면 `with-skill` 대비 `without-skill` 비교 관찰이 남아 있다.
- 시작 역할, 질문 수, 다음 역할 안내, 저장소 근거 연결, 검증 가능성의 관찰 가능한 차이를 설명할 수 있다.
- 운영 감사와 QA가 어느 결과가 더 낫다고 확정하지 않고 사용자가 비교할 원본 결과와 차이를 보존한다.
- `현재 유지 / 부분 수정 / 구조 재설계` 선택지마다 대상, 영향, 잔여 위험과 후보 하네스 Phase가 설명돼 있다.
- 사용자 결정 전 상태는 `사용자 결정 대기`이며, 하네스 Phase 7 파일 변경이 시작되지 않는다.

## 7. 자기진화성 검증

- 신규 구축 결과라면 `initial-generation-contract.md` 기준으로 초기 생성물만 읽어도 다음 시작 역할, 다음 하네스 재진입 Phase, 학습 후보 기록 위치를 알 수 있다.
- 역할 출력이나 로그에 새로 확인한 저장소 사실을 남길 위치가 있다.
- 코드 수정 라우팅이 중단되면 파일을 수정하지 않고 중단 근거와 다음 재진입 조건을 남긴다.
- 모든 역할 스킬이 `team-spec.md`의 해당 `role_id` 섹션을 참조한다. 누락된 역할이 있으면 계약 위반과 `하네스 Phase 4` 부분 수정 후보로 기록한다.
- 모든 역할 스킬이 `team-spec.md`의 공통 출력 블록을 따르도록 지시한다.
- `.codex/agents/*.toml`과 `.agents/skills/*/SKILL.md`가 역할 세부 기준을 별도 기준처럼 복제하면 drift 위험으로 기록한다.
- 학습 후보가 있으면 어느 하네스 Phase로 재진입하고 어느 문서/스킬에 반영할지 설명한다.
- 보존 문서, 운영 문서, 역할 스킬이 서로 다른 진입점이나 역할명을 말하면 충돌로 기록한다.
- 보존 문서 충돌이 있으면 원문을 임의로 덮어쓰기보다 호환성 메모, 하네스 재진입 Phase, 사용자 승인 필요 여부를 함께 남긴다.
- 반복될 수 있는 역할 오판, 검증 공백, 문서 충돌이 로컬 보강인지 생성기 환류 후보인지 분리돼 있다.
- 자기진화 루프가 별도 스크립트, 외부 서비스, 자동 프로젝트 재작성 도구에 의존하지 않는다.

세부 기준은 `evolution-contract.md`를 따른다.

## 8. 사용자 판단 자료 형식

운영 감사 결과는 최소한 아래 형식으로 남긴다. 결정론적인 검증의 통과/실패와 하네스 전체에 대한 사용자 판단을 혼동하지 않는다.

- 통과한 항목
- 실패한 계약과 관찰된 차이
- 확인할 수 없는 항목과 불확실성
- `현재 유지 / 부분 수정 / 구조 재설계` 선택지별 대상과 영향
- 후보 하네스 Phase
- 남은 위험
- 학습 후보와 승격 대상
- 사용자 결정 상태: `대기 / 현재 유지 / 부분 수정 / 구조 재설계`

운영 감사 역할과 QA 역할은 사용자 결정 상태를 임의로 채우거나 한 선택지를 최선으로 표시하지 않는다. 사용자 결정이 `부분 수정` 또는 `구조 재설계`로 확정된 경우에만 하네스 Phase 7이 해당 범위의 변경을 수행한다.

## 다른 레퍼런스와의 연결

- `team-spec-contract.md`: 역할 인벤토리의 권한·불변 조건·생성 순서와 파생 결과의 책임 관계를 검토할 때 쓴다.
- `team-spec-schema.md`: 역할 인벤토리와 역할 카드의 필수 구조·필드·형식·매핑을 검토할 때 쓴다.
- `initial-generation-contract.md`: 신규 구축 결과가 첫 세션부터 자기진화 루프를 갖췄는지 검토할 때 쓴다.
- `evolution-contract.md`: 자기진화 루프와 학습 후보 승격 기준을 검토할 때 쓴다.
- `logging-contract.md`: 로그 문서 기준을 검토할 때 쓴다.
- `reentry-rules.md`: 사용자에게 제시할 후보 하네스 Phase와 확정 후 재진입을 구분할 때 쓴다.
- `quality-evaluation-guide.md`: 사용자 판단을 위한 비교 관찰 자료를 정리할 때 쓴다.
