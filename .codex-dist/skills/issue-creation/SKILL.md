# Issue Creation

이 스킬은 사용자의 비정형 요청이나 Workflow Engine의 이슈 생성 작업을 GitHub 이슈 초안으로 정리한다. 초안 작성과 검증이 책임이며, 사용자 결정과 실제 GitHub 이슈 생성은 Workflow Engine의 후속 작업에서 처리한다.

## 먼저 읽을 문서

- `../github-agentic-loop/references/github-templates.md`
- `../github-agentic-loop/references/artifact-output-contract.md`에서 ``이슈 생성(`issue-creation`) 출력 판정 규칙`` 섹션만 읽는다.
- `../github-agentic-loop/references/artifact-handoff-contract.md`
- `../github-agentic-loop/artifact-manifests/issue-creation.json`

대상 저장소에 `.github/ISSUE_TEMPLATE/*.md`가 있으면 해당 파일을 실제 본문 형식의 단일 원천으로 먼저 읽는다. `github-templates.md`는 본문 복제본이 아니라 title prefix, label, 필수 섹션, 연결 규칙을 검증하는 계약 문서로 사용한다.

## 입력

- 사용자 요청 또는 Workflow Engine이 전달한 이슈 생성 작업
- 요청의 작업 내용, 판단 근거, 완료 기준과 연관 이슈
- 후속 이슈 초안이면 원본 이슈 번호와 본문
- 대상 저장소의 `.github/ISSUE_TEMPLATE/*.md`, `github-templates.md`, 이슈 유형별 라벨 상태

## 책임

1. 요청을 `기능제안`, `정책검토`, `기능변경`, `기능결함` 중 하나로 분류한다.
2. 대상 저장소의 실제 `.github` 이슈 템플릿 형식에 맞춰 본문 초안을 작성한다.
3. 제목 prefix, 이슈 유형별 라벨, 필수 섹션, 완료 기준, 연관 이슈를 `github-templates.md` 계약으로 검증한다.
4. 원본 이슈가 있으면 원본 이슈 본문을 후속 이슈 초안 작성 근거로 사용하고, 새 이슈의 `연관 이슈`에 원본 번호를 기록한다.
5. 정책검토 이슈는 정책 확정, 설계 문서 반영, 기능변경 전환 후속 작업을 기본 체크리스트로 작성한다.
6. 계약을 충족하지 못하면 생성 전 위험과 보류 질문을 정리한다.
7. 실제 GitHub 이슈 생성은 Workflow Engine이 확정한 구조화 실행 요청을 선택된 실행 주체가 수행한다.

## 출력

- 공통 handoff 계약의 닫힌 envelope만 반환한다.
- `artifact_type: issue-creation`을 사용하고 `artifact`는 `issue-creation.json` manifest에 맞춰 구성한다.
- 반환값은 GitHub 이슈 생성 요청이 아닌 사용자 검토용 초안이다. Markdown 표시는 runtime renderer가 담당한다.

## 하지 않는 일

- 이슈 생성, 라벨 생성, 기존 이슈 갱신, 체크리스트 변경 등 GitHub 상태를 변경하지 않는다.
- 이슈 유형, 사용자 결정, 현재 Workflow 상태를 최종 확정하거나 요청 범위를 넓히지 않는다.

## 사용자 결정

- 이슈 유형과 초안 내용은 추천 또는 후보로만 제시한다. 사용자의 선택이나 일반 진행 표현을 확정으로 해석하지 않는다.
- 초안 채택과 GitHub 이슈 생성 요청 확정은 `github-agentic-loop`가 사용자 결정과 전이 규칙으로 처리한다.

## 중단 조건

- 요청, 원본 이슈, 템플릿, 라벨 계약이 없거나 서로 충돌하면 이슈 초안을 확정하지 않는다.
- 요청한 이슈 유형의 범위 밖 정보나 GitHub 변경이 필요하면 구체적인 누락·충돌·범위 밖 사유와 필요한 입력 또는 정렬 조건을 `생성 전 확인해야 할 위험 또는 보류 질문`에 반환한다.

## 후속 전이

- 제어와 위 필수 출력 구조를 `github-agentic-loop`에 반환한다.
- Workflow Engine은 사용자 결정과 산출물 판정 규칙을 적용한 뒤에만 이슈 생성 요청 또는 다음 흐름을 확정한다.

## 분류 기준

- 아직 진행 여부를 판단해야 하는 요청은 `기능제안`이다.
- 설계, 정책, 운영 기준 결정이 필요한 요청은 `정책검토`다.
- 구현 범위와 완료 기준이 확정된 기능 추가 또는 수정은 `기능변경`이다.
- 결함, 회귀, 문서와 구현 불일치, 반영 누락은 `기능결함`이다.

## 초안 검증

- 이슈 본문에는 사용자가 확인할 작업 내용, 판단 근거, 완료 기준만 둔다.
- 실제 본문 heading, optional 표기, 기본 체크리스트 형식은 대상 저장소의 `.github/ISSUE_TEMPLATE/*.md`를 따른다.
- 대상 저장소의 `.github` 템플릿이 없거나 `github-templates.md` 계약과 불일치하면 차이, 영향 범위, 보류 질문을 출력한다.
- 라벨은 `github-templates.md`의 이슈 유형별 라벨 집합 안에서 이슈 유형에 맞는 라벨 하나만 사용한다.
- 이슈 유형별 라벨이 타겟 레포에 없으면 라벨 생성 절차를 대신 수행하지 않고, `repo-bootstrap` 설치 절차로 라벨을 생성해야 한다는 보류 질문을 출력한다.
- 기능제안의 완료 기준은 생성 시 비워 둔다. 진행 방향 판단 뒤 확정 방향에 맞는 종료 체크항목을 Workflow Engine이 추가한다.
- 기능변경의 완료 기준은 이슈를 종료해도 되는지 판단할 수 있는 체크리스트로 쓴다.
- 연관 이슈가 없으면 `N/A`로 둔다.
- 기능결함 이슈 생성 시 `원인과 해결 방향은 무엇인가요?`와 `완료 기준은 무엇인가요?`는 비워 둔다.
- 기능결함의 완료 기준은 결함 해결 계획 확정 뒤 해결 계획 반영 단계에서 해결 단위별 종료 조건으로 작성한다.
- 기능제안의 `판단 결과`는 생성 시 미체크 상태로 둔다.
- 기능제안의 `판단 근거`는 생성 시 비워 둔다.
- 정책검토의 `검토 결과`는 생성 시 비워 둔다.
- 기능제안에서 정책검토 또는 기능변경으로 전환할 때는 원본 기능제안 이슈 본문의 `무엇을 제안하나요?`, `왜 필요한가요?`, `현재 상태는 어떤가요?`, `판단 결과`, `판단 근거`를 참고하여 후속 이슈 초안을 작성한다.

## 정책검토 후속 작업 규칙

- 정책검토 이슈는 `정책 검토 결과 확정`, `결정된 정책을 관련 설계 문서에 반영`, `기능 변경 이슈로 전환` 항목을 기본 후속 작업으로 둔다.
- 후속 작업 체크항목에는 해당 후속 작업의 완료 산출물인 이슈 번호 또는 PR 번호를 `(#번호)` 형식으로 붙일 수 있다.

## Structured artifact handoff

의미 내용은 위 분류·템플릿 검증 기준에 따라 작성하고, 기계 구조는 `issue-creation.json`만 따른다. envelope 밖의 설명이나 직접 조립한 Markdown을 반환하지 않는다.
