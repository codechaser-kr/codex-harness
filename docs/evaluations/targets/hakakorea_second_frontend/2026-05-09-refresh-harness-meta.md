## 현재 판정

판정: `재작성 필요`

역할 집합 정렬은 대체로 성공했다. `team-spec`, `.codex/config.toml`, agent, skill 파일이 같은 역할명을 말하고, 시작 진입 역할과 중심 조율 역할도 분리돼 있다.

다만 자기진화형 하네스로 보기는 아직 이르다. 실제 작업에서 확인한 새 사실이나 반복되는 검증 공백을 어느 문서와 역할 스킬로 승격할지 충분히 고정하지 못했다. 생성 결과는 운영 가능한 골격에 가깝고, 작업을 반복하며 스스로 나아지는 구조는 약하다.

## 가장 약한 축

### 1. 학습 후보 수집 위치가 약함

로그에는 다음 시작 역할과 재진입 Phase가 남아 있지만, 작업 중 새로 확인한 저장소 사실이나 반복될 수 있는 판단을 별도 학습 후보로 남기는 구조가 약했다.

필요한 보강:

- `latest-session-summary.md`에 학습 후보, 반복 신호, 승격 대상, 생성기 환류 후보를 남긴다.
- 각 역할 스킬 출력 형식에 새 저장소 사실과 하네스 갱신 후보를 포함한다.

### 2. 보존 문서와 새 운영 모델의 충돌

새 운영 기준은 `run-harness`를 시작 진입 역할로 둔다. 반면 보존된 Markdown editor 문서 일부는 여전히 `delivery-orchestrator`를 시작 역할로 적고 있었다.

필요한 보강:

- 보존 문서를 역사적 기록으로 둘지, 현재 운영 메타데이터로 갱신할지 기준을 둔다.
- 운영 감사 역할이 보존 문서의 역할명과 현재 `team-spec`의 역할명이 충돌하는지 확인한다.

### 3. QA 전략의 운영 계약이 얕음

`qa-strategy.md`는 검증 방향을 제시하지만, 변경 유형별 필수/선택 기준과 미실행 위험의 승격 기준이 충분히 구체적이지 않았다.

필요한 보강:

- 웹, 공용 UI, 데스크톱, Markdown editor 변경별 검증 우선순위를 분리한다.
- 실행하지 못한 검증이 다음 역할이나 재진입 Phase로 어떻게 이어지는지 적는다.

## 타겟 로컬 보강 후보

- `team-spec.md`: 각 역할에 학습 후보 기록 규칙과 승격 대상 기준을 추가한다.
- `.codex/skills/*/SKILL.md`: 출력 형식에 `새로 확인한 저장소 사실`, `반복될 수 있는 판단`, `하네스 갱신 후보`, `승격 대상`을 넣는다.
- `.harness/docs/orchestration-plan.md`: 보존 문서 충돌을 처리하는 흐름을 추가한다.
- `.harness/docs/qa-strategy.md`: 변경 유형별 검증 계약과 미실행 위험 승격 기준을 보강한다.
- `.harness/logs/latest-session-summary.md`: 다음 시작 정보뿐 아니라 학습 후보와 생성기 환류 후보를 남긴다.

## 생성기 환류 후보

이번 평가는 단일 타겟 프로젝트 관찰이다. 따라서 곧바로 범용 생성기 규칙으로 일반화하지 않는다.

다만 아래 항목은 다른 타겟 프로젝트에서도 반복되면 생성기 reference 보강 후보로 승격한다.

- 생성된 역할 스킬이 `team-spec`보다 얕아지는 문제
- 로그가 다음 재진입 정보만 남기고 학습 후보를 남기지 않는 문제
- 보존 문서와 새 하네스 역할 모델이 충돌하는 문제
- QA 전략이 세션 결과 보고로 남고 운영 계약으로 발전하지 못하는 문제

이 관찰은 이후 `evolution-contract.md`, `team-spec-contract.md`, `skill-writing-guide.md`, `logging-contract.md`, `verification-checklist.md` 보강으로 연결됐다.

## 재검토 메모

2026-05-09 재검토에서는 같은 브랜치의 생성 결과를 다시 읽었다. 구조 정렬은 여전히 괜찮지만, 생성기 계약으로 막아야 할 결함이 더 구체적으로 드러났다.

- `.codex/skills/*/SKILL.md` 전체에서 공통 학습 출력 블록이 빠져 있었다. `team-spec.md`에 학습 후보 관련 설명이 일부 있어도, 실제 역할 스킬 출력 형식에 없으면 다음 실행에서 누락될 가능성이 높다.
- `.harness/docs/logging-policy.md`가 삭제되어 있었다. 이전 문서에 스크립트 기반 내용이 섞여 있었더라도, 스크립트 없는 Markdown 로그 정책 문서 자체는 초기 생성물에 남아야 한다.
- `latest-session-summary.md`에는 다음 시작 역할과 재진입 Phase가 있었지만, 학습 후보, 반복 신호, 승격 대상, 생성기 환류 후보 필드가 없었다.

이 재검토 결과는 생성기 쪽에서 두 가지 회귀 기준으로 반영했다.

- 모든 역할 스킬 출력 형식에 공통 학습 출력 블록이 없으면 `Phase 4` 재작성 대상으로 본다.
- `logging-policy.md`가 없거나 스크립트/TSV 자동화를 필수 조건처럼 설명하면 로그 계약을 통과하지 못한 것으로 본다.

## 다음 재진입 Phase

- 우선 재진입: `Phase 4`
- 함께 볼 Phase: `Phase 5`, `Phase 6`

이유:

- 역할 스킬 출력 형식이 학습 후보를 충분히 담지 못하므로 `Phase 4`가 우선이다.
- 오케스트레이션과 로그가 학습 후보를 다음 실행 입력으로 연결해야 하므로 `Phase 5`도 함께 본다.
- 운영 감사가 자기진화성을 확인해야 하므로 `Phase 6` 기준도 보강한다.
