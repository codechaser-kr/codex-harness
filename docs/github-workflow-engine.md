# GitHub Workflow Engine 설계

이 문서는 `codex-harness`가 GitHub Issue와 Pull Request를 기준으로 작업 상태를 읽고 다음 작업을 결정하기 위한 설계 기준이다.

이 문서는 사람이 읽는 운영 설명서이면서 Agent가 따라야 하는 실행 프롬프트(prompt) 원천이다. 현재 GitHub Workflow Engine 설계 원천은 이 문서이며, 과거 이슈의 결정 기록은 이 문서에 반영된 뒤 별도 원천으로 취급하지 않는다. Workflow Engine은 GitHub 실행 상태를 읽고, 상태 근거를 분류한 뒤, 다음 작업 결정 규칙에 따라 현재 작업과 사용자 결정 필요 여부를 산출한다.

모든 규칙은 다음 질문에 답할 수 있어야 한다.

- 어떤 이슈 또는 PR을 기준 대상으로 삼아야 하는가
- 다음 작업을 판단하기 위해 기준 대상의 어떤 체크리스트, PR, 리뷰, 댓글 상태를 읽어야 하는가
- 읽은 상태에서 완료 근거, 미완료 근거, 보조 근거, 무효 근거는 무엇인가
- 어떤 다음 작업 결정 규칙을 적용해야 하며, 현재 작업은 무엇인가
- 어떤 스킬을 호출하고 어떤 구조의 출력을 받아야 하는가
- 현재 작업에 사용자 결정이 필요한가, 필요하다면 무엇을 결정해야 하는가
- 어떤 GitHub 상태 또는 파일 상태를 어느 범위까지 변경해도 되는가

## 설계 목표

- GitHub 이슈와 PR을 프로젝트 작업 상태의 기준 상태 원천으로 사용한다.
- 사람이 보는 작업 상태와 Agent가 읽는 작업 상태를 일치시킨다.
- 상태 전이는 언어 모델의 자유 판단이 아니라 문서에 정의한 규칙을 따른다.
- 정책 판단, 설계 변경, 커밋 메시지 확정, PR merge처럼 사용자 결정이 필요한 작업은 사용자 결정을 거친다.
- 하나의 작업을 끝낸 뒤 사용자 결정, 중단, 오류, 완료 조건 중 하나에 닿을 때까지 다음 작업 판단을 이어간다.
- 이슈 초안 작성과 실제 GitHub 상태 변경을 분리한다.
- 확정된 실행 범위 안의 파일 작성과 수정은 Codex가 수행하고, PR 리뷰 생성은 선택된 리뷰 실행 모드가 수행한다.
- GitHub Workflow Engine의 설계 문서, 템플릿, 배포본 스킬 기본형은 `codex-harness`에서 관리하고 타겟 레포에 적용한다.

## 핵심 개념

이 섹션은 Workflow Engine이 현재 작업을 산출하고 실행 여부를 판단할 때 사용하는 기본 용어를 정의한다. 용어는 상태 원천, 근거 분류, 이슈 유형, 작업 결정 규칙, 현재 작업과 진행 판단, 사용자 결정, 실행 범위 순서로 이어진다.

### GitHub 실행 상태

GitHub 실행 상태는 Workflow Engine이 현재 작업 상태를 판단하기 위해 GitHub에서 읽는 상태 값이다. 별도 로컬 상태 파일은 기준 상태 원천으로 사용하지 않는다. PR 리뷰 피드백 상태는 diff가 있는 review thread의 resolved/unresolved 상태를 우선 원천으로 읽고, marker가 있는 PR issue comment는 diff 위치로 추적할 수 없는 요약 피드백의 보조 상태 원천으로만 읽는다.

| 상태 원천                   | 역할                                                            |
| --------------------------- | --------------------------------------------------------------- |
| Issue title                 | 이슈 유형과 작업 주제를 식별한다.                               |
| Issue label                 | `기능제안`, `정책검토`, `기능변경`, `기능결함` 유형을 식별한다. |
| Issue body                  | 구조화된 섹션에서 판단 근거, 범위, `완료 기준은 무엇인가요?`, `후속 작업은 무엇인가요?` 후보를 읽는다. |
| Issue checklist             | `완료 기준은 무엇인가요?`와 정책 반영 상태를 읽는다.             |
| Issue state                 | 작업이 열려 있는지 닫혔는지 읽는다.                             |
| Pull Request body           | 변경 이유, 영향 범위, `연관 이슈 (optional)` 섹션의 이슈 번호를 읽는다. |
| Pull Request state          | open, closed, merged 여부를 읽는다.                              |
| Pull Request review threads | diff가 있는 리뷰 피드백과 review thread의 resolved/unresolved 상태를 우선 상태 원천으로 읽는다. |
| Pull Request issue comments | diff 위치로 추적할 수 없는 marker 요약 피드백의 체크 상태만 보조 상태 원천으로 읽고, marker가 없는 일반 PR comment는 상태 전이 근거로 쓰지 않는다. |

### 상태 근거 묶음

상태 근거 묶음은 GitHub 실행 상태와 현재 코드 상태, 보조 로그에서 읽은 근거를 다음 네 묶음으로 분류한 결과다.

| 묶음        | 포함할 수 있는 근거                                                                            |
| ----------- | ---------------------------------------------------------------------------------------------- |
| 완료 근거   | 체크된 완료 조건, merged PR, resolved review thread, diff 위치로 추적할 수 없는 요약 피드백의 체크 상태 |
| 미완료 근거 | 체크되지 않은 완료 조건, merged가 아닌 연결 PR, unresolved review thread, diff 위치로 추적할 수 없는 요약 피드백의 미체크 상태 |
| 보조 근거   | 현재 코드 상태, 보조 로그, 현재 대화에서 확인한 마지막 관련 작업, 마지막 사용자 결정, 마지막 실행 결과 |
| 무효 근거   | 이슈 본문의 일반 설명, 추천 문장, 선택되지 않은 후보, 구조화된 스킬 출력 필드 밖의 설명 문장 |

완료 근거와 미완료 근거는 GitHub 실행 상태에서 읽는다. 보조 근거는 GitHub 실행 상태로 표현되지 않는 중간 실행 상태를 판단할 때만 사용하며, 현재 작업 확정 근거로 단독 사용하지 않는다. 보조 근거가 완료 근거 또는 미완료 근거와 충돌하면 GitHub 실행 상태를 우선한다.

### 이슈 유형

| 유형       | 목적                                                                                         | 가능한 다음 흐름                            |
| ---------- | -------------------------------------------------------------------------------------------- | ------------------------------------------- |
| `기능제안` | 구현 여부와 처리 유형이 아직 확정되지 않은 기능 추가, 기능 수정, 운영 흐름 개선 요청을 판단한다. | 종료, 정책검토 전환, 기능변경 전환          |
| `정책검토` | 설계, 정책, 운영 기준의 결정을 추적하고 설계 원천 반영 여부를 판단한다.                      | 설계 문서 반영, 기능변경 전환, 기능결함 반영 |
| `기능변경` | 확정된 변경 계획에 따라 코드, 문서, 템플릿, 스킬 같은 실행 산출물을 변경한다.                | 변경 계획, 구현 흐름                        |
| `기능결함` | 원인을 확정하고 정책 또는 설계 변경 필요 여부를 판단한 뒤 해결 흐름을 선택한다.              | 원인 조사, 정책검토 전환, 결함 해결 계획    |

라벨을 이슈 유형의 1차 기준으로 삼는다. 제목 prefix와 라벨이 충돌하거나, 유형 라벨이 없거나, 유형 라벨이 둘 이상이면 사용자 결정으로 넘기고 임의 변경하지 않는다.

### 다음 작업 결정 규칙

다음 작업 결정 규칙은 상태 근거 묶음과 조건을 대입해 현재 조건에서 다룰 작업을 산출하는 규칙이다.

| 필드           | 의미                                                                           |
| -------------- | ------------------------------------------------------------------------------ |
| 작업 이름      | 해당 작업을 식별하는 이름                                                      |
| 현재 상태      | 다음 작업 판단에 필요한 GitHub 실행 상태의 요약                                |
| 조건           | 이전 작업에서 이 작업으로 넘어올 수 있는 객관적 완료 근거 또는 확인 결과       |
| 작업 내용      | 수행 주체와 수행 내용                                                          |
| 사용자 결정    | 사용자가 결정해야 하는 대상과 선택 가능한 응답                                 |
| 상태 반영 지침 | GitHub 상태와 보조 로그에 무엇을 반영하는지                                    |

다음 작업 결정 규칙은 자동 실행 명령이 아니다. 사용자 결정이 필요한 작업은 현재 작업으로 산출할 수 있지만, 사용자 결정 전에는 실행하거나 상태에 반영하지 않는다.

### 현재 작업과 진행 판단

현재 작업은 상태 근거 묶음이 다음 작업 결정 규칙의 조건을 만족할 때 산출되는 하나의 작업이다. 조건을 만족하는 작업이 없으면 정보 부족으로 중단하고, 둘 이상이면 상태 충돌로 중단한다.

진행 판단은 현재 작업을 어떻게 처리할지 나타내는 값이며, 현재 작업에 대해 하나만 선택한다.

| 값          | 의미                                                              |
| ----------- | ----------------------------------------------------------------- |
| 사용자 결정 | 사용자가 결정해야 하는 대상과 선택 가능한 응답을 제시하고 멈춘다. |
| 자동 실행   | 사용자 결정, 중단, 완료 조건이 없을 때 실행 범위 안에서 현재 작업을 수행한다. |
| 중단        | 정보 부족, 의존성 누락, 실행 오류, 상태 충돌을 제시하고 멈춘다.   |
| 완료        | 기준 대상의 완료 조건이 충족되었음을 제시하고 후속 작업을 산출하지 않는다. |

Workflow Engine은 하나의 작업을 완료하면 즉시 GitHub 실행 상태와 현재 코드 상태를 다시 읽고, 다음 작업과 진행 판단을 산출한다. 진행 판단이 `자동 실행`이면 다음 작업을 실행하고, `사용자 결정`, `중단`, `완료`이면 해당 판단에 따라 멈추거나 종료한다. 이 기준은 사용자가 “다음 절차가 무엇인가요?”라고 다시 물어야만 흐름이 이어지는 상황을 막기 위한 규칙이다.

### 사용자 결정

사용자 결정은 사용자가 선택하거나 확정해야 하며 Workflow Engine이나 Agent가 임의로 넘길 수 없는 지점이다.

Workflow Engine이 사용자 결정을 요청할 때는 결정 대상과 선택 가능한 응답을 번호 목록으로 함께 제시한다. 선택 가능한 응답은 현재 작업의 사용자 결정 필드에서 허용한 응답을 기준으로 하며, 사용자가 다른 의견을 제시할 수 있도록 `기타 의견 입력`을 항상 마지막 번호 항목에 포함한다. `기타 의견 입력`은 번호 목록 밖의 별도 문장으로 제시하지 않는다. 상태 변경을 수행하는 선택지는 변경 대상과 실행 결과를 함께 표시한다.

사용자 결정의 유효 입력 형식은 다음 네 가지다.

- 제시된 번호
- 선택지 문구 그대로
- `기타 의견 입력 항목 번호: 의견`
- `기타 의견 입력: 의견`

사용자가 제시된 번호 또는 선택지 문구를 그대로 입력하면 Workflow Engine은 해당 선택지를 사용자 결정으로 처리한다. 사용자가 `기타 의견 입력` 허용 형식으로 구체 의견을 입력하면 Workflow Engine은 그 의견을 사용자 결정으로 처리한다. 구체 의견이 현재 사용자 결정 대상에 속하고, 실행 범위 안에 있으며, 상태 반영 지침으로 처리할 수 있으면 해당 지침에 따라 진행한다. 세 조건 중 하나라도 만족하지 않으면 GitHub 상태를 변경하지 않고 중단 사유와 재개 조건을 제시한다.

사용자가 `기타 의견 입력` 항목의 번호만 입력했거나 `기타 의견 입력` 문구만 입력하면 Workflow Engine은 기타 의견이 비어 있다고 보고 같은 선택지와 입력 예시를 다시 제시한다. 사용자 입력이 유효 입력 형식 중 어느 것에도 해당하지 않으면 Workflow Engine은 임의로 해석하지 않고 결정 대상을 다시 요약한 뒤 같은 선택지를 번호 목록으로 다시 제시한다. 이때 입력 예시는 번호 입력, 선택지 문구 입력, `기타 의견 입력` 형식을 모두 포함한다. `이대로 진행`, `생성해주세요`, `좋습니다`, `네` 같은 일반 진행 표현은 선택지 문구와 정확히 일치하지 않으면 유효 입력으로 보지 않는다.

예시:

1. 선택지1
2. 선택지2
3. 기타 의견 입력

입력 예시:

- 번호 입력: `1`
- 선택지 문구 입력: `선택지1`
- 기타 의견 입력: `3: 의견 내용` 또는 `기타 의견 입력: 의견 내용`

사용자 결정 대상은 워크플로우 전이 작업표의 `사용자 결정` 필드가 단일 원천이다. 해당 필드가 `없음`이면 사용자 결정 없이 실행 범위 안에서 진행하고, `없음`이 아니면 그 필드에 적힌 결정 대상을 번호 목록으로 제시한다.

작업표 밖에서 사용자 결정이 필요해지면 먼저 해당 흐름의 작업표에 사용자 결정 필드를 추가하거나 기존 작업의 사용자 결정 필드를 갱신한 뒤 적용한다.

사용자에게 보이는 응답에서는 내부 운영 절차를 과하게 드러내지 않는다.

리뷰 피드백 대응 방향은 사용자 결정의 한 종류이므로 같은 입력 규칙을 적용한다. 이때 선택 가능한 응답은 `수용`, `거절`, `기타 의견 입력`이다. 권장 대응은 기본값이 아니라 제안이며, 사용자 응답이 유효 입력 형식 중 어느 것에도 해당하지 않으면 Workflow Engine은 파일 수정이나 댓글 처리로 넘어가지 않고 대응 방향의 결정 대상, 선택지, 입력 예시를 다시 제시한다.

### 실행 범위

실행 범위는 현재 작업에서 변경할 수 있는 대상의 한계이며, 현재 작업의 작업 내용, 사용자 결정, 상태 반영 지침에서 산출한다.

실행 범위에는 변경할 수 있는 GitHub 상태, 파일 또는 디렉터리, 댓글 또는 review thread, 브랜치, 커밋, PR 생성 여부를 포함한다. 실행 범위에 포함되지 않은 대상은 변경하지 않는다.

전용 스킬은 후보, 초안, 분석 결과만 만든다. Workflow Engine은 확정된 현재 작업의 실행 범위 안에서만 실제 변경을 수행한다.

사용자 요청이나 전용 스킬 출력이 실행 범위를 벗어나면 Workflow Engine은 상태를 변경하지 않고 중단 사유와 재개 조건을 제시한다.

## 실행 모델

이 섹션은 Workflow Engine이 사용자 요청을 처리할 때 따르는 실행 순서와 명령 실행 기준을 정의한다. 모든 하위 스킬은 이 실행 모델 안에서 후보, 초안, 분석 결과만 만들고, 상태 전이와 쓰기 작업은 Workflow Engine이 확정한 현재 작업과 실행 범위 안에서만 수행한다.

### 공통 실행 골격

Workflow Engine은 사용자 요청을 그대로 실행 명령으로 보지 않는다. 먼저 GitHub 실행 상태와 현재 코드 상태를 읽고 다음 값을 산출한 뒤 실행 여부를 판단한다.

| 산출 값        | 의미                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------ |
| 기준 대상      | 현재 전이를 판단할 이슈 또는 PR                                                            |
| 상태 근거 묶음 | GitHub 실행 상태, 현재 코드 상태, 보조 로그에서 읽은 완료 근거, 미완료 근거, 보조 근거, 무효 근거 |
| 현재 작업      | 다음 작업 결정 규칙에서 현재 조건을 만족하는 하나의 작업                                   |
| 진행 판단      | `사용자 결정`, `자동 실행`, `중단`, `완료` 중 현재 작업의 처리 방식을 나타내는 값           |
| 실행 범위      | 현재 작업에서 변경할 수 있는 GitHub 상태, 파일 또는 디렉터리, 댓글 또는 review thread, 브랜치, 커밋, PR 생성 여부 |

사용자 요청은 산출 값의 입력일 뿐이며 다음 작업 결정 규칙이나 사용자 결정을 대체하지 않는다. Workflow Engine은 다섯 값을 하나로 확정한 뒤에만 파일 수정, GitHub 상태 변경, 브랜치 전환, 커밋, PR 생성을 수행한다. 값을 확정할 근거가 부족하거나 충돌하면 쓰기 작업을 하지 않고 중단 사유와 재개 조건을 제시한다.

### 기본 진행 순서

Workflow Engine은 모든 이슈 유형과 연결 PR에 같은 실행 루프를 적용한다.

1. 기준 대상을 정한다.
   - 열린 PR 중 unresolved review thread, 미체크 marker 요약 피드백, merge 대기 상태가 있으면 먼저 처리한다.
   - 이어갈 수 있는 열린 이슈가 있으면 새 작업보다 우선한다.
2. 상태 근거 묶음을 만든다.
   - GitHub 이슈/PR 상태와 현재 코드 상태를 읽는다.
   - GitHub 실행 상태로 표현되지 않는 중간 실행 상태만 보조 로그로 확인한다.
3. 현재 작업을 산출한다.
   - 상태 근거 묶음을 기준 대상 유형의 다음 작업 결정 규칙에 대입한다.
   - 조건을 만족하는 작업이 없으면 정보 부족으로 중단한다.
   - 조건을 만족하는 작업이 둘 이상이면 상태 충돌로 중단한다.
   - 조건을 만족하는 작업이 하나이면 현재 작업으로 확정한다.
4. 진행 판단을 판정한다.
   - 진행 판단이 `사용자 결정`이면 결정 대상과 선택 가능한 응답을 제시하고 멈춘다.
   - 진행 판단이 `자동 실행`이면 실행 범위 안에서 현재 작업을 수행한다.
   - 진행 판단이 `중단`이면 중단 사유와 재개 조건을 제시하고 멈춘다.
   - 진행 판단이 `완료`이면 완료 근거를 제시하고 루프를 종료한다.
5. 실행 범위 안에서만 실행한다.
   - 전용 스킬은 후보, 초안, 분석 결과만 만든다.
   - GitHub 상태 변경, 파일 변경, 브랜치 전환, 커밋, PR 생성은 현재 작업의 상태 반영 지침과 실행 범위 안에서만 수행한다.
6. 작업이 끝나면 다시 GitHub 실행 상태와 현재 코드 상태를 읽고 1번부터 반복한다.

이 루프는 진행 판단이 `자동 실행`인 동안 반복한다. `사용자 결정`, `중단`, `완료`가 산출되면 해당 판단에 따라 멈추거나 종료한다.

### 현재 단계 산출 절차

현재 단계 산출 절차는 `기본 진행 순서`의 상태 근거 묶음 생성과 현재 작업 산출 단계에서 수행하는 세부 절차다. 기준 대상의 상태를 `완료 근거`, `미완료 근거`, `보조 근거`, `무효 근거`로 분류하고, 분류 결과를 현재 작업 산출 입력으로 사용한다.

근거 분류 규칙:

1. 완료 근거와 미완료 근거는 GitHub 실행 상태에서만 읽는다.
2. 보조 근거는 GitHub 실행 상태로 표현되지 않는 중간 실행 상태를 판단할 때만 사용한다.
3. 보조 근거가 완료 근거 또는 미완료 근거와 충돌하면 GitHub 실행 상태를 우선한다.
4. 무효 근거는 배경 설명으로만 참고하고 현재 작업의 확정 근거로 쓰지 않는다.
5. 완료 근거, 미완료 근거, 보조 근거만으로 현재 작업을 하나로 산출할 수 없으면 추론하지 않고 정보 부족 또는 상태 충돌로 중단한다.

### 명령 실행 경로 선택

Workflow Engine은 명령을 실행하기 전에 일반 경로와 권한 확인 경로 중 하나로 분류한다. 일반 경로는 현재 권한 안에서 실행할 수 있고 상태를 변경하지 않는 읽기, 조회, 로컬 검증 명령이다. 권한 확인 경로는 권한 상승, 원격 접근, GitHub 상태 변경, `.git` 쓰기, 파일 수정 또는 삭제 가능성이 있어 실행 전 사용자 의도 확인이 필요한 명령이다.

실행 경로 선택은 명령 호출 권한을 정하는 절차이며, 현재 작업, 실행 범위, 사용자 결정을 대체하지 않는다. 사용자 결정이 필요한 상태 변경, 커밋 메시지 확정, PR merge는 권한 확인 경로를 쓰더라도 사용자 결정 규칙을 따라야 한다.

권한 확인 경로로 분류하는 명령:

- `gh pr comment`, `gh pr review`, `gh pr merge`, `gh issue edit`, `gh api --method POST|PATCH|PUT|DELETE`처럼 GitHub PR, issue, review, checks, comment 상태를 바꾸는 GitHub API 계열 명령
- `git push`, `git fetch`, `git pull`, `git ls-remote`처럼 네트워크나 원격 저장소 접근이 필요한 Git 명령
- `git commit`, `git tag`, `git merge`, `git rebase`처럼 `.git` 쓰기가 필요한 명령
- `sed -i`, `find -delete`, 쓰기나 삭제를 수행하는 `find -exec`처럼 로컬 파일을 수정하거나 삭제하는 명령

일반 경로로 분류하는 명령:

- `gh pr view`, `gh issue view`, `gh pr checks`, `gh api` GET 조회처럼 GitHub 실행 상태를 읽기만 하는 명령
- `git status`, `git diff`, `git log`, `git show`, `rg`, 출력 또는 파이프 변환용 `sed`, `ls`, 탐색 전용 `find`, `wc`처럼 로컬 파일이나 로컬 Git 상태를 읽는 명령
- `git diff --check`처럼 로컬 변경사항만 검증하는 명령

파괴적 명령은 실행 경로와 별도로 판단한다. `rm`, `git reset --hard`, `git clean`, 강제 push처럼 되돌리기 어렵거나 사용자 변경을 잃게 할 수 있는 명령은 현재 작업의 실행 범위 안에 있고 사용자 의도가 명확할 때만 실행한다.

## 워크플로우 전이

이 섹션의 각 작업표에서 `조건`은 이전 작업에서 해당 작업으로 넘어올 수 있는 객관적 완료 근거 또는 확인 결과만 적는다. `사용자 결정`은 현재 작업에서 사용자가 확정해야 하는 결정 대상만 적고, 결정이 필요 없으면 `없음`으로 적는다.

### 다음 계획 요청

다음 계획 요청은 새 작업 생성 명령이 아니다. Workflow Engine은 GitHub 실행 상태를 다시 읽고, 기존 PR 또는 이슈에서 이어갈 작업이 있는지 먼저 판단한다. 이어갈 작업이 없을 때만 새 기능제안 후보 생성을 검토한다.

판단 순서는 다음과 같다.

1. merge 대기 PR
2. 리뷰 대응이 남은 PR
3. 그 밖의 진행 중 PR
4. 열린 기능변경 또는 기능결함 이슈
5. 열린 정책검토 이슈
6. 열린 기능제안 이슈
7. 새 기능제안 후보

이어갈 작업이 있으면 새 계획 후보를 만들지 않고 현재 상태, 남은 작업, 다음 작업 결정 규칙에서 현재 조건을 만족하는 작업을 제시한다.

### 기능제안 흐름

기능제안 흐름은 비정형 기능 요청을 GitHub 이슈로 정리하고, 진행하지 않음, 정책검토 필요, 기능변경 필요 중 하나로 판단하는 흐름이다. 기능제안 이슈 자체에서는 설계 결정이나 구현을 진행하지 않는다.

| 작업               | 조건                                    | 사용자 결정                                    | 상태 반영                                                                 |
| ------------------ | --------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------- |
| 기능제안 초안 작성 | 사용자 요청이 새 기능제안으로 분류됨    | 기능제안 이슈 초안 확정                        | Issue Creation Skill이 타겟 템플릿 형식으로 초안을 작성한다.              |
| 기능제안 이슈 생성 | 기능제안 이슈 초안 확정                 | 없음                                           | 확정된 초안 그대로 GitHub 이슈를 생성한다.                                |
| 진행 방향 판단     | 생성된 기능제안 이슈의 `판단 결과` 미확정 | 진행하지 않음 / 정책검토 필요 / 기능변경 필요 | 선택된 판단 결과와 근거를 기능제안 이슈 본문에 반영한다.                  |
| 미진행 반영        | 진행 방향 판단 결과가 진행하지 않음으로 확정됨 | 없음                                     | 기능제안 이슈의 `완료 기준은 무엇인가요?`를 체크하고 종료한다.             |
| 정책검토 전환      | 진행 방향 판단 결과가 정책검토 필요로 확정됨 | 정책검토 이슈 초안 확정                   | 새 정책검토 이슈 본문의 `연관 이슈`에 기능제안 번호를 반영하고, 기능제안 이슈의 `완료 기준은 무엇인가요?`를 체크한 뒤 종료한다. |
| 기능변경 전환      | 진행 방향 판단 결과가 기능변경 필요로 확정됨 | 기능변경 이슈 초안 확정                   | 새 기능변경 이슈 본문의 `연관 이슈`에 기능제안 번호를 반영하고, 기능제안 이슈의 `완료 기준은 무엇인가요?`를 체크한 뒤 종료한다. |

### 정책검토 흐름

정책검토 흐름은 정책 또는 설계 기준을 결정하고, 결정된 내용을 설계 문서와 관련 이슈에 반영할지를 정하는 흐름이다. 정책검토 이슈 자체에서는 실행 산출물을 직접 수정하지 않는다.

정책검토 이슈의 출발점은 `연관 이슈`와 정책검토 이슈를 만든 전환 작업으로 판단한다. `연관 이슈`가 없으면 단독 시작으로 본다. 출발점, `검토 결과`, `설계 문서 구현 완료` 상태를 아래 표의 조건에 대입해 다음 작업을 결정한다.

| 작업                    | 조건                                                                       | 사용자 결정               | 상태 반영                                                                 |
| ----------------------- | -------------------------------------------------------------------------- | ------------------------- | ------------------------------------------------------------------------- |
| 정책검토 초안 작성      | 사용자 요청 또는 상위 흐름에서 정책 또는 설계 판단 필요가 확정됨           | 정책검토 이슈 초안 확정   | Issue Creation Skill이 정책검토 템플릿 형식으로 초안을 작성한다.          |
| 정책검토 이슈 생성      | 정책검토 이슈 초안 확정                                                    | 없음                      | 확정된 초안 그대로 GitHub 이슈를 생성하고 `검토 결과`는 비워 둔다.        |
| 정책 방향 결정 요청     | 생성된 정책검토 이슈의 `검토 결과` 미확정                                  | 정책 방향 확정            | 결정 질문과 함께 선택지별 배경, 영향 범위, 설계 문서 반영 필요 여부 후보를 번호 목록으로 제시한다. |
| 정책 방향 결정 반영      | 정책 방향 확정                                                             | 없음                      | 정책검토 이슈 본문의 `검토 결과`에 결정, 근거, 설계 문서 반영 필요 여부, 반영 대상 또는 제외 근거를 반영하고, `후속 작업은 무엇인가요?`에서 `정책 검토 결과 확정` 항목을 체크한다. |
| 설계 문서 구현 전환     | 정책 방향 결정 반영 완료, `검토 결과`에 설계 문서 반영 필요와 반영 대상이 기록됨 | 없음                 | `검토 결과`에 기록된 설계 문서 반영 대상, 제외 대상, 반영 단위, 검증 기준을 구현 흐름 입력으로 사용한다. |
| 설계 문서 구현 완료      | 설계 문서 반영 PR merged                                                   | 없음                      | base branch로 복귀해 갱신하고, 정책검토 이슈의 `후속 작업은 무엇인가요?`에서 `결정된 정책을 관련 설계 문서에 반영` 항목을 체크한 뒤 PR 번호를 덧붙인다. |

### 기능결함 흐름

정책검토 필요 여부는 정책 또는 설계 원천의 변경 필요성으로 판단한다. 원천 변경, 현재 원천과의 충돌, 원천에 없는 기준 추가, 정책 선택지 결정이 필요하면 `정책 또는 설계 변경 필요`로 분류하고, 기존 원천을 그대로 적용할 수 있으면 `정책 또는 설계 변경 필요 없음`으로 분류한다.

정책검토에서 원본 기능결함 이슈 반영이 완료되면 해결 계획 수립으로 복귀한다.

### 구현 흐름

구현 흐름은 정책검토, 기능변경, 기능결함에서 전달된 구현 단위 하나를 작업 브랜치, 커밋, PR, 리뷰 대응, merge 반영까지 처리하는 공통 흐름이다. 구현 단위에는 코드뿐 아니라 문서, 템플릿, 스킬, 설정 같은 비기능 산출물 변경도 포함한다.

세부 구현 계획은 의미적 커밋 단위 목록을 반드시 포함한다. 각 커밋 단위는 변경 범위, 검증 기준, 커밋 메시지 확정 지점, 다음 단위 진행 조건을 함께 제시해야 한다. Workflow Engine은 확정된 커밋 단위 하나만 구현하고, 남은 커밋 단위는 커밋 생성 후 다시 확인한다.

| 작업                       | 조건                                                                                                                                      | 사용자 결정              | 상태 반영                                                                                                                                                                                            |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| 브랜치 전환                | 브랜치 이름 확정                                                                                                                          | 없음                          | 확정된 브랜치로 생성 또는 전환한다.                                                                                                                                                                  |
| 세부 구현 계획 수립        | 확정된 작업 브랜치로 전환 완료                                                                                                            | 세부 구현 계획 확정           | 의미적 커밋 단위 목록과 각 단위의 범위, 검증 기준, 커밋 메시지 확정 지점, 다음 단위 진행 조건을 제시한다.                                                                                            |

| 피드백 처리 결과 댓글      | 선택된 피드백 1건의 처리 결과 확정. 수용은 수정 push 완료, 거절 또는 기타 의견 입력은 처리 결과 확정                                      | 없음                          | 선택된 review thread 또는 marker 요약 피드백 항목에 처리 결과를 남긴다. 수용은 `commit-hash 수정했습니다.` 형식으로, 거절은 거절 근거로, 기타 의견 입력은 사용자가 지정한 처리 결과로 남긴다. |
| 피드백 해결 여부 확인      | 피드백 처리 결과 댓글 완료                                                                                                                | 해당 피드백 해결 여부 확정   | 해당 피드백을 `해결` 또는 `미해결` 중 하나로 처리할지 사용자 의도를 확인한다. review thread resolve와 요약 피드백 체크는 사용자 결정 이후 수행한다.                                                  |
| 피드백 해결 결정 반영      | 해당 피드백 해결 여부 확정                                                                                                                | 없음                          | 사용자가 `해결`을 선택하면 라인 피드백은 resolve하고 요약 피드백은 체크한다. 사용자가 `미해결`을 선택하면 GitHub 상태를 현재 상태로 유지한다.                                                       |
| 남은 피드백 확인           | 해당 피드백 해결 또는 미해결 결정 반영 완료                                                                                               | 없음                          | GitHub 실행 상태를 다시 읽고 남은 피드백이 있으면 `피드백 대응 제안`으로 돌아가고, 없으면 `리뷰 대응 대상 없음`으로 이동한다.                                                                        |
| 리뷰 대응 대상 없음        | 리뷰 대응 대상 확인 또는 남은 피드백 확인 완료, unresolved thread와 미체크 요약 피드백이 없음                                             | 없음                          | 리뷰 대응 대상이 없음을 기록하고 `PR merge 대기`로 이동한다.                                                                                                                                          |
| PR merge 대기              | 리뷰 대응 대상 없음, checks 통과, merge 가능                                                                                              | PR merge                      | 사용자가 GitHub에서 PR을 merge한다.                                                                                                                                                                  |
| PR merge 반영              | PR merged                                                                                                                                 | 없음                          | base branch로 복귀해 갱신하고, 연결 이슈의 PR merged 전이로 이동한다.                                                                                                                               |

## 스킬 계약

전용 스킬은 Workflow Engine이 다음 작업을 실행하는 데 필요한 후보, 초안, 분석 결과를 만든다. 상태 확정, 사용자 결정 처리, 이슈 본문 갱신, 브랜치 생성 또는 전환, 커밋 생성, PR 생성, 리뷰 게시는 Workflow Engine이 현재 작업의 실행 범위 안에서 수행한다.

Workflow Engine은 스킬 출력에서 이름이 붙은 필드만 후속 작업의 입력으로 사용한다. 자유 서술, 배경 설명, 추천 문장은 판단 근거로 참고할 수 있지만 상태 원천이나 사용자 결정을 대체할 수 없다.

필수 출력 필드가 없으면 Workflow Engine은 다음 작업으로 전이하지 않는다.

1. 누락된 필드를 사용자에게 알린다.
2. 같은 스킬에 보완 입력을 요청하거나 사용자 결정으로 넘긴다.
3. GitHub 상태 변경, 파일 변경, 브랜치 전환, 커밋, PR 생성은 보류한다.

각 스킬 계약은 다음 네 항목으로 책임을 구분한다.

- `입력`
- `출력`
- `Workflow Engine이 확정할 항목`
- `금지`

### GitHub Workflow Engine

입력:

- GitHub 실행 상태
- 현재 코드 상태
- 선택된 이슈 또는 PR
- 이 문서의 다음 작업 결정 규칙
- 필요한 경우 실행 로그

출력:

- 현재 상태 요약
- 다음 작업 후보
- 사용자 결정 질문
- 호출할 전용 스킬과 입력
- GitHub 상태 변경 또는 파일 변경 필요 여부

Workflow Engine이 확정할 항목:

- 이어갈 이슈 또는 PR
- 적용할 다음 작업 결정 규칙
- 사용자 결정 이후의 상태 변경
- 실행 로그 기록

금지:

- 사용자 결정 없이 GitHub 상태 변경
- 언어 모델의 자유 판단만으로 이슈 유형 변경
- 진행 중인 작업을 무시한 신규 계획 생성

- 원본 이슈가 있으면 원본 이슈 번호와 전환 사유
- 타겟 레포의 `.github/ISSUE_TEMPLATE/*.md`
- `github-templates.md` 계약

출력:

- 제목
- 라벨
- 본문 초안
- `연관 이슈`
- 생성 전 위험 또는 보류 질문

Workflow Engine이 확정할 항목:

- 실제 GitHub 이슈 생성 여부
- 생성된 이슈 번호
- 원본 이슈 체크리스트 갱신

금지:

- GitHub 이슈 직접 생성
- 템플릿 불일치 상태에서 임의 형식으로 생성
- 정책검토의 `검토 결과` 또는 기능결함의 `원인과 해결 방향은 무엇인가요?`를 생성 시점에 확정

### Branch Plan Skill

입력:

- 기준 이슈 유형과 번호
- 작업 주제
- 구현 단위
- 관련 계획 문서 또는 구현 계획
- 저장소의 기존 브랜치 이름 관례

출력:

- 브랜치 이름 후보
- 후보별 근거
- 보류 질문

Workflow Engine이 확정할 항목:

- 브랜치 이름
- 브랜치 생성 또는 전환

금지:

- 브랜치 직접 생성
- 브랜치 직접 전환

브랜치 prefix는 변경 대상 파일 경로가 아니라 변경의 제품 의미와 저장소 성격을 우선한다. 문서가 실행 계약이나 핵심 기능 산출물인 저장소에서는 설계 문서 반영이라도 `feat/...` 후보가 우선될 수 있다.

브랜치 topic은 이슈 제목보다 구현 단위의 핵심 동작을 우선해 만든다. 핵심 동작만으로 충분히 구체적이지 않으면 변경 대상 파일 또는 스킬 이름을 보조 정보로 사용하고, 그다음 이슈 제목의 도메인 키워드를 사용한다. 예를 들어 #47처럼 리뷰 피드백의 중요도와 대응 방향을 분리하는 구현 단위는 `feat/issue-47-separate-review-importance-from-response`처럼 변경 동작이 드러나는 후보를 우선 제안한다.

### Commit Skill

`commit`은 이 저장소가 관리하지 않는 외부 전역 Codex 스킬이다.

하네스 설치 또는 갱신 시 다음 경로 중 하나를 확인하고 결과를 `.harness/workflow-engine.json`의 `dependencies.commit.available`에 기록한다.

- `$CODEX_HOME/skills/commit/SKILL.md`
- `$HOME/.codex/skills/commit/SKILL.md`

입력:

- staged 또는 unstaged 변경사항
- 최근 커밋 스타일
- 확정된 구현 단위

출력:

- 변경사항 요약
- Conventional Commits 형식의 커밋 메시지 후보
- 추천 메시지

Workflow Engine이 확정할 항목:

- 변경 범위 확정
- 커밋 메시지 확정
- 커밋 생성

금지:

- `commit` 스킬 없이 대체 커밋 메시지 생성
- 변경 범위와 메시지 확정 없이 커밋 생성
- 확정되지 않은 파일 stage

### Review Comment Skill

Review Comment Skill은 리뷰 생성 도구와 무관하게 PR Review Template 형식의 리뷰 결과를 게시 가능한 피드백 구조로 변환한다.

입력:

- PR 번호
- 리뷰 실행 결과의 PR Review Template 출력
- 기존 review thread 목록
- 기존 PR issue comments

출력:

- `inline_review_threads`
- `summary_feedback_comment`
- 중복 게시 위험
- 보류 질문

Workflow Engine이 확정할 항목:

- review thread 우선 게시
- review thread 게시 실패 시 marker 요약 피드백 댓글 게시
- 게시 후 피드백 상태 추적

금지:

- 파일 수정
- 피드백 대응 방향 확정
- GitHub에 직접 게시
- 리뷰 결과를 일반 PR review body로만 게시
- 사용자 결정 없는 review thread resolve
- marker 없는 일반 PR comment를 요약 피드백 상태 원천으로 취급

피드백 위치에 따라 출력 대상을 나눈다.

- 파일 경로와 line이 있는 `[차단]` 또는 `[중요]` 피드백은 PR diff position 매핑을 먼저 시도한다.
- PR diff position으로 매핑된 `[차단]` 또는 `[중요]` 피드백은 `inline_review_threads`로 정리한다.
- PR diff position으로 매핑할 수 없는 `[차단]` 또는 `[중요]` 피드백은 `summary_feedback_comment`로 정리한다.
- `summary_feedback_comment`에는 `<!-- codex-harness:summary-feedback v1 -->` marker를 포함한다.

## 리뷰 실행 계약

리뷰 실행 계약은 PR diff와 연결 이슈의 작업 범위, 완료 판단 기준을 검토해 PR Review Template 형식의 리뷰 결과를 만드는 책임만 다룬다. 리뷰 결과 게시, review thread 생성, marker 요약 피드백 댓글 작성, 피드백 resolve는 Review Comment Skill과 리뷰 코멘트 게시 이후의 Workflow Engine 작업에서 처리한다.

입력:

- PR 번호
- 연결 이슈
- 변경 diff
- 완료 판단 기준
- 검토 제외 범위
- 리뷰 실행 모드
- 선택된 모드의 의존성 검사 결과
- PR Review Template 필수 필드

출력:

- PR Review Template 형식의 리뷰 결과

Workflow Engine이 확정할 항목:

- 리뷰 실행 모드
- 선택된 모드의 의존성 충족 여부
- PR Review Template 정규화 필요 여부
- Review Comment Skill 입력

금지:

- 파일 수정
- GitHub comment 게시
- review thread 게시
- PR merge

Workflow Engine을 타겟 레포에 설치할 때는 기본 리뷰 실행 모드를 저장할 수 있다. 저장된 기본 리뷰 실행 모드는 리뷰 실행 모드 선택 사용자 결정에서 기본 후보로만 사용하며, PR 생성 후 실제 사용할 리뷰 실행 모드는 매번 사용자가 확정해야 한다.

지원 리뷰 실행 모드는 다음 세 가지다.

| 리뷰 실행 모드               | 실행 주체 | 실행 전에 확인할 의존성                                                                                 |
| ---------------------------- | --------- | ------------------------------------------------------------------------------------------------------ |
| `claude/code-review`         | Claude    | Claude CLI 인증, Codex에서 호출할 경우 `sendbird/cc-plugin-codex`의 `$cc:setup` 준비 상태 확인         |
| `claude/awesome-code-review` | Claude    | Claude CLI 인증, Claude 환경의 `awesome-code-review`, Codex에서 호출할 경우 `sendbird/cc-plugin-codex` |
| `codex/awesome-code-review`  | Codex     | Codex 전역 `awesome-code-review`                                                                       |

설치 기본 리뷰 실행 모드 저장 형식:

```json
{
  "review": {
    "defaultMode": "claude/code-review"
  }
}
```

- 저장 위치는 타겟 레포의 `.harness/workflow-engine.json`이다.
- `review.defaultMode` 값은 `claude/code-review`, `claude/awesome-code-review`, `codex/awesome-code-review` 중 하나여야 한다.
- 지원 모드의 번호 또는 선택지 문구가 입력되면 리뷰 실행 모드 검사로 전이한다.
- `기타 의견 입력`은 사용자 결정 규칙에 따라 처리하며, 리뷰 실행 모드가 확정된 경우에만 리뷰 실행 모드 검사로 전이한다.

선택된 리뷰 실행 모드의 의존성이 설치되어 있지 않으면 Workflow Engine은 필요한 설치 경로, 설치 주체, 설치 후 확인할 파일 또는 명령, 재개 조건을 안내하고 리뷰 실행 작업을 중단한다. 다른 리뷰 실행 모드로 자동 전환하지 않는다.

Codex 전역 `awesome-code-review` 설치 확인 경로:

- `$CODEX_HOME/skills/awesome-code-review/SKILL.md`
- `$HOME/.codex/skills/awesome-code-review/SKILL.md`

`awesome-code-review` 누락 안내에는 이 저장소가 해당 스킬을 배포하거나 관리하지 않는다는 점, 설치는 `https://github.com/codechaser-kr/repo-bootstrap`의 install 절차를 사용한다는 점, 원천 스킬은 `https://github.com/awesome-skills/code-review-skill`이지만 Codex 전역 설치명과 frontmatter `name`은 기본 내장 리뷰 스킬과의 이름 충돌을 피하기 위해 `awesome-code-review`로 맞춘다는 점을 포함한다. 설치 후에는 위 경로 중 하나에 `SKILL.md`가 있고, 해당 파일의 frontmatter `name`이 `awesome-code-review`여야 리뷰 실행을 재개할 수 있다.

Claude 기반 리뷰 실행 모드를 Codex에서 호출하려면 `sendbird/cc-plugin-codex`가 필요하다. 이 의존성은 `commit`, `awesome-code-review`처럼 외부 전역 의존성으로만 다루며, `codex-harness` 관리 기본형에 포함하지 않는다. 설치 관리는 `https://github.com/codechaser-kr/repo-bootstrap`의 install 절차에서 담당한다.

`sendbird/cc-plugin-codex` 설치 확인 기준:

1. 플러그인 캐시에 `$CODEX_HOME/plugins/cache/sendbird/cc/*/.codex-plugin/plugin.json` 또는 `$HOME/.codex/plugins/cache/sendbird/cc/*/.codex-plugin/plugin.json`이 있어야 한다.
2. 같은 플러그인 루트에 `skills/setup/SKILL.md`와 `scripts/claude-companion.mjs`가 있어야 한다.
3. `$cc:setup`을 실행해 플러그인 설치 상태와 Claude Code 호출 준비 상태를 확인한다.
4. `$cc:setup`이 설치 누락, hook trust, Claude Code 사용 불가, 인증 필요 상태를 보고하면 출력된 안내를 사용자에게 전달하고 리뷰 실행으로 넘어가지 않는다.

Claude CLI 인증 확인 기준:

1. `claude/*` 리뷰 실행 모드에서는 리뷰 실행 전에 `$cc:setup` 결과의 인증 상태를 확인한다.
2. 인증 완료 판정은 `$cc:setup`의 machine-readable probe에서 `auth.available: true`, `auth.loggedIn: true`이거나 사용자 표시 출력이 authenticated 상태를 보고하는 경우로 제한한다.
3. 인증이 없거나 만료되었거나 판단할 수 없으면 리뷰 실행을 중단하고, `$cc:setup`이 제공하는 Claude login 안내를 그대로 전달한다.
4. 재개 조건은 사용자가 Claude CLI 인증을 완료한 뒤 `$cc:setup`을 다시 실행해 인증 완료 상태가 확인되는 것이다.

`claude/awesome-code-review`와 `codex/awesome-code-review`는 PR Review Template 필수 필드를 포함한 결과를 출력해야 한다. 리뷰 결과가 필수 필드를 모두 포함하면 Workflow Engine은 정규화 없이 그 결과를 Review Comment Skill 입력으로 사용한다.

`claude/code-review` 실행 경로:

1. Workflow Engine은 base 브랜치와 head 브랜치를 확인한다.
2. `$cc:setup`으로 Claude CLI 인증과 호출 준비 상태를 확인한다. 실제 리뷰 생성에는 `$cc:review` companion review를 사용하지 않는다.
3. 다음 형태로 base/head 브랜치를 target으로 전달해 Claude Code의 `/code-review` command를 단독 호출한다. PR 번호, 연결 이슈, 완료 판단 기준, 검토 제외 범위, 출력 조건은 `/code-review` command 뒤에 이어 붙이지 않고, 별도 정규화 프롬프트로 넘긴다.

```bash
claude -p --permission-mode plan '/code-review <base-branch>...<head-branch>' > /tmp/claude-code-review.out

{
  cat <<'CLAUDE_REVIEW_NORMALIZE'
다음 입력은 이미 실행한 Claude Code /code-review stdout입니다.
아래 PR 번호, 연결 이슈, 완료 판단 기준, 검토 제외 범위를 반영해 PR Review Template 형식으로 정규화하세요.

PR 번호: <pr-number>
연결 이슈: <issue-number-and-summary>
완료 판단 기준: <completion-criteria>
검토 제외 범위: <review-exclusions>

조건:
- PR Review Template 형식으로 출력하세요.
- Required Changes, Important Suggestions, Minor Suggestions, Learning Notes, Security Considerations, Test Coverage, 리뷰 결론을 포함하세요.
- 각 피드백에는 중요도 라벨, 파일 경로와 diff 위치 또는 요약 피드백 여부, 문제와 영향, 권장 조치를 포함하세요.
- GitHub comment나 review thread를 게시하지 마세요.
- 파일을 수정하지 마세요.
- 리뷰 결과만 대화 출력으로 반환하세요.

--- /code-review stdout ---
CLAUDE_REVIEW_NORMALIZE
  cat /tmp/claude-code-review.out
} | claude -p --permission-mode plan
```

4. Claude stdout만 리뷰 실행 결과로 사용한다.
5. `$cc:review` 기반 companion review가 필요하면 `claude/code-review`와 다른 별도 리뷰 실행 모드로 추가해야 하며, 현재 지원 모드에 자동 매핑하지 않는다.

리뷰 실행 결과는 Review Comment Skill로 전달하기 전에 반드시 PR Review Template 형식이어야 한다. `claude/code-review`처럼 Claude stdout의 피드백이 일반 Claude Code review 형식으로 나오는 모드는 Workflow Engine이 `Required Changes`, `Important Suggestions`, `Minor Suggestions`, `Learning Notes`, `Security Considerations`, `Test Coverage`, 리뷰 결론과 중요도 라벨을 갖춘 PR Review Template으로 정규화한 뒤 Review Comment Skill로 넘긴다.

정규화 필수 필드:

- PR 전체 리뷰 결론: `승인`, `의견`, `변경 요청` 중 하나
- 각 피드백의 중요도 라벨: `[차단]`, `[중요]`, `[사소]`, `[제안]`, `[학습]`, `[칭찬]` 중 하나
- 각 피드백의 파일 경로와 diff 위치 또는 라인에 붙일 수 없는 요약 피드백 여부
- 각 피드백의 문제, 영향, 권장 조치
- 테스트 커버리지 판단 또는 테스트 영향 없음 판단

위치, 중요도, 리뷰 결론, 문제 영향, 권장 조치, 테스트 커버리지 판단 중 하나라도 판단할 수 없어 PR Review Template 필수 필드를 채울 수 없으면 리뷰 코멘트 게시로 넘어가지 않고 누락 필드와 재개 조건을 제시한다.

## 이슈와 PR 본문 계약

### 템플릿 원천

- `.github/ISSUE_TEMPLATE/*.md`와 `.github/pull_request_template.md`는 실제 이슈와 PR 본문 형식의 단일 원천이다.
- `github-templates.md`는 title prefix, label, 필수 섹션, 연결 규칙의 정합성을 검증하는 계약 문서다.
- 작성 지침은 이 문서와 전용 스킬에서 관리하고, 생성된 이슈나 PR 본문에는 복사하지 않는다.
- 이슈나 PR 템플릿의 특정 섹션을 지칭할 때는 실제 섹션 제목을 그대로 쓴다.
- `완료 기준은 무엇인가요?`는 해당 이슈를 종료해도 되는지 판단할 수 있는 체크리스트여야 한다.

### 기능제안 이슈

필수 섹션:

- `무엇을 제안하나요?`
- `왜 필요한가요?`
- `현재 상태는 어떤가요?`
- `판단 결과`
- `완료 기준은 무엇인가요?`
- `추가 정보`

`판단 결과`는 생성 시 미체크로 둔다. 진행 방향이 확정되면 `진행하지 않음`, `정책 검토 필요`, `기능 변경 필요` 중 하나만 체크한다.

### 정책검토 이슈

필수 섹션:

- `무엇을 결정해야 하나요?`
- `왜 지금 필요한가요?`
- `선택지는 무엇인가요?`
- `검토 결과`
- `후속 작업은 무엇인가요?`
- `연관 이슈`

정책검토 이슈 본문은 다음 상태를 분리해 기록한다.

- 정책 방향 결정 여부
- 설계 문서 반영 여부
- 후속 흐름 연결 여부

`검토 결과`는 생성 시 비워 둔다. 정책 방향이 확정되면 결정, 근거, 설계 문서 반영 필요 여부, 반영 대상 또는 제외 근거, 실행 산출물 변경 필요 여부를 기록한다.

`후속 작업은 무엇인가요?` 기본 항목:

- `정책 검토 결과 확정`
- `결정된 정책을 관련 설계 문서에 반영`

`후속 작업은 무엇인가요?` 항목은 정책검토의 출처와 실행 산출물 변경 필요 여부에 따라 추가한다.

- 독립 정책검토 또는 기능제안에서 이어진 정책검토의 `검토 결과`에 실행 산출물 변경 필요가 기록되면 `필요한 경우 기능 변경 이슈의 작업 범위와 완료 기준에 반영` 항목을 추가한다.
- 기능결함에서 이어진 정책검토의 후속 연결은 정책검토 흐름의 `기능결함 이슈 반영` 작업으로 원본 기능결함 이슈에 반영한다.

정책검토의 설계 문서 반영은 결정된 정책을 설계 원천에 기록하는 단계다.

`docs/github-workflow-engine.md`처럼 Workflow Engine의 실행 계약을 정의하는 문서는 설계 원천이면서 이 저장소의 핵심 기능 산출물이다. 이 문서의 정책 반영은 정책검토 흐름의 설계 반영으로 처리할 수 있다.

설계 문서 반영 대상과 실행 산출물 변경 대상은 `완료 기준은 무엇인가요?`의 항목을 분리해 기록한다. 다음 대상은 실행 또는 배포 산출물로 보고, 설계 문서 반영 이후 기능변경 또는 기능결함 흐름의 `작업 범위는 어디까지인가요?`에 기록한다.

- `.codex-dist/skills`
- `.github` 템플릿
- 설치 스크립트
- README
- 그 밖의 실행 산출물 또는 배포 산출물

### 기능변경 이슈

필수 섹션:

- `어떤 기능을 변경하려 하나요?`
- `왜 필요한가요?`
- `작업 범위는 어디까지인가요?`
- `어떤 효과가 기대되나요?`
- `완료 기준은 무엇인가요?`
- `추가 정보`
- `연관 이슈`

`작업 범위는 어디까지인가요?`는 포함과 제외를 나누어 쓴다. `완료 기준은 무엇인가요?`는 기능변경 이슈를 종료해도 되는지 판단할 수 있는 체크리스트로 쓴다.

### 기능결함 이슈

필수 섹션:

- `어떤 문제가 있나요?`
- `문제 유형은 무엇인가요?`
- `재현 과정 또는 확인 위치가 어떻게 되나요?`
- `올바른 동작은 어떻게 되나요?`
- `원인과 해결 방향은 무엇인가요?`
- `완료 기준은 무엇인가요?`
- `추가 정보`

문제 유형은 `코드 버그`, `문서와 구현 불일치`, `정책 문서 간 불일치`, `반영 누락`, `기타` 중 해당 항목을 체크한다. `원인과 해결 방향은 무엇인가요?`는 생성 시 비워 두고, 원인 조사, 정책검토 결과 반영, 해결 계획 반영 작업에서만 갱신한다.

### 연관 이슈

`연관 이슈`는 해당 이슈의 생성 또는 `작업 범위는 어디까지인가요?` 산출에 직접 사용한 근거를 기록하는 섹션이다. PR은 `연관 이슈 (optional)`을 사용한다.

기록 대상:

- 이 이슈나 PR 생성을 직접 유발한 상위 이슈
- `작업 범위는 어디까지인가요?` 또는 `완료 기준은 무엇인가요?`를 결정한 근거 이슈

기록하지 않는 대상:

- 후속으로 생성된 이슈 번호
- 후속으로 생성된 PR 번호

후속 이슈나 PR 번호를 원본 이슈의 `연관 이슈`에 역방향으로 누적하지 않는다. 새로 생성되거나 갱신되는 대상의 `연관 이슈`에 원본 또는 근거 이슈 번호를 기록한다.

- 기능제안에서 정책검토를 만들면 새 정책검토 이슈 본문의 `연관 이슈`에 기능제안 번호를 반영한다.
- 기능제안에서 기능변경을 만들면 새 기능변경 이슈 본문의 `연관 이슈`에 기능제안 번호를 반영한다.
- 기능결함에서 정책검토를 만들면 새 정책검토 이슈 본문의 `연관 이슈`에 기능결함 번호를 반영한다.
- 정책검토에서 기능변경을 만들면 새 기능변경 이슈 본문의 `연관 이슈`에 정책검토 번호를 반영한다.
- 정책검토 결과를 기존 기능변경에 반영하면 기존 기능변경의 `연관 이슈`에 정책검토 번호를 추가한다.
- PR 본문의 `연관 이슈 (optional)`에는 해당 PR이 반영하는 정책검토, 기능변경, 기능결함 이슈 번호를 반영한다.

### PR 본문

필수 섹션:

- `왜 변경하려 하시나요?`
- `어떻게 변경하려고 하나요? (optional)`
- `해당 변경으로 영향받거나 검토해야 할 사항은 무엇인가요? (optional)`
- `머지하기 전에 반드시 확인되어야 할 사항이 있다면 작성해 주세요. (optional)`
- `연관 이슈 (optional)`

`연관 이슈 (optional)` 작성 규칙:

- Workflow Engine이 관리하는 PR에는 `Refs #번호` 형식을 사용한다.
- Workflow Engine 관리 이슈에는 `Closes`, `Fixes`, `Resolves`를 사용하지 않는다.
- 이슈 종료는 PR merge 이후 Workflow Engine이 연결 이슈의 `완료 기준은 무엇인가요?`와 정책검토 이슈의 `후속 작업은 무엇인가요?` 충족 여부를 확인한 뒤 판단한다.

## 리뷰 피드백 처리

리뷰 피드백 분류는 리뷰 피드백을 바로 수정 명령으로 보지 않고, 사람이 작업을 결정할 수 있도록 분류와 맥락을 제공하는 절차다.

### 리뷰 판단 항목

리뷰 결과를 처리할 때 다음 네 가지 판단 항목을 구분한다. 특히 중요도는 피드백의 영향 수준이고, 대응 방향은 사람이 선택하는 처리 방식이다.

| 판단 항목             | 값 또는 예시                                                                   | 책임                                                             |
| --------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| 리뷰 결론             | `승인`, `의견`, `변경 요청`                                                    | `awesome-code-review`가 PR 전체 결론으로 제시한다.               |
| 중요도                | `[차단]`, `[중요]`, `[사소]`, `[제안]`, `[학습]`, `[칭찬]`                    | `awesome-code-review`가 개별 피드백의 영향 수준으로 제시한다.    |
| 대응 방향             | `수용`, `거절`, `기타 의견 입력`                                               | 사용자가 피드백을 어떻게 처리할지 사용자 결정에서 결정한다.      |
| 해결 여부 결정        | `해결`, `미해결`                                                               | 피드백 처리 결과 기록과 필요한 댓글 처리 뒤 사용자가 별도로 결정한다. |

### 대응 분류

| 분류 | 의미                                                                            | 후속 작업                                           |
| ---- | ------------------------------------------------------------------------------- | --------------------------------------------------- |
| 수용 | 피드백을 현재 PR 범위에서 반영한다.                                             | 확정된 범위만 수정하고 커밋 메시지를 다시 확정한다. |
| 거절 | 오탐, 범위 밖, 또는 반영 대상에서 제외할 피드백이다.                            | 선택된 피드백에 거절 근거를 남긴다.                |
| 기타 의견 입력 | 추가 질문, 범위 재조정, 별도 이슈화 등 즉시 수용/거절로 처리 방향을 확정하기 어려운 피드백이다. | 사용자가 지정한 후속 작업을 수행한다. |

파일 경로와 line이 있는 피드백은 PR diff position 매핑을 먼저 시도한다. PR diff position으로 매핑된 피드백은 review thread로 게시하고 `isResolved`로 추적한다. PR diff position으로 매핑할 수 없는 `[차단]` 또는 `[중요]` 피드백은 marker가 있는 요약 피드백 댓글 체크리스트로 추적한다.

요약 피드백 marker:

```markdown
<!-- codex-harness:summary-feedback v1 -->
```

Workflow Engine은 marker가 없는 일반 PR comment를 요약 피드백 상태 원천으로 취급하지 않는다.

피드백은 한 번에 하나만 처리한다. Workflow Engine은 diff가 있는 unresolved review thread를 먼저 처리하고, 남은 unresolved review thread가 없을 때 미체크 요약 피드백을 처리한다. 피드백 1건마다 맥락 설명, 대응 방향 사용자 결정, 수정, 커밋 메시지 사용자 결정, push, 처리 결과 댓글, 해결 여부 확인, 해결 결정 반영, 남은 피드백 확인을 반복한다.

`수용`은 선택된 피드백 1건의 파일 수정을 확정한다는 의미다. 파일 수정과 검증이 끝난 뒤에는 `commit` 스킬로 커밋 메시지 후보를 제안하고, 사용자가 특정 커밋 메시지를 확정하기 전까지 `git commit`을 실행하지 않는다. 작업 진행 안내나 추천 메시지 표시만으로 커밋 메시지 확정 사용자 결정을 충족한 것으로 보지 않는다.

여러 피드백을 조회하거나 맥락으로 확보했더라도 현재 처리 대상은 Workflow Engine이 이번 단계에서 선택해 사용자에게 제시한 피드백 1건뿐이다. 선택되지 않은 피드백은 읽기 전용 맥락이며, 같은 수정 작업이나 같은 커밋에 함께 포함하지 않는다.

피드백 대응 방향은 사용자가 제시된 번호, 선택지 문구, 또는 `기타 의견 입력` 허용 형식을 입력해야 확정된다. Workflow Engine은 `권장 대응: 수용`처럼 추천을 제시할 수 있지만, 일반 진행 표현을 추천안 확정으로 해석하지 않는다. 사용자가 `수정`, `계속 진행`, `다음으로`, `네`, `좋습니다`, `진행해주세요`처럼 일반 진행 표현만 입력하면 선택된 피드백 1건도 수정하지 않고 대응 방향을 다시 확인한다.

리뷰 피드백 대응 방향은 상태 전이를 확정하는 선택지이므로 `수용`, `거절`, `기타 의견 입력`만 유효하다. `수정` 같은 작업 지시는 어떤 대응 방향을 선택했는지 명확히 표현하지 않으므로 대응 방향 확정으로 보지 않는다.

다음 피드백으로 이동하려면 현재 선택된 피드백 1건의 대응 방향 확정, 필요한 수정, 커밋, push, 처리 결과 댓글, 해결 여부 결정, GitHub 실행 상태 재조회가 끝나야 한다.

처리 결과 댓글은 현재 선택된 피드백 1건에 남긴다. 대상이 review thread이면 해당 thread에 답글을 남기고, marker 요약 피드백이면 해당 marker 댓글 항목에 처리 결과를 남긴다. `수용`은 수정 커밋 push 뒤 `commit-hash 수정했습니다.` 형식으로 남긴다. `거절`은 거절 근거를 남긴다. `기타 의견 입력`은 사용자가 지정한 처리 결과를 남긴다.

해결 여부 결정은 처리 결과 댓글이 끝난 뒤 별도로 확인하는 사용자 결정이다. Workflow Engine은 사용자에게 `해결` 또는 `미해결` 중 하나를 확인한다. `해결`을 선택하면 diff 피드백은 review thread를 resolve하고, 요약 피드백은 marker 체크리스트 항목을 체크한다. `미해결`을 선택하면 GitHub 상태를 현재 상태로 유지한다.

피드백을 사람에게 전달할 때 포함할 맥락:

- 피드백 원문
- 관련 파일 또는 문서 위치
- 위험도
- 예상 영향
- 수용/거절/기타 의견 입력 권장 대응
- 중요도
- 추천 작업
- 리뷰 결론 또는 Review Comment Skill의 보류 질문
- 자동 수정 시 위험 요소

## 로그와 재개

### 실행 로그

Workflow Engine은 작업에 진입하거나 중단 또는 재개 상태를 기록해야 할 때 타겟 저장소의 `.harness/logs/github-workflow-log.md`에 보조 로그를 남긴다. 실행 로그는 빠른 맥락 복원과 재개 조건 확인을 돕는 보조 근거이며, GitHub 실행 상태를 대체하지 않는다.

로그 항목은 다음을 포함한다.

- 대상 이슈 또는 PR
- 워크플로우 유형
- 진입한 작업 이름
- 적용한 조건
- 실행 범위와 수행한 작업 내용
- 사용자 결정 필요 여부
- 참조한 GitHub 실행 상태
- GitHub 상태에 반영한 내용
- 남은 판단 질문 또는 재개 조건

### 중단과 재개

자동 실행 루프는 진행 판단이 `사용자 결정`, `중단`, `완료` 중 하나로 산출될 때 멈춘다.

- `사용자 결정`: 현재 작업의 사용자 결정 필드에 따라 결정 대상, 선택 가능한 응답, 입력 예시를 번호 목록으로 제시한다.
- `중단`: 정보 부족, 의존성 누락, 의도 불명확, 실행 오류, 사용자 보류 요청처럼 현재 작업을 확정하거나 실행할 수 없는 사유와 재개 조건을 제시한다.
- `완료`: 기준 대상의 완료 조건이 충족되었음을 GitHub 실행 상태 근거로 제시하고 종료한다.

멈출 때는 현재 이슈 또는 PR, 현재 작업, 진행 판단, 중단 사유 또는 완료 근거, 사용자 결정 질문 또는 재개 조건을 제시한다. 현재 조건을 만족하는 작업 선택지가 있으면 다음 작업 결정 규칙으로 산출한 작업만 번호 목록으로 제시한다.

재개할 때는 GitHub 실행 상태와 현재 코드 상태를 먼저 다시 읽는다. 실행 로그는 GitHub 실행 상태로 표현되지 않는 중간 실행 상태를 확인할 때만 보조 근거로 사용한다. 실행 로그와 GitHub 실행 상태가 충돌하면 GitHub 실행 상태를 우선한다.

중단된 흐름을 재개할 때 사용자 요청이 직전 응답에서 제시한 번호, 선택지 문구, 허용된 `기타 의견 입력` 형식과 일치하지 않으면 Workflow Engine은 현재 워크플로우 상태를 요약하고, 다음 작업 결정 규칙에서 현재 조건을 만족하는 작업 선택지를 번호 목록으로 다시 제시한다. 이때 번호 입력, 선택지 문구 입력, `기타 의견 입력` 형식의 입력 예시를 함께 제시한다.

## 적용과 관리 구조

이 섹션은 `codex-harness`가 관리하는 설계·배포 자산과 타겟 프로젝트에 적용되는 운영 자산의 경계를 정의한다.

### codex-harness 관리 자산

`codex-harness`는 Workflow Engine의 설계 원천과 전역 배포 기본형을 관리한다.

- GitHub Workflow Engine 설계 문서
- 기능제안, 정책검토, 기능변경, 기능결함 이슈 템플릿 기본형
- Pull Request 템플릿 기본형
- Harness, GitHub Workflow Engine, Issue Creation, Feature Plan, Fix Plan, Branch Plan, PR Proposal, PR Creation, Review Comment 전역 스킬 기본형
- 기본 라벨 세트

전역 `commit` 스킬, `awesome-code-review`, `sendbird/cc-plugin-codex`는 외부 의존성으로만 다루며 `codex-harness` 관리 기본형에 포함하지 않는다.

`docs/github-workflow-engine.md`는 Workflow Engine 실행 규칙의 설계 원천이다. Workflow Engine 관련 스킬은 이 설계를 바탕으로 구현하고, 설계 원천의 실행 규칙을 변경하면 스킬 반영 여부와 후속 작업을 정책검토 또는 기능변경 흐름에 기록한다.

표준 배포 구조:

```text
codex-harness/
├── docs/
│   └── github-workflow-engine.md
├── .github/
│   ├── ISSUE_TEMPLATE/
│   │   ├── proposal_template.md
│   │   ├── decision_template.md
│   │   ├── feature_template.md
│   │   └── fix_template.md
│   └── pull_request_template.md
├── .codex-dist/
│   └── skills/
│       ├── harness/
│       ├── github-workflow-engine/
│       ├── issue-creation/
│       ├── feature-plan/
│       ├── fix-plan/
│       ├── branch-plan/
│       ├── pr-proposal/
│       ├── pr-creation/
│       └── review-comment/
```

### 타겟 프로젝트 적용 자산

타겟 프로젝트에는 Workflow Engine 운영에 필요한 GitHub 템플릿과 `.harness` 운영 파일만 적용한다. Workflow Engine 전역 스킬 사본은 타겟 프로젝트 안에 생성하지 않는다.

```text
target-repo/
├── .github/
│   ├── ISSUE_TEMPLATE/
│   │   ├── proposal_template.md
│   │   ├── decision_template.md
│   │   ├── feature_template.md
│   │   └── fix_template.md
│   └── pull_request_template.md
└── .harness/
    ├── workflow-engine.json
    └── logs/
        └── github-workflow-log.md
```

`.harness/workflow-engine.json`은 타겟별 설치 설정, `dependencies.commit.available`, 리뷰 실행 모드 사용 가능 상태를 저장한다. `.harness/logs/github-workflow-log.md`는 실행 로그를 저장한다. 두 파일은 모두 보조 운영 자산이며, 현재 작업 상태의 기준 원천은 GitHub 실행 상태다.

### 템플릿 정합성 검사

타겟 레포에 GitHub Workflow Engine을 적용하거나 템플릿을 갱신하기 전에는 타겟 `.github` 템플릿과 `github-templates.md` 계약의 정합성을 먼저 검사한다. `github-templates.md`는 실제 템플릿 본문 복제본이 아니라 title prefix, label, 필수 섹션, 연결 규칙을 검증하는 계약 문서다.

1. `github-templates.md`에서 기대 파일명, title prefix, label, 필수 섹션, 연결 규칙, 판정 기준을 읽는다.
2. 타겟 레포의 `.github/ISSUE_TEMPLATE/*.md`와 `.github/pull_request_template.md`를 읽는다.
3. 기본 파일명이 없으면 같은 역할의 기존 템플릿이 있는지 찾고 매핑 근거를 남긴다.
4. 각 이슈 템플릿의 YAML frontmatter `title`, `labels`, 필수 섹션, 기본 체크리스트를 비교한다.
5. PR 템플릿의 필수 섹션, `연관 이슈 (optional)`, `Refs #번호` 안내, 자동 종료 키워드 부재를 확인한다.
6. 결과를 `정합`, `허용된 확장`, `불일치`로 분류한다.
7. 불일치가 있으면 차이, 워크플로우 영향, 수정 후보를 사용자에게 제시한다.
8. 사용자 결정으로 확정된 경우에만 타겟 `.github` 템플릿을 생성 또는 갱신한다.

타겟 레포에서 발견한 개선점은 자동으로 `codex-harness`에 역반영하지 않는다. 여러 타겟에서 반복되거나 공통화할 가치가 있을 때만 사용자 결정 후 기본형으로 승격한다.

## 운영 메모

운영 메모는 앞선 규칙을 반복하지 않고, 실제 적용 시 우선 확인할 관리 원칙만 정리한다.

- 이슈와 PR 본문에는 사용자가 확인할 작업 내용, 판단 근거, 완료 기준만 남긴다. Workflow Engine 규칙 자체는 설계 문서와 전역 스킬 배포본에서 관리한다.
- 새 요청이나 다음 계획 요청을 받으면 열린 PR과 이슈에서 이어갈 작업을 먼저 확인한다. 이어갈 작업이 없을 때만 새 기능제안 후보를 검토한다.
- 계획, 진행 상태, 완료 기준처럼 후속 전이 판단에 쓰이는 정보는 이슈 또는 PR 본문에 반영한다. 리뷰 결과, 실행 로그, merge 알림처럼 본문 상태가 아닌 기록은 댓글이나 `.harness/logs/github-workflow-log.md`에 남긴다.
- 정책 판단이나 설계 변경이 구현 중 확인되면 현재 구현 흐름을 계속 확장하지 않고 정책검토 흐름으로 전이한다.
- 리뷰 피드백은 자동 수정 명령이 아니라 사용자 결정 대상이다. 대응 방향과 해결 여부 결정은 리뷰 피드백 처리 규칙을 따른다.
- PR merge는 사람이 수행한다. Workflow Engine은 merge 이후 GitHub 실행 상태를 다시 읽고 연결 이슈의 완료 기준과 후속 작업을 갱신한다.
