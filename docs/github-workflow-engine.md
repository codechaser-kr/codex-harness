# GitHub Workflow Engine 설계

이 문서는 `codex-harness`가 타겟 프로젝트에 GitHub 중심 Workflow Engine을 만들고 적용하기 위한 설계 기준이다.

GitHub 템플릿은 이슈와 PR에 필요한 정보를 적는 양식이다. 이 문서는 GitHub 상태를 어떻게 읽고 다음 작업을 결정할지 정의한다. 상태 전이 규칙은 템플릿 본문에 넣지 않고, 이 설계 문서와 이를 구현한 Workflow Skill에서 관리한다.

## 설계 목표

- GitHub를 프로젝트 작업 상태의 기준 저장소로 사용한다.
- 사람이 보는 작업 상태와 Agent가 읽는 작업 상태를 일치시킨다.
- 정책 판단, 설계 변경, 고위험 작업은 사람이 확인하고 승인한다.
- 파일 작성과 수정은 Codex가 맡고, PR 리뷰 생성은 Claude Code Review Skill이 맡는다.
- 이슈 생성은 Issue Creation Skill 규칙을 따른다.
- 워크플로우는 GitHub에 기록된 상태를 기준으로 중단하고 재개할 수 있어야 한다.
- 상태 전이는 즉흥 판단이 아니라 문서에 정의한 규칙을 따른다.
- GitHub Workflow 운영 구조의 기본형은 `codex-harness`에서 관리하고 타겟 레포에 적용한다.

## 정책 반영 범위

이 문서는 #29의 정책 검토 결과 중 다음 항목을 설계 문서로 반영한다.

- GitHub 기반 Run State 모델
- Workflow Template 구조
- State Transition Table 형식
- Human Checkpoint 기준
- 도구 역할 구분
- Claude Code Review Skill 연동 정책
- Review Feedback Triage 기준
- 리뷰 피드백을 사람에게 전달할 때 포함해야 할 맥락 형식
- 타겟 프로젝트에 GitHub 기반 Workflow Engine을 생성하는 저장소 구조
- 사용자의 비정형 기능 요청을 기능제안 이슈로 정리하는 생성 흐름
- 기능제안 이슈 생성 후 Workflow Skill이 상태 전이를 적용하는 흐름
- 다음 계획 요청 시 병렬 워크플로우를 열지 않고, 이어갈 수 있는 열린 계획을 신규 후보보다 우선하는 다음 작업 후보 판단 규칙
- 모든 상태가 중단되고 재개될 수 있다는 공통 운영 규칙
- 상태 전이를 정해진 Workflow Skill로 수행하는 운영 방식
- 이슈 생성을 이슈 유형별 템플릿과 Issue Creation Skill로 관리하는 운영 방식
- GitHub 이슈/PR 템플릿 기본형을 `codex-harness`에서 관리하고 타겟 레포에 적용하는 Template Bootstrap 흐름

## 상태 모델과 공통 규칙

이 섹션은 GitHub Workflow Engine이 어떤 상태를 읽고, 어떤 공통 규칙으로 흐름을 판단하는지 정의한다. 스킬의 책임과 타겟 레포 적용 방식은 뒤에서 따로 다룬다.

### Workflow Template

Workflow Template은 이슈 유형별 기본 흐름이다. 현재 기본 유형은 다음 네 가지다.

- `기능제안`: 기능 추가, 기능 수정, 운영 흐름 개선 요청을 다룬다.
- `정책검토`: 설계, 정책, 운영 기준을 결정한다.
- `기능변경`: 기능 추가 또는 기존 기능 수정을 실행한다.
- `기능결함`: 결함, 회귀, 문서와 구현 불일치, 반영 누락을 해결한다.

### GitHub Run State

GitHub Run State는 별도 파일이 아니라 GitHub의 이슈, PR, 라벨, 체크리스트, 댓글, 리뷰 상태에서 읽는 현재 작업 상태다.

| 상태 원천                    | 역할                                                                                                                 |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Issue title                  | 이슈 유형과 작업 주제를 식별한다.                                                                                    |
| Issue label                  | `기능제안`, `정책검토`, `기능변경`, `기능결함` 유형을 식별한다.                                                      |
| Issue body                   | 판단 근거, 범위, 완료 기준, 후속 작업을 읽는다.                                                                      |
| Issue checklist              | 완료 기준과 정책 반영 상태를 읽는다.                                                                                 |
| Issue state                  | 작업이 열려 있는지 닫혔는지 읽는다.                                                                                  |
| Pull Request body            | 변경 이유, 영향 범위, `연관 이슈` 섹션의 이슈 번호를 읽는다.                                                         |
| Pull Request state           | 변경이 진행 중인지 병합되었는지 읽는다.                                                                              |
| Pull Request issue reference | PR 본문의 `연관 이슈` 섹션을 파싱해 어떤 정책검토, 기능변경, 기능결함 이슈의 작업을 반영하는지 읽는다.               |
| Review and comments          | 리뷰 피드백과 사람 승인 여부를 읽는다.                                                                               |

### State Transition Rule

State Transition Rule은 현재 GitHub Run State와 조건을 보고 지금 수행할 액션을 정하는 규칙이다. 이 규칙은 Workflow Skill이 적용한다.

State Transition Rule은 모든 이슈 유형에서 같은 필드 형식을 따른다.

| 필드             | 의미                                                                                                                                                      |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 액션 이름        | 해당 액션을 식별하는 이름                                                                                                                                 |
| 현재 상태        | GitHub Run State에서 읽은 이슈/PR 상태                                                                                                                    |
| 조건             | 현재 액션을 선택하기 위한 판정 조건                                                                                                                       |
| 작업 내용        | Workflow Skill, Issue Creation Skill, Codex, Claude Code Review Skill, 또는 사용자가 실제로 진행할 작업                                                   |
| Human Checkpoint | 해당 액션을 진행하거나 확정하기 위해 사용자에게 받아야 하는 승인 또는 결정. 조건에 이미 사용자 결정이 포함되어 있거나 단순 기록만 남기면 `없음`으로 쓴다. |
| 기록 지침        | 해당 액션을 진행할 때 Issue, PR, Comment, Checklist 중 어디에 무엇을 반영해야 하는지                                                                      |

State Transition Rule은 자동 실행 명령이 아니다. Workflow Skill은 이 규칙에 따라 현재 액션을 제안하고, Human Checkpoint가 있으면 사람 승인 없이 해당 액션을 확정하거나 다음 액션으로 넘어가지 않는다.

### Human Checkpoint

Human Checkpoint는 Workflow Skill이나 Agent가 임의로 넘기면 안 되는 사용자 승인 또는 결정 지점이다.

Human Checkpoint가 필요한 경우는 다음과 같다.

- 기능제안, 정책검토, 기능변경, 기능결함 이슈 초안 검토 및 승인
- Workflow Skill이 제안한 작업 후보 중 진행할 대상 선택
- 리뷰 피드백별 추천 액션 설명을 검토하고 대응 방향 승인
- PR 제목과 설명 검토 및 승인
- PR merge
- Codex와 Claude Code Review Skill의 판단 충돌

Human Checkpoint가 필요한 경우 Workflow Skill 또는 Issue Creation Skill은 다음 정보를 사람에게 전달한다.

- 현재 이슈 또는 PR
- 판단해야 할 질문
- 선택 가능한 액션
- 각 액션의 영향과 위험
- 추천 액션과 근거
- 생성 또는 수정될 이슈 초안
- 액션 진입, 중단, 재개 시 확인해야 할 기준

### 전역 실행 로그

전역 실행 로그는 현재 어떤 워크플로우가 어느 액션에 있었는지 빠르게 확인하기 위한 로컬 보조 기록이다. 이 로그는 GitHub 상태를 대체하지 않으며, 다음 액션 판단의 근거가 아니다. 프로젝트 상태의 기준은 GitHub의 열린 이슈, PR, 체크리스트, 리뷰 상태다.

Workflow Skill은 State Transition Rule의 특정 행을 선택해 액션에 진입할 때마다 `.harness/logs/github-workflow-log.md`에 액션 진입 로그를 남긴다.

사용자가 기능 개발 계획, 기능 결함 해결 계획, 커밋 단위, 리뷰 피드백 대응 방향을 승인하면 Workflow Skill은 GitHub 이슈나 PR에 반영해야 하는 내용부터 먼저 기록한다. 같은 내용은 빠른 맥락 복원을 위해 로그에 보조 체크포인트로 남길 수 있다. 같은 대화 세션 안에서 중단과 재개가 반복될 때도 Workflow Skill은 GitHub Run State와 현재 코드 상태를 먼저 확인한다. 체크포인트는 그 상태와 맞을 때만 진행 맥락을 빠르게 복원하는 보조 자료로 사용한다.

액션 진입 로그에는 다음 정보를 남긴다.

- 대상 이슈 또는 PR
- 워크플로우 유형
- 진입한 액션 이름
- 적용한 조건
- 선택한 작업 내용
- Human Checkpoint 필요 여부
- 참조한 GitHub Run State
- GitHub 상태에 반영된 승인 계획 요약 또는 보조 체크포인트
- 남은 판단 질문 또는 다음 확인 항목

### 전역 중단/재개 흐름

모든 워크플로우 상태는 중단될 수 있고, 다시 재개될 수 있다. 중단은 실패가 아니라 판단을 잠시 보류한 상태다. 재개 여부는 GitHub의 열린 이슈, PR, 체크리스트, 리뷰 상태를 기준으로 판단한다. 중단 기록은 기본적으로 이슈나 PR에 남기지 않는다.

중단이 발생할 수 있는 경우는 다음과 같다.

- 사용자가 명시적으로 중단 또는 보류를 요청한다.
- Human Checkpoint에서 사용자가 아직 결정하지 않았다.
- 판단에 필요한 정보가 부족하다.
- 외부 리뷰, 설계 검토, 사용자 확인, 실행 결과를 기다려야 한다.
- Codex 또는 Claude Code Review Skill 실행 중 오류나 충돌이 발생해 사람 판단이 필요하다.

중단이나 보류가 발생하면 Workflow Skill은 현재 GitHub 상태를 유지한다. 필요한 경우 마지막 액션 진입 로그에 중단 정보를 덧붙이거나 별도 중단 로그를 남긴다. 이 기록이 없어도 Workflow Skill은 GitHub Run State와 현재 코드 상태를 다시 읽어 현재 위치를 판단할 수 있어야 한다.

중단 로그에는 다음 정보를 남긴다.

- 중단된 액션
- 중단 사유
- 마지막으로 확인한 GitHub Run State
- 남은 판단 질문
- 선택 가능한 액션
- 추천 액션과 근거
- 재개 시 먼저 확인해야 할 항목

재개할 때 Workflow Skill은 GitHub Run State와 현재 코드 상태를 먼저 읽어 현재 위치와 남은 작업을 판단한다. `.harness/logs/github-workflow-log.md`의 최신 체크포인트는 판단된 GitHub 상태와 맞을 때만 진행 맥락을 복원하는 데 참고한다. 체크포인트가 없거나 실제 상태와 어긋나면 체크포인트를 그대로 실행하지 않고, 이슈 유형별 상태 전이 명세에서 이어갈 액션을 다시 선택한다. 재개는 새 워크플로우를 시작하는 것이 아니라 마지막으로 확인 가능한 상태에서 이어가는 일이다. 닫힌 이슈는 기본적으로 재개 대상이 아니며, 사용자가 다시 열거나 새 이슈로 작성해 달라고 요청한 경우에만 재개 후보가 된다.

중단과 재개는 특정 이슈 유형에만 적용되지 않는다. 정책검토, 기능제안, 기능변경, 기능결함, 연결 PR의 어느 액션에서도 같은 기준을 따른다.

| 액션 이름 | 현재 상태                                            | 조건                                                           | 작업 내용                                                                   | Human Checkpoint | 기록 지침                                         |
| --------- | ---------------------------------------------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------- | ---------------- | ------------------------------------------------- |
| 중단 유지 | `{이슈 유형} open` 또는 `{이슈 유형} PR open`        | 사용자가 중단/보류를 요청하거나 Human Checkpoint 판단이 보류됨 | 현재 GitHub 상태 유지                                                       | 없음             | 없음                                              |
| 중단 유지 | `{이슈 유형} open` 또는 `{이슈 유형} PR open`        | 정보 부족, 외부 검토 대기, 실행 오류로 액션을 확정할 수 없음   | 현재 GitHub 상태 유지                                                       | 없음             | 없음                                              |
| 재개 진행 | 중단된 `{이슈 유형} open` 또는 `{이슈 유형} PR open` | 사용자가 해당 작업의 재개를 요청함                             | GitHub Run State와 현재 코드 상태를 먼저 읽고 이어갈 액션을 선택한다. 최신 체크포인트는 선택한 액션과 실제 상태에 맞을 때만 진행 맥락 복원에 참고한다. | 없음             | 없음                                              |
| 보류 유지 | 중단된 `{이슈 유형} open` 또는 `{이슈 유형} PR open` | 사용자가 보류 유지를 요청함                                    | 현재 GitHub 상태 유지                                                       | 없음             | 없음                                              |
| 종료 처리 | 중단된 `{이슈 유형} open`                            | 사용자가 종료를 결정함                                         | 판단 근거를 남기고 close                                                    | 없음             | 이슈에 종료 사유와 재검토 조건이 있으면 기록한다. |

## 스킬과 도구 책임

이 섹션은 공통 상태 모델을 실제로 적용하는 스킬과 도구의 책임을 정의한다. 상태 전이 판단, 이슈 생성, 개발 계획, 브랜치 제안, 파일 수정, 리뷰 생성은 서로 다른 책임으로 나눈다.

### GitHub Workflow Skill

GitHub Workflow Skill은 GitHub Run State를 읽고, 이 문서의 상태 전이 명세에 따라 현재 조건에서 진행할 액션 후보를 제안하는 실행 규칙이다.

Workflow Skill은 다음 책임을 가진다.

- GitHub Run State에서 진행 중이거나 멈춰 있는 열린 이슈 또는 PR이 있는지 먼저 판단한다.
- 진행 중이거나 멈춰 있는 열린 이슈 또는 PR이 있으면 신규 후보보다 해당 작업의 재개를 우선한다.
- 재개할 열린 이슈 또는 PR이 없을 때만 새로 진행할 수 있는 열린 이슈 후보를 수집한다.
- 선택된 이슈의 유형과 상태에 맞는 State Transition Rule을 적용한다.
- State Transition Rule의 각 액션에 진입할 때 `.harness/logs/github-workflow-log.md`에 액션 진입 로그를 남긴다.
- 액션에 새 이슈 생성이 필요하면 Issue Creation Skill에 이슈 유형과 생성 근거를 전달한다.
- 모든 상태에서 중단 요청, 정보 부족, Human Checkpoint 미승인, 보류 결정을 처리한다.
- 재개 요청이 들어오면 GitHub Run State와 현재 코드 상태를 먼저 읽고, 최신 체크포인트와 중단 사유, 남은 판단 질문, 액션 후보는 실제 상태와 맞을 때만 참고한다.
- 사용자의 merge 알림 또는 다음 계획 요청 시 GitHub Run State를 다시 읽고, merge 결과를 관련 이슈의 체크리스트와 진행 상태에 반영한다.
- Human Checkpoint가 필요한 경우 실행을 멈추고 사용자에게 선택지를 제시한다.
- 사용자가 승인한 액션만 다음 액션으로 넘긴다.

Workflow Skill은 LLM의 자유 추론만으로 상태 전이를 결정하지 않는다. LLM은 이슈 내용을 요약하고, 선택지의 장단점과 추천 근거를 설명할 수 있다. 다만 상태 전이 자체는 Workflow Skill의 규칙을 따른다.

### Issue Creation Skill

Issue Creation Skill은 사용자의 비정형 요청이나 Workflow Skill의 이슈 생성 액션을 받아, GitHub 이슈 유형별 템플릿에 맞는 이슈 초안을 만들고 생성 전 검증을 진행하는 실행 규칙이다.

Issue Creation Skill은 다음 책임을 가진다.

- `기능제안`, `정책검토`, `기능변경`, `기능결함` 네 가지 이슈 유형을 모두 생성할 수 있어야 한다.
- 사용자의 비정형 요청을 적절한 이슈 유형으로 분류하고, 정해진 템플릿에 맞는 제목과 본문 초안으로 정리한다.
- Workflow Skill이 요청한 후속 이슈를 해당 템플릿에 맞게 작성한다.
- 이슈 유형별 제목 prefix, 라벨, 연관 이슈, 필수 본문 항목을 검증한다.
- 템플릿의 각 세부 항목이 오해 없이 작성되었고 다음 워크플로우 판단에 충분한지 검증한다.
- 원본 이슈가 있는 경우 새 이슈 본문에 원본 이슈 링크와 전환 사유를 남긴다.
- 생성 전 사용자에게 초안을 보여주고 승인받는다.
- 사용자가 승인한 이슈만 GitHub에 생성한다.

Issue Creation Skill은 LLM이 자유롭게 작성한 결과를 그대로 이슈로 만들지 않는다. 초안 작성 결과는 이슈 유형, 템플릿, 필수 항목, 라벨, 연결 관계, 생성 여부에 대해 Issue Creation Skill의 규칙과 사용자 승인을 통과해야 한다.

### 기능 개발 계획 Skill

기능 개발 계획 Skill은 생성된 기능변경 이슈와 관련 설계 문서를 바탕으로 실제 구현 전에 개발 계획 초안을 만든다.

기능 개발 계획 Skill은 다음 책임을 가진다.

- 기능변경 이슈의 작업 범위, 완료 기준, 연관 이슈를 읽는다.
- 정책검토 결과와 관련 설계 문서를 함께 참조한다.
- 몇 개의 브랜치로 나누어 작업할지 제안한다.
- 어떤 기능을 어떤 순서로 구현할지 제안한다.
- 각 기능 구현 단위를 하나의 브랜치와 하나의 PR 기준으로 제안한다.
- 각 기능 구현 단위의 검증 기준을 제안한다.
- 확정 전 사용자에게 계획 초안을 보여주고 승인받는다.

사용자가 승인한 기능 개발 계획만 기능 구현 흐름의 입력이 된다.

### Fix Plan Skill

Fix Plan Skill은 기능결함 이슈의 원인, 해결 방향, 완료 기준을 바탕으로 실제 수정 전에 기능 결함 해결 계획 초안을 만든다.

Fix Plan Skill은 다음 책임을 가진다.

- 기능결함 이슈의 문제 현상, 재현 과정 또는 확인 위치, 원인, 해결 방향, 완료 기준을 읽는다.
- 정책검토 결과가 있으면 함께 참조한다.
- 몇 개의 브랜치로 나누어 해결할지 제안한다.
- 어떤 결함 해결 단위를 어떤 순서로 구현할지 제안한다.
- 각 결함 해결 단위를 하나의 브랜치와 하나의 PR 기준으로 제안한다.
- 각 결함 해결 단위의 검증 기준을 제안한다.
- 확정 전 사용자에게 계획 초안을 보여주고 승인받는다.

사용자가 승인한 기능 결함 해결 계획만 기능 구현 흐름의 입력이 된다.

### Branch Name Skill

Branch Name Skill은 기능 구현 흐름에서 작업 브랜치 이름을 제안하는 실행 규칙이다. 이 스킬은 `codex-harness`가 관리하는 Workflow Engine 구성요소에 포함된다.

Branch Name Skill은 다음 책임을 가진다.

- 기준 이슈 유형, 이슈 번호, 작업 주제, 구현 단위를 읽는다.
- 설계 문서 반영 단위, 기능 개발 계획, 기능 결함 해결 계획이 있으면 해당 입력의 브랜치 분할 기준을 따른다.
- 저장소의 기존 브랜치 네이밍 관례를 우선한다.
- 브랜치 이름 후보와 제안 근거를 사용자에게 보여주고 승인받는다.
- 사용자가 승인한 브랜치 이름만 기능 구현 흐름의 브랜치 생성 또는 전환에 사용한다.

### Commit Message Skill

Commit Message Skill은 기능 구현 흐름에서 세부 구현 계획의 커밋 단위 변경에 대한 커밋 메시지를 제안하는 실행 규칙이다.

Commit Message Skill은 다음 책임을 가진다.

- 기준 이슈, 구현 단위, 세부 구현 계획, 변경 파일, 변경 요약을 읽는다.
- 저장소의 기존 커밋 메시지 관례를 우선한다.
- 한 커밋에 포함될 변경 범위와 커밋 메시지 후보를 함께 제안한다.
- 커밋 메시지 후보와 제안 근거를 사용자에게 보여주고 승인받는다.
- 사용자가 함께 승인한 변경 내용과 커밋 메시지만 기능 구현 흐름의 커밋 생성에 사용한다.

### PR Proposal Skill

PR Proposal Skill은 기능 구현 흐름에서 PR 제목과 설명 초안을 제안하는 실행 규칙이다.

PR Proposal Skill은 다음 책임을 가진다.

- 기준 이슈, 구현 단위, 작업 브랜치, 변경 요약, 검증 결과, 연관 이슈를 읽는다.
- PR 템플릿에 맞는 제목과 설명 초안을 작성한다.
- PR의 연관 이슈는 기본적으로 `Refs #번호`로 작성한다.
- PR 제목과 설명 초안을 사용자에게 보여주고 승인받는다.
- 사용자가 승인한 PR 제목과 설명만 PR Creation Skill의 입력으로 넘긴다.

### PR Creation Skill

PR Creation Skill은 승인된 PR 제목과 설명으로 GitHub PR을 생성하는 실행 규칙이다.

PR Creation Skill은 다음 책임을 가진다.

- 승인된 PR 제목, 설명, 기준 브랜치, 원격 head branch를 입력으로 받는다.
- 승인된 PR 템플릿 본문으로 GitHub PR을 생성한다.
- 생성된 PR 번호와 URL을 Workflow Skill에 반환한다.
- PR merge 방식 선택이나 merge 수행은 하지 않는다.
- PR 생성 이후 리뷰 진행은 기능 구현 흐름의 `Claude 리뷰 실행` 액션으로 넘긴다.

### Claude Code Review Skill

Claude Code Review Skill은 Codex가 비대화형 `claude` CLI 호출로 실행하는 리뷰 생성 규칙이다. 이 스킬은 PR diff 또는 브랜치 diff를 검토해 리뷰 결과만 생성한다.

Claude Code Review Skill은 다음 책임을 가진다.

- PR 번호, 기준 브랜치, 작업 브랜치, 연결 이슈, 변경 diff, 완료 기준, 검토 제외 범위를 입력으로 받는다.
- 파일 수정, GitHub comment 작성, review thread 게시, PR merge를 수행하지 않는다.
- 버그, 회귀, 보안, 테스트 누락, 설계 불일치를 우선 검토한다.
- 각 피드백을 파일 위치, diff 위치, 문제, 근거, 위험도, 추천 분류, 확신도로 정리한다.
- 라인에 붙일 수 없는 전체 설계 피드백은 요약 피드백 후보로 분리한다.
- Codex가 후속 처리할 수 있도록 구조화된 리뷰 결과를 반환한다.

Claude Code Review Skill은 Claude Code 구독 또는 인증 상태를 사용해 실행된다. Workflow Engine은 Claude 호출 결과를 리뷰 생성 결과로만 취급하며, GitHub 게시와 피드백 반영은 각각 Review Comment Skill과 Codex가 담당한다.

### Review Comment Skill

Review Comment Skill은 Claude Code Review Skill이 생성한 리뷰 결과를 GitHub Pull Request review thread 또는 요약 피드백 댓글로 게시하는 실행 규칙이다.

Review Comment Skill은 다음 책임을 가진다.

- PR 번호와 Claude Code Review Skill 리뷰 결과를 입력으로 받는다.
- 파일 경로와 diff line이 있는 피드백은 GitHub Pull Request review thread로 게시할 수 있는 형식으로 정리한다.
- 같은 리뷰 결과가 중복 게시되지 않도록 기존 review thread와 요약 피드백 댓글을 확인한다.
- 각 review thread에 문제, 근거, 위험도, 추천 분류, 확신도를 함께 게시한다.
- 파일 경로와 diff line이 없어 review thread로 게시할 수 없는 피드백은 marker가 있는 요약 피드백 댓글의 체크리스트로 게시한다.
- 요약 피드백 댓글에는 `<!-- codex-harness:summary-feedback v1 -->` marker를 포함한다.
- 리뷰 피드백의 적용 여부를 결정하거나 파일을 수정하지 않는다.

### 도구 역할 구분

도구 역할 구분은 실제 작업을 맡는 도구별 책임을 정한다. 현재 Workflow Engine은 파일 수정과 리뷰 생성을 분리해 운영한다.

현재 기준 역할은 다음과 같다.

| 역할             | 도구                     | 책임                                                                                          |
| ---------------- | ------------------------ | --------------------------------------------------------------------------------------------- |
| 파일 수정        | Codex                    | 이슈 범위에 따라 설계 문서와 실제 코드를 수정한다.                                            |
| 리뷰 생성        | Claude Code Review Skill | PR 변경사항을 검토하고 리뷰 결과를 생성한다.                                                  |
| 리뷰 코멘트 게시 | Review Comment Skill     | Claude Code Review Skill 리뷰 결과를 review thread 또는 요약 피드백 댓글로 게시한다.          |
| 피드백 대응 진행 | Codex                    | 미해결 review thread와 미체크 요약 피드백을 수집해 추천 대응 방향을 설명하고, 사용자 승인 후 후속 작업을 수행한다. |

Workflow Skill은 GitHub 상태를 읽고 현재 조건에서 진행할 액션을 제안한다. 실제 파일 수정은 Codex가 맡고, 리뷰 생성은 Claude Code Review Skill이 맡으며, 리뷰 코멘트 게시는 Review Comment Skill이 맡는다.

각 도구는 다음 입출력 기준을 지킨다.

| 구분 | 내용                                                                         |
| ---- | ---------------------------------------------------------------------------- |
| 입력 | 이슈 번호, PR 번호, 작업 범위, 완료 기준, 관련 설계 문서, 승인된 리뷰 피드백 |
| 출력 | 변경 파일, 리뷰 결과, 보류한 판단, 후속 이슈 후보, 검증 결과                 |
| 금지 | 승인되지 않은 정책 변경, 범위 밖 대규모 수정, 리뷰 피드백 자동 일괄 반영     |

도구별 책임은 이 표의 범위 안에서 운영한다. Workflow Template, State Transition Rule, Human Checkpoint, 실행 로그와 중단/재개 규칙은 도구 실행 규칙과 분리해 유지한다.

## 이슈와 PR 운영 규칙

이 섹션은 Workflow Skill과 Issue Creation Skill이 이슈와 PR을 만들거나 갱신할 때 따르는 규칙을 정의한다. PR 리뷰 피드백을 처리하는 기준도 함께 다룬다.

### 이슈 생성 규칙

Issue Creation Skill은 사용자의 요청이나 Workflow Skill의 이슈 생성 액션을 이슈 유형별 템플릿 본문으로 정리한다. 이슈 생성 규칙은 템플릿 본문에 설명 문장을 남기기 위한 규칙이 아니라, 생성 전 초안을 만들고 검증하기 위한 기준이다.

- GitHub 템플릿 본문은 실제 이슈에 남길 섹션과 기본 상태만 담는다.
- 작성 지침은 Workflow Engine 설계 문서와 Issue Creation Skill에서 관리하고, 생성된 이슈 본문에는 복사하지 않는다.
- 이슈 유형별 제목 prefix, 라벨, 필수 섹션, 연관 이슈를 검증한 뒤 사용자 승인을 받는다.
- 조건부 체크항목은 해당 케이스에 필요할 때만 Issue Creation Skill이나 Workflow Skill이 추가한다.
- 종료 기준 같은 운영 규칙은 Workflow Engine 설계 문서와 State Transition Rule에서 관리한다.
- 완료 기준은 해당 이슈가 닫혀도 되는지를 판단할 수 있는 체크리스트여야 한다.

#### 기능제안 이슈

기능제안은 사용자의 기능 추가, 기능 수정, 운영 흐름 개선 요청을 정리하는 시작점이다. 사용자가 직접 작성하거나, 비정형 요청을 Issue Creation Skill이 초안으로 정리하고 사용자가 승인한 뒤 생성한다.

Workflow Skill은 열린 기능제안 이슈를 진행 여부 판단 대상으로 읽는다. 기능제안 이슈는 바로 구현으로 이어지는 이슈가 아니며, 진행하지 않음, 정책검토 전환, 기능변경 전환 중 하나로 정리된다.

| 항목                      | 작성 지침                                                                                                                     |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `무엇을 제안하나요?`      | 추가하거나 수정하려는 기능, 흐름, 문서, 운영 방식을 적는다.                                                                   |
| `왜 필요한가요?`          | 해결할 문제, 기대 효과, 사용자 또는 운영 맥락을 적는다.                                                                       |
| `현재 상태는 어떤가요?`   | 관련 문서, 구현 상태, 사용자 피드백 등 현재 판단에 필요한 맥락을 적는다.                                                      |
| `판단 결과`               | 생성 시에는 미체크 상태로 둔다. 진행 방향이 정해진 뒤 `진행하지 않음`, `정책 검토 필요`, `기능 변경 필요` 중 하나를 체크한다. |
| `완료 기준은 무엇인가요?` | 기본 항목은 `제안 필요성 판단 완료`로 둔다.                                                                                   |
| `추가 정보`               | 위 섹션에 들어가지 않지만 진행 판단에 필요한 맥락을 적는다.                                                                   |

#### 정책검토 이슈

정책검토는 설계, 정책, 운영 기준 결정이 필요한 경우 생성한다. 독립적인 시작점이 될 수 있고, 기능제안이나 기능결함 흐름에서 이어질 수도 있다.

Workflow Skill은 열린 정책검토 이슈를 정책 결정 대상으로 읽는다. 정책검토 이슈는 정책 결정, 설계 문서 반영, 필요한 후속 이슈 반영 여부를 추적한다.

| 항목                      | 작성 지침                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `무엇을 결정해야 하나요?` | 이번 이슈에서 결정할 질문을 한 문장으로 적는다.                                                                                                                                                                                                                                                                                                                                        |
| `왜 지금 필요한가요?`     | 결정이 필요한 배경을 현재 문서, 구현 상태, MVP 범위, 사용자 피드백을 바탕으로 적는다.                                                                                                                                                                                                                                                                                                  |
| `선택지는 무엇인가요?`    | 검토 가능한 방향을 하나 이상 적는다. 선택지 개수는 고정하지 않는다.                                                                                                                                                                                                                                                                                                                    |
| `검토 결과`               | 생성 시에는 비워 둔다. 정책 방향이 정해지면 최종 결정과 근거를 짧게 적는다. 설계 문서 반영과 PR 리뷰 과정에서 결정이 보강되면 최신 결정으로 갱신한다.                                                                                                                                                                                                                                  |
| `후속 작업은 무엇인가요?` | 기본 항목은 `정책 검토 결과 확정`, `결정된 정책을 관련 설계 문서에 반영`만 둔다. 기능 변경 이슈 반영이 필요한 정책검토라면 `기능 변경 이슈 반영이 필요한 정책검토` 체크항목을 추가한다. 기능결함에서 이어진 정책검토라면 기능 변경 이슈 반영 체크항목이나 기능결함 이슈 반영 항목을 작성하지 않는다. 체크항목의 근거가 되는 이슈나 PR이 있으면 항목 뒤에 번호를 괄호로 덧붙일 수 있다. |
| `연관 이슈`               | 이 정책검토 이슈를 만들게 된 원본 이슈를 적는다. 독립 정책검토라면 `N/A`로 둔다.                                                                                                                                                                                                                                                                                                       |

정책검토 이슈의 종료 기준은 템플릿 본문이 아니라 정책검토 흐름에서 판단한다.

- 확정된 정책은 관련 설계 문서에 반영되어야 한다.
- 기능제안에서 이어진 정책검토이거나 독립 정책검토가 기능변경으로 이어진다면, 확정된 정책이 기능변경 이슈의 작업 범위와 완료 기준에 반영되어야 한다.
- 기능결함에서 이어진 정책검토라면, 확정된 정책이 원본 기능결함 이슈의 원인, 해결 방향, 완료 기준에 반영되어야 한다.
- 위 조건이 충족되고 `검토 결과`가 최종 결정과 근거를 설명하면 정책검토 이슈를 닫는다.

#### 기능변경 이슈

기능변경은 기능제안, 정책검토, 기능결함에서 변경 필요가 확정된 뒤 생성되는 실행 이슈다.

Workflow Skill은 열린 기능변경 이슈를 작업 범위와 완료 기준 추적 대상으로 읽는다. 기능변경 이슈는 승인된 개발 계획에 따라 하나 이상의 기능 구현 흐름으로 이어질 수 있다.

| 항목                           | 작성 지침                                                                                                 |
| ------------------------------ | --------------------------------------------------------------------------------------------------------- |
| `어떤 기능을 변경하려 하나요?` | 추가하거나 수정할 기능과 주요 사용 흐름을 적는다.                                                         |
| `왜 필요한가요?`               | 해결할 사용자 문제, 제품 목표, 기준 문서와의 관계를 적는다.                                               |
| `작업 범위는 어디까지인가요?`  | 포함할 범위와 제외할 범위를 나누어 적는다.                                                                |
| `어떤 효과가 기대되나요?`      | 기능이 추가되거나 수정되었을 때 기대되는 효과를 적는다.                                                   |
| `완료 기준은 무엇인가요?`      | 기능별로 완료 여부를 판단할 수 있는 구체적인 기준을 체크리스트로 적는다.                                  |
| `추가 정보`                    | 구현 계획 수립에 필요한 추가 맥락을 적는다.                                                               |
| `연관 이슈`                    | 이 기능변경 이슈를 만들게 된 원본 기능제안, 정책검토, 기능결함 이슈가 있으면 적는다. 없으면 `N/A`로 둔다. |

#### 기능결함 이슈

기능결함은 결함, 회귀, 문서와 구현 불일치, 반영 누락 보고를 정리하는 시작점이다. 사용자가 직접 작성하거나, 비정형 보고를 Issue Creation Skill이 초안으로 정리하고 사용자가 승인한 뒤 생성한다.

Workflow Skill은 열린 기능결함 이슈를 원인 파악과 해결 판단 대상으로 읽는다. 결함이 아니면 닫고, 정책검토가 필요하면 정책검토 흐름으로 이어가며, 정책 수정이 필요 없으면 기능결함 이슈의 대응 방향과 완료 기준을 기준으로 해결 계획을 세운다.

| 항목                                        | 작성 지침                                                                                              |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `어떤 문제가 있나요?`                       | 결함, 회귀, 문서와 구현 불일치, 반영 누락 내용을 적는다.                                               |
| `문제 유형은 무엇인가요?`                   | `코드 버그`, `문서와 구현 불일치`, `정책 문서 간 불일치`, `반영 누락`, `기타` 중 해당 항목을 체크한다. |
| `재현 과정 또는 확인 위치가 어떻게 되나요?` | 문제가 확인되는 화면, 파일, 문서, 이슈, PR을 적는다.                                                   |
| `올바른 동작은 어떻게 되나요?`              | 수정 후 기대되는 동작을 적는다.                                                                        |
| `원인과 해결 방향은 무엇인가요?`            | 생성 시에는 원인과 해결 방향을 확정하지 않는다. 원인 조사 후 `원인`과 `해결 방향`을 갱신한다.          |
| `완료 기준은 무엇인가요?`                   | 결함 해결 여부를 판단할 수 있는 구체적인 기준을 체크리스트로 적는다.                                   |
| `추가 정보`                                 | 재현 보조 정보, 참고 링크, 판단 보류 사유 등 추가 맥락을 적는다.                                       |

### 연관 이슈와 후속 작업 기록 지침

`연관 이슈`는 이 이슈나 PR이 생성된 근원지 또는 작업 범위를 결정하는 근거 이슈를 기록하는 용도다. 후속으로 생성된 이슈나 PR 번호를 원본 이슈의 `연관 이슈`에 역방향으로 누적하지 않는다.

- 기능제안 이슈에서 정책검토 이슈를 만들면, 새 정책검토 이슈의 `연관 이슈`에 원본 기능제안 이슈 번호를 기록한다.
- 기능제안 이슈에서 기능변경 이슈를 만들면, 새 기능변경 이슈의 `연관 이슈`에 원본 기능제안 이슈 번호를 기록한다.
- 기능결함 이슈에서 정책검토 이슈를 만들면, 새 정책검토 이슈의 `연관 이슈`에 원본 기능결함 이슈 번호를 기록한다.
- 정책검토 이슈에서 기능변경 이슈를 만들면, 새 기능변경 이슈의 `연관 이슈`에 원본 정책검토 이슈 번호를 기록한다.
- 정책검토 결과를 기존 기능변경 이슈에 반영하면, 기존 기능변경 이슈의 `연관 이슈`에 정책검토 이슈 번호를 추가한다.
- PR의 `연관 이슈`에는 해당 PR이 반영하는 정책검토, 기능변경, 기능결함 이슈 번호를 기록한다.

원본 이슈의 완료기준 체크리스트에는 필요한 경우 해당 체크항목의 근거가 되는 이슈나 PR 번호를 항목 뒤 괄호로 붙일 수 있다.

```markdown
- [x] 정책 검토 필요 (#29)
- [x] 설계 문서 반영 PR merge 확인 (#32)
```

### PR 연결 기준

PR은 성격에 따라 정책검토, 기능변경, 기능결함 이슈와 연결한다.

- PR Proposal Skill은 변경 내용과 연관 이슈를 바탕으로 PR 제목과 설명 초안을 작성한다.
- 사람은 PR 제목과 설명이 이슈, 변경 범위, 검증 결과를 적절히 설명하는지 승인한다.
- PR Creation Skill은 승인된 제목과 설명으로 PR을 생성한다.
- PR은 기본적으로 `Refs #번호`로 연관 이슈를 기록한다.
- Workflow Skill은 GitHub 공식 linked issue 관계가 아니라 PR 본문의 `연관 이슈` 섹션을 파싱해 연결 이슈를 판단한다.
- Workflow Engine이 관리하는 이슈에는 `Closes #번호`, `Fixes #번호`, `Resolves #번호`처럼 GitHub가 issue를 자동 close할 수 있는 키워드를 사용하지 않는다.
- GitHub sidebar의 linked issue 수동 연결은 표준 흐름에서 사용하지 않는다.
- 이슈 close는 PR merge 후 Workflow Skill이 완료 기준과 후속 작업을 반영한 뒤 수행한다.
- 정책검토 결과를 설계 문서에 반영하는 PR은 정책검토 이슈와 연결한다.
- 기능 구현 PR은 기능변경 이슈와 연결한다.
- 결함 해결 PR은 기능결함 이슈와 연결한다.

PR Proposal Skill은 PR 템플릿 섹션을 다음 기준으로 작성한다. 이 지침은 PR 본문에 복사하지 않는다.

| PR 섹션                                                   | 작성 지침                                                                                                     |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `왜 변경하려 하시나요?`                                   | 변경 이유와 기준 이슈의 요구를 명확하게 적는다.                                                               |
| `어떻게 변경하려고 하나요?`                               | 주요 변경 방식, 설계 반영 방향, 구현 접근을 적는다. 해당 사항이 없으면 `N/A`로 둔다.                          |
| `해당 변경으로 영향받거나 검토해야 할 사항은 무엇인가요?` | 영향 범위, 검토가 필요한 문서/코드 경계, 위험 요소를 적는다. 해당 사항이 없으면 `N/A`로 둔다.                 |
| `머지 전 확인 사항`                                       | merge 전에 반드시 확인해야 하는 검증, 승인, 수동 작업을 체크리스트로 적는다. 해당 사항이 없으면 `N/A`로 둔다. |
| `연관 이슈`                                               | 이 PR이 반영하는 정책검토, 기능변경, 기능결함 이슈를 `Refs #번호` 형식으로 적는다.                            |

### Claude Code Review Skill 연동 정책

Claude Code Review Skill은 변경사항을 독립적으로 검토하고 리뷰 결과를 생성하는 역할이다. Codex는 PR diff 또는 브랜치 diff와 연결 이슈 맥락을 준비하고, 비대화형 `claude` CLI 호출로 Claude Code Review Skill을 실행한다. 리뷰 결과를 review thread 또는 요약 피드백 댓글로 게시하는 작업은 Review Comment Skill이 담당하고, 파일 수정과 피드백 대응 진행은 Codex가 담당한다.

Claude Code Review Skill은 다음 시점에 실행한다.

- 정책검토, 기능변경 또는 기능결함 PR이 생성된 뒤
- 사람이 별도 리뷰를 요청한 뒤
- 위험도가 높은 설계/정책 변경이 포함된 뒤
- 이전 리뷰 피드백 반영 후 재확인이 필요한 경우

입력은 다음과 같다.

- PR 번호
- 연결된 정책검토, 기능변경 또는 기능결함 이슈
- 변경 diff
- 완료 기준
- 검토에서 제외할 범위

출력은 다음 정보를 포함하는 리뷰 결과다.

- 발견한 문제
- 근거 파일 또는 문서 위치
- diff 위치 또는 라인 정보
- 위험도
- 추천 분류: 적용 / 보류 / 거절 / 정책검토 필요 / 사람 승인 필요
- 확신도

Claude Code Review Skill은 review thread 게시, PR comment 게시, 파일 수정을 직접 수행하지 않는다. Review Comment Skill은 리뷰 결과를 review thread 또는 요약 피드백 댓글로 게시한다. Codex는 미해결 review thread와 미체크 요약 피드백을 수집해 사용자에게 대응 방향을 제안하고, 사람이 승인한 항목만 수정한다.

### Review Feedback Triage

Review Feedback Triage는 리뷰 피드백을 바로 수정 명령으로 보지 않고, 사람이 액션을 결정할 수 있도록 분류와 맥락을 제공하는 절차다.

이 분류는 대응 방향을 정하기 위한 판단 기준이다. GitHub 처리 상태는 Pull Request review thread의 `isResolved` 값과 요약 피드백 댓글의 체크리스트 상태로 관리한다.

라인 피드백은 review thread로 게시하고 `isResolved`로 해결 여부를 추적한다. 라인에 붙일 수 없는 설계/정책 수준 피드백은 일반 PR comment 전체를 의미 분석해 수집하지 않는다. Review Comment Skill이 `<!-- codex-harness:summary-feedback v1 -->` marker가 있는 요약 피드백 댓글로 게시하고, Workflow Skill은 PR의 issue comments 중 이 marker가 있는 댓글만 찾아 체크리스트의 미체크 항목을 미해결 요약 피드백으로 본다. 사용자가 대응 방향을 승인하면 Codex가 필요한 작업이나 근거 기록을 수행하고 같은 요약 피드백 댓글의 체크항목을 체크한다. `보류`, `거절`, `정책검토 필요`처럼 파일 수정이 없는 대응도 사용자가 승인한 근거가 기록되면 처리 완료로 본다.

| 분류           | 의미                            | 후속 액션                     |
| -------------- | ------------------------------- | ----------------------------- |
| 적용           | 실제 결함 또는 명확한 개선      | 해당 PR 범위 안에서 수정      |
| 보류           | 더 많은 맥락 필요               | 이슈 또는 PR에 보류 사유 기록 |
| 거절           | 오탐 또는 범위 밖 제안          | 거절 근거 기록                |
| 정책검토 필요  | 정책, 설계, 운영 기준 판단 필요 | 정책검토 이슈 생성            |
| 사람 승인 필요 | 고위험 변경 또는 애매한 판단    | Human Checkpoint로 전달       |

리뷰 피드백을 사람에게 전달할 때 포함할 맥락은 다음과 같다.

- 피드백 원문
- 관련 파일 또는 문서 위치
- 예상 영향
- 적용/보류/거절/정책검토 필요/사람 승인 필요 분류
- 추천 액션
- 확신도
- 자동 수정 시 위험 요소

Triage 결과는 자동 수정 승인으로 해석하지 않는다. 사람이 액션을 확정한 뒤에만 수정 작업으로 넘긴다.

## 워크플로우 흐름 명세

### 다음 계획 요청 처리

다음 계획 요청은 사용자가 “다음 계획이 무엇인지” 또는 “다음 계획을 진행해달라”고 요청했을 때 Workflow Skill이 GitHub Run State를 읽고 다음 작업 후보를 판단하는 흐름이다. 이 흐름은 병렬 작업을 전제로 하지 않으며, 한 번에 하나의 계획만 다룬다.

다음 계획 요청 처리는 특정 이슈나 PR이 선택되기 전의 후보 선정 규칙이다. 따라서 State Transition Rule 표가 아니라 우선순위, 대상, 판단 기준을 드러내는 후보 판단 표로 작성한다.

“다음 계획” 요청은 기능제안 워크플로우의 시작 조건이 아니다. 특정 작업의 재개 명령도 아니다. 진행 중인 작업이 없는 상태에서 이어갈 수 있는 열린 계획이 있는지 확인하는 요청이다.

진행 중인 작업이 있는데 사용자가 다음 계획을 요청하면 병렬 진행 요청으로 해석될 수 있다. 현재 설계 범위에서는 이런 경우 새 계획 후보를 판단하지 않는다. 먼저 진행 중인 작업을 완료하거나, 전역 중단/재개 흐름에 따라 중단 또는 보류해야 한다. 열린 PR은 진행 중인 작업으로 보며, 상태에 따라 merge 대기 안내 또는 PR 진행 재개로 처리한다.

Workflow Skill은 다음 순서로 작업 대상을 판단한다.

| 액션 이름          | 우선순위 | 대상                     | 판단 기준                                                                                                                                                                                                                 | 작업 내용                                                                                                                                                                                                    |
| ------------------ | -------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

이어갈 수 있는 열린 계획은 새 기능제안 이슈 작성 흐름보다 항상 우선한다. Workflow Skill은 기능제안 이슈를 임의로 진행하지 않고, 종료/정책검토/기능변경 선택지를 제시한 뒤 사용자가 결정한 경우에만 다음 액션으로 넘어간다.

### 기능제안 흐름

### 정책검토 흐름

정책검토는 독립적인 워크플로우 시작점이 될 수 있고, 기능제안/기능결함 흐름에서 이어질 수도 있다. 정책검토 이슈는 결정 내용, 설계 문서 반영 여부, 결정된 정책을 기준으로 한 기능변경 이슈 반영 여부를 관리한다. `검토 결과`는 최초 논의 초안이 아니라 설계 문서 반영과 PR 리뷰 과정에서 보강된 최종 정책 결정을 담는다. 같은 결정 질문 안에서 정책 내용이 구체화되면 정책검토 이슈의 `검토 결과`를 최신 결정으로 갱신한다. 원래 결정 질문을 벗어난 새 정책 판단이 필요하면 별도 정책검토 이슈로 분리한다. 독립 정책검토나 기능제안에서 이어진 정책검토는 기능변경 이슈 생성으로 이어진다. 정책검토 결과를 기존 기능변경 이슈에 함께 반영해야 하면 대상 기능변경 이슈의 작업 범위, 완료 기준, 연관 이슈에 반영한다. 기존 기능결함 이슈에서 이어진 정책검토는 원본 기능결함 이슈의 원인/해결 방향과 완료 기준 반영으로 이어진다.

### 기능결함 흐름

### 기능 구현 흐름

기능 구현 흐름은 정책검토, 기능변경, 기능결함에서 실제 파일 변경과 PR 생성이 필요한 경우에 공통으로 적용한다. 이 문서에서 `구현 단위`는 설계 문서 반영 단위, 기능 구현 단위, 결함 해결 단위를 포함한다. 정책검토에서는 설계 문서 반영 단위마다 하나의 브랜치와 하나의 PR로 진행한다. 기능변경에서는 기능 개발 계획에 포함된 각 기능 구현 단위마다 하나의 브랜치와 하나의 PR로 진행한다. 기능결함에서는 기능 결함 해결 계획에 포함된 각 결함 해결 단위마다 하나의 브랜치와 하나의 PR로 진행한다. 하나의 기능 구현 흐름 안에서는 해당 구현 단위를 다시 커밋 단위로 나누는 세부 구현 계획을 세우고, 커밋 단위별 변경과 커밋 메시지 승인을 반복한다. 정책검토, 기능변경, 기능결함 흐름은 기능 구현 흐름으로 들어가는 조건과 PR merge 이후 이슈 갱신만 다룬다. 브랜치 제안, 세부 구현 계획, 커밋 단위 구현, PR 생성, 리뷰, 피드백 대응, merge 대기는 이 섹션에서 다룬다.

Workflow Skill은 PR merge를 상시 감시하지 않는다. 사용자가 PR이 merge되었다고 알리거나, 다음 계획 요청으로 GitHub Run State를 다시 읽을 때 merge된 PR을 확인하고 연결 이슈의 후속 전이를 적용한다.

PR 리뷰 과정에서 Claude Code Review Skill은 피드백을 포함한 리뷰 결과를 만든다. Review Comment Skill은 파일 경로와 diff line이 있는 피드백을 review thread로 게시하고, 라인에 붙일 수 없는 피드백은 marker가 있는 요약 피드백 댓글의 체크리스트로 게시한다. Codex는 미해결 review thread와 미체크 요약 피드백을 모아 피드백별 추천 액션과 근거를 설명할 수 있다. 적용/보류/거절/정책검토 필요/사람 승인 필요 중 어떤 액션을 선택할지는 사람이 확정한다.

기본 흐름은 다음과 같다.

```text

  -> 사용자가 브랜치 이름 승인
  -> 승인된 브랜치로 이동
  -> Codex가 해당 구현 단위의 세부 구현 계획과 커밋 단위 분할 계획 작성
```

리뷰 피드백의 액션 분류와 전달 맥락은 Review Feedback Triage를 따른다. Claude Code Review Skill과 Codex는 액션을 추천할 수는 있지만 확정하지 않는다. 확정 권한은 사람에게 있다.

## 적용과 관리 구조

이 섹션은 `codex-harness`가 GitHub Workflow Engine의 기본 구조를 어떻게 관리하고, 타겟 프로젝트에 어떤 자산을 적용하는지 정의한다.

### GitHub Template Bootstrap

GitHub Template Bootstrap은 GitHub Workflow Engine을 타겟 레포에 적용하기 위해 필요한 이슈 템플릿, PR 템플릿, 라벨, 운영 문서의 기본형을 생성하거나 갱신하는 흐름이다.

`codex-harness`는 다음 기본형을 관리한다.

- 기능제안 이슈 템플릿
- 정책검토 이슈 템플릿
- 기능변경 이슈 템플릿
- 기능결함 이슈 템플릿
- Pull Request 템플릿
- GitHub Workflow Engine 운영 문서
- Workflow Skill 전역 스킬 기본형
- Issue Creation Skill 전역 스킬 기본형
- 기능 개발 계획 Skill 전역 스킬 기본형
- Fix Plan Skill 전역 스킬 기본형
- Branch Name Skill 전역 스킬 기본형
- Commit Message Skill 전역 스킬 기본형
- PR Proposal Skill 전역 스킬 기본형
- PR Creation Skill 전역 스킬 기본형
- Claude Code Review Skill 전역 스킬 기본형
- Review Comment Skill 전역 스킬 기본형
- 기본 라벨 세트

GitHub Template Bootstrap은 다음 원칙을 따른다.

- `codex-harness`는 표준 기본형과 생성 규칙의 원천이다.
- Workflow Engine 스킬은 Codex 전역 스킬로 설치하고 관리한다.
- 타겟 레포는 적용된 템플릿과 프로젝트별 변형의 소유자다.
- GitHub Workflow 운영 구조 생성은 사용자의 타겟 프로젝트 구축 요청 범위 안에서 수행한다.
- 기존 타겟 레포 템플릿을 덮어쓸 수 있으면 diff와 영향 범위를 사용자에게 보여준다.
- 타겟 레포에서 발견한 개선점은 자동으로 `codex-harness`에 역반영하지 않는다.
- 공통화할 가치가 있는 변경만 사용자 승인 후 `codex-harness` 기본형으로 승격한다.

### codex-harness 관리 구조

현재 `codex-harness`의 전역 배포본은 `harness` 스킬이다. `harness` 스킬은 타겟 레포의 하네스 구조를 설계, 생성, 정렬, 검증하는 기반 스킬이며, GitHub Workflow Engine도 이 기반 위에서 템플릿과 운영 기준을 적용한다.

Workflow Engine 전용 스킬은 `harness` 스킬을 대체하지 않는다. 상태 전이, 이슈 생성, 계획 수립, PR 제안, 리뷰 코멘트 게시처럼 반복 실행이 필요한 책임을 분리하기 위한 후속 확장이다. 전용 스킬 배포본과 설치 스크립트 확장이 준비되면 `codex-harness`는 다음 목표 구조로 관리한다.

```text
codex-harness/
├── docs/
│   └── github-workflow-engine.md
├── .github/
│   ├── ISSUE_TEMPLATE/
│   │   ├── proposal_template.md
│   │   ├── decision_template.md
│   │   ├── feature_template.md
│   │   └── fix_template.md
│   └── pull_request_template.md
└── .codex-dist/
    └── skills/
        ├── github-workflow-engine/
        │   └── SKILL.md
        ├── issue-creation/
        │   └── SKILL.md
        ├── feature-plan/
        │   └── SKILL.md
        ├── fix-plan/
        │   └── SKILL.md
        ├── branch-name/
        │   └── SKILL.md
        ├── commit-message/
        │   └── SKILL.md
        ├── pr-proposal/
        │   └── SKILL.md
        ├── pr-creation/
        │   └── SKILL.md
        ├── claude-code-review/
        │   └── SKILL.md
        └── review-comment/
            └── SKILL.md
```

이 구조는 목표 표준 기본형이다. 현재는 `harness` 스킬이 설치 가능한 기반 배포본이고, Workflow Engine 전용 스킬이 준비되면 `.codex-dist/skills/*` 아래 스킬을 Codex 전역 스킬 경로에 추가 설치해 타겟 레포를 읽고 실행한다. 타겟 레포에 로컬 스킬로 복사하지 않는다.

실제 타겟 레포에 적용된 템플릿은 타겟 레포의 맥락에 맞게 달라질 수 있다. 공통화할 가치가 있다고 사용자가 판단한 경우에만 `codex-harness` 기본형으로 승격한다.

### 타겟 프로젝트 적용 구조

`codex-harness`가 타겟 프로젝트에 GitHub Workflow Engine 운영 기준을 생성할 때는 다음 자산을 적용 후보로 둔다.

```text
target-repo/
├── .github/
│   ├── ISSUE_TEMPLATE/
│   │   ├── proposal_template.md
│   │   ├── decision_template.md
│   │   ├── feature_template.md
│   │   └── fix_template.md
│   └── pull_request_template.md
└── .harness/
    └── logs/
        └── github-workflow-log.md
```

타겟 프로젝트에는 Workflow Engine 스킬을 생성하지 않는다. 전역 Workflow Engine 스킬이 타겟 레포의 GitHub Issue, PR, 템플릿을 기준으로 상태 전이를 수행하고, 실행 로그는 보조 기록으로 참고한다.

타겟 프로젝트의 도메인과 기존 운영 방식에 따라 운영 문서 경로는 달라질 수 있다. 중요한 기준은 GitHub Issue와 PR이 프로젝트 상태의 기준이며, 별도 Runtime 상태 저장소가 필수가 아니라는 점이다.

## 운영 메모

- 이슈 제목 prefix와 라벨은 템플릿 기준을 따른다.
- 이슈 본문에 Workflow Engine 규칙을 반복해서 적지 않는다.
- 사용자의 비정형 기능 요청은 Issue Creation Skill이 기능제안 템플릿 초안으로 정리한다.
- 기능제안 이슈는 사용자가 직접 작성하거나 Issue Creation Skill의 도움을 받아 생성할 수 있다.
- 기능제안 이슈가 생성되면 “다음 계획” 요청을 기다리지 않고 Workflow Skill이 열린 기능제안 이슈로 읽고 상태 전이를 적용한다.
- 사용자의 비정형 기능결함 보고는 Issue Creation Skill이 기능결함 템플릿 초안으로 정리한다.
- 기능결함 이슈는 사용자가 직접 작성하거나 Issue Creation Skill의 도움을 받아 생성할 수 있다.
- 기능결함 이슈가 생성되면 “다음 계획” 요청을 기다리지 않고 Workflow Skill이 열린 기능결함 이슈로 읽고 상태 전이를 적용한다.
- “다음 계획” 요청은 병렬 워크플로우를 전제로 하지 않으며, 진행 중인 작업이 없는 상태에서 이어갈 수 있는 열린 계획이 있는지 판단하기 위한 요청이다.
- 모든 액션 진입은 `.harness/logs/github-workflow-log.md`에 로컬 실행 로그로 남긴다. 승인된 계획과 진행상태는 먼저 GitHub 이슈나 PR에 반영하고, 같은 내용을 로그에 보조 체크포인트로 남길 수 있다.
- 재개는 새 워크플로우 시작이 아니라 GitHub Run State와 현재 코드 상태를 먼저 읽어 이어갈 액션을 선택하는 것이다. 체크포인트는 실제 상태와 맞을 때만 진행 맥락 복원에 참고한다.
- 이슈 생성은 항상 이슈 유형별 템플릿, 필수 항목, 라벨, 연관 이슈 규칙을 따른다.
- 이슈는 사용자 승인 없이 생성하지 않는다.
- GitHub 템플릿과 라벨 생성/갱신은 사용자의 타겟 프로젝트 구축 요청 범위 안에서 수행한다.
- `codex-harness`는 GitHub Workflow 템플릿 기본형의 소유자이고, 타겟 레포는 적용된 템플릿의 소유자다.
- 진행 중인 작업이 있으면 다음 계획 후보를 판단하지 않는다. 이어갈 수 있는 열린 계획이 있으면 신규 기능제안 후보보다 해당 계획을 우선한다.
- 기능제안 이슈 선택 후에도 종료, 정책검토 전환, 기능변경 전환은 사용자가 결정한다.
- 상태 전이는 LLM 자유 판단이 아니라 Workflow Skill의 규칙으로 정한다.
- LLM은 이슈 요약, 선택지 설명, 추천 근거 작성, 이슈 본문 초안 작성에 사용할 수 있지만 상태 전이 또는 이슈 생성 승인 권한을 갖지 않는다.
- 흐름이 애매하면 새 이슈를 만들기보다 현재 이슈에 판단 근거를 먼저 남긴다.
- 작업 중 정책 판단이 필요해지면 구현을 계속 진행하기 전에 정책검토 이슈를 만든다.
- 리뷰 피드백은 자동 수정 명령이 아니라 판단 대상이다.
- 리뷰 피드백별 액션은 PR 과정에서 사용자가 직접 결정한다.
- 실제 반영 여부는 연결 이슈의 후속 작업 또는 완료 기준과 PR 리뷰에서 확인한다.
- PR merge는 사람이 수행하고, Workflow Skill은 사용자의 merge 알림 또는 다음 계획 요청 시 GitHub Run State를 다시 읽어 관련 이슈의 진행 상태와 체크리스트에 반영한다.
