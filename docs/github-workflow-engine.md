# GitHub Workflow Engine 설계

이 문서는 `codex-harness`가 GitHub Issue와 Pull Request를 기준으로 작업 상태를 읽고 다음 작업을 결정하기 위한 설계 기준이다.

이 문서는 Workflow Engine의 배경, 이유, 책임 경계와 상태 모델, 선언형 워크플로우 정의 계약을 설명하는 설계 원천이다. 런타임의 작업 전이는 `definitions/*.json`, 각 state adapter와 `evaluator.mjs`가 단일 원천으로 평가한다. 세부 런타임 계약은 목적별 reference와 `SKILL.md`에 있으며 이 설계 문서는 런타임 입력으로 사용하지 않는다. 과거 이슈의 결정 기록은 설계와 실행 계약에 반영된 뒤 별도 원천으로 취급하지 않는다.

## 문서 역할

- 스킬 문서는 선언형 런타임의 오케스트레이션 순서만 담는다.
- 목적별 runtime reference는 상태 관측, 산출물, 리뷰, 구조화 실행과 검증 모드 계약을 각각 담는다.
- 배경, 이유, 설계 설명은 이 설계 문서에 두며 런타임은 이 문서를 읽지 않는다.

설계는 다음 질문의 배경과 책임 관계를 설명할 수 있어야 한다.

- 어떤 이슈 또는 PR을 기준 대상으로 삼아야 하는가
- 다음 작업을 판단하기 위해 기준 대상의 어떤 체크리스트, PR, 리뷰, 댓글 상태를 읽어야 하는가
- 읽은 상태에서 완료 근거, 미완료 근거, 보조 근거, 무효 근거는 무엇인가
- 어떤 Workflow Definition과 state adapter를 선택하며 현재 `task_action_id`는 무엇인가
- 실행 오케스트레이션과 전용 스킬의 책임은 어떻게 나뉘는가
- 현재 작업에 사용자 결정이 필요한가, 필요하다면 무엇을 결정해야 하는가
- 어떤 GitHub 상태 또는 파일 상태를 어느 범위까지 변경해도 되는가

## 설계 목표

- GitHub 이슈와 PR을 프로젝트 작업 상태의 기준 상태 원천으로 사용한다.
- 사람이 보는 작업 상태와 Agent가 읽는 작업 상태를 일치시킨다.
- 상태 전이는 언어 모델의 자유 판단이 아니라 Workflow Definition과 evaluator의 결정론적 평가를 따른다.
- 정책 판단, 설계 변경, 커밋 메시지 확정, PR merge처럼 사용자 결정이 필요한 작업은 사용자 결정을 거친다.
- 하나의 작업을 끝낸 뒤 사용자 결정, 중단, 오류, 완료 조건 중 하나에 닿을 때까지 다음 작업 판단을 이어간다.
- 이슈 초안 작성과 실제 GitHub 상태 변경을 분리한다.
- `github-agentic-loop`는 얇은 오케스트레이터로 유지하고, 생성·분석·제안 책임은 전용 스킬이나 필요한 경우 좁은 서브에이전트 위임으로 분리한다.
- 경량 모델은 읽기 전용 상태 요약, 후보 분류, 단순 라우팅, 참조문서 추출과 실행 내용이 확정된 단순 상태 변경처럼 실패 비용과 판단 범위가 낮은 작업에만 적용 후보로 둔다.
- 전이 매칭과 평가는 검증기와 평가기가 담당한다. LLM은 근거에 묶인 의미 사실과 사용자 결정 입력만 구조화해 반환하며 `task_action_id`를 추론하지 않는다.
- 확정된 단순 상태 변경은 결정론적 실행기를 우선하고, 결정론적 실행이 불가능할 때만 제한된 저비용 서브에이전트에 맡긴다.
- 코드 수정은 `workflow-code-editor`가 Harness 일반 진입점 또는 현재 Codex 세션의 일반 코드 변경 경로 중 하나를 실행 전에 선택하며, PR 리뷰 생성은 선택된 리뷰 실행 모드가 수행한다.
- GitHub Workflow Engine의 설계 문서, 템플릿, 배포본 스킬 기본형은 `codex-harness`에서 관리하고 타겟 레포에 적용한다.

## 핵심 개념

이 섹션은 Workflow Engine이 현재 작업을 산출하고 실행 여부를 판단할 때 사용하는 기본 용어를 정의한다. 용어는 상태 원천, 사실의 종류와 정규화, 워크플로우 정의 계약, 근거 분류, 이슈 유형, 선언형 작업 평가, 현재 작업과 진행 판단, 사용자 결정, 실행 범위 순서로 이어진다.

### GitHub 실행 상태

GitHub 실행 상태는 Workflow Engine이 현재 작업 상태를 판단하기 위해 GitHub에서 읽는 상태 값이다. 별도 로컬 상태 파일은 기준 상태 원천으로 사용하지 않는다. PR 리뷰 피드백 상태는 diff가 있는 review thread의 resolved/unresolved 상태를 원천으로 읽는다.

| 상태 원천                   | 역할                                                            |
| --------------------------- | --------------------------------------------------------------- |
| Issue title                 | 이슈 유형과 작업 주제를 식별한다.                               |
| Issue label                 | 이슈 유형별 라벨 집합인 `기능제안`, `정책검토`, `기능변경`, `기능결함` 중 하나로 이슈 유형을 식별한다. |
| Issue body                  | 구조화된 섹션에서 판단 근거, 범위, `완료 기준은 무엇인가요?`, `후속 작업은 무엇인가요?` 후보를 읽는다. |
| Issue checklist             | `완료 기준은 무엇인가요?`와 정책 반영 상태를 읽는다.             |
| Issue state                 | 작업이 열려 있는지 닫혔는지 읽는다.                             |
| Pull Request body           | 변경 이유, 영향 범위, `연관 이슈 (optional)` 섹션의 이슈 번호를 읽는다. |
| Pull Request state          | open, closed, merged 여부를 읽는다.                              |
| Pull Request review threads | diff가 있는 리뷰 피드백과 review thread의 resolved/unresolved 상태를 리뷰 피드백 상태 원천으로 읽는다. |
| Pull Request issue comments | 리뷰 피드백 상태 원천으로 쓰지 않는다. |

### 상태 근거 묶음

상태 근거 묶음은 GitHub 실행 상태와 현재 코드 상태, 보조 로그에서 읽은 근거를 다음 네 묶음으로 분류한 결과다.

| 묶음        | 포함할 수 있는 근거                                                                            |
| ----------- | ---------------------------------------------------------------------------------------------- |
| 완료 근거   | 체크된 완료 조건, merged PR, resolved review thread |
| 미완료 근거 | 체크되지 않은 완료 조건, merged가 아닌 연결 PR, unresolved review thread |
| 보조 근거   | 현재 코드 상태, 보조 로그, 현재 대화에서 확인한 마지막 관련 작업, 마지막 사용자 결정, 마지막 실행 결과 |
| 무효 근거   | 이슈 본문의 일반 설명, 추천 문장, 선택되지 않은 후보, 구조화된 스킬 출력 필드 밖의 설명 문장 |

완료 근거와 미완료 근거는 GitHub 실행 상태에서 읽는다. 보조 근거는 GitHub 실행 상태로 표현되지 않는 중간 실행 상태를 판단할 때만 사용하며, 현재 작업 확정 근거로 단독 사용하지 않는다. 보조 근거가 완료 근거 또는 미완료 근거와 충돌하면 GitHub 실행 상태를 우선한다.

### 사실의 종류와 정규화

Workflow Engine이 전이를 평가할 때는 관찰된 사실과 의미 해석 결과를 구분한다.

- 결정론적 사실은 GitHub API 조회 결과, 로컬 파일 상태, Git 상태, 명시된 사용자 입력처럼 같은 입력에서 같은 값이 나오는 사실이다.
- LLM이 도출하는 의미 사실은 이슈 본문의 의도, 리뷰 피드백의 의미, 자연어로 표현된 완료 근거처럼 관찰값을 해석한 결과다. 이 결과는 반드시 구조화된 필드와 원본 근거 위치를 함께 반환해야 한다.
- LLM은 관찰하지 않은 GitHub 또는 로컬 상태를 사실로 만들 수 없다. 근거가 없거나 서로 충돌하는 의미 사실은 `불확실` 또는 `충돌`로 반환하며, 값을 추측해 채우지 않는다.

선언형 전이 설계에서 정규화는 결정론적 사실을 표준 필드로 바꾸고, 필요한 의미 사실을 근거에 연결된 구조화 결과로 바꾸는 단계다. 전이 조건은 정규화된 사실만 읽으며, 자연어 설명이나 LLM의 자유 형식 판단을 직접 읽지 않는다.

### Evaluation-cycle observation snapshot

Workflow Engine은 한 평가 주기에서 같은 GitHub Issue·PR과 local repository 원본을 state adapter와 thin
skill이 각각 다시 조회하지 않도록 content-addressed observation snapshot을 준비한다. Snapshot identity는
repository, 조회 시점, source type·identifier, GitHub `updatedAt`·body digest·PR base/head SHA와 local
HEAD·worktree digest를 포함하며 `input_snapshot_digest`로 식별한다.

`snapshot-runtime.mjs`는 현재 `request_id` 안에서 exact source identity와 digest가 같은 immutable raw
source만 공유한다. 같은 cycle의 state adapter와 thin skill은 `observation_snapshot_consumer_input`을 받아
같은 source object를 사용한다. 새 재개 request, GitHub body·head 변화, local HEAD·worktree 변화는 이전
runtime을 무효화하고 새 snapshot을 준비한다. 닫힌 runtime이나 embedded digest가 손상되면 이전 source를
부분 사용하거나 재계산으로 보정하지 않고 fail-closed 중단한다.

Snapshot은 특정 시점의 raw 관측 baseline이지 Workflow 실행 결과 cache가 아니다. 의미 판단, artifact
handoff·receipt, renderer 결과, 사용자 결정과 다음 작업은 저장하거나 재사용하지 않는다. PR 생성,
review thread 게시, merge, 권한과 remote branch처럼 실행 계약이 요구한 live preflight 또는 실행 직전
재검증은 snapshot hit와 관계없이 새로 수행한다. GitHub live state가 snapshot·로그·repository profile과
충돌하면 GitHub 실행 상태를 우선한다.

### 워크플로우 정의 계약

워크플로우 정의는 이슈 유형별 흐름과 전이를 선언하는 구조화 계약이다. 루트는 정확히 다음 필드를 가진다.

| 필드 | 의미 |
| --- | --- |
| `workflow_id` | 닫힌 워크플로우 식별자이며 작업 ID 접두어를 결정한다. |
| `entry_task_action_id` | 최초로 평가할 작업 ID |
| `facts` | fact ID를 key, 유한 허용값 배열을 value로 갖는 객체 |
| `transitions` | 작업과 다음 작업 규칙의 배열 |

각 작업은 `task_action_id`, `normalized_fact_conditions`, `user_decision_options`,
`completion_predicate`, `executor_reference`, `next_transition_rules`만 가진다. `task_action_id`가 그래프
노드와 동작의 유일한 식별자다. 다음 작업 규칙도 `task_action_id`를 직접 참조하며, 빈
`next_transition_rules`를 가진 작업을 종료 작업으로 추론한다.

`facts`의 값 배열은 비어 있지 않고 boolean, string, integer 중 하나의 동질적인 scalar 타입으로
구성한다. 타입은 값에서 추론한다. 모든 정규화 관측값에는 공통 adapter 계약에 따라 evidence가
필요하다. `user_decision_options`가 비어 있으면 사용자 결정이 없고, 비어 있지 않으면 자유 형식 입력을
허용하는 명시적 사용자 결정을 확정하기 전까지 실행을 중단한다.

워크플로우 정의는 실행 명령이 아니다. 임의의 셸 명령, GitHub 상태 변경 명령, 파일 수정 명령을 포함할 수 없다. `executor_reference`는 직접 실행 대상 식별자일 뿐 실행 권한이나 명령 경로를 선언하지 않는다. Workflow Engine은 워크플로우 정의를 검증하고 조건을 평가한 뒤 구조화 실행 요청으로 선택된 실행 주체를 호출하며, 실행 주체는 요청 범위를 넓힐 수 없다.

별도의 JSON Schema 산출물은 두지 않는다. `validator.mjs`가 닫힌 구조, 필수 필드, 타입, 참조와
그래프 의미를 검사하는 단일 실행 계약이다. 검증기와 평가기는 다음 결과를 오류로 분류한다.

- 존재하지 않는 사실 필드
- 중복된 `task_action_id` 또는 `workflow_id`와 맞지 않는 작업 ID 접두어
- 도달할 수 없는 작업 또는 도달 가능한 완료 조건·종료 작업이 없는 순환
- 조건이 겹쳐 같은 정규화 상태에서 복수 전이가 매칭될 수 있는 워크플로우 정의
- 종료 작업이 아닌데 조건에 맞는 다음 작업이 0개인 결과
- 평가 중 조건에 맞는 전이가 2개 이상인 결과

유효한 워크플로우 정의는 같은 정규화 상태에서 정확히 하나의 다음 작업만 매칭되도록 해야 한다. 빈 `next_transition_rules`인 종료 작업에서만 0개 매칭을 허용한다. 조건 중첩으로 복수 매칭이 가능한 정의는 검증 오류이며, 평가 중 실제로 복수 후보가 나오면 정의 결함으로 `중단`한다.

명시적으로 선언한 리뷰 및 커밋 반복 흐름은 순환 자체만으로 무효로 보지 않는다. `completion_predicate`와 도달 가능한 종료 전이가 있으면 유효할 수 있으며, 검증기와 평가기가 종료 가능성과 사후조건을 검증해야 한다.

정의, 정규화 결과 또는 평가 결과가 유효하지 않거나 모호하면 Workflow Engine은 사용자 결정 또는 `중단`을 산출한다. LLM이 전이를 임의로 고르거나 다수결로 보정하지 않는다.

### Artifact manifest와 renderer

thin 스킬의 structured artifact는 `artifact-manifests/*.json`을 기계 구조의 단일 원천으로 사용한다. manifest는 artifact type별 닫힌 필드 구조, 필수 여부, enum, ID·참조·구현 순서 rule, renderer section 순서를 선언하고 compiler가 source·contract·compiled digest와 immutable lookup을 준비한다. artifact validator는 같은 입력에 안정적인 error code와 JSON Pointer path를 반환하며 구조 오류가 있으면 의미 판정과 후속 실행을 fail closed한다.

`artifact-output-contract.md`는 manifest 구조를 다시 실행하지 않고 사용자 설명과 정책 후보의 타당성, 원인 확인 수준, 계획 범위 적합성, PR template 같은 의미 판정을 소유한다. manifest가 가진 contract section·producer skill·render label과 Markdown·thin skill의 대응은 drift test로 검증한다. renderer는 구조 검증이 성공한 artifact만 manifest 순서대로 Markdown에 표시하며 값을 생성·수정하거나 의미를 판단하지 않는다.

thin skill은 `artifact_type`과 manifest field object만 가진 닫힌 handoff를 생산한다. Workflow Engine의 artifact consumer는 호출한 producer identity와 active compiled manifest의 `contract_digest`를 expected 값으로 고정하고, runtime gate가 승인한 immutable receipt만 의미 판정과 상태 관측에 전달한다. 다음 fact 근거는 receipt와 digest에 연결하며 renderer Markdown을 parse하지 않는다. 구조 오류, stale contract 또는 digest mismatch에서는 의미 판정·상태 정규화·후속 Workflow 계산을 호출하지 않는 fail-closed 경계를 사용한다.

### Immutable PR input과 live preflight

`pr-proposal`이 제목 형식, 본문 template와 연관 이슈 의미를 만족하는 초안을 만들고 사용자가 확정하면,
Workflow Engine은 exact title/body와 base/head/related issue를 닫힌 immutable PR input으로 준비한다. 입력은
type/version과 결정론적 SHA-256 `input_digest`를 가지며 deep-freeze된다. raw artifact나 renderer Markdown을
다시 parse해 PR 생성값을 만들지 않고, serialized input의 shape·digest·현재 확정 원본 mismatch를
fail closed한다.

`pr-creation`은 immutable input identity와 생성 요청의 digest/title/body/base/head exact equality를 확인한
뒤, 실행 직전 remote base/head 존재, expected local head와 remote head OID 일치, same-head open PR 부재만
fresh live preflight로 검증한다. 제목과 본문 의미는 이 단계에서 재판정하지 않는다. 기존 `pr-proposal`과
`pr-creation` artifact public field와 renderer output은 유지하며, identity 또는 live observation mismatch면
PR 생성 실행을 시작하지 않는다.

### 이슈 유형

| 유형       | 목적                                                                                         | 가능한 다음 흐름                            |
| ---------- | -------------------------------------------------------------------------------------------- | ------------------------------------------- |
| `기능제안` | 구현 여부와 처리 유형이 아직 확정되지 않은 기능 추가, 기능 수정, 운영 흐름 개선 요청을 판단한다. | 종료, 정책검토 전환, 기능변경 전환          |
| `정책검토` | 설계, 정책, 운영 기준의 결정을 추적하고 결정된 정책을 설계 원천에 반영한다.                  | 정책 설계 계획 수립, 설계 문서 반영, 기능변경 전환 |
| `기능변경` | 확정된 변경 계획에 따라 코드, 문서, 템플릿, 스킬 같은 실행 산출물을 변경한다.                | 변경 계획, 구현 흐름                        |
| `기능결함` | 원인을 확정하고 해결 계획에 따라 코드, 문서, 템플릿, 스킬 같은 산출물을 함께 변경한다.       | 원인 조사, 결함 해결 계획, 구현 흐름        |

라벨을 이슈 유형의 1차 기준으로 삼는다. 제목 prefix와 라벨이 충돌하거나, 유형 라벨이 없거나, 유형 라벨이 둘 이상이면 사용자 결정으로 넘기고 임의 변경하지 않는다.

### 이슈 유형별 라벨

Workflow Engine이 이슈 유형 판단과 이슈 생성에 사용하는 프로젝트 라벨 집합은 다음 네 가지로 제한한다.

- `기능제안`
- `정책검토`
- `기능변경`
- `기능결함`

이슈 생성 시에는 이슈 유형에 맞는 이슈 유형별 라벨 하나를 반드시 붙인다. 이슈 유형별 라벨 집합에 없는 라벨은 Workflow Engine이 임의로 붙이지 않는다.

Workflow Engine은 현재 작업에서 해당 이슈 유형 라벨을 최초로 필요로 할 때 정확한 이름의 존재 여부를 검사한다. 라벨이 없으면 현재 GitHub 실행 경로와 권한 조건을 확인한 뒤 필요한 라벨 하나만 생성한다. Harness 설치·생성·갱신 과정은 이 라벨을 만들거나 검사하지 않는다.

### 선언형 작업 평가

state adapter는 관측값을 Definition의 fact 집합으로 정규화한다. evaluator는 `currentTaskActionId`의
`normalized_fact_conditions`와 `completion_predicate`를 평가하고 `next_transition_rules`에서 정확히
하나의 다음 `task_action_id`를 산출한다. 현재 작업과 다음 작업은 이 경로 밖에서 이름이나 자연어
조건으로 선택하지 않는다.

`action_required`는 실행할 `task_action_id`, `user_decision_options`, `executor_reference`와
`completion_predicate`를 반환한다. `user_decision_options`가 비어 있지 않으면 사용자 결정 전에는
실행하지 않는다. 종료 작업의 완료 조건이 충족되면 `completed`를 반환하고, 조건 없음·복수 조건,
정규화 실패와 유효하지 않은 작업 ID는 `stopped` 또는 오류로 중단한다.

### 현재 작업과 진행 판단

현재 작업은 evaluator가 반환한 하나의 `task_action_id`다. 매칭되는 작업이 없거나 둘 이상이면 Definition 또는 관측 상태 결함으로 중단한다.

진행 판단은 현재 작업을 어떻게 처리할지 나타내는 값이며, 현재 작업에 대해 하나만 선택한다.

| 값          | 의미                                                              |
| ----------- | ----------------------------------------------------------------- |
| 사용자 결정 | 사용자가 결정해야 하는 대상과 선택 가능한 응답을 제시하고 멈춘다. |
| 자동 실행   | 사용자 결정, 중단, 완료 조건이 없을 때 실행 범위 안에서 현재 작업을 수행한다. |
| 중단        | 정보 부족, 의존성 누락, 실행 오류, 상태 충돌을 제시하고 멈춘다.   |
| 완료        | 기준 대상의 완료 조건이 충족되었음을 제시하고 후속 작업을 산출하지 않는다. |

Workflow Engine은 하나의 작업을 완료하면 즉시 GitHub 실행 상태와 현재 코드 상태를 다시 읽고, 다음 작업과 진행 판단을 산출한다. 진행 판단이 `자동 실행`이면 다음 작업을 실행하고, `사용자 결정`, `중단`, `완료`이면 해당 판단에 따라 멈추거나 종료한다. 이 기준은 사용자가 “다음 절차가 무엇인가요?”라고 다시 물어야만 흐름이 이어지는 상황을 막기 위한 규칙이다.

### 사용자 결정

사용자 결정은 사용자가 선택하거나 확정해야 하며 Workflow Engine이나 Agent가 임의로 넘길 수 없는 지점이다.

Workflow Engine이 사용자 결정을 요청할 때는 결정 대상과 선택 가능한 응답을 번호 목록으로 함께 제시한다. 선택 가능한 응답은 현재 작업의 사용자 결정 필드에서 허용한 응답을 기준으로 하며, 사용자가 다른 의견을 제시할 수 있도록 `기타 의견 입력`을 항상 마지막 번호 항목에 포함한다. `기타 의견 입력`은 번호 목록 밖의 별도 문장으로 제시하지 않는다. 상태 변경을 수행하는 선택지는 변경 대상과 실행 결과를 함께 표시한다.

사용자 결정의 유효 입력 형식은 다음 네 가지다.

- 제시된 번호
- 선택지 문구 그대로
- `기타 의견 입력 항목 번호: 의견`
- `기타 의견 입력: 의견`

사용자가 제시된 번호 또는 선택지 문구를 그대로 입력하면 Workflow Engine은 해당 선택지를 사용자 결정으로 처리한다. 사용자가 `기타 의견 입력` 허용 형식으로 구체 의견을 입력하면 Workflow Engine은 그 의견을 사용자 결정으로 처리한다. 구체 의견이 현재 사용자 결정 대상에 속하고, 실행 범위 안에 있으며, 작업내역으로 수행할 수 있고 완료기준으로 처리 결과를 확인할 수 있으면 해당 작업내역에 따라 진행한다. 세 조건 중 하나라도 만족하지 않으면 GitHub 상태를 변경하지 않고 중단 사유와 재개 조건을 제시한다.

사용자가 `기타 의견 입력` 항목의 번호만 입력했거나 `기타 의견 입력` 문구만 입력하면 Workflow Engine은 기타 의견이 비어 있다고 보고 같은 선택지와 입력 예시를 다시 제시한다. 사용자 입력이 유효 입력 형식 중 어느 것에도 해당하지 않으면 Workflow Engine은 임의로 해석하지 않고 결정 대상을 다시 요약한 뒤 같은 선택지를 번호 목록으로 다시 제시한다. 이때 입력 예시는 번호 입력, 선택지 문구 입력, `기타 의견 입력` 형식을 모두 포함한다. `이대로 진행`, `생성해주세요`, `좋습니다`, `네` 같은 일반 진행 표현은 선택지 문구와 정확히 일치하지 않으면 유효 입력으로 보지 않는다.

예시:

1. 선택지1
2. 선택지2
3. 기타 의견 입력

입력 예시:

- 번호 입력: `1`
- 선택지 문구 입력: `선택지1`
- 기타 의견 입력: `3: 의견 내용` 또는 `기타 의견 입력: 의견 내용`

사용자 결정 대상은 현재 작업의 `user_decision_options`가 단일 원천이다. 배열이 비어 있으면 사용자
결정 없이 실행 범위 안에서 진행하고, 비어 있지 않으면 선언된 선택지를 번호 목록으로 제시한다.

선언되지 않은 사용자 결정을 런타임에서 추가하지 않는다. 새 결정이 필요하면 해당 Definition의 현재
작업에 `user_decision_options`를 추가하고 검증을 통과시킨 뒤 적용한다.

사용자에게 보이는 응답에서는 내부 운영 절차를 과하게 드러내지 않는다.

리뷰 피드백 대응 방향은 사용자 결정의 한 종류이므로 같은 입력 규칙을 적용한다. 이때 선택 가능한 응답은 `수용`, `거절`, `기타 의견 입력`이다. 권장 대응은 기본값이 아니라 제안이며, 사용자 응답이 유효 입력 형식 중 어느 것에도 해당하지 않으면 Workflow Engine은 파일 수정이나 댓글 처리로 넘어가지 않고 대응 방향의 결정 대상, 선택지, 입력 예시를 다시 제시한다.

### 실행 범위

실행 범위는 현재 작업에서 변경할 수 있는 대상의 한계이며, 현재 작업의 작업 내용, 사용자 결정, 작업내역에서 산출한다.

실행 범위에는 변경할 수 있는 GitHub 상태, 파일 또는 디렉터리, 댓글 또는 review thread, 브랜치, 커밋, PR 생성 여부를 포함한다. 실행 범위에 포함되지 않은 대상은 변경하지 않는다.

전용 스킬은 후보, 초안, 분석 결과만 만든다. Workflow Engine은 확정된 현재 작업의 실행 범위 안에서 구조화 실행 요청을 확정하고 결과를 검증한다. 실제 변경은 요청을 받은 유형별 실행 주체만 수행한다.

사용자 요청이나 전용 스킬 출력이 실행 범위를 벗어나면 Workflow Engine은 실행 요청을 만들지 않고 중단 사유와 재개 조건을 제시한다.

## 실행 모델

이 섹션은 Workflow Engine이 사용자 요청을 처리할 때 따르는 실행 순서와 명령 실행 기준을 정의한다. 모든 하위 스킬은 이 실행 모델 안에서 후보, 초안, 분석 결과만 만든다. Workflow Engine은 현재 작업과 실행 범위를 확정하고, 유형별 실행 주체는 그 범위 안에서만 상태 전이와 쓰기 작업을 수행한다.

### 선언형 실행 흐름

선언형 Workflow Engine의 기본 흐름은 다음 여섯 단계다.

`관찰 -> 정규화 -> 전이 매칭/평가 -> 결정 -> 구조화 실행 -> 사후조건 검증`

1. `관찰`은 고정된 GitHub 실행 상태와 로컬 상태를 읽는다.
2. `정규화`는 결정론적 사실과 근거에 묶인 LLM 의미 사실을 공통 사실 스키마로 만든다.
3. `전이 매칭/평가`는 워크플로우 정의의 조건을 검증기와 평가기로 검사해 매칭 결과를 산출한다.
4. `결정`은 정상 종료 상태가 아니면 정확히 하나의 유효한 전이와 그 전이의 사용자 결정 필요 여부를 확정한다. 매칭이 없으면 사용자 결정 또는 `중단`으로 멈추고, 복수 후보는 정의 결함으로 `중단`한다.
5. `구조화 실행`은 확정된 작업/동작 ID, 실행 범위, 직접 실행 대상 참조, 전제조건과 예상 사후조건을 담은 요청만 선택된 실행 주체에 전달한다.
6. `사후조건 검증`은 실행 주체의 반환 결과와 다시 관찰한 상태가 완료 조건을 만족하는지 확인한 뒤 다음 전이를 평가한다.

현재 런타임은 다섯 Workflow Definition을 준비 단계에서 한 번 검증·compile하고 같은 immutable compiled
representation을 각 state adapter와 evaluator에 전달한다. Adapter는 compiled fact metadata를,
evaluator는 compiled transition lookup을 사용하며 candidate·evidence·normalized state·현재 작업 입력은
매 실행 검증한다. `github-agentic-loop`는 기준 대상을 관찰하고 정규화·평가·
실행·사후조건 검증을 연결하는 얇은 오케스트레이터이며 전이를 자연어로 선택하지 않는다.

### 명시적 검증 모드

검증 모드는 사용자가 명시적으로 요청한 경우에만 활성화한다. 일반 실행이나 운영 중 비교를 자동으로 검증 모드로 바꾸지 않는다. 현재 운영 이중 실행 비교 모드는 구현하지 않는다.

검증 모드에서는 다음 입력과 조건을 고정한다.

- 같은 GitHub 상태와 로컬 상태 스냅샷을 모든 실행에서 사용한다.
- 같은 스킬 버전, 모델, 추론 설정, 역할 설정, 입력을 사용한다.
- LLM 의존 하위 스킬 또는 서브에이전트 호출마다 서로 독립된 세션 10개를 시작한다. 세션 사이에 대화 문맥이나 결과를 공유하지 않는다.
- 결정론적 평가기와 상태 조회는 반복하지 않으며, 고정된 상태 스냅샷과 한 번의 결정론적 평가 결과를 사용할 수 있다.
- 모든 raw 결과와 session ID를 보존해 사용자에게 제시한다. 결과 의미, 구조화 필드, patch의 일치 여부는 자동 비교하지 않는다.
- fan-out을 시작하기 전에 session 생성 주체가 현재 host의 callable `close_agent`를 확인한다. capability가
  없으면 첫 session 전에 중단하고 10개보다 적은 수로 축소하지 않으며 호출하지 않은 결과를 만들지 않는다.
- raw 결과, 오류, timeout과 session ID를 먼저 보존한 뒤 검증 session을 실제 생성한 구성 요소가 자신이 직접 발급받은 모든 session ID에 `close_agent`를 호출한다. Workflow Engine의 직접 fan-out은 Workflow Engine이, `workflow-code-editor`의 격리 fan-out은 editor가 소유한다. `completed`와 `timed_out`은 작업 결과 상태일 뿐 실행 리소스 정리 완료가 아니다.
- 파일 수정처럼 대상 실행 계약이 격리를 요구하는 호출은 같은 baseline의 독립 workspace 10개에서 실행한다. 검증 모드에서도 실제 LLM 호출을 수행하며 dry-run이나 결과 예측으로 대체하지 않는다.

검증 모드에서는 정확히 10개의 고유 session, 동일 고정 조건, raw 결과 보존, 필요한 격리, primary와 외부 상태 미변경만 확인한다. 하나라도 충족하지 못하면 실험 무결성 실패를 보고한다. 재현성 판단, skill/prompt 개선 여부, 이후 일반 workflow 재개 여부는 사용자가 결정한다. 검증 결과는 transition을 진행하거나 결과를 채택하지 않는다.

일반 실행에서도 서브에이전트 수명 주기는 생성 주체가 소유한다. 생성 주체는 첫 spawn 전에 callable
`close_agent`를 확인하고, `interrupt_agent`를 대체 수단으로 사용하지 않는다. Workflow Engine은 자신이 직접 시작한 상태 요약·단순 실행·리뷰 session만 닫고, `workflow-code-editor` 또는 Harness는 자신이 직접 시작한 편집 session만 닫는다. 부모는 하위 실행 주체의 child ID를 중복으로 닫지 않으며, 하위 실행 주체는 기존 `verification_results`와 `residual_risks_or_failure_reasons`로 정리 결과와 실패를 반환한다. 같은 session의 단순 스킬 호출은 수명 주기 대상이 아니다. Harness의 선택적 보조 위임과 일반 코드 변경은 close capability가 없으면 주 에이전트 또는 같은 session에서 계속할 수 있지만, 별도 session이 필수인 target editor와 정확히 10개 session이 필요한 검증 모드는 첫 spawn 전에 중단한다.

### 현재 선언형 런타임

다섯 흐름은 다음 Definition과 state adapter 조합으로 실행한다.

| 흐름 | Definition | state adapter |
| --- | --- | --- |
| 기능제안 | `definitions/feature-proposal.json` | `feature-proposal-state-adapter.mjs`의 `normalizeFeatureProposalFacts` |
| 정책검토 | `definitions/policy-review.json` | `policy-review-state-adapter.mjs` |
| 기능변경 | `definitions/feature-change.json` | `feature-change-state-adapter.mjs` |
| 기능결함 | `definitions/feature-fix.json` | `feature-fix-state-adapter.mjs` |
| 구현흐름 | `definitions/implementation.json` | `implementation-state-adapter.mjs` |

모든 조합은 한 번 준비한 compiled representation을 공유하는 adapter 정규화와
`evaluateWorkflowDefinition`의 단일 경로를 사용한다. Raw Definition을 직접 받는 API와 CLI는 호환성을
유지하며 내부 준비 경로를 사용한다. 새 fact, 파싱,
정규화 또는 실행 동작이 필요하면 Definition만 바꾸지 않고 대응 adapter·계약·시험 사례를 함께
변경한다. 자연어 전이 경로나 전이 결과 비교 경로는 두지 않는다.

### 공통 실행 골격

Workflow Engine은 사용자 요청을 그대로 실행 명령으로 보지 않는다. 먼저 GitHub 실행 상태와 현재 코드 상태를 읽고 다음 값을 산출한 뒤 실행 여부를 판단한다.

| 산출 값        | 의미                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------ |
| 기준 대상      | 현재 전이를 판단할 이슈 또는 PR                                                            |
| 상태 근거 묶음 | GitHub 실행 상태, 현재 코드 상태, 보조 로그에서 읽은 완료 근거, 미완료 근거, 보조 근거, 무효 근거 |
| 현재 작업      | evaluator가 반환한 하나의 `task_action_id`                                                  |
| 진행 판단      | `사용자 결정`, `자동 실행`, `중단`, `완료` 중 현재 작업의 처리 방식을 나타내는 값           |
| 실행 범위      | 현재 작업에서 변경할 수 있는 GitHub 상태, 파일 또는 디렉터리, 댓글 또는 review thread, 브랜치, 커밋, PR 생성 여부 |

사용자 요청은 관측·정규화 입력일 뿐이며 Definition이나 사용자 결정을 대체하지 않는다. Workflow Engine은 다섯 값을 하나로 확정한 뒤 작업 유형에 맞는 구조화 실행 요청을 만들고, 실행 주체의 반환 결과가 예상 사후조건과 검증 기준을 충족하는지 확인한다. 값을 확정할 근거가 부족하거나 충돌하면 실행 요청을 만들지 않고 중단 사유와 재개 조건을 제시한다.

### 기본 진행 순서

Workflow Engine은 모든 이슈 유형과 연결 PR에 같은 실행 루프를 적용한다.

1. 기준 대상을 정한다.
   - 열린 PR 중 unresolved review thread 또는 merge 대기 상태가 있으면 먼저 처리한다.
   - 이어갈 수 있는 열린 이슈가 있으면 새 작업보다 우선한다.
2. 상태 근거 묶음을 만든다.
   - GitHub 이슈/PR 상태와 현재 코드 상태를 읽는다.
   - GitHub 실행 상태로 표현되지 않는 중간 실행 상태만 보조 로그로 확인한다.
3. 현재 작업을 산출한다.
   - 기준 대상 유형의 state adapter로 관측값을 정규화한다.
   - 선택한 Definition과 `currentTaskActionId`를 evaluator에 전달한다.
   - evaluator가 반환한 단일 `task_action_id`를 현재 작업으로 확정한다.
   - 정규화·검증 실패, 조건 없음 또는 복수 조건은 중단한다.
4. 진행 판단을 판정한다.
   - 진행 판단이 `사용자 결정`이면 결정 대상과 선택 가능한 응답을 제시하고 멈춘다.
   - 진행 판단이 `자동 실행`이면 실행 범위 안에서 구조화 실행 요청과 유형별 실행 절차로 진행한다.
   - 진행 판단이 `중단`이면 중단 사유와 재개 조건을 제시하고 멈춘다.
   - 진행 판단이 `완료`이면 완료 근거를 제시하고 루프를 종료한다.
5. 실행 범위 안에서 구조화 실행 요청을 만들고 결과를 검증한다.
   - 전용 스킬은 후보, 초안, 분석 결과만 만든다.
   - GitHub 상태 변경은 단순 상태 변경 실행 절차에 따라 결정론적 실행기를 우선하고, 불가능할 때만 저비용 서브에이전트에 맡긴다.
   - 파일 변경은 `workflow-code-editor`가 실행 전 Harness 준비도를 확인해 Harness 일반 진입점 또는 현재 Codex 세션의 일반 코드 변경 경로 하나로 실행한다.
   - 실행 주체는 현재 작업의 작업내역과 실행 범위를 넓히지 않고 요청을 처리한 뒤 결과를 반환한다.
   - Workflow Engine은 반환 결과를 확인한 뒤에만 작업 완료 여부와 다음 전이를 판단한다.
6. 작업이 끝나면 다시 GitHub 실행 상태와 현재 코드 상태를 읽고 1번부터 반복한다.

이 루프는 진행 판단이 `자동 실행`인 동안 반복한다. `사용자 결정`, `중단`, `완료`가 산출되면 해당 판단에 따라 멈추거나 종료한다.

### 현재 단계 산출 절차

현재 단계 산출 절차는 `기본 진행 순서`의 상태 근거 묶음 생성과 현재 작업 산출 단계에서 수행하는 세부 절차다. 기준 대상의 상태를 `완료 근거`, `미완료 근거`, `보조 근거`, `무효 근거`로 분류하고, 분류 결과를 현재 작업 산출 입력으로 사용한다.

근거 분류 규칙:

1. 완료 근거와 미완료 근거는 GitHub 실행 상태에서만 읽는다.
2. 보조 근거는 GitHub 실행 상태로 표현되지 않는 중간 실행 상태를 판단할 때만 사용한다.
3. 보조 근거가 완료 근거 또는 미완료 근거와 충돌하면 GitHub 실행 상태를 우선한다.
4. 무효 근거는 배경 설명으로만 참고하고 현재 작업의 확정 근거로 쓰지 않는다.
5. 완료 근거, 미완료 근거, 보조 근거만으로 현재 작업을 하나로 산출할 수 없으면 추론하지 않고 정보 부족 또는 상태 충돌로 중단한다.
6. 사용자 결정 없이 작업 전이가 특정 반영 대상, 기존 이슈, 완료 기준 항목 중 하나를 확정해야 하는데 명시 근거가 없거나 후보가 둘 이상이면 추론하지 않고 정보 부족 또는 상태 충돌로 중단한다.

### 명령 실행 경로 선택

Workflow Engine은 구조화 실행 요청을 확정하기 전에 요청에 포함된 명령을 일반 경로와 권한 확인 경로 중 하나로 분류하고, 판정 결과와 권한 요구사항을 요청에 기록한다. 일반 경로는 현재 권한 안에서 실행할 수 있고 상태를 변경하지 않는 읽기, 조회, 로컬 검증 명령이다. 권한 확인 경로는 권한 상승, 원격 접근, GitHub 상태 변경, `.git` 쓰기, 파일 수정 또는 삭제 가능성이 있어 실행 전 권한 확인이 필요한 명령이다.

사용자 의도 확인과 명령 실행 경로는 서로 다른 판단 항목이다. 사용자 결정은 현재 작업과 실행 범위를 확정하는 절차이고, 명령 실행 경로는 확정된 작업을 어떤 권한 경로로 호출할지 정하는 절차다. 따라서 실행 경로 선택은 현재 작업, 실행 범위, 사용자 결정을 대체하지 않는다.

사용자의 상태 변경 의도가 이미 명확한지는 명령 실행 경로 판정 입력으로 사용하지 않는다. 권한 확인 경로 대상 명령은 일반 경로 실패 여부를 관찰하기 전에 권한 확인 경로로 판정하고, 실제 명령 실행 주체는 구조화 실행 요청에 기록된 판정 결과를 그대로 적용한다.

실행 직전 확인 절차는 보안과 권한 확인뿐 아니라 실행 최적화 기준이다. 실제 명령 실행 주체는 명령을 호출하기 직전에 `이 명령이 권한 상승, GitHub 상태 변경, 원격 접근, .git 쓰기, 파일 수정 또는 삭제 중 하나인가?`를 다시 확인한다. 해당하면 일반 경로 실패를 먼저 유발하지 않고 처음부터 권한 확인 경로로 보낸다. 구조화 실행 요청의 판정과 실제 명령이 일치하지 않거나 필요한 권한을 확인할 수 없으면 실행하지 않고 실패 사유를 메인 Workflow Engine에 반환한다. 이 기준은 예측 가능한 실패 로그, 재시도, 불필요한 토큰·시간 소비를 줄이기 위한 운영 규칙이다.

권한 확인 경로로 분류하는 명령:

- `gh issue create`, `gh issue edit`, `gh pr create`, `gh pr comment`, `gh pr review`, `gh pr merge`, `gh api --method POST|PATCH|PUT|DELETE`처럼 GitHub issue, PR, review, checks, comment 상태를 바꾸는 GitHub API 계열 명령
- `git push`, `git fetch`, `git pull`, `git ls-remote`처럼 네트워크나 원격 저장소 접근이 필요한 Git 명령
- `git switch`, `git checkout`, `git branch`, `git commit`, `git tag`, `git merge`, `git rebase`처럼 `.git` 쓰기 또는 작업 브랜치 변경이 필요한 명령
- `sed -i`, `find -delete`, 쓰기나 삭제를 수행하는 `find -exec`처럼 로컬 파일을 수정하거나 삭제하는 명령

일반 경로로 분류하는 명령:

- `gh pr view`, `gh issue view`, `gh pr checks`, `gh api` GET 조회처럼 GitHub 실행 상태를 읽기만 하는 명령
- `git status`, `git diff`, `git log`, `git show`, `rg`, 출력 또는 파이프 변환용 `sed`, `ls`, 탐색 전용 `find`, `wc`처럼 로컬 파일이나 로컬 Git 상태를 읽는 명령
- `git diff --check`처럼 로컬 변경사항만 검증하는 명령

파괴적 명령은 실행 경로와 별도로 판단해 구조화 실행 요청에 기록한다. `rm`, `git reset --hard`, `git clean`, `git branch -D`, 작업 브랜치 삭제, 강제 push처럼 되돌리기 어렵거나 사용자 변경을 잃게 할 수 있는 명령은 현재 작업의 실행 범위 안에 있고 사용자 의도가 명확할 때만 실행한다. 실제 명령 실행 주체는 두 조건을 다시 확인하고, 충족하지 않으면 명령을 실행하지 않고 실패 사유를 반환한다.

PR merge 반영 작업의 작업 브랜치 정리는 별도 사용자 판단을 요구하지 않는다. Workflow Engine이 만든 PR head branch이고 현재 branch가 아니며 원격 head와 로컬 상태가 안전하면 자동 정리한다. 안전하지 않으면 삭제하지 않고 보류 사유를 기록한다.

## 흐름별 설계

이 섹션은 흐름별 목적과 상태 기록 방식을 설명한다. 정확한 작업 조건, 사용자 결정, 실행 참조와
완료기준은 각 `definitions/*.json`과 state adapter가 표현하고 evaluator가 계산한다.

### 다음 계획 요청

다음 계획 요청은 새 작업 생성 명령이 아니다. Workflow Engine은 GitHub 실행 상태를 다시 읽고, 기존 PR 또는 이슈에서 이어갈 작업이 있는지 먼저 판단한다. 이어갈 작업이 없을 때만 새 기능제안 후보 생성을 검토한다.

판단 순서는 다음과 같다.

1. merge 대기 PR
2. 리뷰 대응이 남은 PR
3. 그 밖의 진행 중 PR
4. 열린 기능변경 또는 기능결함 이슈
5. 열린 정책검토 이슈
6. 열린 기능제안 이슈
7. 새 기능제안 후보

이어갈 작업이 있으면 새 계획 후보를 만들지 않고 현재 상태, 남은 작업과 evaluator가 반환한 현재 `task_action_id`를 제시한다.

### 기능제안 흐름

기능제안 흐름은 비정형 기능 요청을 GitHub 이슈로 정리하고, 진행하지 않음, 정책 검토 필요, 기능 변경 필요 중 하나로 판단하는 흐름이다. 새 기능제안은 명시적인 기능제안 요청뿐 아니라 기능 추가, 기능 수정, 운영 흐름 개선 요청을 포함한다. 기능제안 이슈 자체에서는 설계 결정이나 구현을 진행하지 않는다. 진행 방향이 확정되면 기능제안 이슈의 `판단 근거`와 `완료 기준은 무엇인가요?`에 확정 방향의 근거와 방향별 체크항목을 추가하고, 후속 정책검토 또는 기능변경 흐름의 초안 작성은 원본 기능제안 이슈 본문을 참조한다.

### 정책검토 흐름

정책검토 흐름은 정책 또는 설계 기준을 결정하고, 결정된 내용을 설계 문서에 반영한 뒤 반영된 설계를 기준으로 기능변경 전환 여부를 정하는 흐름이다. 정책검토 이슈 자체에서는 실행 산출물을 직접 수정하지 않는다.

정책 설계는 정책검토 이슈의 `검토 결과`에 기록되고, 설계 문서 반영은 공통 구현 흐름을 사용한다. 설계 반영이 끝난 뒤에만 기존 기능변경 이슈 갱신과 새 기능변경 이슈 생성 중 후속 방향을 정하므로, 정책 결정과 기능 구현 범위가 섞이지 않는다.

### 기능변경 흐름

기능변경 흐름은 기능제안 또는 정책검토에서 전이된 변경 범위와 조건을 충족한 단독 요청을 기능변경 이슈로 확정하고, 변경 계획에 따라 하나 이상의 브랜치/PR 단위로 나눈 뒤, 각 PR merge 결과를 기능변경 이슈의 `완료 기준은 무엇인가요?`에 반영해 종료하는 흐름이다.

변경 계획의 브랜치/PR 단위는 기능변경 이슈의 작업 범위와 완료 기준에 기록한다. 각 단위는 공통 구현 흐름을 독립적으로 통과하며, merge 결과가 대응하는 완료 기준에 반영된 뒤 모든 단위가 끝나면 기능변경 이슈를 종료한다.

기능변경 흐름의 단독 시작은 다음 조건을 모두 충족한 요청에만 허용한다.

- 변경 필요성과 진행 의사가 확정돼 있다.
- 구현 또는 문서 변경 범위가 식별돼 있다.
- 기능변경 이슈의 종료를 판단할 완료 기준을 작성할 수 있다.
- 추가적인 정책 또는 설계 결정이 필요하지 않다.
- 결함 원인 조사와 해결 방향 확정이 필요하지 않다.

조건을 충족하지 않으면 요청의 성격에 따라 기능제안, 정책검토 또는 기능결함 흐름으로 시작한다.
Workflow Engine은 단독 시작 조건을 충족했다는 관측 근거와 기능제안 또는 정책검토에서 전환됐다는
GitHub 실행 상태를 구분해 정규화한다.

### 종료 후 이슈 유형 전환

원본 이슈의 판단 또는 정책 책임과 후속 이슈의 책임 기간이 겹치지 않도록 다음 세 전환에서만 원본
이슈 종료를 후속 흐름 시작보다 먼저 수행한다.

```text
기능제안 → 정책검토
정책 검토 필요 방향 확정
→ 판단 결과·판단 근거·완료 기준 반영
→ 기능제안 이슈 종료
→ 닫힌 기능제안 이슈를 출발점으로 정책검토 흐름 시작
```

```text
기능제안 → 기능변경
기능 변경 필요 방향 확정
→ 판단 결과·판단 근거·완료 기준 반영
→ 기능제안 이슈 종료
→ 닫힌 기능제안 이슈를 출발점으로 기능변경 흐름 시작
```

```text
정책검토 → 기능변경
정책 설계 확정
→ 설계 문서 반영과 PR merge 완료
→ 기능변경 전환 방향·범위와 정책검토 후속 작업 상태 반영
→ 정책검토 이슈 종료
→ 닫힌 정책검토 이슈를 출발점으로 기존 기능변경 이슈 갱신 또는 새 기능변경 흐름 시작
```

각 전환은 원본 이슈의 상태 반영, 원본 이슈 종료, 후속 흐름 시작을 서로 다른 완료 조건으로 둔다.
원본 이슈가 열린 상태에서는 후속 흐름 시작 조건을 충족한 것으로 정규화하지 않는다.
세 전환 모두 원본 이슈 종료 전에는 전환 방향과 범위까지만 확정하고, 원본 이슈 종료를 확인한 뒤
후속 이슈를 생성하거나 갱신한다. 생성 또는 갱신된 후속 이슈 번호는 닫힌 원본 이슈에 전환 결과로
사후 기록하며, 이 기록은 원본 이슈의 종료 선행조건이 아니다.

원본 이슈 종료 후 후속 흐름 시작이 실패하면 원본 이슈는 닫힌 상태를 유지한다. Workflow Engine은
원본 이슈에 기록된 전환 방향과 후속 Workflow를 다시 읽는다. 대응하는 후속 이슈가 없거나, 기존
후속 이슈 갱신 방향을 확정했지만 반영 범위와 완료 기준의 갱신이 끝나지 않았으면 닫힌 원본 이슈를
전환 출발점으로 사용한다. 후속 이슈의 현재 상태를 확인해 없는 이슈는 생성하고 미완료 갱신은 남은
범위만 다시 수행한다. 이미 확정된 판단이나 정책은 다시 요청하지 않고, 완료된 반영을 되돌리거나
중복 적용하지 않는다.

이 순서 규칙을 모든 이슈 또는 Workflow handoff의 공통 규칙으로 확대하지 않는다. 정책검토·기능변경·
기능결함에서 구현 흐름으로 진입하는 경우, 구현 흐름 안의 브랜치·커밋·PR·리뷰·피드백·merge 반복,
구현 단위 완료 후 상위 이슈로 복귀하는 경우에는 상위 이슈를 닫지 않는다. 그 밖에 위 세 경로에
포함되지 않은 이슈 또는 작업 간 handoff도 이 규칙의 적용 대상이 아니다.

### 기능결함 흐름

기능결함 흐름은 Fix Analysis Skill로 관찰 사실과 원인 후보를 구분해 제시하고 사용자가 원인 조사 결과를 확정한 뒤, Fix Plan Skill로 해결 계획을 수립하는 흐름이다. 해결 계획은 모든 브랜치/PR 단위를 기능결함 이슈 본문에 반영하며, 구현 순서에 따라 미전환 단위를 하나씩 구현 흐름으로 전환한다. 원인 조사 중 설계 문서, 규칙 문서, 코드, 템플릿, 스킬 변경이 함께 필요하다고 확인되면 해당 변경을 결함 해결 계획의 브랜치/PR 단위에 포함한다.

확정된 원인과 해결 계획은 기능결함 이슈에 기록한다. 해결 계획의 브랜치/PR 단위는 기능변경과 같은 방식으로 공통 구현 흐름을 반복하고, merge 결과가 모든 완료 기준에 반영되면 기능결함 이슈를 종료한다.

### 구현 흐름

구현 흐름은 정책검토, 기능변경, 기능결함에서 전달된 구현 단위 하나를 작업 브랜치, 커밋, PR, 리뷰 대응, merge 반영까지 처리하는 공통 흐름이다. 구현 단위에는 코드뿐 아니라 문서, 템플릿, 스킬, 설정 같은 비기능 산출물 변경도 포함한다. 구현 흐름은 base branch 복귀와 갱신을 수행하지만, 연결 이슈의 완료 기준 체크나 후속 작업 체크는 상위 흐름의 결과 반영 작업에 맡긴다.

Commit Plan은 확정된 현재 브랜치/PR 단위를 상위 계획으로 삼고 그 범위를 넓히지 않은 채 의미적 커밋 단위로 나눈다. 이 분리는 상위 계획과 커밋 진행 상태를 같은 이슈에서 추적하면서도 서로 다른 완료 수준으로 유지하기 위한 것이다.

Workflow Engine은 확정된 커밋 단위의 ID와 작업 범위로 체크항목 내용을 정하고, 상위 이슈의 현재 구현 단위 부모 항목 아래에 중첩하는 구조화 실행 요청을 만든다. 결정론적 실행기 또는 저비용 서브에이전트가 요청을 적용하고 결과를 반환한다. 기능변경과 기능결함은 `완료 기준은 무엇인가요?`의 현재 브랜치/PR 단위 항목을 부모로 사용하고, 정책검토의 설계 문서 구현은 `후속 작업은 무엇인가요?`의 `결정된 정책을 관련 설계 문서에 반영` 항목을 부모로 사용한다. 하위 커밋 단위는 구현 진행 상태이며, 상위 이슈 종료를 판정하는 완료 기준은 부모 항목이다.

Workflow Engine은 현재 커밋 단위의 구현 범위와 검증 기준을 확정하고 `workflow-code-editor`에 코드 수정을 요청한다. editor는 실행 전에 Harness 준비도를 확인해 Harness 일반 진입점 또는 현재 Codex 세션의 일반 코드 변경 경로 하나를 선택한다. 수정·검증 결과를 현재 실행 범위와 대조한 뒤 커밋 메시지 확정, 커밋 생성, 하위 항목 체크와 `(<commit hash>)` 기록 요청을 순서대로 확정한다. 각 실행 주체의 사후조건 반환을 확인한 뒤 남은 단위가 있으면 Commit Plan의 구현 순서상 다음 미체크 커밋 단위를 현재 단위로 지정하고 `구현 작업`부터 반복한다.

구현 흐름은 브랜치 이름 확정, 커밋 단위 계획, 구현과 커밋 반복, push, PR 생성, 리뷰, 피드백 반복, merge 반영을 하나의 공통 수명주기로 묶는다. 리뷰 피드백은 한 건씩 처리하고 해결 여부를 반영한 뒤 GitHub 상태를 다시 읽는다. 남은 피드백이 있으면 피드백 대응으로 돌아가고, 없을 때만 merge 결정으로 진행한다.

## 책임 구조

Workflow Engine은 GitHub와 코드 상태를 읽고 규칙에 따라 현재 작업을 정하며, 사용자 결정을 받은 뒤 허용된 실행 요청을 확정한다. 전용 스킬은 현재 작업에 필요한 후보, 초안 또는 분석 결과만 만들고 상태를 확정하거나 GitHub를 직접 변경하지 않는다.

`github-agentic-loop`의 핵심 책임은 기준 대상 식별, 관찰·정규화 결과 연결, 전이 평가 결과 처리, 사용자 결정 관리, 실행 범위 확정, 상태 변경 경계 통제다. 선언형 워크플로우 정의가 적용되면 전이 조건의 매칭과 평가는 검증기와 평가기가 담당하고, Workflow Engine은 그 결과를 받아 현재 작업과 실행 여부를 조율한다. 이 분리는 `github-agentic-loop`를 제거하거나 최종 실행 권한을 전용 스킬에 넘긴다는 뜻이 아니다. 상태 읽기 보조, 전이 후보 분류, 리뷰 실행 모드 검사, 로그 기록 준비처럼 분리 가능한 책임은 참조문서나 전용 스킬로 옮길 수 있지만, 사용자에게 제시할 현재 작업과 GitHub 상태 변경 여부는 Workflow Engine이 확정한다.

하위 작업은 단순 스킬 호출과 서브에이전트 위임을 구분한다. 단순 스킬 호출은 현재 메인 모델이 수행하며, 스킬 자체가 모델을 바꾸지는 않는다. 별도 서브에이전트 위임은 입력과 산출이 좁고 독립적인 읽기 전용 요약, 후보 분류, 단순 라우팅, 참조문서 추출 또는 확정된 실행 요청 처리에만 적용 후보로 둔다. 서브에이전트 결과는 최종 결정이 아니라 메인 Workflow Engine의 입력이다.

경량 모델은 전체 Workflow Engine에 적용하지 않는다. GitHub 이슈/PR 상태 전이, 커밋 또는 PR 생성 여부, 리뷰 코멘트 내용, 피드백 resolve 여부, 사용자 결정 해석처럼 상태나 작업 경계를 확정하는 판단은 강한 모델 또는 메인 에이전트 책임으로 남긴다. 판단이 끝난 뒤 대상과 실행 내용이 고정된 댓글 게시, 체크 변경, 지정된 review thread resolve, 정해진 상태 전이는 결정론적 실행기를 우선한다. 결정론적 실행 경로가 없거나 LLM 도구 호출이 필요한 경우에만 저비용 서브에이전트가 같은 요청을 처리한다.

### 판단 책임과 실행 주체

Workflow Engine은 실행 주체에 작업을 넘기기 전에 구조화 실행 요청을 만든다. 이 요청에는 작업 종류, 대상 ID 또는 대상 파일, 확정된 실행 요청값, 전제조건, 예상 사후조건, 검증 기준, 명령 실행 경로와 권한 요구사항, 파괴적 명령 여부가 포함되어야 한다. 실행 주체는 요청값을 다시 판단하거나 범위를 넓히지 않는다.

단순 상태 변경 실행은 다음 순서를 따른다.

1. 결정론적 실행기가 요청을 처리할 수 있으면 추가 LLM 호출 없이 실행하고 성공 결과를 메인 Workflow Engine에 반환한다.
2. 결정론적 실행이 불가능하면 저비용 서브에이전트가 실행 전 상태를 확인하고 단일 동작을 수행한 뒤 사후조건을 검증해 성공 결과를 메인 Workflow Engine에 반환한다.
3. 전제조건 불일치, 범위 밖 변경 필요, 실행 실패, 사후조건 불충족은 재판단하지 않고 실패 사유와 함께 메인 Workflow Engine에 반환한다.

코드 수정 실행은 단순 상태 변경 실행과 분리한다. 구현 작업과 수용된 리뷰 피드백처럼 파일 수정이 필요한 작업은 `workflow-code-editor`가 담당한다. Workflow Engine은 수정 범위, 검증 기준과 권한 요구사항을 확정하고, editor는 실행 전에 정확히 한 경로를 선택한다. Harness와 대상 저장소의 일반 진입점이 준비됐으면 Workflow Engine 전용 설정·필드·역할·결과 형식을 제외한 일반 코드 변경 요청으로 Harness를 호출한다. Harness가 없거나 실행 전에 사용할 수 없음이 확인되면 현재 Codex 세션에서 저장소 지시와 일반 파일 편집 도구로 수정한다.

Harness 경로와 일반 코드 변경 경로는 같은 baseline, 요청 범위, 권한·도구·명령 경로, 검증과 구조화 결과 계약을 적용한다. 선택 경로 실행이 시작된 뒤 실패하면 부분 변경을 중복 실행할 위험이 있으므로 다른 경로로 fallback하지 않는다. Harness는 호출자가 Workflow Engine인지 알 필요가 없으며 Workflow Engine 전용 타겟 역할이나 Team Spec 필드를 생성하지 않는다.

`codex-harness` 메타 저장소처럼 프로젝트 로컬 Harness가 없는 저장소도 일반 코드 변경 경로로 처리할 수 있다. 일반 경로 선택은 Harness 설치·생성·갱신을 유발하지 않는다.

각 전용 스킬은 불분명한 프롬프트로 상태 변경 책임을 넘겨받지 않도록 `description`, 입력, 출력, 책임, 하지 않는 일, 사용자 결정, 중단 조건, 후속 전이 대상을 명확히 가져야 한다. 특히 제안형 스킬은 초안이나 후보와 보류 질문만 반환한다. Workflow Engine은 스킬 결과를 산출물 계약으로 검증해 정규화 입력에 반영하고, evaluator 결과로 상태와 실행 요청을 확정한다. GitHub 변경은 결정론적 실행기 또는 저비용 서브에이전트가 수행한다.

정확한 전이는 `definitions/*.json`, state adapter와 evaluator를 단일 원천으로 사용한다. 상태 관측,
전용 스킬 산출물, 리뷰, 구조화 실행과 검증 모드는 각각의 runtime reference를 따르며, 각 스킬의
`SKILL.md`는 필요한 계약을 호출 시점에 연결한다. 이 문서는 그 런타임의 배경과 책임 경계를 설명할
뿐 실행 입력으로 사용하지 않는다.

| 구성 요소 | 책임 |

## 리뷰 실행 설계

리뷰 실행은 PR diff와 연결 이슈의 작업 범위 및 완료 판단 기준을 검토해 PR Review Template 형식의 결과를 만드는 책임만 가진다. Review Comment는 review thread 게시 초안을 만들고, Workflow Engine은 게시·resolve 요청의 내용과 실행 범위를 확정한다. 실제 GitHub 변경은 단순 상태 변경 실행 절차를 따르며, Workflow Engine은 반환된 사후조건을 확인한다. 리뷰 판정은 `review-runtime-contract.md`, 실행 절차와 출력 형식은 관련 스킬을 따른다.

Workflow Engine이 리뷰 설정을 최초로 필요로 할 때는 사용 가능한 모드를 관측하고 사용자 결정 뒤 기본 리뷰 실행 모드를 저장할 수 있다. 저장된 기본 리뷰 실행 모드는 리뷰 실행 모드 선택 사용자 결정에서 기본 후보로만 사용하며, PR 생성 후 실제 사용할 리뷰 실행 모드는 매번 사용자가 확정해야 한다. 설치만으로 설정 파일이나 기본값을 만들지 않는다.

지원 리뷰 실행 모드는 다음 세 가지다.

| 리뷰 실행 모드               | 실행 주체 | 실행 전에 확인할 의존성                                                                                 |
| ---------------------------- | --------- | ------------------------------------------------------------------------------------------------------ |
| `claude/code-review`         | Claude    | Claude CLI 인증, Codex에서 호출할 경우 `sendbird/cc-plugin-codex`의 `$cc:setup` 준비 상태 확인         |
| `claude/awesome-code-review` | Claude    | Claude CLI 인증, `sendbird/cc-plugin-codex`의 `$cc:setup` 및 `$cc:adversarial-review` 준비 상태          |
| `codex/awesome-code-review`  | Codex     | Codex 전역 `awesome-code-review`                                                                       |

설치 기본 리뷰 실행 모드 저장 형식:

```json
{
  "review": {
    "defaultMode": "claude/code-review"
  }
}
```

- 저장 위치는 타겟 레포의 `.github-agentic-loop/settings.json`이며 Workflow Engine만 필요한 시점에 필요한 필드를 생성하거나 보완한다.
- `review.defaultMode` 값은 `claude/code-review`, `claude/awesome-code-review`, `codex/awesome-code-review` 중 하나여야 한다.
- 지원 모드의 번호 또는 선택지 문구가 입력되면 리뷰 실행 모드 검사로 전이한다.
- `기타 의견 입력`은 사용자 결정 규칙에 따라 처리하며, 리뷰 실행 모드가 확정된 경우에만 리뷰 실행 모드 검사로 전이한다.
- 설정 파일이나 필요한 필드 부재는 지연 초기화하고, JSON 파싱 실패나 인식할 수 없는 타입·값은 자동 교정·기본값·fallback·Harness 호출 없이 리뷰 흐름을 중단한다.
- 인식 불가 중단 결과에는 설정 경로, 문제 필드·값, 기대 형식·지원 값, 영향받은 작업과 수정 후 재개 조건을 포함한다.

선택된 리뷰 실행 모드의 의존성이 설치되어 있지 않으면 Workflow Engine은 필요한 설치 경로, 설치 주체, 설치 후 확인할 파일 또는 명령, 재개 조건을 안내하고 리뷰 실행 작업을 중단한다. 다른 리뷰 실행 모드로 자동 전환하지 않는다.

`codex/awesome-code-review`에서 사용하는 Codex 전역 `awesome-code-review` 설치 확인 경로:

- `$HOME/.agents/skills/awesome-code-review/SKILL.md`

`codex/awesome-code-review`의 `awesome-code-review` 누락 안내에는 이 저장소가 해당 스킬을 배포하거나 관리하지 않는다는 점, 설치는 `https://github.com/codechaser-kr/repo-bootstrap`의 install 절차를 사용한다는 점, 원천 스킬은 `https://github.com/awesome-skills/code-review-skill`이지만 Codex 전역 설치명과 frontmatter `name`은 기본 내장 리뷰 스킬과의 이름 충돌을 피하기 위해 `awesome-code-review`로 맞춘다는 점을 포함한다. 설치 후에는 위 경로에 `SKILL.md`가 있고, 해당 파일의 frontmatter `name`이 `awesome-code-review`여야 리뷰 실행을 재개할 수 있다. 이 검사는 `claude/awesome-code-review`에는 적용하지 않는다.

Claude 기반 리뷰 실행 모드를 Codex에서 호출하려면 `sendbird/cc-plugin-codex`가 필요하다. `claude/awesome-code-review`는 이 플러그인의 `$cc:adversarial-review`를 실행하며 Claude 환경 또는 Codex 전역의 `awesome-code-review` 스킬에 의존하지 않는다. 이 플러그인은 `commit`, `awesome-code-review`처럼 외부 전역 의존성으로만 다루며, `codex-harness` 관리 기본형에 포함하지 않는다. 설치 관리는 `https://github.com/codechaser-kr/repo-bootstrap`의 install 절차에서 담당한다.

`sendbird/cc-plugin-codex` 설치 확인 기준:

1. 플러그인 캐시에 `$CODEX_HOME/plugins/cache/sendbird/cc/*/.codex-plugin/plugin.json` 또는 `$HOME/.codex/plugins/cache/sendbird/cc/*/.codex-plugin/plugin.json`이 있어야 한다.
2. 같은 플러그인 루트에 `skills/setup/SKILL.md`와 `scripts/claude-companion.mjs`가 있어야 한다.
3. `$cc:setup`을 실행해 플러그인 설치 상태와 Claude Code 호출 준비 상태를 확인한다.
4. `$cc:setup`이 설치 누락, hook trust, Claude Code 사용 불가, 인증 필요 상태를 보고하면 출력된 안내를 사용자에게 전달하고 리뷰 실행으로 넘어가지 않는다.

Claude CLI 인증 확인 기준:

1. `claude/*` 리뷰 실행 모드에서는 리뷰 실행 전에 `$cc:setup` 결과의 인증 상태를 확인한다.
2. 인증 완료 판정은 `$cc:setup`의 machine-readable probe에서 `auth.available: true`, `auth.loggedIn: true`이거나 사용자 표시 출력이 authenticated 상태를 보고하는 경우로 제한한다.
3. 인증이 없거나 만료되었거나 판단할 수 없으면 리뷰 실행을 중단하고 Claude CLI 인증 확인이 필요하다고 안내한다.
4. 재개 조건은 사용자가 Claude CLI 인증을 직접 복구한 뒤 재개를 요청한 상태다.

Claude 리뷰 실행 실패 판정 기준:

1. `claude/*` 리뷰 실행 모드에서 선택된 `$cc:* --wait` foreground 실행의 companion 명령이 exit code `0`이 아닌 값으로 종료되면 companion stdout과 stderr 출력을 확인한다.
2. companion wrapper는 호출 전 인증이 없으면 `Claude Code CLI is not authenticated`와 `Run \`claude auth login\``을 stderr에 기록한다. 이 문구 또는 raw Claude의 `Failed to authenticate`, `401 Invalid authentication credentials`, `Invalid authentication credentials` 중 하나가 있으면 재로그인 필요로 판정한다.
3. raw 오류 문구가 companion 경계에서 바뀌거나 누락될 수 있으므로 실패 직후 `$cc:setup` machine-readable probe를 다시 실행한다. `auth.available: false` 또는 `auth.loggedIn: false`면 출력 문구와 무관하게 재로그인 필요로 판정한다.
4. `$cc:setup`이 인증 가능 상태를 유지할 때만 네트워크·socket·rate limit·service unavailable 오류를 재시도 후보로 분류하고, 어느 조건에도 맞지 않으면 원인 확인 필요로 둔다.
5. 재로그인 필요의 재개 조건은 사용자가 Claude CLI 인증을 직접 복구한 뒤 재개를 요청한 상태다.

`codex/awesome-code-review`는 PR Review Template 필수 필드를 포함한 결과를 직접 출력해야 한다. `claude/awesome-code-review`의 `$cc:adversarial-review` companion stdout은 해당 Template을 직접 보장하는 것으로 간주하지 않는다. Workflow Engine은 companion 결과를 PR Review Template 필수 섹션과 필드에 맞게 정규화하고 PR 번호와 head commit SHA에 연결한 뒤 Review Comment Skill 입력으로 사용한다. 필수 필드를 채울 수 없으면 누락 필드와 재개 조건을 제시하고 게시로 전이하지 않는다.

Workflow Engine의 Claude 리뷰 실행 경로:

| Workflow 작업 | 논리 실행 모드 | 고정 호출 |
| --- | --- | --- |
| `FI-15` | `claude/code-review` | `$cc:review --wait --base <pr-base-branch> --scope branch` |
| `FI-16` | `claude/awesome-code-review` | `$cc:adversarial-review --wait --base <pr-base-branch> --scope branch` |

1. Workflow Engine은 현재 PR의 base branch를 확인하고 `<pr-base-branch>`에 그대로 사용한다.
2. `$cc:setup`으로 Claude CLI 인증과 companion 호출 준비 상태를 확인한다.
3. `--wait`, `execution_mode=foreground`, `planned_session_relation=same_session`을 구조화 실행 요청의 변경 불가능한 값으로 기록한다.
4. `--wait`가 있으므로 foreground/background 선택 질문을 추가하지 않고 `--background`를 전달하지 않는다.
5. 두 리뷰는 Workflow Engine 오케스트레이션과 같은 세션에서 실행하며 companion 결과가 반환된 뒤에만 `FI-18`의 리뷰 결과 정규화로 전이한다.
6. 이 고정 호출은 `FI-15`와 `FI-16`에만 적용한다. Workflow Engine 밖에서 직접 사용하는 `$cc:review`, `$cc:adversarial-review`의 일반 실행 정책과 `FI-17`의 `codex/awesome-code-review` 실행 방식은 유지한다.

리뷰 실행 결과는 Review Comment로 전달하기 전에 PR Review Template 형식이어야 한다. 일반 리뷰 형식을 출력하는 실행 모드는 Workflow Engine이 규칙 문서의 판정 기준에 맞게 정규화한다. 정규화 결과는 PR 번호와 head commit SHA에 연결해 현재 코드에 대한 리뷰 결과임을 구분한다.

PR Review Template의 섹션명은 사람이 읽는 출력 구조이므로 한글로 쓴다. Review Comment와 Workflow Engine 사이의 기계 판독용 필드명은 해당 스킬 계약에 따라 영어 snake_case를 유지한다.

정규화 필수 필드:

- PR 전체 리뷰 결론: `승인`, `의견`, `변경 요청` 중 하나
- 각 피드백의 중요도 라벨: `[차단]`, `[중요]`, `[사소]`, `[제안]`, `[학습]`, `[칭찬]` 중 하나
- 각 `[차단]` 또는 `[중요]` 피드백의 파일 경로와 diff 위치
- 각 피드백의 문제, 영향, 권장 조치
- 테스트 커버리지 판단 또는 테스트 영향 없음 판단

위치, 중요도, 리뷰 결론, 문제 영향, 권장 조치, 테스트 커버리지 판단 중 하나라도 판단할 수 없어 PR Review Template 필수 필드를 채울 수 없으면 리뷰 코멘트 게시로 넘어가지 않고 누락 필드와 재개 조건을 제시한다.

## 이슈와 PR 본문 계약

### 템플릿 원천

- `.github/ISSUE_TEMPLATE/*.md`와 `.github/pull_request_template.md`는 실제 이슈와 PR 본문 형식의 단일 원천이다.
- `github-templates.md`는 이슈 title prefix, label, 필수 섹션, 연결 규칙의 정합성을 검증하는 계약 문서다.
- 작성 지침은 이 문서와 전용 스킬에서 관리하고, 생성된 이슈나 PR 본문에는 복사하지 않는다.
- 이슈나 PR 템플릿의 특정 섹션을 지칭할 때는 실제 섹션 제목을 그대로 쓴다.
- `완료 기준은 무엇인가요?`는 해당 이슈를 종료해도 되는지 판단할 수 있는 체크리스트여야 한다.

### 기능제안 이슈

필수 섹션:

- `무엇을 제안하나요?`
- `왜 필요한가요?`
- `현재 상태는 어떤가요?`
- `판단 결과`
- `판단 근거`
- `완료 기준은 무엇인가요?`

`판단 결과`는 생성 시 미체크로 둔다. 진행 방향이 확정되면 `진행하지 않음`, `정책 검토 필요`, `기능 변경 필요` 중 하나만 체크한다.

`판단 근거`는 생성 시 비워 둔다. 진행 방향이 확정되면 Workflow Engine이 사용자가 확정한 방향의 근거와 기록 요청을 확정하고, 단순 상태 변경 실행 절차로 반영한다.

`완료 기준은 무엇인가요?`는 생성 시 비워 둔다. 진행 방향이 확정되면 Workflow Engine이 확정 방향에 맞는 체크항목과 추가 요청을 확정하고, 단순 상태 변경 실행 절차로 반영한다. 후속 작업의 체크와 기능제안 이슈 종료도 같은 절차를 따른다.

방향별 완료 기준 항목:

- `진행하지 않음 결정 반영`
- `정책검토 전환 방향과 범위 확정`
- `기능변경 전환 방향과 범위 확정`

정책검토 또는 기능변경 방향의 완료 기준은 원본 기능제안 이슈를 종료하기 전에 충족한다. 각 전환
항목은 후속 이슈에 반영할 방향과 범위를 확정했다는 뜻이며, 실제 후속 이슈 생성과 이슈 번호 기록은
기능제안 이슈 종료 후 수행하는 별도 전환 결과다.

### 정책검토 이슈

필수 섹션:

- `무엇을 결정해야 하나요?`
- `왜 지금 필요한가요?`
- `선택지는 무엇인가요?`
- `검토 결과`
- `후속 작업은 무엇인가요?`
- `연관 이슈`

정책검토 이슈 본문은 다음 상태를 분리해 기록한다.

- 정책 설계 결정 여부
- 설계 문서 반영 대상과 반영 단위
- 설계 반영 후 기능변경 전환 범위
- 후속 흐름 연결 여부

`검토 결과`는 생성 시 비워 둔다. 정책 설계가 확정되면 결정, 근거, 필수 설계 문서 반영 대상, 설계 문서 반영 단위, 검증 기준, 설계 반영 후 기능변경 전환 범위를 기록한다.

`후속 작업은 무엇인가요?` 기본 항목:

- `정책 검토 결과 확정`
- `결정된 정책을 관련 설계 문서에 반영`
- `기능변경 전환 방향과 범위 확정`

이 세 항목은 정책검토 이슈를 종료하기 전에 충족한다. `기능변경 전환 방향과 범위 확정`은 기존
기능변경 이슈 갱신 또는 새 기능변경 이슈 생성 중 어느 방향으로 어떤 범위를 반영할지 확정했다는
뜻이다. 실제 기능변경 이슈 갱신이나 생성은 정책검토 이슈 종료 후 수행하는 별도 전환 결과이며,
정책검토 이슈의 종료 선행조건이 아니다.

정책검토의 `검토 결과`에는 설계 문서 반영 후 기능변경 전환 범위를 기록한다.

Workflow Engine은 정책 설계를 자동 확정하지 않는다. 정책 설계 계획 수립 단계에서는 판단에 필요한 맥락, 근거, 선택지, 추천 설계, 필수 설계 문서 반영 대상을 제시하고, 사용자가 정책 설계를 확정한다.

확정된 정책 설계는 정책검토 이슈의 `검토 결과`에 손실 없이 반영되어야 한다. 설계 문서 반영 대상과 후속 기능변경 범위까지 정할 수 없는 후보는 정책 설계 결정에 충분하지 않으므로 보완 뒤 다시 검토한다.

정책검토의 설계 문서 반영은 결정된 정책을 설계 원천에 기록하는 필수 단계다. 정책검토 흐름은 설계 문서 반영을 건너뛰지 않는다.

`docs/github-workflow-engine.md`처럼 Workflow Engine의 실행 계약을 정의하는 문서는 설계 원천이면서 이 저장소의 핵심 기능 산출물이다. 이 문서의 정책 반영은 정책검토 흐름의 설계 반영으로 처리할 수 있다.

설계 문서 반영 대상과 실행 산출물 변경 대상은 `완료 기준은 무엇인가요?`의 항목을 분리해 기록한다. 다음 대상은 실행 또는 배포 산출물로 보고, 설계 문서 반영 이후 기능변경 흐름의 `작업 범위는 어디까지인가요?`에 기록한다.

- `.codex-dist/skills`
- `.github` 템플릿
- 설치 스크립트
- README
- 그 밖의 실행 산출물 또는 배포 산출물

### 기능변경 이슈

필수 섹션:

- `어떤 기능을 변경하려 하나요?`
- `왜 필요한가요?`
- `작업 범위는 어디까지인가요?`
- `어떤 효과가 기대되나요?`
- `완료 기준은 무엇인가요?`
- `추가 정보`
- `연관 이슈`

`작업 범위는 어디까지인가요?`는 포함과 제외를 나누어 쓴다. `완료 기준은 무엇인가요?`는 기능변경 이슈를 종료해도 되는지 판단할 수 있는 체크리스트로 쓴다.

### 기능결함 이슈

필수 섹션:

- `어떤 문제가 있나요?`
- `문제 유형은 무엇인가요?`
- `재현 과정 또는 확인 위치가 어떻게 되나요?`
- `올바른 동작은 어떻게 되나요?`
- `원인과 해결 방향은 무엇인가요?`
- `완료 기준은 무엇인가요?`
- `추가 정보`

문제 유형은 `코드 버그`, `문서와 구현 불일치`, `정책 문서 간 불일치`, `반영 누락`, `기타` 중 해당 항목을 체크한다. `원인과 해결 방향은 무엇인가요?`는 생성 시 비워 두고, 원인 조사와 해결 계획 반영 작업에서 갱신한다. `완료 기준은 무엇인가요?`는 생성 시 비워 두고, 해결 계획 반영 작업에서 확정된 해결 단위별 종료 조건으로 작성한다.

### 구현 진행 체크항목

Workflow Engine은 Commit Plan의 커밋 단위 ID와 작업 범위로 체크항목 내용과 중첩 위치를 확정하고, 현재 구현 단위의 부모 체크항목 아래에 반영하는 구조화 실행 요청을 만든다. 실제 체크항목 변경은 단순 상태 변경 실행 절차를 따른다.

- 기능변경과 기능결함은 `완료 기준은 무엇인가요?`의 현재 브랜치/PR 단위 항목을 부모로 사용한다.
- 정책검토의 설계 문서 구현은 `후속 작업은 무엇인가요?`의 `결정된 정책을 관련 설계 문서에 반영` 항목을 부모로 사용한다.
- 커밋 생성 후 해당 하위 항목을 체크하고 항목 끝에 `(<commit hash>)` 형식으로 기록한다.
- 하위 항목은 구현 진행 상태이며, 부모 항목은 PR merge 결과를 반영한 뒤 체크한다.

### 연관 이슈

`연관 이슈`는 해당 이슈의 생성 또는 `작업 범위는 어디까지인가요?` 산출에 직접 사용한 근거를 기록하는 섹션이다. PR은 `연관 이슈 (optional)`을 사용한다.

기능제안에서 정책검토 또는 기능변경으로 전환할 때는 원본 기능제안 이슈 본문의 `무엇을 제안하나요?`,
`왜 필요한가요?`, `현재 상태는 어떤가요?`, `판단 결과`, `판단 근거`를 새 이슈 초안의 입력으로
확정한다. 실제 초안 작성은 기능제안 이슈가 닫힌 것을 확인한 뒤 시작한다.

기록 대상:

- 이 이슈나 PR 생성을 직접 유발한 상위 이슈
- `작업 범위는 어디까지인가요?` 또는 `완료 기준은 무엇인가요?`를 결정한 근거 이슈

기록하지 않는 대상:

- 후속으로 생성된 이슈 번호
- 후속으로 생성된 PR 번호

후속 이슈나 PR 번호를 원본 이슈의 `연관 이슈`에 역방향으로 누적하지 않는다. 새로 생성되거나 갱신되는 대상의 `연관 이슈`에 원본 또는 근거 이슈 번호를 기록한다.

- 기능제안에서 정책검토를 만들면 새 정책검토 이슈 본문의 `연관 이슈`에 기능제안 번호를 반영한다.
- 기능제안에서 기능변경을 만들면 새 기능변경 이슈 본문의 `연관 이슈`에 기능제안 번호를 반영한다.
- 정책검토에서 기능변경을 만들면 새 기능변경 이슈 본문의 `연관 이슈`에 정책검토 번호를 반영한다.
- 정책검토 결과를 기존 기능변경에 반영하면 기존 기능변경의 `연관 이슈`에 정책검토 번호를 추가하고, 확정된 반영 범위를 `작업 범위는 어디까지인가요?`와 `완료 기준은 무엇인가요?`에 반영한다.
- PR 본문의 `연관 이슈 (optional)`에는 해당 PR이 반영하는 정책검토, 기능변경, 기능결함 이슈 번호를 반영한다.

정책검토에서 기능변경으로 전환할 때 Workflow Engine은 open 기능변경 이슈 중 `연관 이슈`에 정책검토
이슈 번호가 있는 후보를 먼저 제시한다. 정책검토 이슈 종료 전에는 사용자가 기존 후보 반영 또는 새
기능변경 이슈 생성 방향과 반영 범위까지만 확정한다. 정책검토 이슈가 닫힌 것을 확인한 뒤 기존 후보
반영은 기존 이슈 갱신으로 처리하고, 새 기능변경 이슈 생성은 기능변경 흐름의 초안 작성으로 처리한다.

### 후속 작업 체크항목

후속 작업 체크항목에는 해당 후속 작업의 완료 산출물인 이슈 번호 또는 PR 번호를 괄호로 붙일 수 있다. 이 기록은 `연관 이슈` 갱신으로 보지 않는다.

세 전환의 후속 이슈가 생성되거나 갱신되면 닫힌 원본 이슈의 대응 체크항목 뒤에 전환 결과인 후속
이슈 번호를 붙인다.

- 기능제안에서 정책검토로 전환하면 `정책검토 전환 방향과 범위 확정`에 정책검토 이슈 번호를 붙인다.
- 기능제안에서 기능변경으로 전환하면 `기능변경 전환 방향과 범위 확정`에 기능변경 이슈 번호를 붙인다.
- 정책검토에서 기능변경으로 전환하면 `기능변경 전환 방향과 범위 확정`에 생성하거나 갱신한 기능변경
  이슈 번호를 붙인다.

이 사후 기록은 이미 충족된 체크항목의 의미나 원본 이슈의 종료 상태를 바꾸지 않는다.

### PR 본문

필수 섹션:

- `왜 변경하려 하시나요?`
- `어떻게 변경하려고 하나요? (optional)`
- `해당 변경으로 영향받거나 검토해야 할 사항은 무엇인가요? (optional)`
- `머지하기 전에 반드시 확인되어야 할 사항이 있다면 작성해 주세요. (optional)`
- `연관 이슈 (optional)`

`연관 이슈 (optional)` 작성 규칙:

- Workflow Engine이 관리하는 PR에는 `Refs #번호` 형식을 사용한다.
- Workflow Engine 관리 이슈에는 `Closes`, `Fixes`, `Resolves`를 사용하지 않는다.
- 이슈 종료는 PR merge 이후 Workflow Engine이 연결 이슈의 `완료 기준은 무엇인가요?`와 정책검토 이슈의 `후속 작업은 무엇인가요?` 충족 여부를 확인한 뒤 판단한다.
- 기능제안에서 정책검토 또는 기능변경으로, 정책검토에서 기능변경으로 전환하는 경우에는 원본 이슈에
  전환 방향과 범위를 기록하고 종료 전 체크항목을 충족한 상태를 원본 이슈 종료 조건으로 본다. 실제
  후속 이슈 생성이나 기존 이슈 갱신은 원본 이슈 종료 후 수행하므로 원본 이슈 종료의 선행조건에
  포함하지 않는다.

## 리뷰 피드백 처리

리뷰 피드백 분류는 리뷰 피드백을 바로 수정 명령으로 보지 않고, 사람이 작업을 결정할 수 있도록 분류와 맥락을 제공하는 절차다.

### 리뷰 판단 항목

리뷰 결과를 처리할 때 다음 네 가지 판단 항목을 구분한다. 특히 중요도는 피드백의 영향 수준이고, 대응 방향은 사람이 선택하는 처리 방식이다.

| 판단 항목             | 값 또는 예시                                                                   | 책임                                                             |
| --------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| 리뷰 결론             | `승인`, `의견`, `변경 요청`                                                    | `awesome-code-review`가 PR 전체 결론으로 제시한다.               |
| 중요도                | `[차단]`, `[중요]`, `[사소]`, `[제안]`, `[학습]`, `[칭찬]`                    | `awesome-code-review`가 개별 피드백의 영향 수준으로 제시한다.    |
| 대응 방향             | `수용`, `거절`, `기타 의견 입력`                                               | 사용자가 피드백을 어떻게 처리할지 사용자 결정에서 결정한다.      |
| 해결 여부 결정        | `해결`, `미해결`                                                               | 피드백 처리 결과 기록과 필요한 댓글 처리 뒤 사용자가 별도로 결정한다. |

### 대응 분류

| 분류 | 의미                                                                            | 후속 작업                                           |
| ---- | ------------------------------------------------------------------------------- | --------------------------------------------------- |
| 수용 | 피드백을 현재 PR 범위에서 반영한다.                                             | 확정된 범위만 수정하고 커밋 메시지를 다시 확정한다. |
| 거절 | 오탐, 범위 밖, 또는 반영 대상에서 제외할 피드백이다.                            | 선택된 피드백에 거절 근거를 남긴다.                |
| 기타 의견 입력 | 추가 질문, 범위 재조정, 별도 이슈화 등 즉시 수용/거절로 처리 방향을 확정하기 어려운 피드백이다. | 사용자가 지정한 후속 작업을 수행한다. |

피드백 게시 위치는 `review-runtime-contract.md`의 리뷰 게시 위치 판정 규칙을 따른다. 중요도와 관계없이 모든 피드백은 `file`, `line`, diff position 매핑 성공 근거가 있을 때만 review thread 게시 초안으로 만든다. 근거가 없거나 매핑할 수 없으면 GitHub 상태를 변경하지 않고 `위치 매핑 보류`로 분류한다. Workflow Engine은 보류 피드백을 한 번에 하나씩 제시하고 사용자가 `review thread 게시 위치 재지정`, `피드백 철회`, `기타 의견 입력` 중 하나를 확정할 때까지 멈춘다. `review thread 게시 위치 재지정`은 새 `file`과 `line`의 diff position 매핑 성공 결과를 요구하고, `피드백 철회`는 철회 근거를 기록하며 해당 피드백을 게시 대상에서 제거하고, `기타 의견 입력`은 위치 재지정 또는 피드백 철회에 필요한 추가 판단을 수집한다. 중요도 라벨은 피드백의 의미를 유지하며 diff 위치를 대체하지 않는다. 확정 방향을 반영해 게시 초안을 다시 정리하고 남은 보류 항목을 반복 확인하며, 모든 위치 매핑 보류가 해소되기 전에는 GitHub 상태를 변경하지 않는다. 게시할 피드백이 있으면 모든 review thread 게시 대상에 GitHub id가 기록된 때 리뷰 결과가 반영된 것으로 보고, 없으면 댓글을 만들지 않고 리뷰 결과가 반영된 것으로 본다. 이후 `리뷰 대응 대상 확인`과 `남은 피드백 확인` 작업은 현재 GitHub 상태에서 unresolved review thread를 선택한다. 리뷰 결과가 반영되고 모든 review thread가 resolved인 상태는 별도로 기록하지 않고 GitHub 상태에서 `모든 피드백 대응 완료`로 판정한다. 확인 작업의 완료 여부는 이 판정에 사용하지 않는다. 이 판정과 `PR merge 가능`을 모두 충족해야 merge 결정을 요청한다. 리뷰 실행 결과 파일에만 있는 피드백은 게시 전 분류 대상일 뿐, 대응 대상은 아니다.

피드백은 한 번에 하나만 처리한다. Workflow Engine은 diff가 있는 unresolved review thread를 처리한다. 피드백 1건마다 맥락 설명, 대응 방향 사용자 결정, 수정, 커밋 메시지 사용자 결정, push, 처리 결과 댓글, 해결 여부 확인, 해결 결정 반영, 남은 피드백 확인을 반복한다.

`수용`은 선택된 피드백 1건의 파일 수정을 확정한다는 의미다. 파일 수정과 검증이 끝난 뒤에는 `commit` 스킬로 커밋 메시지 후보를 제안하고, 사용자가 특정 커밋 메시지를 확정하기 전까지 `git commit`을 실행하지 않는다. 작업 진행 안내나 추천 메시지 표시만으로 커밋 메시지 확정 사용자 결정을 충족한 것으로 보지 않는다.

여러 피드백을 조회하거나 맥락으로 확보했더라도 현재 처리 대상은 Workflow Engine이 이번 단계에서 선택해 사용자에게 제시한 피드백 1건뿐이다. 선택되지 않은 피드백은 읽기 전용 맥락이며, 같은 수정 작업이나 같은 커밋에 함께 포함하지 않는다.

피드백 대응 방향은 사용자가 제시된 번호, 선택지 문구, 또는 `기타 의견 입력` 허용 형식을 입력해야 확정된다. Workflow Engine은 `권장 대응: 수용`처럼 추천을 제시할 수 있지만, 일반 진행 표현을 추천안 확정으로 해석하지 않는다. 사용자가 `수정`, `계속 진행`, `다음으로`, `네`, `좋습니다`, `진행해주세요`처럼 일반 진행 표현만 입력하면 선택된 피드백 1건도 수정하지 않고 대응 방향을 다시 확인한다.

리뷰 피드백 대응 방향은 상태 전이를 확정하는 선택지이므로 `수용`, `거절`, `기타 의견 입력`만 유효하다. `수정` 같은 작업 지시는 어떤 대응 방향을 선택했는지 명확히 표현하지 않으므로 대응 방향 확정으로 보지 않는다.

다음 피드백으로 이동하려면 현재 선택된 피드백 1건의 대응 방향 확정, 필요한 수정, 커밋, push, 처리 결과 댓글, 해결 여부 결정, GitHub 실행 상태 재조회가 끝나야 한다.

처리 결과 댓글은 현재 선택된 review thread의 답글로 게시한다. Workflow Engine은 `수용`이면 수정 커밋 push 뒤 `commit-hash 수정했습니다.` 형식, `거절`이면 거절 근거, `기타 의견 입력`이면 사용자가 지정한 처리 결과로 댓글 요청을 확정한다. 실제 게시와 게시 후 댓글 ID 확인은 단순 상태 변경 실행 절차를 따른다.

해결 여부 결정은 처리 결과 댓글이 끝난 뒤 별도로 확인하는 사용자 결정이다. Workflow Engine은 사용자에게 `해결` 또는 `미해결` 중 하나를 확인한다. `해결`을 선택하면 대상 review thread와 예상 resolved 상태를 포함한 요청을 확정하고, 단순 상태 변경 실행 절차로 resolve한 뒤 사후조건을 확인한다. `미해결`을 선택하면 실행 요청을 만들지 않고 GitHub 상태를 현재 상태로 유지한다.

피드백을 사람에게 전달할 때 포함할 맥락:

- 피드백 원문
- 관련 파일 또는 문서 위치
- 위험도
- 예상 영향
- 수용/거절/기타 의견 입력 권장 대응
- 중요도
- 추천 작업
- 리뷰 결론 또는 Review Comment Skill의 보류 질문
- 자동 수정 시 위험 요소

## 로그와 재개

### 실행 로그

Workflow Engine은 작업에 진입하거나 중단 또는 재개 상태를 기록해야 할 때 타겟 저장소의
`.github-agentic-loop/logs/github-workflow-log-YYYY-MM-DD.md`에 보조 로그를 남긴다. 파일명의
`YYYY-MM-DD`는 기록 시점의 실행 환경 현재 날짜다. 같은 날짜의 사건은 같은 파일에 추가하고 날짜가
바뀌면 새 날짜 파일을 선택한다. Workflow Engine은 Harness 소유의 `.harness/logs/`에 실행 로그를
기록하지 않는다. 실행 로그는 빠른 맥락 복원과 재개 조건 확인을 돕는 보조 근거이며, GitHub 실행 상태를
대체하지 않는다.

날짜 경계를 넘긴 재개 요청에서는 현재 실행 환경 날짜 파일을 먼저 읽는다. 현재 날짜 파일이 없거나 같은
기준 이슈 또는 PR과 워크플로에 해당하는 `request_id`, `task_action_id`, 재개 조건이 없으면 로그 파일명을
날짜 내림차순으로 확인하고 최신 관련 이전 날짜 파일부터 필요한 근거가 복원될 때까지만 최소 범위로
읽는다. 관련 이전 날짜 파일에서도 재개 근거를 찾지 못하면 값을 추론하지 않고 중단하며, 로그가 GitHub
완료·미완료 근거와 충돌하면 GitHub 실행 상태를 우선한다.

로그 항목은 다음을 포함한다.

- 대상 이슈 또는 PR
- 작업 대상 식별자
- 워크플로우 유형
- 진입한 작업 이름
- 적용한 조건
- 실행 범위와 수행한 작업 내용
- 확정된 사용자 결정 또는 사용자 결정 필요 여부
- 완료기준과 충족 근거
- 참조한 GitHub 실행 상태
- GitHub 상태에 반영한 내용
- 남은 판단 질문 또는 재개 조건

### 중단과 재개

자동 실행 루프는 진행 판단이 `사용자 결정`, `중단`, `완료` 중 하나로 산출될 때 멈춘다.

- `사용자 결정`: 현재 작업의 사용자 결정 필드에 따라 결정 대상, 선택 가능한 응답, 입력 예시를 번호 목록으로 제시한다.
- `중단`: 정보 부족, 의존성 누락, 의도 불명확, 실행 오류, 사용자 보류 요청처럼 현재 작업을 확정하거나 실행할 수 없는 사유와 재개 조건을 제시한다.
- `완료`: 기준 대상의 완료 조건이 충족되었음을 GitHub 실행 상태 근거로 제시하고 종료한다.

멈출 때는 현재 이슈 또는 PR, 현재 `workflow_id`와 `task_action_id`, 진행 판단, 중단 사유 또는 완료 근거, 사용자 결정 질문 또는 재개 조건을 제시한다. 사용자 결정 선택지가 있으면 현재 작업의 `user_decision_options`만 번호 목록으로 제시한다.

재개할 때는 GitHub 실행 상태와 현재 코드 상태를 다시 읽고 state adapter 정규화와 evaluator 평가를 다시 적용한다. 날짜별 실행 로그는 위의 최신 관련 파일 선택 규칙에 따라 보조 근거로만 사용하며, 실행 로그와 GitHub 상태가 충돌하면 GitHub 상태를 우선한다. 종료 이슈에 후속 흐름 전환이 체크되어 있지만 대응하는 후속 대상이 없으면 해당 종료 이슈를 전환 출발점으로 사용한다.

중단된 흐름을 재개할 때 사용자 요청이 직전 응답에서 제시한 번호, 선택지 문구, 허용된 `기타 의견 입력` 형식과 일치하지 않으면 Workflow Engine은 현재 워크플로우 상태를 요약하고, 현재 `task_action_id`의 `user_decision_options`를 번호 목록으로 다시 제시한다. 이때 번호 입력, 선택지 문구 입력, `기타 의견 입력` 형식의 입력 예시를 함께 제시한다.

## 적용과 관리 구조

이 섹션은 `codex-harness`가 관리하는 설계·배포 자산과 타겟 프로젝트에 적용되는 운영 자산의 경계를 정의한다.

### codex-harness 관리 자산

`codex-harness`는 Workflow Engine의 설계 원천과 전역 배포 기본형을 관리한다.

- GitHub Workflow Engine 설계 문서
- 기능제안, 정책검토, 기능변경, 기능결함 이슈 템플릿 기본형
- Pull Request 템플릿 기본형
- Harness, GitHub Workflow Engine, Workflow Code Editor, Issue Creation, Feature Proposal Triage, Policy Plan, Policy Review Next Triage, Feature Plan, Fix Analysis, Fix Plan, Branch Proposal, Commit Plan, PR Proposal, PR Creation, Review Comment 전역 스킬 기본형
- 이슈 유형별 라벨 계약

전역 `commit` 스킬, `awesome-code-review`, `sendbird/cc-plugin-codex`는 외부 의존성으로만 다루며 `codex-harness` 관리 기본형에 포함하지 않는다.

`docs/github-workflow-engine.md`는 Workflow Engine 실행 규칙의 설계 원천이다. Workflow Engine 관련 스킬은 이 설계를 바탕으로 구현하고, 설계 원천의 실행 규칙을 변경하면 스킬 반영 여부와 후속 작업을 정책검토 또는 기능변경 흐름에 기록한다.

```text
│       ├── branch-proposal/
│       ├── commit-plan/
│       ├── pr-proposal/
│       ├── pr-creation/
│       └── review-comment/
```

### 타겟 프로젝트 적용 자산

현재 편의 설치 스크립트는 전역 `harness`와 Workflow Engine 스킬 묶음을 함께 배치하지만 두 런타임은 서로의 설치를 전제로 하지 않는다. 전역 `harness`는 명시적으로 요청받았을 때만 타겟 프로젝트의 로컬 실행 하네스를 생성한다. Workflow Engine은 실제 작업에서 설정이나 템플릿을 최초로 요구할 때만 필요한 항목을 준비하며, 전역 스킬 사본을 타겟 프로젝트 안에 생성하지 않는다.

편의 설치·제거 스크립트의 기본 사용자 스킬 루트는 `$HOME/.agents/skills`다. `CODEX_HOME`은 이 루트를 변경하지 않으며 `$CODEX_HOME/skills`는 설치, 탐지, 이전, 제거하지 않는다. 명시적 설치 위치가 필요하면 `CODEX_HARNESS_DEST_ROOT` 또는 Harness 전용 `CODEX_HARNESS_DEST`를 사용한다. 재설치와 제거로 보존되는 기존 디렉터리는 스킬 탐색 범위 밖의 `${XDG_STATE_HOME:-$HOME/.local/state}/codex-harness/backups`에 저장하고, `CODEX_HARNESS_BACKUP_ROOT`로 이 위치를 재정의할 수 있다.

Workflow Engine 배포 스킬 식별자는 `github-agentic-loop`다. 설치 시 레거시 `github-workflow-engine` 디렉터리가 사용자 스킬 루트에 남아 있으면 먼저 같은 백업 정책으로 이동해 두 식별자가 동시에 활성화되지 않게 한다. `workflow-engine` 제거는 새 이름과 레거시 이름을 모두 검사하고 발견한 디렉터리를 각각 복구 가능한 백업으로 이동한다.

```text
target-repo/
├── .github-agentic-loop/
│   ├── settings.json
│   └── logs/
│       └── github-workflow-log-YYYY-MM-DD.md
├── .codex/
│   ├── config.toml
│   └── agents/
│       └── run-harness.toml
├── .agents/
│   └── skills/
│       └── run-harness/
│           └── SKILL.md
├── .github/
│   ├── ISSUE_TEMPLATE/
│   │   ├── proposal_template.md
│   │   ├── decision_template.md
│   │   ├── feature_template.md
│   │   └── fix_template.md
│   └── pull_request_template.md
└── .harness/
    ├── docs/
    │   ├── team-spec.md
    │   └── orchestration-plan.md
    └── logs/
        ├── session-log.md
        └── latest-session-summary.md
```

`.codex/agents/*`, `.agents/skills/*`, `.harness/docs/*`는 Harness를 별도로 구성한 프로젝트에만 존재하며 일반 코드 변경 경로의 선행 조건이 아니다. `.github-agentic-loop/settings.json`은 Workflow Engine이 독점적으로 생성·해석하는 타겟별 런타임 설정으로 `dependencies.commit.available`, 리뷰 실행 모드 사용 가능 상태와 사용자가 선택한 기본 모드를 필요할 때 저장한다. `.github-agentic-loop/logs/github-workflow-log-YYYY-MM-DD.md`는 Workflow Engine의 날짜별 실행 로그를 저장한다. Harness는 이 설정과 로그를 생성하거나 읽거나 보완하지 않으며 자체 운영 로그는 `.harness/logs/`에 저장한다. 두 런타임의 운영 파일은 보조 운영 자산이며, 현재 작업 상태의 기준 원천은 GitHub 실행 상태다.

### 템플릿 정합성 검사

Workflow Engine이 이슈 또는 PR 템플릿을 최초로 요구할 때 해당 유형의 타겟 `.github` 템플릿, 라벨과 `github-templates.md` 계약의 정합성을 검사한다. `github-templates.md`는 실제 템플릿 본문 복제본이 아니라 이슈 title prefix, label, 이슈 유형별 라벨, 필수 섹션, 연결 규칙을 검증하는 계약 문서다. 아직 요구하지 않은 다른 유형의 템플릿과 라벨은 미리 만들지 않는다.

1. Workflow Engine 소유의 `target-runtime-bootstrap-contract.md`와 `workflow-engine-template-compatibility-contract.md`에서 현재 요구 범위와 적용·보존 규칙을 읽는다.
2. `github-templates.md`에서 기대 파일명, 이슈 title prefix, label, 이슈 유형별 라벨 집합, 필수 섹션, 연결 규칙, 판정 기준을 읽는다.
3. 타겟 레포에서 현재 요구 유형에 대응하는 `.github/ISSUE_TEMPLATE/*.md` 또는 `.github/pull_request_template.md`를 읽는다.
4. 타겟 GitHub 레포에 현재 이슈 유형 라벨이 정확한 이름으로 존재하는지 확인한다.
5. 기본 파일명이 없으면 같은 역할의 기존 템플릿이 있는지 찾고 매핑 근거를 남긴다.
6. 이슈 템플릿의 YAML frontmatter `title`, `labels`, 필수 섹션, 기본 체크리스트 또는 PR 템플릿의 필수 섹션과 연결 규칙을 비교한다.
7. 결과를 `정합`, `허용된 확장`, `불일치`로 분류한다.
8. 템플릿이나 라벨이 없으면 Workflow Engine이 권한·명령 경로를 확인한 뒤 현재 요구 항목만 생성한다.
9. 불일치가 있으면 자동으로 덮어쓰지 않고 차이, 워크플로우 영향, 수정 후보를 사용자에게 제시한다.
10. 사용자 결정으로 확정된 경우에만 기존 타겟 템플릿의 필요한 부분을 갱신한다.

타겟 레포에서 발견한 개선점은 자동으로 `codex-harness`에 역반영하지 않는다. 여러 타겟에서 반복되거나 공통화할 가치가 있을 때만 사용자 결정 후 기본형으로 승격한다.

## 운영 메모

운영 메모는 앞선 규칙을 반복하지 않고, 실제 적용 시 우선 확인할 관리 원칙만 정리한다.

- 이슈와 PR 본문에는 사용자가 확인할 작업 내용, 판단 근거, 완료 기준만 남긴다. Workflow Engine 규칙 자체는 설계 문서와 전역 스킬 배포본에서 관리한다.
- 새 요청이나 다음 계획 요청을 받으면 열린 PR과 이슈에서 이어갈 작업을 먼저 확인한다. 이어갈 작업이 없을 때만 새 기능제안 후보를 검토한다.
- 계획, 진행 상태, 완료 기준처럼 후속 전이 판단에 쓰이는 정보는 이슈 또는 PR 본문에 반영한다. 리뷰 결과, 실행 로그, merge 알림처럼 본문 상태가 아닌 기록은 댓글이나 `.github-agentic-loop/logs/github-workflow-log-YYYY-MM-DD.md`에 남긴다.
- 기능결함 구현 중 확인된 설계 문서, 규칙 문서, 코드, 템플릿, 스킬 변경은 결함 해결 계획의 해결 단위로 반영한다.
- 리뷰 피드백은 자동 수정 명령이 아니라 사용자 결정 대상이다. 대응 방향과 해결 여부 결정은 리뷰 피드백 처리 규칙을 따른다.
- PR merge는 사람이 수행한다. Workflow Engine은 merge 이후 GitHub 실행 상태를 다시 읽고 연결 이슈의 완료 기준과 후속 작업 갱신 요청을 확정한다. 실제 GitHub 변경은 단순 상태 변경 실행 절차를 따른다.
