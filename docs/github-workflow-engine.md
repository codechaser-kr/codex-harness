# GitHub Workflow Engine 설계

이 문서는 `codex-harness`가 타겟 프로젝트에 GitHub 중심 Workflow Engine을 만들고 적용하기 위한 설계 기준이다.

GitHub 템플릿은 이슈와 PR에 필요한 정보를 적는 양식이다. 이 문서는 GitHub 상태를 어떻게 읽고 다음 작업을 결정할지 정의한다. 상태 전이 규칙은 템플릿 본문에 넣지 않고, 이 설계 문서와 이를 구현한 Workflow Skill에서 관리한다.

## 설계 목표

- GitHub를 프로젝트 작업 상태의 기준 저장소로 사용한다.
- 사람이 보는 작업 상태와 Agent가 읽는 작업 상태를 일치시킨다.
- 정책 판단, 설계 변경, 고위험 작업은 사람이 확인하고 승인한다.
- 파일 작성과 수정은 Codex가 맡고, PR 리뷰는 `open-code-review`가 맡는다.
- 이슈 생성은 Issue Creation Skill 규칙을 따른다.
- 워크플로우는 GitHub에 기록된 상태를 기준으로 중단하고 재개할 수 있어야 한다.
- 상태 전이는 즉흥 판단이 아니라 문서에 정의한 규칙을 따른다.
- GitHub Workflow 운영 구조의 기본형은 `codex-harness`에서 관리하고 타겟 레포에 적용한다.

## 정책 반영 범위

이 문서는 #29의 정책 검토 결과 중 다음 항목을 설계 문서로 반영한다.

- GitHub 기반 Run State 모델
- Workflow Template 구조
- State Transition Table 형식
- Human Checkpoint 기준
- 도구 역할 구분
- `open-code-review` 연동 정책
- Review Feedback Triage 기준
- 리뷰 피드백을 사람에게 전달할 때 포함해야 할 맥락 형식
- 타겟 프로젝트에 GitHub 기반 Workflow Engine을 생성하는 저장소 구조
- 사용자의 비정형 기능 요청을 기능제안 이슈로 정리하는 생성 흐름
- 기능제안 이슈 생성 후 Workflow Skill이 상태 전이를 적용하는 흐름
- 다음 계획 요청 시 병렬 워크플로우를 열지 않고, 이어갈 수 있는 열린 계획을 신규 후보보다 우선하는 다음 작업 후보 판단 규칙
- 모든 상태가 중단되고 재개될 수 있다는 공통 운영 규칙
- 상태 전이를 정해진 Workflow Skill로 수행하는 운영 방식
- 이슈 생성을 이슈 유형별 템플릿과 Issue Creation Skill로 관리하는 운영 방식
- GitHub 이슈/PR 템플릿 기본형을 `codex-harness`에서 관리하고 타겟 레포에 적용하는 Template Bootstrap 흐름

## 상태 모델과 공통 규칙

이 섹션은 GitHub Workflow Engine이 어떤 상태를 읽고, 어떤 공통 규칙으로 흐름을 판단하는지 정의한다. 스킬의 책임과 타겟 레포 적용 방식은 뒤에서 따로 다룬다.

### Workflow Template

Workflow Template은 이슈 유형별 기본 흐름이다. 현재 기본 유형은 다음 네 가지다.

- `기능제안`: 기능 추가, 기능 수정, 운영 흐름 개선 요청을 다룬다.
- `정책검토`: 설계, 정책, 운영 기준을 결정한다.
- `기능변경`: 기능 추가 또는 기존 기능 수정을 실행한다.
- `기능결함`: 결함, 회귀, 문서와 구현 불일치, 반영 누락을 해결한다.

### GitHub Run State

GitHub Run State는 별도 파일이 아니라 GitHub의 이슈, PR, 라벨, 체크리스트, 댓글, 리뷰 상태에서 읽는 현재 작업 상태다.

| 상태 원천                 | 역할                                                                    |
| ------------------------- | ----------------------------------------------------------------------- |
| Issue title               | 이슈 유형과 작업 주제를 식별한다.                                       |
| Issue label               | `기능제안`, `정책검토`, `기능변경`, `기능결함` 유형을 식별한다.         |
| Issue body                | 판단 근거, 범위, 완료 기준, 후속 작업을 읽는다.                         |
| Issue checklist           | 완료 기준과 정책 반영 상태를 읽는다.                                    |
| Issue state               | 작업이 열려 있는지 닫혔는지 읽는다.                                     |
| Pull Request body         | 변경 이유, 영향 범위, 연관 이슈를 읽는다.                               |
| Pull Request state        | 변경이 진행 중인지 병합되었는지 읽는다.                                 |
| Pull Request linked issue | PR이 어떤 정책검토, 기능변경, 기능결함 이슈의 작업을 반영하는지 읽는다. |
| Review and comments       | 리뷰 피드백과 사람 승인 여부를 읽는다.                                  |

### State Transition Rule

State Transition Rule은 현재 GitHub Run State와 조건을 보고 지금 수행할 액션을 정하는 규칙이다. 이 규칙은 Workflow Skill이 적용한다.

State Transition Rule은 모든 이슈 유형에서 같은 필드 형식을 따른다.

| 필드             | 의미                                                                                                                                                      |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 액션 이름        | 해당 액션을 식별하는 이름                                                                                                                                 |
| 현재 상태        | GitHub Run State에서 읽은 이슈/PR 상태                                                                                                                    |
| 조건             | 현재 액션을 선택하기 위한 판정 조건                                                                                                                       |
| 작업 내용        | Workflow Skill, Issue Creation Skill, Codex, `open-code-review`, 또는 사용자가 실제로 진행할 작업                                                         |
| Human Checkpoint | 해당 액션을 진행하거나 확정하기 위해 사용자에게 받아야 하는 승인 또는 결정. 조건에 이미 사용자 결정이 포함되어 있거나 단순 기록만 남기면 `없음`으로 쓴다. |
| 기록 지침        | 해당 액션을 진행할 때 Issue, PR, Comment, Checklist 중 어디에 무엇을 반영해야 하는지                                                                      |

State Transition Rule은 자동 실행 명령이 아니다. Workflow Skill은 이 규칙에 따라 현재 액션을 제안하고, Human Checkpoint가 있으면 사람 승인 없이 해당 액션을 확정하거나 다음 액션으로 넘어가지 않는다.

### Human Checkpoint

Human Checkpoint는 Workflow Skill이나 Agent가 임의로 넘기면 안 되는 사용자 승인 또는 결정 지점이다.

Human Checkpoint가 필요한 경우는 다음과 같다.

- 기능제안, 정책검토, 기능변경, 기능결함 이슈 초안 검토 및 승인
- Workflow Skill이 제안한 작업 후보 중 진행할 대상 선택
- 리뷰 피드백별 추천 액션 설명을 검토하고 대응 방향 승인
- PR 제목과 설명 검토 및 승인
- PR merge
- Codex와 `open-code-review`의 판단 충돌

Human Checkpoint가 필요한 경우 Workflow Skill 또는 Issue Creation Skill은 다음 정보를 사람에게 전달한다.

- 현재 이슈 또는 PR
- 판단해야 할 질문
- 선택 가능한 액션
- 각 액션의 영향과 위험
- 추천 액션과 근거
- 생성 또는 수정될 이슈 초안
- 액션 진입, 중단, 재개 시 확인해야 할 기준

### 전역 실행 로그

전역 실행 로그는 현재 어떤 워크플로우가 어느 액션에 있는지 빠르게 확인하기 위한 로컬 기록이다. 이 로그는 GitHub 상태를 대체하지 않는다. 프로젝트 상태의 기준은 GitHub의 열린 이슈, PR, 체크리스트, 리뷰 상태다.

Workflow Skill은 State Transition Rule의 특정 행을 선택해 액션에 진입할 때마다 `.harness/log`에 액션 진입 로그를 남긴다.

액션 진입 로그에는 다음 정보를 남긴다.

- 대상 이슈 또는 PR
- 워크플로우 유형
- 진입한 액션 이름
- 적용한 조건
- 선택한 작업 내용
- Human Checkpoint 필요 여부
- 참조한 GitHub Run State
- 남은 판단 질문 또는 다음 확인 항목

### 전역 중단/재개 흐름

모든 워크플로우 상태는 중단될 수 있고, 다시 재개될 수 있다. 중단은 실패가 아니라 판단을 잠시 보류한 상태다. 재개 여부는 GitHub의 열린 이슈, PR, 체크리스트, 리뷰 상태를 기준으로 판단한다. 중단 기록은 기본적으로 이슈나 PR에 남기지 않는다.

중단이 발생할 수 있는 경우는 다음과 같다.

- 사용자가 명시적으로 중단 또는 보류를 요청한다.
- Human Checkpoint에서 사용자가 아직 결정하지 않았다.
- 판단에 필요한 정보가 부족하다.
- 외부 리뷰, 설계 검토, 사용자 확인, 실행 결과를 기다려야 한다.
- Codex 또는 `open-code-review` 실행 중 오류나 충돌이 발생해 사람 판단이 필요하다.

중단이나 보류가 발생하면 Workflow Skill은 현재 GitHub 상태를 유지한다. 필요한 경우 마지막 액션 진입 로그에 중단 정보를 덧붙이거나 별도 중단 로그를 남긴다. 이 기록이 없어도 Workflow Skill은 GitHub Run State를 다시 읽어 현재 위치를 판단할 수 있어야 한다.

중단 로그에는 다음 정보를 남긴다.

- 중단된 액션
- 중단 사유
- 마지막으로 확인한 GitHub Run State
- 남은 판단 질문
- 선택 가능한 액션
- 추천 액션과 근거
- 재개 시 먼저 확인해야 할 항목

재개할 때 Workflow Skill은 `.harness/log` 실행 로그를 먼저 참고한다. 로그가 없으면 GitHub Run State를 직접 읽어 현재 위치를 판단한다. 재개는 새 워크플로우를 시작하는 것이 아니라 마지막으로 확인 가능한 상태에서 이어가는 일이다. 닫힌 이슈는 기본적으로 재개 대상이 아니며, 사용자가 다시 열거나 새 이슈로 작성해 달라고 요청한 경우에만 재개 후보가 된다.

중단과 재개는 특정 이슈 유형에만 적용되지 않는다. 정책검토, 기능제안, 기능변경, 기능결함, 연결 PR의 어느 액션에서도 같은 기준을 따른다.

| 액션 이름 | 현재 상태                                            | 조건                                                           | 작업 내용                                                                   | Human Checkpoint | 기록 지침                                         |
| --------- | ---------------------------------------------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------- | ---------------- | ------------------------------------------------- |
| 중단 유지 | `{이슈 유형} open` 또는 `{이슈 유형} PR open`        | 사용자가 중단/보류를 요청하거나 Human Checkpoint 판단이 보류됨 | 현재 GitHub 상태 유지                                                       | 없음             | 없음                                              |
| 중단 유지 | `{이슈 유형} open` 또는 `{이슈 유형} PR open`        | 정보 부족, 외부 검토 대기, 실행 오류로 액션을 확정할 수 없음   | 현재 GitHub 상태 유지                                                       | 없음             | 없음                                              |
| 재개 진행 | 중단된 `{이슈 유형} open` 또는 `{이슈 유형} PR open` | 사용자가 해당 작업의 재개를 요청함                             | GitHub Run State와 실행 로그를 참고해 현재 위치를 다시 판단하고 액션을 진행 | 없음             | 없음                                              |
| 보류 유지 | 중단된 `{이슈 유형} open` 또는 `{이슈 유형} PR open` | 사용자가 보류 유지를 요청함                                    | 현재 GitHub 상태 유지                                                       | 없음             | 없음                                              |
| 종료 처리 | 중단된 `{이슈 유형} open`                            | 사용자가 종료를 결정함                                         | 판단 근거를 남기고 close                                                    | 없음             | 이슈에 종료 사유와 재검토 조건이 있으면 기록한다. |

## 스킬과 도구 책임

이 섹션은 공통 상태 모델을 실제로 적용하는 스킬과 도구의 책임을 정의한다. 상태 전이 판단, 이슈 생성, 개발 계획, 브랜치 제안, 파일 수정, 리뷰 생성은 서로 다른 책임으로 나눈다.

### GitHub Workflow Skill

GitHub Workflow Skill은 GitHub Run State를 읽고, 이 문서의 상태 전이 명세에 따라 현재 조건에서 진행할 액션 후보를 제안하는 실행 규칙이다.

Workflow Skill은 다음 책임을 가진다.

- GitHub Run State에서 진행 중이거나 멈춰 있는 계획이 있는지 먼저 판단한다.
- 진행 중이거나 멈춰 있는 계획이 있으면 신규 후보보다 해당 계획의 재개를 우선한다.
- 재개할 계획이 없을 때만 새로 진행할 수 있는 열린 이슈 후보를 수집한다.
- 선택된 이슈의 유형과 상태에 맞는 State Transition Rule을 적용한다.
- State Transition Rule의 각 액션에 진입할 때 `.harness/log`에 액션 진입 로그를 남긴다.
- 액션에 새 이슈 생성이 필요하면 Issue Creation Skill에 이슈 유형과 생성 근거를 전달한다.
- 모든 상태에서 중단 요청, 정보 부족, Human Checkpoint 미승인, 보류 결정을 처리한다.
- 재개 요청이 들어오면 마지막 액션 진입 로그, 중단 사유, 남은 판단 질문, 액션 후보를 먼저 복원한다.
- 사용자의 merge 알림 또는 다음 계획 요청 시 GitHub Run State를 다시 읽고, merge 결과를 관련 이슈의 체크리스트와 진행 상태에 반영한다.
- Human Checkpoint가 필요한 경우 실행을 멈추고 사용자에게 선택지를 제시한다.
- 사용자가 승인한 액션만 다음 액션으로 넘긴다.

Workflow Skill은 LLM의 자유 추론만으로 상태 전이를 결정하지 않는다. LLM은 이슈 내용을 요약하고, 선택지의 장단점과 추천 근거를 설명할 수 있다. 다만 상태 전이 자체는 Workflow Skill의 규칙을 따른다.

### Issue Creation Skill

Issue Creation Skill은 사용자의 비정형 요청이나 Workflow Skill의 이슈 생성 액션을 받아, GitHub 이슈 유형별 템플릿에 맞는 이슈 초안을 만들고 생성 전 검증을 진행하는 실행 규칙이다.

Issue Creation Skill은 다음 책임을 가진다.

- `기능제안`, `정책검토`, `기능변경`, `기능결함` 네 가지 이슈 유형을 모두 생성할 수 있어야 한다.
- 사용자의 비정형 요청을 적절한 이슈 유형으로 분류하고, 정해진 템플릿에 맞는 제목과 본문 초안으로 정리한다.
- Workflow Skill이 요청한 후속 이슈를 해당 템플릿에 맞게 작성한다.
- 이슈 유형별 제목 prefix, 라벨, 연관 이슈, 필수 본문 항목을 검증한다.
- 템플릿의 각 세부 항목이 오해 없이 작성되었고 다음 워크플로우 판단에 충분한지 검증한다.
- 원본 이슈가 있는 경우 새 이슈 본문에 원본 이슈 링크와 전환 사유를 남긴다.
- 생성 전 사용자에게 초안을 보여주고 승인받는다.
- 사용자가 승인한 이슈만 GitHub에 생성한다.

Issue Creation Skill은 LLM이 자유롭게 작성한 결과를 그대로 이슈로 만들지 않는다. 초안 작성 결과는 이슈 유형, 템플릿, 필수 항목, 라벨, 연결 관계, 생성 여부에 대해 Issue Creation Skill의 규칙과 사용자 승인을 통과해야 한다.

### 기능 개발 계획 Skill

기능 개발 계획 Skill은 생성된 기능변경 이슈와 관련 설계 문서를 바탕으로 실제 구현 전에 개발 계획 초안을 만든다.

기능 개발 계획 Skill은 다음 책임을 가진다.

- 기능변경 이슈의 작업 범위, 완료 기준, 연관 이슈를 읽는다.
- 정책검토 결과와 관련 설계 문서를 함께 참조한다.
- 몇 개의 브랜치로 나누어 작업할지 제안한다.
- 어떤 기능을 어떤 순서로 구현할지 제안한다.
- 각 기능 구현 단위를 하나의 브랜치와 하나의 PR 기준으로 제안한다.
- 각 기능 구현 단위의 검증 기준을 제안한다.
- 확정 전 사용자에게 계획 초안을 보여주고 승인받는다.

사용자가 승인한 기능 개발 계획만 기능 구현 흐름의 입력이 된다.

### Branch Proposal Skill

Branch Proposal Skill은 기능 구현 흐름에서 작업 브랜치 이름을 제안하는 실행 규칙이다. 이 스킬은 `codex-harness`가 관리하는 Workflow Engine 구성요소에 포함된다.

Branch Proposal Skill은 다음 책임을 가진다.

- 기준 이슈 유형, 이슈 번호, 작업 주제, 기능 구현 단위를 읽는다.
- 승인된 기능 개발 계획이 있으면 해당 계획의 브랜치 분할 기준을 따른다.
- 저장소의 기존 브랜치 네이밍 관례를 우선한다.
- 브랜치 이름 후보와 제안 근거를 사용자에게 보여주고 승인받는다.
- 사용자가 승인한 브랜치 이름만 기능 구현 흐름의 브랜치 생성 또는 전환에 사용한다.

### Commit Message Proposal Skill

Commit Message Proposal Skill은 기능 구현 흐름에서 세부 구현 계획의 커밋 단위 변경에 대한 커밋 메시지를 제안하는 실행 규칙이다.

Commit Message Proposal Skill은 다음 책임을 가진다.

- 기준 이슈, 기능 구현 단위, 세부 구현 계획, 변경 파일, 변경 요약을 읽는다.
- 저장소의 기존 커밋 메시지 관례를 우선한다.
- 한 커밋에 포함될 변경 범위와 커밋 메시지 후보를 함께 제안한다.
- 커밋 메시지 후보와 제안 근거를 사용자에게 보여주고 승인받는다.
- 사용자가 함께 승인한 변경 내용과 커밋 메시지만 기능 구현 흐름의 커밋 생성에 사용한다.

### PR Proposal Skill

PR Proposal Skill은 기능 구현 흐름에서 PR 제목과 설명 초안을 제안하는 실행 규칙이다.

PR Proposal Skill은 다음 책임을 가진다.

- 기준 이슈, 작업 브랜치, 변경 요약, 검증 결과, 연관 이슈를 읽는다.
- PR 템플릿에 맞는 제목과 설명 초안을 작성한다.
- PR 하나가 이슈를 닫는지, 여러 PR 중 하나로 참조하는지에 따라 `Closes`, `Fixes`, `Refs` 사용 후보를 제안한다.
- PR 제목과 설명 초안을 사용자에게 보여주고 승인받는다.
- 사용자가 승인한 PR 제목과 설명만 PR Creation Skill의 입력으로 넘긴다.

### PR Creation Skill

PR Creation Skill은 승인된 PR 제목과 설명으로 GitHub PR을 생성하는 실행 규칙이다.

PR Creation Skill은 다음 책임을 가진다.

- 승인된 PR 제목, 설명, 기준 브랜치, 작업 브랜치를 입력으로 받는다.
- 승인된 PR 템플릿 본문으로 GitHub PR을 생성한다.
- 생성된 PR 번호와 URL을 Workflow Skill에 반환한다.
- PR merge 방식 선택이나 merge 수행은 하지 않는다.
- PR 생성 이후 리뷰 진행은 기능 구현 흐름의 `OCR 리뷰 실행` 액션으로 넘긴다.

### Review Comment Skill

Review Comment Skill은 `open-code-review`가 생성한 리뷰 결과를 GitHub PR comment로 게시하는 실행 규칙이다.

Review Comment Skill은 다음 책임을 가진다.

- PR 번호와 `open-code-review` 리뷰 결과를 입력으로 받는다.
- 각 리뷰 피드백을 PR comment에 남길 수 있는 형식으로 정리한다.
- 같은 리뷰 결과가 중복 게시되지 않도록 기존 PR comment를 확인한다.
- 각 피드백을 PR comment에 문제, 근거, 위험도, 추천 분류와 함께 게시한다.
- 리뷰 피드백의 적용 여부를 결정하거나 파일을 수정하지 않는다.

### 도구 역할 구분

도구 역할 구분은 실제 작업을 맡는 도구별 책임을 정한다. 현재 Workflow Engine은 파일 수정과 리뷰 생성을 분리해 운영한다.

현재 기준 역할은 다음과 같다.

| 역할             | 도구                 | 책임                                                                                |
| ---------------- | -------------------- | ----------------------------------------------------------------------------------- |
| 파일 수정        | Codex                | 이슈 범위에 따라 설계 문서와 실제 코드를 수정한다.                                  |
| 리뷰 생성        | `open-code-review`   | PR 변경사항을 검토하고 리뷰 결과를 생성한다.                                        |
| 리뷰 코멘트 게시 | Review Comment Skill | `open-code-review` 리뷰 결과를 PR comment로 게시한다.                               |
| 피드백 대응 진행 | Codex                | PR comment를 수집해 추천 대응 방향을 설명하고, 사용자 승인 후 후속 작업을 수행한다. |

Workflow Skill은 GitHub 상태를 읽고 현재 조건에서 진행할 액션을 제안한다. 실제 파일 수정은 Codex가 맡고, 리뷰 생성은 `open-code-review`가 맡으며, 리뷰 코멘트 게시는 Review Comment Skill이 맡는다.

각 도구는 다음 입출력 기준을 지킨다.

| 구분 | 내용                                                                         |
| ---- | ---------------------------------------------------------------------------- |
| 입력 | 이슈 번호, PR 번호, 작업 범위, 완료 기준, 관련 설계 문서, 승인된 리뷰 피드백 |
| 출력 | 변경 파일, 리뷰 결과, 보류한 판단, 후속 이슈 후보, 검증 결과                 |
| 금지 | 승인되지 않은 정책 변경, 범위 밖 대규모 수정, 리뷰 피드백 자동 일괄 반영     |

도구별 책임은 이 표의 범위 안에서 운영한다. Workflow Template, State Transition Rule, Human Checkpoint, 실행 로그와 중단/재개 규칙은 도구 실행 규칙과 분리해 유지한다.

## 이슈와 PR 운영 규칙

이 섹션은 Workflow Skill과 Issue Creation Skill이 이슈와 PR을 만들거나 갱신할 때 따르는 규칙을 정의한다. PR 리뷰 피드백을 처리하는 기준도 함께 다룬다.

### 이슈 생성 규칙

이슈 생성은 다음 규칙을 따른다.

| 이슈 유형 | 생성 출발점                                             | 생성 주체                                                                | 필수 확인                                                             | Workflow Skill 초기 해석                                            |
| --------- | ------------------------------------------------------- | ------------------------------------------------------------------------ | --------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 기능제안  | 사용자의 기능 추가, 기능 수정, 운영 흐름 개선 요청      | 사용자가 직접 작성하거나 Issue Creation Skill이 초안 작성, 사용자가 승인 | 제안 내용, 배경, 현재 상태, 판단 결과 후보, 제안 필요성 판단 기준     | 열린 기능제안 이슈로 읽고 진행 여부 판단 대상으로 본다.             |
| 정책검토  | 설계, 정책, 운영 기준 결정이 필요함                     | Issue Creation Skill이 초안 작성, 사용자가 승인                          | 결정 질문, 배경, 선택지, 검토 결과 작성 위치, 후속 작업 기준          | 열린 정책검토 이슈로 읽고 정책 결정 대상으로 본다.                  |
| 기능결함  | 사용자의 결함, 회귀, 문서와 구현 불일치, 반영 누락 보고 | 사용자가 직접 작성하거나 Issue Creation Skill이 초안 작성, 사용자가 승인 | 문제 현상, 문제 유형, 확인 위치, 기대 동작, 원인/해결 방향, 완료 기준 | 열린 기능결함 이슈로 읽고 원인 파악과 해결 판단 대상으로 본다.      |
| 기능변경  | 기능제안, 정책검토, 기능결함에서 변경 필요가 확정됨     | Workflow Skill이 필요성을 판단하고 Issue Creation Skill이 생성           | 변경할 기능, 필요성, 포함/제외 범위, 기대 효과, 완료 기준, 연관 이슈  | 열린 기능변경 이슈로 읽고 작업 범위와 완료 기준 추적 대상으로 본다. |

`기능제안`, `정책검토`, `기능결함`은 일반적인 워크플로우 시작점이다. 서로 이어질 수 있지만, 모든 작업이 기능제안에서 시작해야 하는 것은 아니다.

- 정책검토 흐름: 정책검토 이슈에서 정책을 결정하고, 결정된 정책을 설계 문서 반영 PR로 반영한다. 이후 변경된 설계를 기준으로 기능변경 이슈를 만들고, 필요한 경우 기존 기능결함 이슈의 대응 방향과 완료 기준에 반영한 뒤 정책검토 이슈를 닫는다.
- 기능제안 흐름: 기능제안 이슈에서 진행 여부를 판단한다. 진행하지 않으면 기능제안 이슈를 닫고, 정책 수정이 필요하면 기능제안 이슈를 닫은 뒤 정책검토 흐름으로 전환하며, 정책 수정이 필요 없으면 기능제안 이슈를 닫은 뒤 기능변경 이슈를 만든다.
- 기능결함 흐름: 기능결함 이슈에서 결함 여부와 대응 방향을 판단한다. 결함이 아니면 닫고, 정책 수정이 필요 없으면 기능결함 이슈의 대응 방향과 후속 작업을 정리한 뒤 PR로 해결한다. 정책 수정이 필요하면 정책검토 이슈를 만들고, 검토 결과를 기능결함 이슈의 대응 방향과 후속 작업에 반영한 뒤 PR로 해결한다.

`기능변경`은 일반적으로 위 시작점에서 변경 필요가 확정된 뒤 생성되는 실행 이슈다. 사용자가 기능제안 작성을 요청했을 때 Issue Creation Skill은 바로 기능변경 이슈를 만들지 않는다. 먼저 기능제안 이슈로 정리한다. 이후 Workflow Skill이 GitHub Run State에서 열린 기능제안 이슈를 읽고, 필요한 판단 질문을 제시한 뒤 사용자의 결정에 따라 정책검토 또는 기능변경 이슈로 전환하거나 기능제안을 중단한다.

각 이슈 템플릿은 다음 기준을 만족해야 한다.

- 각 세부 항목의 작성 지침이 오해 없이 구체적이어야 한다.
- 이슈 생성 직후 다음 판단에 필요한 정보가 본문에 있어야 한다.
- 후속 이슈나 PR로 전환해야 하는 경우 연결 근거를 남길 수 있어야 한다.
- 완료 기준은 해당 이슈가 닫혀도 되는지를 판단할 수 있는 체크리스트여야 한다.

### 연관 이슈와 후속 작업 기록 지침

`연관 이슈`는 이 이슈나 PR이 생성된 근원지를 기록하는 용도다. 후속으로 생성된 이슈나 PR 번호를 원본 이슈의 `연관 이슈`에 역방향으로 누적하지 않는다.

- 기능제안 이슈에서 정책검토 이슈를 만들면, 새 정책검토 이슈의 `연관 이슈`에 원본 기능제안 이슈 번호를 기록한다.
- 기능제안 이슈에서 기능변경 이슈를 만들면, 새 기능변경 이슈의 `연관 이슈`에 원본 기능제안 이슈 번호를 기록한다.
- 기능결함 이슈에서 정책검토 이슈를 만들면, 새 정책검토 이슈의 `연관 이슈`에 원본 기능결함 이슈 번호를 기록한다.
- 정책검토 이슈에서 기능변경 이슈를 만들면, 새 기능변경 이슈의 `연관 이슈`에 원본 정책검토 이슈 번호를 기록한다.
- PR의 `연관 이슈`에는 해당 PR이 반영하는 정책검토, 기능변경, 기능결함 이슈 번호를 기록한다.

원본 이슈의 완료기준 체크리스트에는 필요한 경우 해당 체크항목의 근거가 되는 이슈나 PR 번호를 항목 뒤 괄호로 붙일 수 있다.

```markdown
- [x] 정책 검토 필요 (#29)
- [x] 설계 문서 반영 PR merge 확인 (#32)
```

### PR 연결 기준

PR은 성격에 따라 정책검토, 기능변경, 기능결함 이슈와 연결한다.

- PR Proposal Skill은 변경 내용과 연관 이슈를 바탕으로 PR 제목과 설명 초안을 작성한다.
- 사람은 PR 제목과 설명이 이슈, 변경 범위, 검증 결과를 적절히 설명하는지 승인한다.
- PR Creation Skill은 승인된 제목과 설명으로 PR을 생성한다.
- PR 하나가 이슈를 완전히 해결하면 `Closes #번호` 또는 `Fixes #번호`를 사용할 수 있다.
- PR 여러 개가 같은 이슈를 나누어 처리하면 `Refs #번호`를 사용하고, 이슈의 완료 기준에서 진행 상태를 관리한다.
- 정책검토 결과를 설계 문서에 반영하는 PR은 정책검토 이슈와 연결한다.
- 기능 구현 PR은 기능변경 이슈와 연결한다.
- 결함 해결 PR은 기능결함 이슈와 연결한다.

### open-code-review 연동 정책

`open-code-review`는 변경사항을 독립적으로 검토하고 리뷰 결과를 생성하는 역할이다. 리뷰 결과를 PR comment로 게시하는 작업은 Review Comment Skill이 담당하고, 파일 수정과 피드백 대응 진행은 Codex가 담당한다.

`open-code-review`는 다음 시점에 실행한다.

- 정책검토, 기능변경 또는 기능결함 PR이 생성된 뒤
- 사람이 별도 리뷰를 요청한 뒤
- 위험도가 높은 설계/정책 변경이 포함된 뒤
- 이전 리뷰 피드백 반영 후 재확인이 필요한 경우

입력은 다음과 같다.

- PR 번호
- 연결된 정책검토, 기능변경 또는 기능결함 이슈
- 변경 diff
- 완료 기준
- 검토에서 제외할 범위

출력은 다음 정보를 포함하는 리뷰 결과다.

- 발견한 문제
- 근거 파일 또는 문서 위치
- 위험도
- 추천 분류: 적용 / 보류 / 거절 / 정책검토 필요 / 사람 승인 필요

`open-code-review`는 PR comment 게시나 파일 수정을 직접 수행하지 않는다. Review Comment Skill은 리뷰 결과를 PR comment로 게시한다. Codex는 PR comment를 수집해 사용자에게 대응 방향을 제안하고, 사람이 승인한 항목만 수정한다.

### Review Feedback Triage

Review Feedback Triage는 리뷰 피드백을 바로 수정 명령으로 보지 않고, 사람이 액션을 결정할 수 있도록 분류와 맥락을 제공하는 절차다.

이 분류는 대응 방향을 정하기 위한 판단 기준이다. GitHub PR comment의 처리 상태는 `해결` 또는 `미해결`로만 관리한다.

| 분류           | 의미                            | 후속 액션                     |
| -------------- | ------------------------------- | ----------------------------- |
| 적용           | 실제 결함 또는 명확한 개선      | 해당 PR 범위 안에서 수정      |
| 보류           | 더 많은 맥락 필요               | 이슈 또는 PR에 보류 사유 기록 |
| 거절           | 오탐 또는 범위 밖 제안          | 거절 근거 기록                |
| 정책검토 필요  | 정책, 설계, 운영 기준 판단 필요 | 정책검토 이슈 생성            |
| 사람 승인 필요 | 고위험 변경 또는 애매한 판단    | Human Checkpoint로 전달       |

리뷰 피드백을 사람에게 전달할 때 포함할 맥락은 다음과 같다.

- 피드백 원문
- 관련 파일 또는 문서 위치
- 예상 영향
- 적용/보류/거절/정책검토 필요/사람 승인 필요 분류
- 추천 액션
- 자동 수정 시 위험 요소

Triage 결과는 자동 수정 승인으로 해석하지 않는다. 사람이 액션을 확정한 뒤에만 수정 작업으로 넘긴다.

## 워크플로우 흐름 명세

워크플로우 흐름 명세는 State Transition Rule의 공통 필드 형식을 따른다. 각 표의 한 행은 자동 실행 규칙이 아니라, Workflow Skill이 현재 조건에서 수행할 액션을 제안하고 사람의 확인이 필요한 지점을 드러내는 판단 단위다.

### 다음 계획 요청 처리

다음 계획 요청은 사용자가 “다음 계획이 무엇인지” 또는 “다음 계획을 진행해달라”고 요청했을 때 Workflow Skill이 GitHub Run State를 읽고 다음 작업 후보를 판단하는 흐름이다. 이 흐름은 병렬 작업을 전제로 하지 않으며, 한 번에 하나의 계획만 다룬다.

“다음 계획” 요청은 기능제안 워크플로우의 시작 조건이 아니다. 특정 작업의 재개 명령도 아니다. 진행 중인 작업이 없는 상태에서 이어갈 수 있는 열린 계획이 있는지 확인하는 요청이다.

진행 중인 작업이 있는데 사용자가 다음 계획을 요청하면 병렬 진행 요청으로 해석될 수 있다. 현재 설계 범위에서는 이런 경우 다음 계획 후보를 판단하지 않는다. 먼저 진행 중인 작업을 완료하거나, 전역 중단/재개 흐름에 따라 중단 또는 보류해야 한다. 특히 리뷰 피드백 처리가 끝났지만 아직 merge되지 않은 PR은 진행 중인 작업으로 본다.

Workflow Skill은 다음 순서로 작업 대상을 판단한다.

| 액션 이름          | 우선순위 | 대상                     | 판단 기준                                                                                                                                                                                                | 작업 내용                                                                                                                                                                                     |
| ------------------ | -------- | ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PR merge 안내      | 1        | merge 대기 PR            | 리뷰 피드백 처리가 끝났지만 아직 merge되지 않은 열린 PR이 있다.                                                                                                                                          | 새 계획 후보를 제안하지 않고, 사용자가 GitHub에서 PR merge를 수행한 뒤 다시 알려주거나 다음 계획을 요청해야 한다고 안내한다.                                                                  |
| 열린 계획 이어가기 | 2        | 이어갈 수 있는 열린 계획 | 진행 중인 작업은 없고, `.harness/log` 실행 로그가 있거나 GitHub Run State에서 전환되지 않은 열린 이슈, 열린 PR, 또는 열린 기능변경/기능결함 이슈의 완료 기준에 아직 반영되지 않은 merge된 PR이 확인된다. | 현재 상태, 남은 판단 질문, 진행할 액션을 보여준다. merge된 PR이 아직 연결 이슈에 반영되지 않았다면 `main` 브랜치로 전환한 뒤 원격 `main`을 pull하고, 이슈 유형별 `PR merged` 전이를 적용한다. |
| 기능제안 요청 연결 | 3        | 새 계획 없음             | 진행 중인 작업도 없고 이어갈 수 있는 열린 계획도 없다.                                                                                                                                                   | 사용자에게 새 기능제안 요청을 받아 Issue Creation Skill의 기능제안 이슈 초안 작성 흐름으로 연결한다.                                                                                          |

이어갈 수 있는 열린 계획은 새 기능제안 이슈 작성 흐름보다 항상 우선한다. Workflow Skill은 기능제안 이슈를 임의로 진행하지 않고, 진행/중단/정책검토/기능변경 선택지를 제시한 뒤 사용자가 결정한 경우에만 다음 액션으로 넘어간다.

### 기능제안 흐름

기능제안은 사용자의 아이디어를 정리하는 시작점이다. 사용자가 직접 기능제안 이슈를 작성할 수 있고, 요청이 비정형이면 Issue Creation Skill이 기능제안 템플릿에 맞게 정리하고, 사용자가 승인한 뒤 기능제안 이슈로 생성한다. 기능제안 이슈가 생성되면 Workflow Skill은 열린 기능제안 이슈로 읽고 상태 전이를 적용한다. 액션 진입은 전역 실행 로그를 따르고, 중단과 재개는 전역 중단/재개 흐름을 따른다.

| 액션 이름          | 현재 상태     | 조건                             | 작업 내용                                                                                                   | Human Checkpoint   | 기록 지침                                                                                                                                                                                   |
| ------------------ | ------------- | -------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 기능제안 초안 작성 | 기능제안 요청 | 사용자가 비정형 기능 제안을 요청 | Issue Creation Skill이 기능제안 템플릿 초안으로 정리해서 승인 요청                                          | 기능제안 초안 승인 | 초안의 `무엇을 제안하나요?`, `왜 필요한가요?`, `현재 상태는 어떤가요?`, `완료 기준은 무엇인가요?`, `추가 정보`를 채운다.                                                                    |
| 기능제안 이슈 생성 | 기능제안 요청 | 사용자가 기능제안 초안을 승인함  | Issue Creation Skill이 기능제안 이슈 생성                                                                   | 없음               | 승인된 초안 그대로 기능제안 이슈를 생성하고, `판단 결과`는 미체크 상태로 둔다.                                                                                                              |
| 진행 방향 제시     | 기능제안 open | 기능제안 이슈가 생성됨           | Workflow Skill이 제안 내용, 배경, 영향 범위, 판단 질문을 설명하고 진행/중단/정책검토/기능변경 선택지를 제시 | 진행 방향 결정     | 필요하면 `추가 정보`에 판단에 필요한 맥락을 보강하고, 최종 선택 전까지 `판단 결과`는 확정하지 않는다.                                                                                       |
| 기능제안 종료      | 기능제안 open | 사용자가 종료를 결정함           | 판단 근거를 남기고 기능제안 close                                                                           | 없음               | `판단 결과`의 `진행하지 않음`을 체크하고, `완료 기준은 무엇인가요?`의 `제안 필요성 판단 완료`를 체크한다. 종료 사유는 `추가 정보`에 기록한다.                                               |
| 정책검토 전환      | 기능제안 open | 사용자가 정책검토 전환을 결정함  | 정책검토 이슈 생성 후 기능제안 close                                                                        | 없음               | 생성되는 정책검토 이슈의 `연관 이슈`에 원본 기능제안 이슈 번호를 기록한다. 기능제안 이슈에는 `판단 결과`의 `정책 검토 필요`를 체크하고, 체크항목 뒤에 정책검토 이슈 번호를 괄호로 덧붙인다. |
| 기능변경 전환      | 기능제안 open | 사용자가 기능변경 전환을 결정함  | 기능변경 이슈 생성 후 기능제안 close                                                                        | 없음               | 생성되는 기능변경 이슈의 `연관 이슈`에 원본 기능제안 이슈 번호를 기록한다. 기능제안 이슈에는 `판단 결과`의 `기능 변경 필요`를 체크하고, 체크항목 뒤에 기능변경 이슈 번호를 괄호로 덧붙인다. |

### 정책검토 흐름

정책검토는 독립적인 워크플로우 시작점이 될 수 있고, 기능제안/기능변경/기능결함 흐름에서 이어질 수도 있다. 정책검토 이슈는 결정 내용, 설계 문서 반영 여부, 결정된 정책을 기준으로 한 기능변경 이슈 생성 여부를 관리한다. 필요한 경우 기존 기능결함 이슈에 검토 결과가 반영되었는지도 확인한다.

| 액션 이름           | 현재 상태          | 조건                                                                                               | 작업 내용                                                                 | Human Checkpoint        | 기록 지침                                                                                                                                                                                                                                                                                                  |
| ------------------- | ------------------ | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 정책검토 초안 작성  | 정책검토 생성 필요 | 사용자가 정책/설계 판단을 직접 요청했거나 Workflow Skill이 정책 또는 설계 판단이 필요하다고 판단함 | Issue Creation Skill이 정책검토 이슈 초안 작성                            | 정책검토 초안 승인      | 초안의 `무엇을 결정해야 하나요?`, `왜 지금 필요한가요?`, `선택지는 무엇인가요?`, `후속 작업은 무엇인가요?`, `연관 이슈`를 채운다.                                                                                                                                                                          |
| 정책검토 이슈 생성  | 정책검토 생성 필요 | 사용자가 정책검토 초안을 승인함                                                                    | Issue Creation Skill이 정책검토 이슈 생성                                 | 없음                    | 승인된 초안 그대로 정책검토 이슈를 생성하고, `검토 결과`는 비워 둔다.                                                                                                                                                                                                                                      |
| 정책 방향 결정 요청 | 정책검토 open      | 정책검토 이슈가 생성됨                                                                             | Workflow Skill이 결정 질문, 배경, 선택지를 설명하고 정책 방향 결정을 요청 | 정책 결정               | 사용자가 결정한 방향과 근거를 `검토 결과`에 기록한다. 필요하면 최종 선택지 기준으로 `선택지는 무엇인가요?`를 정리한다.                                                                                                                                                                                     |
| 설계 문서 반영 착수 | 정책검토 open      | 정책 결정 완료                                                                                     | 설계 문서 반영을 위한 기능 구현 흐름으로 이동                             | 없음                    | `후속 작업은 무엇인가요?`의 `정책 검토 결과 확정`을 체크한다. 필요하면 `검토 결과`에 최종 결정 근거를 보강한다.                                                                                                                                                                                            |
| 설계 문서 PR 반영   | 정책검토 PR merged | 설계 문서 반영 PR이 merge됨                                                                        | Workflow Skill이 정책검토 이슈에 설계 문서 반영 PR merge를 반영           | 없음                    | `후속 작업은 무엇인가요?`의 `결정된 정책을 관련 설계 문서에 반영`을 체크하고, 필요하면 체크항목 뒤에 설계 문서 반영 PR 번호를 괄호로 덧붙인다.                                                                                                                                                             |
| 기능변경 초안 작성  | 정책검토 open      | 설계 문서 반영 PR merge가 정책검토 이슈에 반영됨                                                   | Issue Creation Skill이 변경된 설계 기준으로 기능변경 이슈 초안 작성       | 기능변경 이슈 초안 승인 | 기능변경 이슈 초안의 `연관 이슈`에 정책검토 이슈 번호를 기록한다. 정책검토 이슈의 `후속 작업은 무엇인가요?`에서 `필요한 경우 기능 변경 이슈의 작업 범위와 완료 기준에 반영`은 기능변경 이슈가 생성되고 정책 기준이 반영된 뒤 체크하며, 필요하면 체크항목 뒤에 기능변경 이슈 번호를 괄호로 덧붙인다.        |
| 정책검토 종료       | 정책검토 open      | 설계 문서 반영과 후속 이슈 반영 완료                                                               | 정책검토 close                                                            | 없음                    | `후속 작업은 무엇인가요?`의 필요한 항목이 모두 체크되었는지 확인한다. 기존 기능결함 이슈에서 파생된 정책검토라면 기능결함 이슈의 `원인과 해결 방향은 무엇인가요?` 또는 `완료 기준은 무엇인가요?`에 정책검토 결과가 반영되었는지 확인한다. `검토 결과`가 최종 결정과 근거를 설명하는지 확인한 뒤 close한다. |

### 기능변경 흐름

기능변경은 기능 추가 또는 기존 기능 수정을 실행하는 이슈다. 기능변경 흐름은 기능변경 이슈가 생성된 뒤부터 시작하며, 기능변경 이슈 생성은 기능제안, 정책검토, 기능결함 흐름 또는 Issue Creation Skill의 책임으로 다룬다. 기능변경 이슈 하나에 PR이 하나일 수도 있고 여러 개일 수도 있다.

| 액션 이름           | 현재 상태          | 조건                                              | 작업 내용                                                                 | Human Checkpoint    | 기록 지침                                                                                                                                   |
| ------------------- | ------------------ | ------------------------------------------------- | ------------------------------------------------------------------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 기능 개발 계획 수립 | 기능변경 open      | 기능변경 이슈가 생성됨                            | 관련 설계 문서와 연관 이슈를 참조해 기능 개발 계획 Skill로 개발 계획 수립 | 기능 개발 계획 승인 | 계획에는 참조한 설계 문서와 연관 이슈, 브랜치를 몇 개로 나눌지, 어떤 기능을 어떤 순서로 구현할지, 각 기능 구현 단위의 검증 기준을 포함한다. |
| 기능 구현 착수      | 기능변경 open      | 승인된 기능 개발 계획에 남은 기능구현 단위가 있음 | 계획의 각 기능 구현 단위를 기능 구현 흐름으로 순차적으로 이동             | 없음                | 승인된 기능 개발 계획을 기능 구현 순서와 브랜치 단위의 기준으로 사용한다.                                                                   |

### 기능결함 흐름

기능결함은 사용자의 결함 보고를 정리하는 시작점이다. 사용자가 직접 기능결함 이슈를 작성할 수 있고, 보고가 비정형이면 Issue Creation Skill이 기능결함 템플릿에 맞게 정리하고, 사용자가 승인한 뒤 기능결함 이슈로 생성한다. 기능결함 이슈가 생성되면 Workflow Skill은 열린 기능결함 이슈로 읽고 결함 여부와 원인을 판단한다. 결함이 맞다면 정책 또는 설계 변경이 필요한지 확인한다. 정책검토가 필요한 경우에도 해결 작업의 추적 기준은 기능결함 이슈에 남긴다.

### 기능 구현 흐름

기능 구현 흐름은 정책검토, 기능변경, 기능결함에서 실제 기능 구현이 필요한 경우에 공통으로 적용한다. 기능변경에서는 승인된 기능 개발 계획의 각 기능 구현 단위마다 하나의 브랜치와 하나의 PR로 진행한다. 하나의 기능 구현 흐름 안에서는 해당 기능 구현 단위를 다시 커밋 단위로 나누는 세부 구현 계획을 세우고, 커밋 단위별 변경과 커밋 메시지 승인을 반복한다. 정책검토, 기능변경, 기능결함 흐름은 기능 구현 흐름으로 들어가는 조건과 PR merge 이후 이슈 갱신만 다룬다. 브랜치 제안, 세부 구현 계획, 커밋 단위 구현, PR 생성, 리뷰, 피드백 대응, merge 대기는 이 섹션에서 다룬다.

Workflow Skill은 PR merge를 상시 감시하지 않는다. 사용자가 PR이 merge되었다고 알리거나, 다음 계획 요청으로 GitHub Run State를 다시 읽을 때 merge된 PR을 확인하고 연결 이슈의 후속 전이를 적용한다.

PR 리뷰 과정에서 `open-code-review`는 피드백을 포함한 리뷰 결과를 만든다. Review Comment Skill은 각 피드백을 PR comment로 게시한다. Codex는 PR comment를 모아 피드백별 추천 액션과 근거를 설명할 수 있다. 적용/보류/거절/정책검토 필요/사람 승인 필요 중 어떤 액션을 선택할지는 사람이 확정한다.

| 액션 이름           | 현재 상태           | 조건                                                   | 작업 내용                                                                                                          | Human Checkpoint             | 기록 지침                                                                                                                                                       |
| ------------------- | ------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| PR 생성             | PR 생성 필요        | PR 제목과 설명 승인 완료                               | PR Creation Skill이 PR 생성                                                                                        | 없음                         | 승인된 PR 템플릿으로 PR을 생성한다.                                                                                                                             |

기본 흐름은 다음과 같다.

```text
기능 구현 흐름 진입
  -> Branch Proposal Skill이 브랜치 이름 제안
  -> 사용자가 브랜치 이름 승인
  -> 승인된 브랜치로 이동
  -> Codex가 해당 기능 구현 단위의 세부 구현 계획과 커밋 단위 분할 계획 작성
  -> 사용자가 세부 구현 계획 승인
  -> 남은 커밋 단위가 있는 동안 반복
     -> Codex가 다음 커밋 단위 변경 작업 수행
     -> Commit Message Proposal Skill이 커밋 메시지 제안
     -> 사용자가 변경 내용과 커밋 메시지 승인
     -> 승인된 변경 내용과 커밋 메시지로 커밋 생성
  -> PR Proposal Skill이 PR 제목과 설명 초안 작성
  -> 사용자가 PR 제목과 설명 승인
  -> PR Creation Skill이 PR 생성
  -> open-code-review 실행
  -> open-code-review가 리뷰 결과 생성
  -> Review Comment Skill이 각 피드백을 PR comment로 게시
  -> 해결되지 않은 PR 피드백이 있는 동안 반복
     -> Codex가 피드백별 설명, 개선 방향, 커밋 메시지 제시
     -> 사용자가 피드백별 대응 방향과 커밋 메시지 승인
     -> 승인된 피드백만 Codex가 반영
  -> 필요하면 재리뷰
  -> 사용자가 GitHub에서 PR merge
  -> 사용자가 PR merge를 알리거나 다음 계획 요청
  -> Workflow Skill이 GitHub Run State를 다시 읽고 main 브랜치로 전환한 뒤 원격 main을 pull
  -> 이슈 유형별 PR merged 전이로 이동
```

리뷰 피드백의 액션 분류와 전달 맥락은 Review Feedback Triage를 따른다. `open-code-review`와 Codex는 액션을 추천할 수는 있지만 확정하지 않는다. 확정 권한은 사람에게 있다.

## 적용과 관리 구조

이 섹션은 `codex-harness`가 GitHub Workflow Engine의 기본 구조를 어떻게 관리하고, 타겟 프로젝트에 어떤 자산을 적용하는지 정의한다.

### GitHub Template Bootstrap

GitHub Template Bootstrap은 GitHub Workflow Engine을 타겟 레포에 적용하기 위해 필요한 이슈 템플릿, PR 템플릿, 라벨, 운영 문서의 기본형을 생성하거나 갱신하는 흐름이다.

`codex-harness`는 다음 기본형을 관리한다.

- 기능제안 이슈 템플릿
- 정책검토 이슈 템플릿
- 기능변경 이슈 템플릿
- 기능결함 이슈 템플릿
- Pull Request 템플릿
- GitHub Workflow Engine 운영 문서
- Workflow Skill 설치 구조
- Branch Proposal Skill 설치 구조
- Commit Message Proposal Skill 설치 구조
- PR Proposal Skill 설치 구조
- PR Creation Skill 설치 구조
- Review Comment Skill 설치 구조
- 기본 라벨 세트

GitHub Template Bootstrap은 다음 원칙을 따른다.

- `codex-harness`는 표준 기본형과 생성 규칙의 원천이다.
- 타겟 레포는 적용된 템플릿과 프로젝트별 변형의 소유자다.
- GitHub Workflow 운영 구조 생성은 사용자의 타겟 프로젝트 구축 요청 범위 안에서 수행한다.
- 기존 타겟 레포 템플릿을 덮어쓸 수 있으면 diff와 영향 범위를 사용자에게 보여준다.
- 타겟 레포에서 발견한 개선점은 자동으로 `codex-harness`에 역반영하지 않는다.
- 공통화할 가치가 있는 변경만 사용자 승인 후 `codex-harness` 기본형으로 승격한다.

### codex-harness 관리 구조

`codex-harness`는 GitHub Workflow Engine 기본형을 다음 구조로 관리한다.

```text
codex-harness/
├── docs/
│   └── github-workflow-engine.md
├── .github/
│   ├── ISSUE_TEMPLATE/
│   │   ├── proposal_template.md
│   │   ├── decision_template.md
│   │   ├── feature_template.md
│   │   └── fix_template.md
│   └── pull_request_template.md
└── .codex-dist/
    └── skills/
        ├── github-workflow-engine/
        │   └── SKILL.md
        ├── branch-proposal/
        │   └── SKILL.md
        ├── commit-message-proposal/
        │   └── SKILL.md
        ├── pr-proposal/
        │   └── SKILL.md
        ├── pr-creation/
        │   └── SKILL.md
        └── review-comment/
            └── SKILL.md
```

이 구조는 표준 기본형이다. 실제 타겟 레포에 적용된 템플릿은 타겟 레포의 맥락에 맞게 달라질 수 있다. 공통화할 가치가 있다고 사용자가 판단한 경우에만 `codex-harness` 기본형으로 승격한다.

### 타겟 프로젝트 생성 구조

`codex-harness`가 타겟 프로젝트에 GitHub Workflow Engine 운영 기준을 생성할 때는 다음 자산을 적용 후보로 둔다.

```text
target-repo/
├── .codex/
│   └── skills/
│       ├── github-workflow-engine/
│       │   └── SKILL.md
│       ├── branch-proposal/
│       │   └── SKILL.md
│       ├── commit-message-proposal/
│       │   └── SKILL.md
│       ├── pr-proposal/
│       │   └── SKILL.md
│       ├── pr-creation/
│       │   └── SKILL.md
│       └── review-comment/
│           └── SKILL.md
├── .github/
│   ├── ISSUE_TEMPLATE/
│   │   ├── proposal_template.md
│   │   ├── decision_template.md
│   │   ├── feature_template.md
│   │   └── fix_template.md
│   └── pull_request_template.md
└── docs/
    └── github-workflow-engine.md
```

타겟 프로젝트의 도메인과 기존 운영 방식에 따라 문서 경로는 달라질 수 있다. 중요한 기준은 GitHub Issue와 PR이 프로젝트 상태의 기준이며, 별도 Runtime 상태 저장소가 필수가 아니라는 점이다.

## 운영 메모

- 이슈 제목 prefix와 라벨은 템플릿 기준을 따른다.
- 이슈 본문에 Workflow Engine 규칙을 반복해서 적지 않는다.
- 사용자의 비정형 기능 요청은 Issue Creation Skill이 기능제안 템플릿 초안으로 정리한다.
- 기능제안 이슈는 사용자가 직접 작성하거나 Issue Creation Skill의 도움을 받아 생성할 수 있다.
- 기능제안 이슈가 생성되면 “다음 계획” 요청을 기다리지 않고 Workflow Skill이 열린 기능제안 이슈로 읽고 상태 전이를 적용한다.
- 사용자의 비정형 기능결함 보고는 Issue Creation Skill이 기능결함 템플릿 초안으로 정리한다.
- 기능결함 이슈는 사용자가 직접 작성하거나 Issue Creation Skill의 도움을 받아 생성할 수 있다.
- 기능결함 이슈가 생성되면 “다음 계획” 요청을 기다리지 않고 Workflow Skill이 열린 기능결함 이슈로 읽고 상태 전이를 적용한다.
- “다음 계획” 요청은 병렬 워크플로우를 전제로 하지 않으며, 진행 중인 작업이 없는 상태에서 이어갈 수 있는 열린 계획이 있는지 판단하기 위한 요청이다.
- 모든 액션 진입은 `.harness/log`에 로컬 실행 로그로 남기고, 중단 시 GitHub 상태는 유지하며 같은 로그에 중단 사유와 재개 기준을 남긴다.
- 재개는 새 워크플로우 시작이 아니라 GitHub Run State와 마지막 실행 로그를 기준으로 이어서 진행하는 것이다.
- 이슈 생성은 항상 이슈 유형별 템플릿, 필수 항목, 라벨, 연관 이슈 규칙을 따른다.
- 이슈는 사용자 승인 없이 생성하지 않는다.
- GitHub 템플릿과 라벨 생성/갱신은 사용자의 타겟 프로젝트 구축 요청 범위 안에서 수행한다.
- `codex-harness`는 GitHub Workflow 템플릿 기본형의 소유자이고, 타겟 레포는 적용된 템플릿의 소유자다.
- 진행 중인 작업이 있으면 다음 계획 후보를 판단하지 않는다. 이어갈 수 있는 열린 계획이 있으면 신규 기능제안 후보보다 해당 계획을 우선한다.
- 기능제안 이슈 선택 후에도 진행, 중단, 종료, 정책검토 전환, 기능변경 전환은 사용자가 결정한다.
- 상태 전이는 LLM 자유 판단이 아니라 Workflow Skill의 규칙으로 정한다.
- LLM은 이슈 요약, 선택지 설명, 추천 근거 작성, 이슈 본문 초안 작성에 사용할 수 있지만 상태 전이 또는 이슈 생성 승인 권한을 갖지 않는다.
- 흐름이 애매하면 새 이슈를 만들기보다 현재 이슈에 판단 근거를 먼저 남긴다.
- 작업 중 정책 판단이 필요해지면 구현을 계속 진행하기 전에 정책검토 이슈를 만든다.
- 리뷰 피드백은 자동 수정 명령이 아니라 판단 대상이다.
- 리뷰 피드백별 액션은 PR 과정에서 사용자가 직접 결정한다.
- 실제 반영 여부는 연결 이슈의 후속 작업 또는 완료 기준과 PR 리뷰에서 확인한다.
- PR merge는 사람이 수행하고, Workflow Skill은 사용자의 merge 알림 또는 다음 계획 요청 시 GitHub Run State를 다시 읽어 관련 이슈의 진행 상태와 체크리스트에 반영한다.
