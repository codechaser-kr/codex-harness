# GitHub Workflow Engine 설계

이 문서는 `codex-harness`가 GitHub Issue와 Pull Request를 기준으로 작업 상태를 읽고 다음 액션을 결정하기 위한 설계 기준이다.

이 문서는 사람이 읽는 운영 설명서이면서 Agent가 따라야 하는 실행 프롬프트(prompt) 원천이다. 모든 규칙은 다음 질문에 답할 수 있어야 한다.

- 지금 어떤 GitHub 상태를 읽어야 하는가
- 어떤 이슈 또는 PR을 기준 작업으로 삼아야 하는가
- 어떤 State Transition Rule을 적용해야 하는가
- 어떤 스킬을 호출하고 어떤 구조의 출력을 받아야 하는가
- 어디에서 Human Checkpoint로 멈춰야 하는가
- 어떤 GitHub 상태 또는 파일 상태를 변경해도 되는가

GitHub 템플릿은 이슈와 PR에 남길 본문 형식이다. 이 문서는 템플릿 본문에 운영 규칙을 반복해 넣지 않고, GitHub 상태를 읽고 다음 작업을 결정하는 기준을 정의한다.

## 설계 목표

- GitHub를 프로젝트 작업 상태의 기준 저장소로 사용한다.
- 사람이 보는 작업 상태와 Agent가 읽는 작업 상태를 일치시킨다.
- 상태 전이는 LLM 자유 판단이 아니라 문서에 정의한 규칙을 따른다.
- 정책 판단, 설계 변경, 고위험 작업은 Human Checkpoint를 거친다.
- 액션 하나를 끝낸 뒤 다음 Human Checkpoint까지 자동으로 이어간다.
- 이슈 초안 작성과 실제 GitHub 상태 변경을 분리한다.
- 파일 작성과 수정은 Codex가 맡고, PR 리뷰 생성은 외부 `awesome-code-review`가 맡는다.
- GitHub Workflow 운영 구조의 기본형은 `codex-harness`에서 관리하고 타겟 레포에 적용한다.

## 정책 원천

Workflow Engine 설계는 정책검토 이슈에서 확정된 결정을 원천으로 삼는다. 새 정책검토 결과가 설계에 반영되면 이 섹션에 원천 이슈와 결정 범위를 추가한다.

#29는 GitHub 기반 Workflow Engine의 기본 구조를 확정했다.

- GitHub 기반 Run State 모델
- Workflow Template 구조
- State Transition Table 형식
- Human Checkpoint 기준
- 도구 역할 구분
- 외부 `awesome-code-review` 연동 정책
- Review Feedback Triage 기준
- 리뷰 피드백 전달 맥락
- 타겟 프로젝트에 GitHub 기반 Workflow Engine을 생성하는 저장소 구조
- 비정형 기능 요청을 기능제안 이슈로 정리하는 생성 흐름
- 기능제안 이슈 생성 후 Workflow Skill이 상태 전이를 적용하는 흐름
- 다음 계획 요청 시 이어갈 수 있는 열린 계획을 신규 후보보다 우선하는 규칙
- 모든 상태가 중단되고 재개될 수 있다는 공통 운영 규칙
- 상태 전이를 정해진 Workflow Skill로 수행하는 운영 방식
- 이슈 생성을 이슈 유형별 템플릿과 Issue Creation Skill로 관리하는 운영 방식
- GitHub 이슈/PR 템플릿 기본형을 `codex-harness`에서 관리하고 타겟 레포에 적용하는 Template Bootstrap 흐름

### #39 GitHub 템플릿 단일 원천 정책

#39는 GitHub 템플릿과 상태 변경 기준을 정리했다.

- GitHub 이슈/PR 템플릿 본문의 단일 원천은 타겟 레포의 `.github` 템플릿이다.
- `github-templates.md`는 실제 템플릿 본문 복제본이 아니라 title prefix, label, 필수 섹션, 연결 규칙을 검증하는 계약 문서다.
- GitHub 상태 변경은 사용자의 생성/수정/닫기 의도가 자연어 맥락에서 명확할 때만 수행한다.

### #40 Workflow Engine 공통 실행 골격

#40은 Workflow Engine의 공통 실행 골격과 스킬 계약 정렬 방향을 확정했다.

- Workflow Engine의 기본 흐름을 하나의 공통 실행 골격으로 정리한다.
- 정책검토, 기능제안, 기능변경, 기능결함 흐름은 공통 실행 골격 위에서만 분기한다.
- 정책 결정, 설계 문서 반영, 실행 산출물 변경을 구분한다.
- 하위 스킬의 입력, 출력, Workflow Engine 확정 항목, 금지 동작을 계약으로 관리한다.
- 구조화된 출력만 후속 액션의 입력으로 사용한다.
- 외부 의존 스킬의 설치명, 설치 경로, 출력 형식 기대치를 명시한다.
- 액션 완료 후 다음 Human Checkpoint, 명시적 중단, 외부 의존성 누락, 실행 오류, 완료 상태 중 하나에 닿을 때까지 다음 전이를 이어간다.

### #40 반영 기준

#40의 반영 목표는 문서를 보기 좋게 재배열하는 것이 아니다. Workflow Engine이 실제 실행 중 어떤 규칙을 우선해야 하는지 바로 판단할 수 있도록 프롬프트 계약을 선명하게 만드는 것이다.

이 문서는 다음 항목을 만족해야 한다.

- 공통 실행 골격이 하나의 순서로 읽힌다.
- 정책검토, 기능제안, 기능변경, 기능결함은 공통 실행 골격의 분기 흐름으로만 설명된다.
- 정책 결정, 설계 문서 반영, 실행 산출물 변경의 경계가 분리된다.
- 정책검토 결과가 기능변경 또는 기능결함으로 전환되는 기준이 있다.
- Workflow Engine이 호출하거나 의존하는 스킬 목록이 빠짐없이 제시된다.
- 각 스킬마다 `입력`, `출력`, `Workflow Engine이 확정할 항목`, `금지 동작`이 정리된다.
- 외부 의존 스킬은 설치 확인 경로와 출력 기대치를 함께 적는다.
- Workflow Engine은 구조화된 출력만 후속 액션의 입력으로 사용한다.

## 실행 프롬프트 계약

Workflow Skill을 실행하는 Agent는 이 섹션을 최우선 실행 프롬프트로 사용한다.

### 공통 실행 골격

Workflow Engine의 모든 흐름은 다음 골격을 따른다.

1. GitHub Run State를 읽는다.
2. 다음 액션을 판단한다.
3. 필요한 전용 스킬을 호출한다.
4. 전용 스킬의 구조화된 초안이나 후보를 받는다.
5. Human Checkpoint가 있으면 사용자 결정을 받는다.
6. 승인된 범위에서만 GitHub 상태 또는 파일을 변경한다.
7. 변경 내용과 다음 판단 기준을 적절한 상태 원천 또는 보조 로그에 반영한다.

기능제안, 정책검토, 기능변경, 기능결함은 이 순서의 일부 단계를 건너뛰거나 반복할 수 있다. 별도 흐름처럼 보여도 공통 골격 밖에서 상태를 확정하지 않는다.

### 기본 진행 순서

1. GitHub Run State를 읽는다.
2. 현재 코드 상태를 읽는다.
3. 이어갈 수 있는 열린 PR 또는 이슈가 있는지 먼저 판단한다.
4. 선택한 대상의 이슈 유형과 연결 PR 상태를 확인한다.
5. 해당 유형의 State Transition Rule을 선택한다.
6. 필요한 전용 스킬을 호출해 구조화된 초안이나 후보를 받는다.
7. Human Checkpoint가 있으면 후보, 영향, 위험, 추천 근거를 제시하고 멈춘다.
8. Human Checkpoint가 없고 사용자 의도가 명확한 상태 변경이면 GitHub 상태를 변경한다.
9. 파일 변경이 필요한 구현 액션이면 승인된 범위만 수정한다.
10. 액션이 끝나면 GitHub Run State와 현재 코드 상태를 다시 읽고 다음 전이를 선택한다.

이 순서는 모든 이슈 유형과 연결 PR에 공통으로 적용한다.

### 멈춰야 하는 조건

다음 중 하나에 닿으면 Workflow Skill은 다음 작업을 확정하지 않고 멈춘다.

- Human Checkpoint가 필요한 경우
- 사용자가 중단 또는 보류를 요청한 경우
- 사용자의 생성/수정/닫기 의도가 모호한 경우
- 외부 의존 스킬이 설치되어 있지 않은 경우
- GitHub API, 로컬 명령, 테스트, 리뷰 호출에서 실행 오류가 발생한 경우
- 현재 이슈 또는 PR의 완료 조건을 만족한 경우

멈출 때는 다음 정보를 제시한다.

- 현재 이슈 또는 PR
- 방금 끝난 액션
- 다음으로 가능한 액션
- 각 액션의 영향과 위험
- 추천 액션과 근거
- 사용자가 결정해야 할 질문

### 금지

- GitHub 상태를 LLM 자유 판단만으로 변경하지 않는다.
- 사용자의 의도가 모호한 상태에서 이슈, PR, 체크리스트, 댓글을 변경하지 않는다.
- 계획/제안형 스킬이 상태 확정, 브랜치 전환, 커밋 생성, PR 생성, 리뷰 게시를 직접 수행하지 않는다.
- 일반 설명 문장을 후속 액션의 상태 원천으로 해석하지 않는다.
- PR 본문에 `Closes`, `Fixes`, `Resolves` 자동 close 키워드를 쓰지 않는다.
- 진행 중인 PR 또는 열린 계획이 있는데 새 기능제안 후보를 병렬로 만들지 않는다.
- 정책검토의 설계 문서 반영과 실행 산출물 변경을 같은 단계로 압축하지 않는다.
- 구조화된 스킬 출력에 없는 값을 일반 설명 문장에서 추론해 확정하지 않는다.

## 상태 모델

### GitHub Run State

GitHub Run State는 별도 Runtime 파일이 아니라 GitHub의 이슈, PR, 라벨, 체크리스트, 댓글, 리뷰 상태에서 읽는 현재 작업 상태다.

| 상태 원천 | 역할 |
| --- | --- |
| Issue title | 이슈 유형과 작업 주제를 식별한다. |
| Issue label | `기능제안`, `정책검토`, `기능변경`, `기능결함` 유형을 식별한다. |
| Issue body | 판단 근거, 범위, 완료 기준, 후속 작업을 읽는다. |
| Issue checklist | 완료 기준과 정책 반영 상태를 읽는다. |
| Issue state | 작업이 열려 있는지 닫혔는지 읽는다. |
| Pull Request body | 변경 이유, 영향 범위, `연관 이슈` 섹션의 이슈 번호를 읽는다. |
| Pull Request state | 변경이 진행 중인지 병합되었는지 읽는다. |
| Pull Request review threads | 해결되지 않은 라인 피드백을 읽는다. |
| Pull Request issue comments | marker가 있는 요약 피드백 댓글만 상태 원천으로 읽는다. |

### 이슈 유형

| 유형 | 목적 | 다음 흐름 |
| --- | --- | --- |
| `기능제안` | 기능 추가, 기능 수정, 운영 흐름 개선 요청의 진행 여부를 판단한다. | 종료, 정책검토 전환, 기능변경 전환 |
| `정책검토` | 설계, 정책, 운영 기준 결정을 추적한다. | 설계 문서 반영, 후속 기능변경/기능결함 반영 |
| `기능변경` | 기능 추가 또는 기존 기능 수정을 실행한다. | 기능 개발 계획, 기능 구현 흐름 |
| `기능결함` | 결함, 회귀, 문서와 구현 불일치, 반영 누락을 해결한다. | 원인 조사, 정책검토 전환, 결함 해결 계획 |

라벨을 이슈 유형의 1차 기준으로 삼는다. 제목 prefix와 라벨이 충돌하면 Human Checkpoint로 넘기고 임의 변경하지 않는다.

### State Transition Rule 형식

State Transition Rule은 현재 상태와 조건을 보고 지금 수행할 액션을 선택하는 규칙이다.

| 필드 | 의미 |
| --- | --- |
| 액션 이름 | 해당 액션을 식별하는 이름 |
| 현재 상태 | GitHub Run State에서 읽은 이슈 또는 PR 상태 |
| 조건 | 현재 액션을 선택하기 위한 판정 조건 |
| 작업 내용 | Workflow Skill, 전용 스킬, Codex, 외부 리뷰 스킬, 사용자 중 누가 무엇을 하는지 |
| Human Checkpoint | 사용자 결정이 필요한 지점 |
| 상태 반영 지침 | 이슈 본문, PR 본문, 댓글, 체크리스트, 로그 중 어디에 무엇을 남기는지 |

State Transition Rule은 자동 실행 명령이 아니다. Human Checkpoint가 있으면 사람 결정 없이 해당 액션을 확정하지 않는다.

### 액션 완료 후 진행 기준

Workflow Skill은 액션 하나를 완료하면 즉시 GitHub Run State와 현재 코드 상태를 다시 읽고 다음 State Transition Rule을 선택한다.

다음 중 하나에 닿을 때까지 이어간다.

- 다음 Human Checkpoint
- 명시적 중단 또는 보류
- 외부 의존성 누락
- 실행 오류
- 완료 상태

이 기준은 사용자가 “다음 절차가 무엇인가요?”라고 다시 물어야만 흐름이 이어지는 상황을 막기 위한 규칙이다. 다음 액션이 Human Checkpoint라면 Workflow Skill은 후보와 근거를 제시하고 멈춘다.

## Human Checkpoint

Human Checkpoint는 Workflow Skill이나 Agent가 임의로 넘기면 안 되는 사용자 승인 또는 결정 지점이다.

### Human Checkpoint 대상

- 기능제안, 정책검토, 기능변경, 기능결함 이슈 초안 확인
- 정책 방향 결정
- 기능 개발 계획 또는 결함 해결 계획 확정
- 브랜치 이름 확정
- 세부 구현 계획 확정
- 변경 내용과 커밋 메시지 확정
- PR 제목과 본문 확정
- 리뷰 피드백별 대응 방향 확정
- PR merge
- Codex와 외부 `awesome-code-review`의 판단 충돌

### 사용자 의도 확인

사용자-facing 응답에서는 `승인 절차`, `절차 누락` 같은 운영 용어를 과하게 드러내지 않는다.

다음처럼 현재 초안이나 후보에 대한 진행 의도가 명확하면 상태 변경 액션으로 볼 수 있다.

- `이대로 진행`
- `생성해주세요`
- `좋습니다`
- `네`

의도가 모호하면 GitHub 상태를 변경하지 않고 초안, 수정 후보, 필요한 확인 질문만 제시한다.

## 로그와 재개

### 실행 로그

Workflow Skill은 액션에 진입할 때마다 타겟 저장소의 `.harness/logs/github-workflow-log.md`에 보조 로그를 남긴다. 이 로그는 빠른 맥락 복원을 돕지만 GitHub 상태를 대체하지 않는다.

로그 항목은 다음을 포함한다.

- 대상 이슈 또는 PR
- 워크플로우 유형
- 진입한 액션 이름
- 적용한 조건
- 선택한 작업 내용
- Human Checkpoint 필요 여부
- 참조한 GitHub Run State
- GitHub 상태에 반영된 승인 계획 요약 또는 보조 체크포인트
- 남은 판단 질문 또는 다음 확인 항목

### 중단과 재개

중단은 실패가 아니라 판단을 잠시 보류한 상태다. 중단이나 재개는 정책검토, 기능제안, 기능변경, 기능결함, 연결 PR 어디에서나 발생할 수 있다.

중단이 발생할 수 있는 경우는 다음과 같다.

- 사용자가 중단 또는 보류를 요청한 경우
- Human Checkpoint에서 사용자가 아직 결정하지 않은 경우
- 판단에 필요한 정보가 부족한 경우
- 외부 리뷰, 설계 검토, 사용자 확인, 실행 결과를 기다려야 하는 경우
- Codex 작업 또는 외부 리뷰 호출 중 오류나 충돌이 발생한 경우

재개할 때는 GitHub Run State와 현재 코드 상태를 먼저 읽는다. 최신 로그는 실제 상태와 맞을 때만 참고한다. 로그와 실제 상태가 다르면 실제 GitHub 상태를 우선한다.

## 스킬 계약

계획/제안형 스킬은 후보, 초안, 분석 결과만 만든다. 사용자 승인, 상태 확정, 이슈 본문 갱신, 브랜치 생성 또는 전환, 커밋 생성, PR 생성, 리뷰 게시는 Workflow Skill의 Human Checkpoint와 후속 액션에서 처리한다.

Workflow Engine은 스킬 출력 중 이름이 붙은 필드만 후속 액션의 입력으로 사용한다. 자유 서술, 배경 설명, 추천 문장은 판단 근거로 참고할 수 있지만 상태 원천이 될 수 없다.

스킬 출력에 필요한 필드가 없으면 다음 전이로 넘어가지 않는다.

1. 누락된 필드를 사용자에게 알린다.
2. 같은 스킬에 보완 입력을 요청하거나 Human Checkpoint로 넘긴다.
3. GitHub 상태 변경, 파일 변경, 브랜치 전환, 커밋, PR 생성은 보류한다.

각 스킬 계약은 다음 네 항목을 반드시 가진다.

- `입력`
- `출력`
- `Workflow Engine이 확정할 항목`
- `금지`

입력:

- 현재 코드 상태
- 선택된 이슈 또는 PR
- 이 문서의 State Transition Rule
- 필요한 경우 실행 로그

출력:

Workflow Engine이 확정할 항목:

- 적용할 State Transition Rule
- 사용자 승인 이후의 상태 변경
- 실행 로그 기록

금지:

### Review Comment Skill

Review Comment Skill은 리뷰 생성 도구와 무관하게 PR Review Template 형식의 리뷰 결과를 게시 가능한 피드백 구조로 변환한다.

입력:

- PR 번호
- 리뷰 스킬의 PR Review Template 출력
- 기존 review thread 목록
- 기존 PR issue comments

출력:

- `inline_review_threads`
- `summary_feedback_comment`
- 중복 게시 위험
- 보류 질문

Workflow Engine이 확정할 항목:

- 실제 review thread 게시
- marker가 있는 요약 피드백 댓글 게시

금지:

- 파일 수정
- 피드백 적용 여부 확정
- GitHub 직접 게시
- 리뷰 결과를 일반 PR review body로만 게시

- marker 없는 일반 PR comment를 요약 피드백 상태 원천으로 취급

- 라인에 붙일 수 없는 `[blocking]` 또는 `[important]` 피드백은 `summary_feedback_comment`로 정리한다.
- `summary_feedback_comment`에는 `<!-- codex-harness:summary-feedback v1 -->` marker를 포함한다.

## 이슈와 PR 본문 계약

### 템플릿 원천

- `.github/ISSUE_TEMPLATE/*.md`와 `.github/pull_request_template.md`는 실제 이슈와 PR에 남길 본문 형식의 단일 원천이다.
- `github-templates.md`는 title prefix, label, 필수 섹션, 연결 규칙을 검증하는 계약 문서다.
- 작성 지침은 이 문서와 전용 스킬에서 관리하고, 생성된 이슈 본문에는 복사하지 않는다.
- 완료 기준은 해당 이슈가 닫혀도 되는지를 판단할 수 있는 체크리스트여야 한다.

### 기능제안 이슈

필수 섹션:

- `무엇을 제안하나요?`
- `왜 필요한가요?`
- `현재 상태는 어떤가요?`
- `판단 결과`
- `완료 기준은 무엇인가요?`
- `추가 정보`

`판단 결과`는 생성 시 미체크로 둔다. 진행 방향이 정해진 뒤 `진행하지 않음`, `정책 검토 필요`, `기능 변경 필요` 중 하나만 체크한다.

### 정책검토 이슈

필수 섹션:

- `무엇을 결정해야 하나요?`
- `왜 지금 필요한가요?`
- `선택지는 무엇인가요?`
- `검토 결과`
- `후속 작업은 무엇인가요?`
- `연관 이슈`

정책검토 이슈는 다음 상태를 추적한다.

- 정책 결정 여부
- 설계 문서 반영 여부
- 필요한 후속 이슈 반영 여부

`검토 결과`는 생성 시 비워 둔다. 정책 방향이 정해지면 최종 결정과 근거를 정책검토 이슈 본문에 짧게 반영한다.

기본 후속 작업:

- `정책 검토 결과 확정`
- `결정된 정책을 관련 설계 문서에 반영`

후속 작업 항목은 정책검토의 출처에 따라 다르게 둔다.

- 독립 정책검토 또는 기능제안에서 이어진 정책검토가 기능변경으로 이어질 수 있으면 `필요한 경우 기능 변경 이슈의 작업 범위와 완료 기준에 반영` 항목을 조건부로 추가한다.
- 기능결함에서 이어진 정책검토에는 기능변경 이슈 반영 항목이나 기능결함 이슈 반영 항목을 자동으로 추가하지 않는다.

정책검토의 설계 문서 반영은 결정된 정책을 설계 원천에 기록하는 단계다.

`docs/github-workflow-engine.md`처럼 Workflow Engine의 실행 계약을 정의하는 문서는 설계 원천이면서 이 저장소의 핵심 기능 산출물이다. 이 문서의 정책 반영은 정책검토 흐름의 설계 반영으로 처리할 수 있다.

설계 반영 이후 별도 흐름으로 넘겨야 하는 대상:

- `.codex-dist/skills`
- `.github` 템플릿
- 설치 스크립트
- README
- 그 밖의 실행 산출물 또는 배포 산출물

이 대상들은 설계 문서 반영이 끝난 뒤 기능변경 또는 기능결함 흐름에서 다룬다.

### 기능변경 이슈

필수 섹션:

- `어떤 기능을 변경하려 하나요?`
- `왜 필요한가요?`
- `작업 범위는 어디까지인가요?`
- `어떤 효과가 기대되나요?`
- `완료 기준은 무엇인가요?`
- `추가 정보`
- `연관 이슈`

작업 범위는 포함과 제외를 나누어 쓴다. 완료 기준은 기능별로 닫아도 되는지를 판단할 수 있는 체크리스트로 쓴다.

### 기능결함 이슈

필수 섹션:

- `어떤 문제가 있나요?`
- `문제 유형은 무엇인가요?`
- `재현 과정 또는 확인 위치가 어떻게 되나요?`
- `올바른 동작은 어떻게 되나요?`
- `원인과 해결 방향은 무엇인가요?`
- `완료 기준은 무엇인가요?`
- `추가 정보`

문제 유형은 `코드 버그`, `문서와 구현 불일치`, `정책 문서 간 불일치`, `반영 누락`, `기타` 중 해당 항목을 체크한다. 생성 시에는 원인과 해결 방향을 확정하지 않는다.

### 연관 이슈

`연관 이슈`는 이슈나 PR의 근거를 기록하는 섹션이다.

기록 대상:

- 이 이슈나 PR이 생성된 근원지
- 작업 범위를 결정한 근거 이슈

기록하지 않는 대상:

- 후속으로 생성된 이슈 번호
- 후속으로 생성된 PR 번호

후속 이슈나 PR 번호를 원본 이슈의 `연관 이슈`에 역방향으로 누적하지 않는다.

- 기능제안에서 정책검토를 만들면 새 정책검토 이슈 본문의 `연관 이슈`에 기능제안 번호를 반영한다.
- 기능제안에서 기능변경을 만들면 새 기능변경 이슈 본문의 `연관 이슈`에 기능제안 번호를 반영한다.
- 기능결함에서 정책검토를 만들면 새 정책검토 이슈 본문의 `연관 이슈`에 기능결함 번호를 반영한다.
- 정책검토에서 기능변경을 만들면 새 기능변경 이슈 본문의 `연관 이슈`에 정책검토 번호를 반영한다.
- 정책검토 결과를 기존 기능변경에 반영하면 기존 기능변경의 `연관 이슈`에 정책검토 번호를 추가한다.
- PR 본문의 `연관 이슈`에는 해당 PR이 반영하는 정책검토, 기능변경, 기능결함 이슈 번호를 반영한다.

### PR 본문

필수 섹션:

- `왜 변경하려 하시나요?`
- `어떻게 변경하려고 하나요? (optional)`
- `해당 변경으로 영향받거나 검토해야 할 사항은 무엇인가요? (optional)`
- `머지하기 전에 반드시 확인되어야 할 사항이 있다면 작성해 주세요. (optional)`
- `연관 이슈 (optional)`

`연관 이슈 (optional)` 작성 규칙:

- `Refs #번호` 형식을 사용한다.
- Workflow Engine 관리 이슈에는 `Closes`, `Fixes`, `Resolves`를 사용하지 않는다.
- 이슈 close는 PR merge 이후에만 판단한다.
- Workflow Skill이 완료 기준과 후속 작업을 확인한 뒤 close를 수행한다.

## 워크플로우 전이

### 다음 계획 요청

다음 계획 요청은 새 작업 생성 명령이 아니다. 진행 중인 작업이 없는 상태에서 이어갈 수 있는 열린 계획이 있는지 확인하는 요청이다.

Workflow Skill은 다음 순서로 판단한다.

1. merge 대기 PR
2. 진행 중 PR
3. 열린 기능변경 또는 기능결함 이슈
4. 열린 정책검토 이슈
5. 열린 기능제안 이슈
6. 새 기능제안 후보

진행 중인 작업이 있으면 새 계획 후보를 만들지 않고 현재 작업의 남은 액션을 보여준다.

| 액션 | 조건 | Human Checkpoint | 상태 반영 |

## 리뷰 피드백 처리

Review Feedback Triage는 리뷰 피드백을 바로 수정 명령으로 보지 않고, 사람이 액션을 결정할 수 있도록 분류와 맥락을 제공하는 절차다.

| 분류 | 의미 | 후속 액션 |
| --- | --- | --- |
| 적용 | 실제 결함 또는 명확한 개선 | 해당 PR 범위 안에서 수정 |
| 보류 | 더 많은 맥락 필요 | 이슈 또는 PR에 보류 사유 기록 |
| 거절 | 오탐 또는 범위 밖 제안 | 거절 근거 기록 |
| 사람 승인 필요 | 고위험 변경 또는 애매한 판단 | Human Checkpoint로 전달 |

라인 피드백은 review thread로 게시하고 `isResolved`로 추적한다. 라인에 붙일 수 없는 `[blocking]` 또는 `[important]` 피드백은 marker가 있는 요약 피드백 댓글 체크리스트로 추적한다.

요약 피드백 marker:

```markdown
<!-- codex-harness:summary-feedback v1 -->
```

Workflow Skill은 marker가 없는 일반 PR comment를 요약 피드백 상태 원천으로 취급하지 않는다.

피드백을 사람에게 전달할 때 포함할 맥락:

- 피드백 원문
- 관련 파일 또는 문서 위치
- 위험도
- 예상 영향
- 적용/보류/거절/사람 승인 필요 분류
- 추천 액션
- Verdict 또는 Review Comment Skill의 보류 질문
- 자동 수정 시 위험 요소

## 적용과 관리 구조

### codex-harness 관리 자산

`codex-harness`는 다음 기본형을 관리한다.

- GitHub Workflow Engine 설계 문서
- 기능제안, 정책검토, 기능변경, 기능결함 이슈 템플릿
- Pull Request 템플릿
- Harness 전역 스킬 기본형
- GitHub Workflow Engine 전역 스킬 기본형
- Issue Creation Skill 전역 스킬 기본형
- Feature Plan Skill 전역 스킬 기본형
- Fix Plan Skill 전역 스킬 기본형
- Branch Plan Skill 전역 스킬 기본형
- PR Proposal Skill 전역 스킬 기본형
- PR Creation Skill 전역 스킬 기본형
- Review Comment Skill 전역 스킬 기본형
- 기본 라벨 세트

전역 `commit` 스킬과 `awesome-code-review`는 외부 의존성으로만 다루며 `codex-harness` 관리 기본형에 포함하지 않는다.

표준 배포 구조:

```text
codex-harness/
├── docs/
│   └── github-workflow-engine.md
├── .github/
│   ├── ISSUE_TEMPLATE/
│   │   ├── proposal_template.md
│   │   ├── decision_template.md
│   │   ├── feature_template.md
│   │   └── fix_template.md
│   └── pull_request_template.md
├── .codex-dist/
│   └── skills/
│       ├── harness/
│       ├── github-workflow-engine/
│       ├── issue-creation/
│       ├── feature-plan/
│       ├── fix-plan/
│       ├── branch-plan/
│       ├── pr-proposal/
│       ├── pr-creation/
│       └── review-comment/
```

### 타겟 프로젝트 적용 자산

타겟 프로젝트에는 다음 자산을 적용 후보로 둔다.

```text
target-repo/
├── .github/
│   ├── ISSUE_TEMPLATE/
│   │   ├── proposal_template.md
│   │   ├── decision_template.md
│   │   ├── feature_template.md
│   │   └── fix_template.md
│   └── pull_request_template.md
└── .harness/
    └── logs/
        └── github-workflow-log.md
```

타겟 프로젝트에는 Workflow Engine 스킬을 생성하지 않는다. 전역 Workflow Engine 스킬이 타겟 레포의 GitHub Issue, PR, 템플릿을 기준으로 상태 전이를 수행한다.

### 템플릿 정합성 검사

타겟 레포에 GitHub Workflow Engine을 적용하거나 템플릿을 갱신하기 전에는 정합성을 먼저 검사한다.

1. `github-templates.md`에서 기대 파일명, title prefix, label, 필수 섹션, 연결 규칙을 읽는다.
2. 타겟 레포의 `.github/ISSUE_TEMPLATE/*.md`와 `.github/pull_request_template.md`를 읽는다.
3. 기본 파일명이 없으면 같은 역할의 기존 템플릿이 있는지 찾고 매핑 근거를 남긴다.
4. 각 이슈 템플릿의 frontmatter `title`, `labels`, 필수 섹션, 기본 체크리스트를 비교한다.
5. PR 템플릿의 필수 섹션, `연관 이슈 (optional)`, `Refs #번호`, 자동 close 키워드 부재를 확인한다.
6. 결과를 `정합`, `허용된 확장`, `불일치`로 분류한다.
7. 불일치가 있으면 차이, Workflow 영향, 수정 후보를 사용자에게 제시한다.
8. 사용자가 승인한 경우에만 타겟 `.github` 템플릿을 생성 또는 갱신한다.

타겟 레포에서 발견한 개선점은 자동으로 `codex-harness`에 역반영하지 않는다. 여러 타겟에서 반복되거나 공통화할 가치가 있을 때만 사용자 승인 후 기본형으로 승격한다.

## 운영 메모

- 이슈 제목 prefix와 라벨은 템플릿 기준을 따른다.
- 이슈 본문에 Workflow Engine 규칙을 반복해서 적지 않는다.
- 기능제안과 기능결함 이슈가 생성되면 다음 계획 요청을 기다리지 않고 열린 이슈로 읽고 상태 전이를 적용한다.
- 다음 계획 요청은 진행 중인 작업이 없는 상태에서 이어갈 수 있는 열린 계획을 찾기 위한 요청이다.
- 모든 액션 진입은 `.harness/logs/github-workflow-log.md`에 보조 로그로 남긴다.
- 승인된 계획과 진행 상태는 먼저 GitHub 이슈나 PR에 반영한다.
- 상태 전이는 LLM 자유 판단이 아니라 Workflow Skill의 규칙으로 정한다.
- LLM은 요약, 선택지 설명, 추천 근거 작성, 초안 작성에 사용할 수 있지만 상태 전이 또는 승인 권한을 갖지 않는다.
- 흐름이 애매하면 새 이슈를 만들기보다 현재 이슈에 판단 근거를 먼저 남긴다.
- 작업 중 정책 판단이 필요해지면 구현을 계속 진행하기 전에 정책검토 이슈를 만든다.
- 리뷰 피드백은 자동 수정 명령이 아니라 판단 대상이다.
- PR merge는 사람이 수행한다.
