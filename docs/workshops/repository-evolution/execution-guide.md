# Repository Evolution Execution Guide

## 목적

이 문서는 모든 Phase에 공통으로 적용하는 학습·조사·개선 절차를 정의한다.

학습 문서는 탐색과 사고를 위한 작업 문서다. 검증되지 않은 해석을 공식 설계처럼 다루지 않는다.

## 공통 진행 절차

### 1. 최신 상태 확인

- 현재 브랜치와 최근 커밋을 확인한다.
- 관련 열린 Issue와 PR을 확인한다.
- 관련 문서, 스킬, 코드, 테스트를 직접 읽는다.
- 과거 대화나 이전 분석을 현재 사실로 가정하지 않는다.

### 2. 현재 구조 조사

관련 파일을 다음 기준으로 분류한다.

- 진입점
- 정책
- 설계
- 실행 코드
- 상태
- 검증
- 예제
- 생성 산출물

### 3. 실제 흐름 재구성

문서 설명만 요약하지 말고 실제 흐름을 추적한다.

```text
입력
→ 진입점
→ 상태 및 근거 조회
→ 정책·스킬·역할 선택
→ 실행
→ 검증
→ 상태 반영
→ 결과 보고
```

가능하면 관련 파일 경로, 명령, 함수, 스킬을 근거로 남긴다.

### 4. 설계 의도 분석

다음을 구분한다.

- 명시적으로 결정된 구조
- 코드와 문서로 강하게 추론되는 구조
- 임시 구현
- 과거 구조의 잔재
- 아직 구현되지 않은 계획
- 문서와 실제 동작의 불일치

추론은 사실과 구분해 표시한다.

### 5. 관련 개념 학습

공식 문서와 주요 설계 원칙을 학습하되 현재 저장소에 기계적으로 적용하지 않는다.

비교 항목:

- 외부 권장 원칙
- 현재 저장소의 목적과 제약
- 현재 구조의 장점
- 변경 비용
- 기대 효과
- 호환성 및 회귀 위험

### 6. Gap Analysis

각 항목은 가능하면 다음 형식을 따른다.

```markdown
### 문제 또는 기회

#### 현재 상태

#### 저장소 근거

#### 영향

#### 가능한 원인

#### 개선 선택지

#### 권장 방향

#### 변경하지 않을 경우
```

### 7. 변경 유형 분류

#### 즉시 수정

- 오탈자
- 잘못된 경로
- 코드와 문서의 명백한 불일치
- 동작을 바꾸지 않는 정리
- 명백한 검증 누락

#### 정책 검토 필요

- 책임 경계 변경
- 상태 모델 변경
- 워크플로우 변경
- Source of Truth 변경
- 승인 또는 자동화 수준 변경

#### 기능 제안 필요

- 새로운 명령
- 새로운 스킬 또는 역할
- 새로운 런타임 기능
- 새로운 평가 도구
- 새로운 외부 통합

#### 보류

- 근거가 부족함
- 효과가 불명확함
- 현재 규모에 과도함
- 선행 작업이 필요함

### 8. 공식 반영

학습 결과를 곧바로 공식 설계로 승격하지 않는다.

```text
학습 및 조사 결과
→ 개선 후보
→ 정책 검토 또는 기능 제안
→ 사용자 결정
→ 구현 계획
→ 변경 및 검증
→ 공식 문서 반영
```

### 9. Day 종료 기록

각 Day가 끝나면 다음을 남긴다.

```markdown
## 오늘 새롭게 이해한 것

## 기존 생각이 바뀐 부분

## 저장소에서 확인한 근거

## 현재 구조의 강점

## 개선 후보

## 변경 유형 분류

## 남은 의문

## 다음 Day의 선행 조건
```

## Codex CLI 기본 프롬프트

```text
현재 저장소의 최신 상태를 기준으로 작업하세요.

과거 대화나 이전 분석을 사실로 가정하지 말고 관련 문서, 스킬,
코드, 테스트와 GitHub 상태를 직접 조사해 현재 구조를 먼저 파악하세요.

이번 작업은 Repository Evolution Workshop의 Phase [N], Day [N]입니다.

주제:
[주제]

목표:
[학습 목표]

수행 요구사항:
1. 관련 파일과 실제 동작을 조사합니다.
2. 사실, 문서에 명시된 설계, 추론을 구분합니다.
3. 현재 구조의 의도와 장점을 먼저 설명합니다.
4. 학습한 원칙과 현재 구현을 비교합니다.
5. 개선 후보를 즉시 수정, 정책 검토, 기능 제안, 보류로 분류합니다.
6. 명백한 오류가 아니라면 바로 구현하지 않습니다.
7. 조사 근거와 남은 질문을 기록합니다.
8. 다음 Day 또는 새 세션에서 문서만으로 재개할 수 있게 작성합니다.
```

## Phase 종료 기준

- 현재 구조가 코드와 문서를 근거로 설명된다.
- 강점과 문제가 분리된다.
- 개선 후보가 처리 유형별로 분류된다.
- 필요한 정책 검토와 기능 제안이 정의된다.
- 승인된 변경이 구현되고 검증된다.
- 공식 문서에는 확정된 내용만 반영된다.
- 다음 Phase의 선행 조건이 명확하다.
